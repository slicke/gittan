# The Files page

Read this when touching `gittan.filespage`, `umain.files.inc`, the Files row of the sidebar, Browse Files... in the commit, tag and reflog menus, or a file of a commit shown in the editor.

- The Files page is the tree of a commit as it was, one folder at a time, as a code host lists files: `TGittanFilesPage` (`gittan.filespage.pp`), painted like the Repository page in the same scroll box (`FView = gvFiles`; `ShowFilesAt` in `umain.files.inc`), opened from the fifth row of the sidebar (`navFiles`, under Commands; `niFiles`, a page) and View > Files (Cmd+Option+5, Ctrl+Shift+5 elsewhere), which show HEAD's files (`ShowFiles`: `CommitDetails('HEAD')`, named by the branch, or the short id on a detached HEAD; before the first commit the page says there is none, `ClearCommit`), and from Browse Files... in the commit menu, the tag menu and the reflog's menu (`BrowseCommit`, which keeps its signature from the dialog it replaced), which show that commit's under its name. `FFilesHead` tells the two apart: while the page follows HEAD, `RefreshFilesPage` (from `ApplySnapshot` while the page is shown) moves it to the new HEAD after a commit, and a commit picked with Browse Files... stays until the row is picked again. The page has the repository's name with "Files" after it, the commit under them (the branch icon, its name and its subject, cut to the width), a row of crumbs naming the folder shown (the repository's name first; every crumb before the last is a link back up, the last stands in bold) over a divider, then a row per entry as git lists them, folders first: its icon from `TreeImages` (`SetImages`, `iconFolder` for a folder or a submodule, `iconFile` for the rest), its name, a submodule's short commit ("@ b0193be") or "link" dimmed after it, and the size at the right (`ByteSize`; none for a folder or a submodule). A row fills under the mouse. A folder's row and a crumb open that folder on the page (`LoadFolder`; `OnFolderChange` lets the owner scroll the box to the top); the folders are read as they are opened through `OnRead` (`FilesPageRead`: `TGittanRepo.TreeEntries` for the page's commit, `Screen.Cursor` an hourglass meanwhile) and kept per commit (`FCachePaths`, `FCacheLists`), so going back up reads nothing again; a folder git could not list shows git's message in the error color in its place, an empty folder says so. `SetCommit` with another id drops what was read and reads the folder shown again, the root when the commit lacks it; the same id changes nothing. The content is painted on a measuring canvas first (`Layout`, as the Commands page does) so the height is known before the page is shown.
- A click on anything but a folder raises `OnOpen` (`FilesPageOpen`): a submodule's row shows the submodule's page when its path is one of the work tree's (`FSubmodules`), else a status note says it is not; a file or a link is shown by `ShowBlob` as it is in the page's commit (`FileBlob`): an image (`IsImagePath`) in the image view as a new image alone, a binary file (a NUL in its first 8000 bytes, git's own rule) in the binary view with its size (`SetFile`), anything else read-only in the editor under the file's lexer (`ShowText` with `FLexers.ForFile`; text that is not valid UTF-8 is read as Windows-1252). The view is `gvBlob` (`FBlobPath`, `FBlobCommit`, `FBlobName`), which the editor's code treats as a plain file (`FoldingShown`, `FileLineOfRow`, `FoldPath`, `AutoLexer`, the caret position in the status bar) and the Files row stays selected for. The header names the file with its badge and, dimmed at the right where the stage would show (`SetDetail`), "at <name>"; its pills are Open and Save As... (`HeaderAction` in `umain.repofiles.inc`), and for a file of HEAD that Git LFS may lock a third, Lock, Unlock or Force Unlock (`BlobActions`, see special-views.md): Open writes the blob (`BlobData`, read again) to `gittan-<short id>/<path>` in the temporary directory and opens it with `OpenDocument`, so the application sees the file's own name and two commits do not share a copy; Save As... writes it where a `TSaveDialog` says. A failure to read or write is a status note. A refresh leaves the view alone (`ApplySnapshot`'s restore has no case for it), since the commit's file does not change.

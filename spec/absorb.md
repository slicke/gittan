# Putting changes into their commits

Read this when touching `gittan.absorb`, `gittan.absorbdlg`, `umain.absorb.inc`, the pill Put into Its Commit, Changes > Put Change into Its Commit... or Commit > Put Changes into Their Commits....

- What it is: a changed block of the work tree goes into the commit of the branch that last wrote the lines it changes, as a fixup commit that an interactive rebase folds in at once, so the rounds of small fixes after a review end up in the commits they fix rather than in a "fixes" commit on top. It is what the `git absorb` command does; the command need not be installed. Three ways in: the hover pills over a block in the change view have Put into Its Commit between Leave Out of Commit and Discard (`FPillAbsorb` in `ShowDiscardPills`, `DiscardPillsPick` index 2, icons `'k  d'`), Changes > Put Change into Its Commit... does the same for the block the caret is in (`FAbsorbChangeItem`, `MenuAbsorbChangeClick`), and Commit > Put Changes into Their Commits... (`FAbsorbItem`, after Split Changes into Commits, `MenuAbsorbClick`) takes every ticked file and lists the changes in a dialog. All three need `CanAbsorb`: a repository open and not busy (`RepoReady`), the tree choosing what to commit (`CommitChoosing`), HEAD on a branch, no file in conflict and Amend off; the pill and the Changes item need `CanLeaveOut` too (a tracked text file compared with HEAD). `UpdateAbsorbItems` enables the items, from `UpdateDiscardItems` (the Changes menu opening, the caret moving) and `CommitMenuOpen`, so the palette sees them right.
- The branch's commits (`AbsorbBase` in `gittan.absorb`, tested): those after the merge base with the branch's upstream (`TGittanRepo.Upstream`, `MergeBase`), else with the default branch (`DefaultBranch`, origin/main), else the last `AbsorbMaxStack` (10) commits, or every commit after the root when the branch is shorter; so a commit pushed to the upstream or on the default branch is never rewritten. An upstream that is gone (`HasCommit` false) counts as none; an upstream or default branch with no merge base gives `rsAbsorbNoBase` rather than the last commits. With no commit of its own (the merge base is HEAD) nothing is offered (`rsAbsorbNoCommits`). `TGittanAbsorbPlan.Build` notes the branch and HEAD's id (`Branch`, `Head`), reads the commits as rebase steps (`RebaseSteps`, oldest first, `Pushed` counted into `Pushed` for the note) and, for every path given, the file's diff against HEAD with the whole file as context (`FileChanges`, kept in `Diff` for the run) and HEAD's blame of it (`TGittanRepo.Blame`, `TGittanBlame.Parse`), and gives a `TGittanAbsorbHunk` per block of changed lines: its path, its pairs (`BlockPairs` of gittan.keep), the line of the file as it is where it starts, and its target, an index into the steps, or -1 with a reason. `BlockOldLines` (tested) gives the old file's lines the block stands for: the deleted lines' numbers and the lines before and after it; `Build` goes through `BlockOldLinesAt`, carrying the count of old lines from block to block rather than counting from the top for each. `AbsorbTarget` (tested through `Build`): a block that deletes lines belongs to the one commit of the branch that wrote them all; a block that only adds lines belongs to the one commit of the branch that wrote the line before and the line after it (the one of them in the file); otherwise it cannot be placed: its lines were last changed before the branch (`rsAbsorbOlder`), come from different commits (`rsAbsorbMixed`), have no neighbours (`rsAbsorbNoNeighbours`), or the file is new (`rsAbsorbNewFile`, nothing to blame), deleted (`rsAbsorbDeletedFile`) or binary (no lines, so no hunks). `HunkOf` finds the hunk a pair is in, which is how the pill's block (from `FChangeLines`, whose blocks the keeps may have split) finds its hunk in the fresh diff; the hunk goes whole, kept lines inside it included.
- The run (`AbsorbRun`, tested: all hunks, some, none, a stale file, a moved branch): first the branch and HEAD are compared with the plan's, and when either moved nothing is written (`rsAbsorbMoved`). Then for each step in replay order that has a chosen hunk, one fixup commit of those hunks' paths through `TGittanRepo.Commit` with `fixup! <subject>` as its message (`fixup! <id>` when an earlier step has the same subject, since the autosquash takes the first with it), the Commit section's Sign Off and Skip Hooks as its options, and for a file with other hunks a part (`TGittanCommitPart`) holding the work tree's text with every hunk not taken yet put back as HEAD has it (`LeaveOutText` of gittan.leaveout, which checks the file against the diff, so a file changed meanwhile stops the run with `rsDiscardStale`); a file whose hunks are all taken goes whole, but is checked against the diff the same way first, and one that cannot be read (deleted meanwhile) stops the run with the reader's message; the hunks are taken in step order and the texts are cumulative, so each fixup's diff is its own hunks alone and what is not chosen, or cannot be placed, stays in the work tree. Then the steps are read again (the fixups among them), `AutosquashSteps` moves each after its commit as `raFixup`, and `TGittanRepo.RebaseInteractive` replays the branch from `Onto` with `--autostash`, which stashes what is left in the work tree and puts it back after. When putting it back clashes, git still exits with 0 and leaves the files in conflict, so files in conflict after the rebase (`git ls-files -u`) give `AConflicts` with `rsAbsorbStashConflicts`, git keeping the stash. A rebase that stops (`AConflicts`, `AStopped`) is left to the Commit section as any interactive rebase is, the fixup commits still on the branch. Nothing chosen gives `rsAbsorbNothingChosen` and touches nothing. The fixup commits raise no extension events: they are made and folded in as one step.
- In the window (`umain.absorb.inc`): `AbsorbPlanFor` builds the plan with the cursor busy and says a failure in the banner. `AbsorbBlockAt` asks first (`AskDlg`, `rsAbsorbAsk`: the line, the file, the commit's short id and subject, how many of the branch's commits are pushed when any is (`AbsorbPushedNote`, `rsRiPushedOne`/`rsRiPushed`), and that the commits after it are rewritten and Branch > Undo takes it back) with Put as the default, and says why in the banner when the block cannot be placed (`rsAbsorbCannot`). `MenuAbsorbClick` shows `ChooseAbsorb` (`gittan.absorbdlg`, built in code like the clean dialog): a `TCheckListBox` with a row per hunk, "docs.txt:2 → 6dcd367 Write docs" ticked and enabled, or "parser.txt:11 — its lines were last changed before the branch" unticked and disabled (`ItemEnabled`), "3 of 3 ticked" with Tick All and Untick All over the rows that can go, the note about rewriting and the pushed commits, and Put with the count, off while none is ticked; the ticked files with no hunks say so in the status bar (`rsAbsorbNoChanges`). `RunAbsorb` runs `AbsorbRun` as `RebaseInteractiveAsk` runs a rebase: the watcher stopped, the cursor busy, the repository read again after (`FLoadError`, `FSummary.Notice` cleared, `RefreshRepository`), Skip Hooks reset as after a commit; a run that went through says "Put the changes into 3 commits" or, for one commit, 'Put the change into "Add parser"' (the subject alone, since the id is new after the rebase) in a green banner and the status bar; conflicts and a stop are said as for a rebase (`rsCaConflicts`, `rsRebaseStoppedAt`, `rsRiStopped`), another failure in a red banner (`rsAbsorbFailed`). The undo history sees the rebase as one step (Branch > Undo Rebase), since the ref state is not noted while the operation runs.
- Tested in `tests/testabsorb.pp` against a repository with three commits on a base: the old lines of a block (`TestBlockOldLines`), the base without a remote (the root), with an upstream (the pushed commit, nothing once all is pushed) and with an unrelated upstream (no base) that then goes (the root), the plan (a changed line, an addition between two lines of one commit, a line older than the branch, a new file, `HunkOf`), and the run with every hunk, with one, with none, with a file changed or deleted after the plan and after a commit made since (nothing committed), checking each commit's file afterwards, the subjects of the branch, the work tree's rest and that no stash is left.

# Find, go to definition, symbols and callers

Read this when touching `gittan.findbar`, `umain.gotodef.inc`, the symbol index (`gittan.symbolindex`), the symbol bar, changed symbols or callers.

- `gittan.findbar.pp` holds `TGittanFindBar`, the row under the header that Go > Find (Cmd+F) shows: a native `TEdit`, a `TGittanChangeNav` pill reused as previous/next with the match counter, a "Not found" note and a close cross. It only raises `OnSearch`; `FindText` in `umain.actions.inc` searches the editor's lines itself (case-insensitive substring, up to `MaxMatches`), picks the first match after the caret (or the selection start, so retyping extends the match in place), selects it through `DoGotoPos` with the caret after the match, and answers with `SetMatches`. Hidden lines of the change view are skipped. In Side by Side the deleted lines are searched in the old side's text (`FEditOld`), the other lines only in the new side's, since the two have the same rows: the matches go by row, the old side first, and a match in the old side is selected there, with the new side scrolled to it. The next search starts from the caret of the side that has the focus, else of the side of the last match (`FFindInOld`). Enter and Shift+Enter step, Escape closes; Find Next/Previous (Cmd+G, Cmd+Shift+G) work with the bar closed.
- Go > Go to Definition (F12) and Cmd+click (Ctrl+click elsewhere) in an editor jump to the definition of the word under the caret (`umain.gotodef.inc`). The lexer's code tree is the only symbol table: `CodeTree` walks the adapter's `AnClient.PublicData.FoldRanges` for the ranges whose rule has `DisplayInTree` (functions, methods, classes), names them with `GetRangeName` as CudaText's code tree does, and answers a flat `TGittanSymbols` (name, row and column of the identifier token, depth, line text; the record and `BestSymbol`, which ranks by `SymbolRank`, are in `gittan.symbols.pp`: the word must equal one of the name's identifiers; a hit before the first parenthesis, and in the same case, ranks higher; a lexer names a range in its own way, "TForm1.Foo", "func foo(int a)", "class Foo"). The lookup runs on the text of the clicked editor first (the symbol on the caret's own row is skipped, so a lookup from a definition goes on), then, for the old side, on the new side, then on the rest of the repository through `FindInRepo` (see the symbol index). A hit shows the file (`ShowRepoFile`) and runs the lookup again on the text the editor shows, so the rows of the change view need no mapping. A definition on a hidden row opens its gap (`ExpandGap`) and looks again. `JumpToDefinition` selects the word on the definition's line (`WordPos`), since the lexer's position is the range's header, which may start with a keyword. The parse runs in the adapter's thread: every adapter's `OnParseBegin` and `OnParseDone` set its `Tag` to 0 and 1 (`AdapterParseBegin`/`AdapterParseDone`), and `WaitForParse` polls it with `Application.ProcessMessages`, up to `ParseTimeout`. `SetupEditor` gives both editors `InitEditorMouseActions(..., True)`, so Cmd+click moves the caret instead of adding one, and `EditMouseUp` runs the lookup when the modifier is down and nothing is selected. A word without a definition leaves a note in the status bar.
- `WaitForParse` waits for an adapter's parse with `Application.ProcessMessages`, so anything may happen to the adapter meanwhile: another file scrolled into the view sets a new lexer on `FAdapter`, and another lookup loads a file into the scratch editor (`ParseScratch` sets `Lexer := nil`); either frees the parser (`AnClient`) it had. `CodeRanges` and `EnclosingRange` take `AnClient` after the wait, never before: one taken before was freed under a hover's repository lookup while the user scrolled through a merge, an access violation in `TCriticalSection.Enter`. `FileSymbols` refuses a nested parse in the scratch editor (`FScratchBusy`; it finds nothing and caches nothing then) and caches only when the scratch editor still holds its file, and the hover timer does not start a lookup inside another (`FHoverBusy`, `HoverLookup`).
- The word under the mouse shows its definition after `HoverPause` ms: `EditMouseMove` (both editors) maps the mouse to a text position (`ClientPosToCaretPos`) and the word there (`WordAt`); a new word restarts `FHoverTimer`, whose tick looks the word up like Go to Definition (the word's own row skipped, so a definition shows nothing for itself; other files through `FindInRepo`) and shows a hint through the editor's `Hint` and `Application.ActivateHint`: "file:line" (the change view's own number, `RowLabel`) and the definition's line. While Cmd (Ctrl elsewhere) is held the word is underlined in `FLinkColor` through an attribute tagged `tagHoverLink` and the cursor is a hand, as a link. `ClearHover` drops hint, timer and underline; `EditMouseLeave` calls it.
- The symbol index (`umain.index.inc`, `gittan.symbolindex.pp`) holds the code tree of every file of the repository that has a lexer, so Go to Definition and the hover reach past the changed files. `OpenRepository` calls `StartIndexing`: the index is read from its file (one per repository, named by the MD5 of the root, in `IndexCacheDir`: `~/Library/Caches/Gittan/index/` on macOS, `$XDG_CACHE_HOME` or `~/.cache/Gittan/index/` on Linux, `%LOCALAPPDATA%\Gittan\index\` on Windows; a cache, since it is rebuilt from the repository), the files `TGittanRepo.Files` lists (`git ls-files` with the untracked, not ignored files) are queued, entries of files no longer listed are dropped, the queue is sorted by extension and then path (`CompareByExt`) so the files of one lexer come together, and `IndexNext` walks it, started from the message loop (`IndexNextAsync`), since `OpenRepository` also runs in `FormCreate` and loading a large file pumps messages for its progress, which ran `FocusTreeAsync` before the window was shown ("Cannot focus"), and which `FIndexLoading` keeps a queued `IndexNextAsync` from using to load the next file into the editor mid-load: a file whose size and time (`FileStamp`) match its entry is kept, one without a lexer or larger than `MaxIndexedSize` gets no symbols, the rest are parsed one at a time in `FIndexEdit`, a hidden editor with its own adapter, whose `OnParseDone` (`IndexParseDone`) collects the symbols with `CodeTree` and queues the next file through `Application.QueueAsyncCall`, so the window stays responsive; `FIndexTimer` (`ParseTimeout`) gives up on a parse that never reports. The adapter keeps its lexer, and so its parser thread, from one file to the next when the adapter is idle and the file takes the same lexer: `LoadFromFile` starts the parse through the editor's change event. Otherwise (another lexer, or a parse still running after a timeout or a repository closed mid-parse) the lexer is dropped and set again, which ends the thread and starts a new one, up to a tenth of a second (the thread polls its event every 100 ms), and so is done as seldom as possible: indexing 300 files took 69 s with a new thread per file and 7 s without, and a done event of a parse still running is never taken for the next file's. `UpdateStatus` moves the status bar's progress bar ("Indexing N/M") every `IndexReportEvery` files. The index is written (`SaveIndex`, only when `FIndexSaveNeeded`) when the indexing ends and when the repository or the window closes. A symbol keeps at most `MaxSymbolLine` characters of its row, around the name (`SymbolLineSpan`, read with `LineSub` without copying the row): a minified file is one row of thousands of symbols, and the whole row for each gave an index of tens of gigabytes; the file's header is `gittan-index 2`, and `Load` reads only the header of a file of another version and deletes it. `FileSymbols` gives a changed file's symbols from the index when its stamp is current, else parses it at once in `FScratch`, so a lookup never waits for the indexer and an edited file is parsed again. `FindInRepo` searches the changed files first, in tree order, then the rest of the index; `ShowRepoFile` shows a hit through the tree, or through `OpenFile` for a file that is not changed. `AdapterOf` must know every hidden editor: a lexer set through it on the wrong adapter starts no parse. `gittan.symbolindex.pp` has no LCL dependency and is tested, as is `Files`.
- Go > Go to Symbol... (Cmd+Enter, Ctrl+Enter elsewhere; Cmd+P is the command palette, Cmd+T is File > New Tab) shows `FSymbolBar`, a `TGittanSymbolBar` (`gittan.symbolbar.pp`) under the find bar: a native filter field and a native list of the code tree of the shown file, from `CodeTree`, kept in `FSymbols` (the list indents by each symbol's depth while there is no filter). Typing filters by substring (the names matched at the start of a word listed first, at most `MaxRows` rows, the rest counted in a last row), Up and Down move in the list from the field, Enter or a double click raises `OnPick` with the index into the list given, and `SymbolBarPick` jumps through `JumpToDefinition` with the name's identifier (`NameIdentifier` in `gittan.symbols.pp`). The list's native row height is unknown before it has a handle, so the bar has a fixed `ListHeight`. `ShowEditor` and `ShowSummary` hide the bar, since its list belongs to the file shown before. The menu may get Cmd+Enter before the focused control, so `MenuGoToSymbolClick` commits when the commit message has the focus and asks the agent when the tree's filter has it, what the key does there.
- Go > Go to Symbol in Repository... (Cmd+Shift+T) fills the same bar with the symbols of every file (`MenuGoToRepoSymbolClick`): the changed files first through `FileSymbols`, then the rest of the index as far as it has got, each with its file and line as the bar's details (`SetSymbols` with `ADetails`, which also keeps the list empty until something is typed), and the file of each in `FSymbolFiles` (nil while the bar lists the shown file). A pick shows the file through `ShowRepoFile` and looks the symbol up again in the text the editor shows, by its full code tree name first, then by its identifier, since the change view's rows are not the file's.
- The change view names the symbols the diff touched (`gittan.symbolchanges.pp`, no LCL, tested in `tests/testsymbolchanges.pp`). `CodeRanges` in `umain.gotodef.inc` is `CodeTree` with the rows each range spans (`TGittanCodeRange`: the symbol, `FromRow`, `ToRow`; a range the lexer never closed runs to the end of the text), and `CodeTree` is now its symbols alone. `RowMarkers` in `umain.diffview.inc` gives the view's rows one marker each (' ', '+', '-'; a filler row of the side-by-side view takes the marker of the line opposite, '-' on the new side and '+' on the old, so the two sides count in one row space). `SymbolChanges` lays the ranges over the markers: a changed row belongs to the innermost range, a range whose every row was added or deleted is reported once as added or deleted and swallows the ranges inside it, then the deleted and the added ranges are paired: the same name next to each other (no unchanged row between) is one rewritten symbol, reported as changed with both counts; the same name apart is a move (`scMoved` at the new place, `scMovedFrom` at the old, `Same` when the bodies match without whitespace); the same body (header row left out, at least two rows) under another name is a rename (`scRenamed`, `scRenamedFrom`). With two sides the wholly deleted ranges come from the old side (`OnOld`). `InnermostRange` finds the range around a row; `ChangeDetail` words a change for the symbol bar ("+3  −1", "added  +12", "moved here, changed", "renamed from X").
- Go > Changed Symbols... (Cmd+Shift+Y, since the editor's keymap takes Cmd+Y for delete line; `MenuChangedSymbolsClick`) lists those symbols in the symbol bar with the detail after each name (`SetSymbols` with details but no filter needed, and its own hint); `FSymbolOnOld` marks the ones that are only in the old side's text, so `SymbolBarPick` jumps in `FEditOld` for them. A file without changed symbols says so in the status bar.
- A gap row names the symbol the block of changes after it is in, as git's hunk headers do, and the file header names the symbol the caret is in (`TGittanFileHeader.SetSymbol`, dimmed after the file name when it fits). The code tree is known only when the background parse of the text ends, so `AdapterParseDone` (for `FAdapter` and `FAdapterOld` in the change view) calls `UpdateSymbolHeadings`: it keeps each side's `CodeRanges` (`FCodeRanges`, `FOldRanges`, valid from then until the next `BuildChangeView`, `FRangesValid`), updates the header through `UpdateSymbolCrumb` (also from `UpdateChangeNav`, so the caret moves it), and names every block of changed lines (`FBlockStarts`, the first diff line of each, found in `BuildChangeView`) by the innermost range around the row of its first line, on the new side, or on the old side for a block of deleted lines the new side shows as fillers. The names are kept per block in `FHeadings` (blocks do not move when gaps open, rows do), and `GapHeading` gives a gap row the name of the block after it, which `GapRowText` appends after the labels (`AHeadingCol` is where it starts; `EditMouseUp` ignores a click on it). New names rebuild the view once more, from the message loop (`RebuildForHeadingsAsync`, through `RebuildIfChanges`, at the same place) so the gap rows show them; the parse of that text finds the same names and ends it, and `FHeadingRebuilds` caps it at two per shown file (`ShowChanges` clears the headings and the count) in case a lexer reads a heading as code. A parse can end while `BuildChangeView` is still filling the editors (one side's text replaced, the other's not), so the update is skipped while `FBuildingView` is set and the build calls it once at its end; it also skips while an editor's line count is not its rows plus the empty line the text ends with.
- Go > Callers of Changed Symbols... (Cmd+Shift+C; `MenuCallersClick`) shows the impact of the shown file's diff on the rest of the repository: the index knows definitions only, so the identifiers of the changed symbols (`ShownSymbolChanges`, shared with Changed Symbols; the old end of a move left out) go to one `TGittanRepo.Grep`, `git grep -z -n -w -F -I --untracked --no-color` over the work tree (`--no-color`, since `color.grep` or `color.ui` set to always colored the matches and the output no longer parsed; `TestGrep` sets `color.grep`), with `-i` when `LexerIgnoresCase` says the shown file's lexer reads identifiers so (Pascal, SQL, Basic), run synchronously. `gittan.callers.pp` (no LCL, tested in `tests/testcallers.pp`) reads the output (`ParseGrep`: one `TGittanCaller` per identifier found as a whole word on a row, the rows of the changed files and the shown file left out, since their uses are in the diff), and the handler drops the rows of files without a lexer or with one for prose (`LexerIsProse`: Markdown and the like mention a symbol, they do not call it) and the rows the index knows as definitions of the same identifier (`IsDefinitionRow`). The symbol bar then lists each changed symbol at depth 0 with `CallersDetail` ("used in 4 files, 7 lines", "removed, still used in ..." for a deleted symbol or the old name of a rename, "not used elsewhere"; a second symbol with the same identifier says "same name, listed above") and under it, at depth 1, one row per use: the symbol the index puts the row in (`EnclosingSymbol`, the last one starting on or before it, since the index keeps no ends) or the file name, then "path:row" and the text as the detail. `FSymbolFiles` holds the file of each use row ('' for a changed symbol, which is jumped to as Changed Symbols does), and `FSymbolPlaces` tells `SymbolBarPick` the rows are places to go to as they are: it shows the file and jumps to the row after `UpdateWrapInfo` with `LineTopTodo` cleared, since the editor otherwise restores the line top it kept from the resize of showing the file at the next paint. The status bar counts the files that use the changed symbols; without any, or without changed symbols, it says so and the bar stays hidden.

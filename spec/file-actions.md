# Discard, leave out, keep, revert, rename, remove, clean and context menus

Read this when touching `gittan.discard`, `gittan.keep`, `gittan.leaveout`, `umain.discard.inc`, `umain.leaveout.inc`, `umain.revert.inc`, `umain.movefiles.inc`, `umain.clean.inc`, the file and editor popup menus.

- A block of changed lines can be discarded: put back to how it is in the version compared against (`umain.discard.inc`, `gittan.discard.pp`, the latter without LCL and tested in `tests/testdiscard.pp`). It is offered while `CanDiscard`: the change view of a tracked text file that is modified, renamed or deleted (not a new file, whose one block would empty it, nor a conflict or a binary), against a commit or a snapshot but not a range, since the right side is not the work tree then. Every changed row of `Edit` is live across the text: `DiscardAt` (from `EditMouseMove`) gives the block and the row the mouse is on (or the kept change, see below), `SetHotDiscard` keeps them (`FHotDiscard`, `FHotRow`; cleared by `EditMouseLeave`, a scroll of `Edit` and `BuildChangeView`, since the blocks are counted anew) and, once the mouse has rested on the row (`FPillTimer`, `PillPause`; at once while they are already up, so a mouse passing through the diff raises none), `ShowDiscardPills` shows `FDiscardPills` at the right end of the row, a `TGittanHoverPills` (`gittan.hoverpills.pp`: a strip of pills in a font a size under the form's, a child of the form like the popup lists, placed at the right end of an anchor rectangle, `OnPick` on a click, `OnLeave` when the mouse leaves it, colored by `SetColors` from `ApplyTheme`, each pill with a hint the strip shows itself under it after `Application.HintPause` in a `THintWindow`, and a pill with the discard arrow set `DiscardGap` apart from the ones before it, since it is the one that loses work), Reviewed (`rsKeepPill`, the keep, see below) after a check mark and Discard after an arrow going back round a circle, both for the block the row is in. The word hover goes on under them. The mouse going from the rows onto the pills keeps the block (`MouseOnDiscardPills` in `EditMouseLeave`) and going back from the pills onto the rows too (`MouseOnDiscardRows` in `DiscardPillsLeave`). `DiscardPillsPick` runs `KeepBlockAt` or `DiscardBlockAt`, which File > Discard Change (Cmd+Shift+Backspace) also uses for the block the caret is in (`BlockAtRow`; `UpdateDiscardItems`, from `UpdateChangeNav` and when the File menu opens, enables the two items). `DiscardThis` asks (`rsDiscardAsk` with `DiscardBackText`: how many lines go back to what, HEAD or the base as `BaseLabel` names it) and writes. A conflicted file has a gutter band of its own instead, `gutterTagDiscard`, added rightmost in `SetupEditor` and shown by `SetDiscardBand` (from `ApplyBlame`, so every view change and zoom sets it) on `Edit` only while `CanResolveBlocks` (see Resolving conflicts in conflicts.md): `DrawDiscard` (from `EditDrawEditor`) paints a fork button on each conflict's first row in view, the one under the mouse on a disc, with its hint and the hand cursor through the blame hint's path (`FHoverBlame`), and `EditClickGutter` sends a click on it to `ResolveConflictAt`. `DiffBlock` reads the block out of `FChangeLines` (its deleted lines, its added lines, and the 1-based line the added lines start at in the file as it is, one past the last line for lines deleted at the end) and `DiscardBlock` writes the deleted lines over the added ones by line number, not from the diff's text, since the diff may have been taken with whitespace ignored: it reads the file as bytes, splits at LF, checks that the lines at that place are the block's added lines (`rsDiscardStale` otherwise, so a file that changed since the diff was taken is left alone), keeps the file's line end (that of its first line) and whether it ends with a newline, and makes a missing file for a block of deleted lines at line 1 (a deleted file comes back). The blocks discarded are kept in `FDiscards` (cleared by `OpenRepository`), and File > Undo Discard (Cmd+Alt+Z) writes the latest back through `Swapped` (the same block with old and new exchanged, checked against the file the same way), showing its file when another is shown; a discard that fails is dropped from the list too. Both refresh the repository (`RefreshRepository`) and say what they did in the status bar. The index is not touched: a staged change discarded in the work tree stays staged, as `git status` then shows.
- A block can be left out of the commit (`umain.leaveout.inc`, `gittan.leaveout.pp`, the latter without LCL and tested in `tests/testleaveout.pp`). While `CanLeaveOut` (`CanDiscard` while the tree's boxes choose, `CommitChoosing`, and no commit runs) the hover pills are Reviewed, Skip in Commit and Discard (`FPillChoose`, the middle one without an icon, `'k d'`); on a block left out, or any block of a file not ticked, the middle pill is Include in Commit (`LeaveOutCaption`, its hint from `LeaveOutHint`). File > Leave Change Out of Commit (Cmd+Alt+K, `FLeaveOutItem`, `MenuLeaveOutClick`) does the same for the block the caret is in, and `UpdateLeaveOutItem` (from `UpdateDiscardItems`) enables it and names it Include Change in Commit where the pill reads Include in Commit. The changes left out are pairs of a block, as keeps are, held in `FLeftOut` (a second `TGittanKeeps`, by path, cleared by `OpenRepository` and after a commit) and matched to the shown diff by `MatchKeeps` in `gittan.keep` (both lines of a pair get the index; `ApplyKeeps` uses it too): `ApplyLeftOut` (from `ShowChanges` once `FView` is set, and `RebuildKeeps`) first drops those the raw diff no longer holds (`TGittanKeeps.Prune`) and fills `FLeftOutOf` for `FChangeLines`. `BuildRows` gives a line left out the muted tint `bmLeftOutAdded` or `bmLeftOutDeleted` with its strip and no word shades. Leaving out a block's pairs that leaves nothing of the file (`AllLeftOut` over the raw diff) unticks the file instead; Include on a block of a file not ticked ticks it with every other block shown left out, so a kept line goes in, and Keep includes the pairs it keeps (`IncludeKept`), since a kept line has nothing to show it is left out. A ticked file with changes left out has a mixed box (`ApplyCommitChecks`) and the header the pill Include All (`FHeaderInclude`, `IncludeFile`); a click on a file's box takes it whole, in or out, and drops its changes left out (`DropLeftOut`). `StartCommit` turns them into commit parts (`CommitParts`): the file's diff against HEAD again (`FileChanges`, so with whitespace ignored when that is on, whose whitespace-only changes then go in) and `LeaveOutText`, which writes the work tree's bytes with each left out pair's deleted line put back and its added line taken out, by line as `DiscardBlock` does: the added lines are checked against the file (`rsDiscardStale`, which stops the commit with a banner), context lines are not, since `-w` may show them as HEAD has them, line ends and a missing final newline are kept, and a line put back gets the CR when the file's first line has one. A file whose changes left out are all gone goes in whole.
- A block can also be kept: shown as plain code for the rest of the session, once the user has looked at it and accepted it (`gittan.keep.pp`, no LCL, tested in `tests/testkeep.pp`; the Reviewed pill, `KeepBlockAt`, named for what the user means by it, since "Keep" read as keeping the change in the file). Neither the file nor git is touched: `FKeeps` (a `TGittanKeeps`, cleared by `OpenRepository`) holds the keeps of every file by path, and `ShowChanges` keeps the diff as git gave it in `FRawChangeLines` and applies them to `FChangeLines` (`FKeeps.Apply`), which the view is built from, so a kept line has no color, no strip and no button, the navigator does not count it, Hide Unchanged Lines folds it away, and `DiffBlock` still finds the right lines for a discard of the blocks left (a kept added line counts as a line of the file, as it is). A keep is one pair of a block (`TGittanKeep`: the k-th deleted line with the k-th added line, as the side-by-side view puts them next to each other, a deleted line past the added ones, or an added line past the deleted ones; `BlockPairs`), kept by its content and found again in a fresh diff by it (`ApplyKeeps`: each keep takes the nearest unkept pair with its text, by `Line`, where it was), so it survives the diff being taken again after the file changed elsewhere and goes by itself when its lines are gone; keeping a block keeps every pair of it. `ApplyKeeps` drops a kept pair's deleted line and makes its added line a context line, and gives `FKeptOf`, the keep each line of the rewritten diff comes from (-1 for none): the mouse resting on a kept line (`DiscardAt` reports it as `FHotKeep`) gets a Not Reviewed pill (`UnkeepAt`), and the header gets a "Show n Reviewed" pill (`SetChangeActions`, which also sets Edit for one of the repository's own files; `FHeaderUnkeep` is its index, and `HeaderAction` runs `UnkeepFile`). `RebuildKeeps` applies the keeps to the raw diff again and rebuilds the view at the same place (`RebuildIfChanges`), with the headings found again, since the blocks are others now. The old side's numbers after a kept block are those of the rewritten diff, not the old file's: the kept lines count as if the old file had them. The tree's counts and badges come from git and show the whole change, and a commit takes the whole file as before.
- Reverting files (`umain.revert.inc`): Revert Changes... in the file menu (`FRevertItem`; the tree, the summary's rows, the file header) puts a changed file back as HEAD has it, or, on a folder of the tree (`FContextFolder`, the menu's only enabled item then), every changed file under it; File > Revert File... (Cmd+Alt+Backspace) does it to the file shown. It asks first, and is offered only while the work tree is compared with HEAD (`CanRevert`) and no commit or remote job runs: Discard is one block against the version compared with, Revert whole files against HEAD. `TGittanRepo.RevertFiles` adds a rename's old path (from `git status`), saves every file on disk as a blob first (`hash-object -w --no-filters`; `ASaved` gets the path, a NUL and the id, empty for a file that was not there), then runs `restore --source=HEAD --staged --worktree` for the paths HEAD has and `rm --cached --ignore-unmatch` plus a delete for the rest (added and untracked files); a submodule is left alone. File > Undo Revert (`FRevertUndo`, latest last, cleared by `OpenRepository`) writes the saved blobs back with `RestoreReverted` and deletes again a file that was not there; the index is not brought back. Tested in `tests/testgit.pp` (`TestRevertFiles`).
- Renaming and removing files (`umain.movefiles.inc`): Rename or Move... and Remove from Git... in the file menu (`FMoveItem`, `FRemoveItem`; the tree, the summary's rows, the file header) act on a file the index holds (`TGittanRepo.IsTracked`, `ls-files`), not a folder, while no commit or remote job runs (`CanMoveFiles`; Rename also needs the file on disk). Rename asks the new path from the top of the repository (`InputQuery`, the old path filled in; backslashes become slashes, and one that is absolute or holds `..`, `.git` or a colon is refused in the status bar) and runs `MovePath` (`git mv -- <old> <new>`, the new folder made first since git mv makes none), so git shows a staged rename. Remove asks, Cancel the default, Stop Tracking (`RemovePaths` with `AKeep`: `git rm --cached`, the file kept on disk) or Delete (`git rm`, which refuses a file with changes not committed; its message goes in a red banner). `ChangedFiles` lists a file taken out of the index but kept once, as the staged deletion, not also as untracked, and `Commit` commits it through the temporary index (`Untrack`: a chosen path whose deletion is staged and whose file is on disk is taken out of that index with `rm --cached` too), since `commit --only` would take it as the work tree has it and see no change. Tested in `tests/testgit.pp` (`TestMoveAndRemove`).
- Clean (`umain.clean.inc`, `gittan.cleandlg.pp`), with a preview: File > Clean... (`FCleanItem`, off while a commit, fetch, pull or push runs, `CanClean`) opens a dialog built in code like the rebase dialog (`ChooseClean`): a box chooses Untracked files, Ignored files or Untracked and ignored files (`TGittanCleanKind`: `cnUntracked`, `cnIgnored`, `cnAll`; the last choice, `FCleanKind`, is offered first until another repository is opened) and a native `TCheckListBox` lists what `TGittanRepo.CleanPreview` gives for it, every row ticked: `git clean -n -d`, with `-X` or `-x` (`CleanFlags`), read by `ParseCleanPreview` (the "Would remove <path>" lines, a path git quotes C-style unquoted by `UnquoteCPath`; "Would skip repository" lines, a nested repository, are left out), a folder whose every file goes as one row ending in a slash. Under the list the count ("2 of 5 ticked"), Tick All and Untick All, a failed preview in red, and that git keeps no copy and nothing goes to the trash; Delete counts the ticked rows and is off while none is, Cancel is the default button. `TGittanRepo.Clean` deletes the ticked paths with the same flags (`git --literal-pathspecs clean -f -d[X|x] -- <paths>`, a hundred paths per call since git clean reads no pathspec file), so only what that preview listed goes: an ignored file named while cleaning untracked ones stays. Unlike a revert nothing is saved first, since ignored files are mostly build output. The watcher is stopped meanwhile; the status bar says what was deleted. Tested in `tests/testgit.pp` (`TestParseCleanPreview`, `TestClean`).
- The tree (right click selects, `tvoRightClickSelect`), the summary rows (`OnContextFile`) and the file header share the popup menu `FFilePopup`: copy the full or the relative path, reveal the file in Finder (or the file manager), Open in Editor, which runs the `EditorCommand` of the settings file with the path appended, or `OpenDocument` when none is set, and Show History, the commit graph filtered to the file, or to the folder of the tree (`FContextFolder`; see the commit graph in commit-graph.md). `FilePopupPopup` finds the file from the summary's row, the header's file or the tree's selection, and disables the file actions for a path not on disk (a deleted file). The editors have a menu of their own, `FEditPopup`, set as ATSynEdit's `PopupText` (so its standard menu, mostly disabled in a read-only editor, is not shown): Copy, Select All, then Show Commit (what a click on the blame band does: `ShowHistoryCommit` by the row's key in the history view, else `ShowBlameCommit`) and Copy Commit Hash, and, with gh, Open on GitHub, Copy GitHub URL, Open Commit on GitHub and "Open #123 on GitHub", shown only when the row's commit summary names an issue or pull request (`IssueNumber` in `gittan.github.pp`, `FPopupIssue`; `gh browse 123` opens either). ATSynEdit pops it up itself, so `EditPopupPopup` finds the editor under the mouse and the row there (`FPopupEd`, `FPopupRow`) and the commit of that row through `CommitOfRow` (`FPopupHash`, empty for an uncommitted line or when neither blame nor the history view gives one, and `FPopupKey` in the history view), which enables the commit items. The file menu has Copy GitHub URL too; `GitHubUrl` runs `gh browse --no-browser` and answers the address, `OpenOnGitHub` opens it, and `FileGitHubArgs` builds the arguments for a file at a line.

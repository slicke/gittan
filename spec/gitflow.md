# Git flow

Read this when touching `gittan.gitflow`, `umain.gitflow.inc`, Branch > Git Flow, or the Finish item in the branch list's menu.

- Git flow keeps a development branch beside the production one: features branch off the development branch and are merged back into it; releases branch off it too and hotfixes off the production branch, and both are merged into the two branches and tagged. `gittan.gitflow.pp` (no LCL, tested in `tests/testgitflow.pp`) does it with plain git, so the git-flow command need not be installed, and keeps the setup in the keys that command uses (`gitflow.branch.master`, `gitflow.branch.develop`, `gitflow.prefix.feature`, `.release`, `.hotfix`, `.versiontag`, and `.bugfix` and `.support`, which Gittan does not use but the command looks for), so a repository set up in either works in the other. `TGittanFlow` holds the two branches, a prefix per `TGittanFlowKind` (`fkFeature`, `fkRelease`, `fkHotfix`; a prefix not set has git-flow's default) and the version tag prefix; it is `Initialized` when both branches are set and differ (`ParseFlowConfig` reads `git config --get-regexp ^gitflow\.`, `ReadFlow` runs it).
- `InitFlow` writes the keys (`--local`). The production branch must exist, here or on a remote, which it is then made from with tracking; the development branch is made from its remote's when one has it, else from the production branch. An empty value (the version tag prefix, mostly) cannot go to `git config` as an argument, since `RunTool` refuses an empty one on Unix (see git-core.md), so `SetEmptyKey` unsets the key and appends it to the config file (`rev-parse --git-path config`) as `key =` in a section of its own, after a line break when the file lacks its last one, and under the header already there when `--unset-all` left it as the last line (a git before 2.42 keeps an emptied section). The bugfix and support prefixes are written only when the config lacks them, so what the git-flow command set stays.
- `FlowKindOf` tells a branch's kind and name by prefix, the longest prefix winning; `FlowBranchesOf` and `ListFlowBranches` list the branches of git flow by kind. `FlowBase` is the production branch for a hotfix, the development branch otherwise. `StartFlowBranch` makes the branch from its base (the local one, made from the remote's when missing) with `switch --no-track -c`, so changes in the work tree come along. `NextFlowVersion` suggests the next release (the second number up, 1.2.3 to 1.3.0) or hotfix (the last up, a third added to two, 1.2 to 1.2.1) after `LatestFlowVersion`, the newest tag with the prefix that is numbers and dots (`tag --sort=-v:refname`).
- `FinishFlowBranch` needs the tracked files without changes (untracked files are no obstacle). `FlowTargets` are the development branch for a feature; the production branch, then the development branch for a release; the production branch, then the release branch under way (as git-flow does, so the fix goes out with it) or the development branch for a hotfix. Each target that does not have the branch yet (`merge-base --is-ancestor`) gets it with `merge --no-ff --no-edit` (`GIT_EDITOR=:`); a release or hotfix tags the production branch with `FlowTag` (the prefix and the name) after the merge into it, annotated with the message given, plain without one, unless the tag is there already (refused at the start when the branch is not yet in the production branch, since that tag is another one). Then it switches to the development branch and deletes the branch with `-D`, since it is in every target, which `-d` would check against HEAD alone. A merge that stops with conflicts leaves git in the middle of it on that target (`AConflicts`, `AStoppedAt`); once the merge is committed, finishing again leaves out every step done.
- Branch > Git Flow (`FFlowMenu`, filled by `FillFlowMenu` as the Branch menu opens, so the palette lists its items, from `FSnapFlow` and `FSnapFlowBranches`: the snapshot carries the config's git flow keys in `FlowConfig`, and `ApplyFlowSnapshot` parses them and finds the branches among `RefState`'s local branches, so opening the menu, or the branch list's, runs no git; a setup changed by the git-flow command shows once a snapshot runs) has Set Up Git Flow... alone while the repository has no git flow. Then Start Feature..., Start Release... and Start Hotfix...; a Finish item per branch of git flow (the current branch's first, at most 20, its tag `FlowFinishTag` plus the index in `FFlowBranches`); and Git Flow Settings.... Starting and finishing are off while `RepoReady` is false; the setup while git is in the middle of something.
- The setup (`FlowSetupAsk`) asks the six values in one `AskInput`, filled with the current setup or the defaults (`SuggestFlowMaster`: main or master, whichever exists), checked by `CheckFlowSetup`. A start (`FlowStartAsk`) refuses a second release or hotfix while one is under way, as git-flow does, and asks the name with the next version filled in for a release or hotfix, checked by `CheckFlowStart` (a valid branch name not taken, and for a release or hotfix no tag of that name). A finish (`FlowFinishAsk`) says where the branch goes and the tag it gets: a question for a feature, the tag's message (filled with "Release 1.2", empty for a plain tag) for a release or hotfix. Success is a green banner, which for a tagged finish says nothing is pushed yet; conflicts are an error banner that says to commit the merge and finish again.
- The branch list's menu (`BranchContext` in `umain.branches.inc`) offers the same Finish for a local branch of git flow (`FlowBranchOf`, `FlowFinishCaption`, `bmFlowFinish`).

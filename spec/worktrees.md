# Worktrees

Read this when touching `gittan.worktrees`, `umain.worktrees.inc`, Branch > Worktrees..., or how a worktree is added, opened, locked, removed or pruned.

- A linked worktree is a second work tree of the same repository on a branch of its own (`git worktree`), so two branches can be worked on side by side, each in a tab. `gittan.worktrees.pp` (no LCL, tested in `tests/testworktrees.pp`) holds `TGittanWorktree` (the folder as git prints it, the commit checked out, the branch without `refs/heads/`, and whether it is the repository's own (`Main`, the first git lists), bare, detached, locked (with the reason) or prunable (its folder gone, with git's reason)) and the functions that run git in a root: `ListWorktrees` (`git worktree list --porcelain`, read by `ParseWorktreeList`: a block per worktree, blank lines between), `AddWorktree` (`git worktree add`: with `-b <branch> -- <path> <start>` for a new branch, `-- <path> <branch>` for one that exists, `-- <path>` alone to let git name a branch after the folder), `RemoveWorktree` (`git worktree remove`, `--force` twice when asked, which a lock needs; `ADirty` says git refused it for changes not committed or a lock, by its words), `LockWorktree` (`lock` or `unlock`), `PruneWorktrees` (`prune`) and `SuggestWorktreePath` (a folder beside the repository named after it and the branch, a slash as a dash, "-wt" with no branch, a number added while the folder exists).
- Branch > Worktrees... (`FWorktreesItem`, `MenuWorktreesClick` in `umain.worktrees.inc`) drops `FWorktreePopup` from the status bar's branch (`ShowWorktreeList`, the list read then and kept in `FListedWorktrees`): Add Worktree... (`wtRowAdd`), a header, then a row per worktree with its folder's name and as its detail the branch (or "at <id>" while detached, "bare" for a bare one), "this one" for the one open in the frame (`IsThisWorktree`: the root as given or expanded), "the repository" for the main one, "locked" and "folder is gone" where they apply; the one open here is checked. A pick opens the worktree through the window (`OpenWorktree`, `TRepoWindow.OpenRepository`: the tab that has it, else a new one); a bare one or one whose folder is gone says so in the status bar. A right click (`WorktreeContext`, `FWorktreeMenu`) offers Open in New Tab, Reveal in Finder (Show in Explorer, Show in File Manager), Lock or Unlock (not the main one), Remove... (not the main one, nor the one open here) and Prune Worktrees (enabled while one is prunable). Add Worktree... (`AddWorktreeAsk`) asks the folder (`SuggestWorktreePath` filled in; a relative one is taken beside the repository, one that exists is refused) and a branch in one `InputQuery` ("Branch (made if new, empty for one named after the folder)"): a branch that exists locally (`HasCommit` on `refs/heads/`) is checked out there, another is made from HEAD, none lets git name one after the folder; the new worktree opens in a tab. Remove... (`RemoveWorktreeAsk`) asks first, saying the folder is deleted and the branch stays, and when git refuses for changes not committed or a lock asks again with git's words before `--force`. The list is read anew each time it drops, so a worktree added or removed in a terminal shows up; nothing is polled.

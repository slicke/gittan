# Project kinds

Read this when touching `gittan.project`, `gittan.manifest`, adding a kind of project, `RegisterProjectKind`, `DetectProjects`, `ProjectsOfRoot`, `ProjectReport`, or the `project =` line of `.gittan/commands.ini`. The Commands page that lists the kinds' commands is in repo-commands.md, the Project page that shows their dependencies and checks in project-page.md.

## What a kind is

- A kind of project is what the files at a repository's root tell: a Lazarus project (a `.lpi`, or a `.lpr` alone), a Node package (`package.json`), a Rust crate (`Cargo.toml`), a Go module (`go.mod`), a Python project (`pyproject.toml`, `setup.py` or `requirements.txt`). `gittan.project.pp` (`src/core`, no LCL, tested in `tests/testproject.pp`) holds `TGittanProjectKind`, a class per kind registered as the unit loads (`RegisterProjectKind` in its `initialization`; `Gittan.lpr` lists the unit so it is linked, as it does the forges), and the five kinds in that order. Node offers no commands (its scripts are the Commands page's Scripts section already) and is a kind for its dependencies and checks. `ProjectKinds` is the list in the order registered, `ProjectKindByName` finds one whatever the case, and `DetectProjects(ARoot)` asks every kind for its manifest and gives those that have one as `TGittanProjects` (`Kind`, `Name`, `Manifest`), in the registered order, which is the order of the page's sections. A kind is a class so a kind with more to it can move to a unit of its own, and so an extension or a Project page can ask what a repository is without reading the files again.
- Every method is a class function that reads files at most, never runs a program or goes to the network, since the kinds are asked on every snapshot (`LoadRepoCommands` from `ApplySnapshot`); the ones after `Commands` have a default in the base class (none, '') so a kind implements what it has:
  1. `Name` – how the interface names it ("Rust", "Go"), the heading of its section and the word a `project =` line uses. Short and stable.
  2. `Manifest(ARoot)` – the file that makes the repository this kind, as the page shows it after the name ("Cargo.toml", "Polyglot.lpi", "a.lpi +1" for several), '' when the repository is not one.
  3. `Commands(ARoot)` – the commands its tools offer, `TGittanProjectCommand` (`Name`, `Command`, `Terminal`), made with `ProjectCommand`. The names are the plain verbs the tool uses (`build`, `test`, `run`, `fmt`), so a `[test]` section of the commands file reaches a kind's test as it does a script's; a kind with several of one verb names them `build:a`, `build:b`, which the page groups under `build` (`SplitCommandName`). What is offered follows the files: Rust has `run` with a `src/main.rs` or a `[[bin]]`, Go with a root `.go` file of `package main` (`RootIsMainPackage`), Python's `test` needs pytest named, a `tests` or `test` folder, a `pytest.ini` or a `conftest.py`, its `lint` and `fmt` ruff (else `lint` flake8), `typecheck` mypy, `tox` and `nox` their files, and its commands run through `uv run`, `poetry run` or `pdm run` and install with `uv sync`, `poetry install` or `pdm install` when a lock file or a `[tool.x]` table says so, else `pip install -r requirements.txt` or `pip install -e .`. Lazarus builds with `lazbuild X.lpi`, lazbuild taken from where Lazarus is usually installed when it is not on the PATH (`LazbuildCommand`: `/Applications/lazarus`, `/usr/local/bin`, `/usr/lib/lazarus`, `C:\lazarus`, fpcupdeluxe's), as an app started from the Finder has a short PATH, and a bare `.lpr` with `fpc`.
  4. `DependencyFile(ARoot)` – the file that lists the dependencies, relative to the root (`Cargo.toml`, `package.json`, `go.mod`, `pyproject.toml` else `requirements.txt`, the first `.lpi`); `LockFile(ARoot)` the one with the resolved versions when it is there (`Cargo.lock`; `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` or `npm-shrinkwrap.json`; `uv.lock`, `poetry.lock` or `pdm.lock`; none for Go, whose go.mod holds them, or Lazarus).
  5. `Dependencies(AText)` – what the dependency file's text asks for, `TGittanDependency` of `gittan.manifest` (`Name`, `Version` as written, `Group`: '' for a plain one, `dev`, `build`, `peer`, `optional`, `indirect`, or an extras group's name); `Locked(AName, AText)` the packages the lock file's text resolved, with the version in `Resolved`; `Version(AText)` the project's own version from the dependency file. All are functions of the text, so a file of a commit is read the same as the work tree's: the parsers are in `gittan.manifest.pp` (no LCL, tested in `tests/testmanifest.pp`), one per file form (`ParseCargoDependencies`, `ParseCargoLock`, `ParsePackageDependencies`, `ParsePackageLock`, `ParseYarnLock`, `ParsePnpmLock`, `ParseGoMod`, `ParsePyproject`, `ParseRequirements`, `ParsePythonLock`, `ParseLpiPackages`, and `CargoVersion`, `PackageVersion`, `PyprojectVersion`, `LpiVersion`), over a TOML reader of what the manifests need (`ReadToml`: tables, array tables with an index per element, strings, inline tables, arrays, comments stripped, a value that opens a bracket joined to the line that closes it; `TomlString`, `TomlInlineValue`, `TomlArrayStrings`), fpjson for the JSON ones, and `SplitRequirement` for PEP 508.
  6. `PackageUrl(AName)` – the package's page on the registry (crates.io, npmjs.com, pkg.go.dev, pypi.org), the link a dependency's name is on the Project page.
  7. `Checks(ARoot, ATracked)` – what is worth a warning, `TGittanProjectCheck` (`Text`, `Path` it is about, `IgnorePattern` when putting it in .gitignore is the answer), over the paths git tracks (`TGittanRepo.TrackedFiles`, a sorted list): Lazarus a tracked `.lps` (`*.lps`), `lib/` or `backup/`; Node `node_modules/` tracked, or no lock file with dependencies; Rust `Cargo.lock` there but not tracked in a crate with a binary (no pattern: it should be committed), `target/` tracked; Go no `go.sum` with requirements; Python `.venv/` or `venv/` tracked, a tracked `.pyc` (`__pycache__/`).
- `ProjectReport(AProject, ARoot, AOldManifest, AOldLock, ASince, ATracked)` is what the Project page shows of one kind (`TGittanProjectReport`): the files, the version, the dependencies with `Resolved` filled from the lock (`ResolveDependencies`), `Changes` against the old texts when `ASince` names what they are from (`DependencyChanges`: by name and group, added and changed in the new order, changed when the version shown differs, `DependencyShown` being the resolved one else the one asked for, then removed in the old order) and the checks. The frame reads the old texts from the tag with `FileBlob` (project-page.md).
- `DiscoverRepoCommands` in `gittan.repocommands` turns each kind's commands into `TGittanRepoCommand`s with `Source = csProject` and `Project = Kind.Name`, after the file's, the scripts and the targets, and gives the kinds to the caller through its `out AProjects`. `ProjectsOfRoot` is `DetectProjects` kept to what the commands file's `project =` line names when there is one (`ParseCommandsProjects`: a line before the first section, `project = rust, go`, names separated by commas or spaces, case ignored, `none` or an empty value for no kind, an unknown name skipped, a name once however often it is written); a kind the line names whose file is missing is listed with an empty `Manifest`, which the page shows as "named in commands.ini", since the line says what the repository is.

## Adding a kind

1. A class in `gittan.project.pp` (or a unit of its own that `Gittan.lpr` and the tests list) inheriting `TGittanProjectKind`, its three class functions over the files and whichever of the rest it has, and `RegisterProjectKind` in the initialization; a new unit also goes after `gittan.project` in `Gittan.lpr`. A parser of its manifest goes in `gittan.manifest.pp` as a function of the text.
2. Its tests in `tests/testproject.pp` (`TestRegistry` counts the kinds; a kind's own test puts its files in the temporary folder and checks `DetectProjects`, the commands' names and lines, and the checks) and the parser's in `tests/testmanifest.pp`, and a line in `rsNoCommands` of `gittan.commandpage` and `rsNoProject` of `gittan.projectpage` when its file is worth naming there.
3. Nothing in `src/ui` needs to change: the Commands page makes a section of every kind with commands, the Project page of every kind found.

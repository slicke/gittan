# Project drivers

Read this when touching `gittan.project`, `gittan.manifest`, a `gittan.proj.*` driver, adding a driver, `RegisterProjectKind`, `Identify`, `TGittanProjectContext`, the Project page's model, or the `project =` line of `.gittan/commands.ini`. The Commands page that lists the drivers' commands is in repo-commands.md, the Project page that paints their sections in project-page.md.

## What a driver is

- A kind of project is a driver: a class in a unit of its own under `src/proj/` (`gittan.proj.lazarus`, `gittan.proj.node`, `gittan.proj.rust`, `gittan.proj.go`, `gittan.proj.python`), no LCL, inheriting `TGittanProjectKind` of `gittan.project` (`src/core`) and registering itself as it loads (`RegisterProjectKind` in its `initialization`). `Gittan.lpr` lists the drivers so they are linked, as it does the forges; the registered order (Lazarus, Node, Rust, Go, Python, the order of the uses) is the order of the page's sections. Nothing outside a driver names its class, except its own tests.
- A driver owns what only its kind has: its parsers (as functions of a file's text, so a file of a tag is read as the work tree's), its commands, its checks and its section of the Project page. What the drivers share is in `gittan.manifest` (`src/core`): the dependency record `TGittanDependency` (`Name`, `Version` as asked for, `Resolved` from the lock file, `Group`: '' or `dev`, `build`, `peer`, `optional`, `indirect`, an extras group's name), the TOML reader of what the manifests need (`ReadToml` with an index per array-table element, `TomlString`, `TomlInlineValue`, `TomlArrayStrings`, `BareKey`; comments stripped, a value that opens a bracket joined to the line that closes it), `AddDependency` (once per name and group), `ParseTomlLock` (the `[[package]]` lock of Cargo.lock, uv.lock, poetry.lock and pdm.lock) and `ParseJsonObject`.
- Every method is a class function that reads files at most and asks git only through the context, never the network, since the kinds are asked on every snapshot. Only `Name` and `Identify` are abstract; the rest default to nothing:
  1. `Name` – the kind's name ("Rust"): the section's heading, the word a `project =` line and the settings use. Short and stable.
  2. `Identify(ARoot, out AManifest)` – whether the files at the root make the repository one of this kind, with the file that tells it as the page shows it ("Cargo.toml", "Trndi.lpi", "a.lpi +1"). `DetectProjects` asks every driver.
  3. `Commands(ARoot)` – the commands its tools offer (`TGittanProjectCommand`: name, shell line, terminal), plain verbs (`build`, `test`) so a `[test]` section of commands.ini reaches them, `build:<mode>` for several of a verb, which the Commands page groups (`SplitCommandName`).
  4. `DependencyFile`, `LockFile`, `Dependencies(AText)`, `Locked(AName, AText)`, `Version(AText)`, `PackageUrl(AName)` – what `StandardSection` needs for the dependencies table.
  5. `Checks(AContext)` – what is worth a warning (`TGittanProjectCheck`: text, path, `IgnorePattern` when .gitignore settles it).
  6. `Section(AContext, AManifest)` – the driver's section of the Project page. The default is `StandardSection`: the heading (the manifest, the version, the count of dependencies, how many changed since the tag), the dependencies table (`DependencyTable`) and the checks. A driver overrides it to show more, usually around `StandardSection`'s blocks.
- `TGittanProjectContext` is what a driver may ask of git while it builds its section: `Root`, `Since` (the tag compared with, '' for none), the tracked paths (`IsTracked`, `TrackedUnder`, `TrackedWithExt`), `ReadAt(APath)` (the file at the tag), `GitlinkAt(APath, ARef)` (a submodule's commit at a ref, '' for HEAD), `Describe(APath, ACommit)` (a submodule's commit by its tag, `git describe --tags --always`, else the short hash) and `Submodules`. The base answers from what it was given and nothing for the rest, which the tests subclass; `TGittanGitProjectContext` asks git (`describe --tags --abbrev=0` for `Since`, `ls-files`, `cat-file blob`, `ls-tree`, `ListSubmodules` once).
- `ReadDependencies` gives a kind's dependencies resolved by its lock file and how they differ from those at `Since` (`DependencyChanges`: by name and group, by the resolved version when there is one; `DependencyShown`); `ProjectSections(AProjects, AContext)` asks each kind for its section, `StandardSection` for one picked by hand with no manifest (it says the file is missing).

## The page's model

- A section (`TGittanProjectSection`) is a heading (`Name`, `Detail`, `State` in a `StateStyle`) over blocks (`TGittanProjectBlock`): `pbFacts` (a dim label and a value per row, and any further cell, a button, after it), `pbTable` (`Columns` as headers when set, rows of cells, `Heading` rows as subheadings, `RightLast` to put the last column at the right end), `pbChecks` and `pbNote`. A block's `Title` is a subheading over it. A cell (`TGittanProjectCell`) has its text, a style (`psText`, `psDim`, `psStrong`, `psLink`, `psOk`, `psWarn`, `psError`, `psButton`), a `Hint`, a `Url` that makes it a link, and for a button the `Command` it runs under `CommandName`. The helpers build it: `ProjectCell`, `ProjectButton`, `ProjectRow`, `ProjectHeadingRow`, `ProjectBlock`, `AddRow`, `AddFact` (nothing for an empty value), `AddBlock` (nothing for an empty block), `ProjectNote`, `ChecksBlock`.

## The drivers

- **Lazarus** (`gittan.proj.lazarus`): a `.lpi` at the root, else a `.lpr`. It reads the project with fcl-xml's DOM (`ReadLazProject`): the title, the version of `<VersionInfo>` when in use, the session storage, the units, the required packages (with `<MinVersion>` as ">= 2.4"), and the build modes (`TLazBuildMode`): a mode with `<CompilerOptions>` of its own reads them, one without (the one marked `Default`) the project's `<CompilerOptions>` after `<ProjectOptions>`; the target file, `TargetOS`, `TargetCPU`, the widgetset its `<MacroValues>` set (`LCLWidgetType`), the unit output folder, the optimization (Lazarus's -O1 when unset), the debug info (off, DWARF 2, DWARF 3, stabs, on), strip, smart link and the custom options. Its commands build each mode (`build:<mode>`, `LazBuildCommand`: lazbuild --bm, quoted for the shell, lazbuild found where Lazarus is usually installed when it is not on the PATH), one `build` when there is one mode, `build:<project>` for several .lpi, fpc for a bare .lpr. Its section: the facts, the build modes as a table (Mode with "default" after the default one unless it is named Default and the custom options as its hint, Output with the unit folder as its hint, Platform, Code, Debug and a Build button), and the packages (`FindLazPackages`: the .lpk files at most `LazPackageDepth` folders down, skipping hidden folders, lib, backup and node_modules; `ReadLazPackage` for its version, description and requirements): where each is from, a .lpk's path, `vendor/ATSynEdit @ 2026.10.28` for one in a submodule (the URL in the hint), Lazarus for one that comes with it (`IsLazarusPackage`), "not found" in the warning color; its version; and the change since the tag at the right: added, removed, the minimum version changed ("any → >= 2.4"), or the submodule moved ("2026.08.03-2-g… → 2026.08.03-16-g…"), each counted in the heading's state. Its checks: a tracked .lps, lib/ or backup/; a submodule not checked out (its folder empty); a required package found nowhere and not Lazarus's own.
- **Node** (`gittan.proj.node`): `package.json`. No commands (its scripts are the Commands page's Scripts section). Its section: the package's name, the package manager (`NodePackageManager`: the `packageManager` field, else the lock file, else npm) with an Install button, the module type, the engines and the workspaces (`ParseNodeInfo`), then the standard section; the dependencies resolved by package-lock.json (v1 to v3), yarn.lock (classic and berry) or pnpm-lock.yaml (both key forms). Checks: node_modules/ tracked; no lock file with dependencies.
- **Rust** (`gittan.proj.rust`): `Cargo.toml`. Commands: cargo build, run (with a src/main.rs or a [[bin]]), test, check, clippy, fmt, doc. Its section: the package, edition, rust-version, repository and the workspace's members (`ParseCargoInfo`), the dependencies by Cargo.lock (also [target.X.dependencies], [dependencies.name] tables and [workspace.dependencies]), the features with what each turns on and which are on by default, and the [[bin]] binaries with a Run button each (`cargo run --bin`). Checks: Cargo.lock not committed in a crate with a binary; target/ tracked.
- **Go** (`gittan.proj.go`): `go.mod`. Commands: go build, run (when a root file is package main), test, vet, fmt over ./... Its section: the module (a link to pkg.go.dev), the go and toolchain lines (`ParseGoModInfo`), the requirements (resolved as asked, so one version column; `// indirect` as the Indirect group), and the replace lines, a path in the warning color. Checks: no go.sum; a replace with a path whose folder is not there.
- **Python** (`gittan.proj.python`): `pyproject.toml`, `setup.py` or `requirements.txt`. Commands through the tool that owns the environment (`PythonTool`: uv, poetry or pdm by its lock file or `[tool.x]` table, else pip): install, test with pytest, lint and fmt with ruff (lint with flake8), typecheck with mypy, tox, nox. Its section: the project's name, the Python it requires (poetry's python dependency when there is no requires-python), the environment's tool and the build backend (`ParsePythonInfo`), the dependencies (PEP 621, optional-dependencies, dependency-groups, poetry's tables, requirements.txt; `SplitRequirement` for PEP 508) by uv.lock, poetry.lock or pdm.lock, and the programs of `[project.scripts]` with a Run button each. Checks: .venv/ or venv/ tracked; a .pyc tracked.

## Which kinds a repository is

- `ProjectsOfRoot(ARoot, AChoice)` in `gittan.repocommands`: the kinds the user picked on the Project page (`AChoice`, from the settings, `TGittanSettings.ProjectKindsOf`: "Lazarus,Go", "none"), else a `project = rust, go` line of commands.ini before its first section (`ParseCommandsProjects`), else `DetectProjects`. A named kind is listed through `ProjectsNamed`, with the manifest its `Identify` gives, '' when it does not identify the root; an unknown name is skipped; `SplitProjectChoice` reads either form. `DiscoverRepoCommands(ARoot, out AProjects, AChoice)` gives the kinds to `LoadRepoCommands`, which keeps them in `FRepoProjects` for both pages.

## Adding a driver

1. A unit `src/proj/gittan.proj.<kind>.pp` with the class (in the interface, so its tests reach it), its parsers as functions of the text, `Name` and `Identify` and whichever of the rest it has, its own `Section` when it has more to show than dependencies, and `RegisterProjectKind` in the initialization. List it in `Gittan.lpr` with the others.
2. Its tests in `tests/testproj<kind>.pp`, registered in `tests/gittantests.lpr`: the parsers on texts, the section built in a temporary folder with a `TGittanProjectContext` (a subclass of it for the tag's files and submodules). `TestRegistry` in `tests/testproject.pp` counts the drivers. A line in `rsNoCommands` of `gittan.commandpage` and `rsNoProject` of `gittan.projectpage` when its file is worth naming.
3. Nothing in `src/ui` changes: the Commands page makes a section of every kind with commands, the Project page paints every section, and the kinds' list offers every driver.

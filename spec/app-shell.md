# Opening repositories, settings, the CLI command and updates

Read this when touching File > Open, `gittan.app`, `gittan.settings`, the settings dialog, `gittan.cli`, `gittan.update`, the window caption or `UpdateStatus`.

- File > Open Repository (Cmd+Shift+O) uses the `TSelectDirectoryDialog` on the form (a folder on the command line, `gittan <folder>`, a folder dropped on the window, or File > Open Recent opens one too), then `OpenRepository` in `umain.pp` fills the tree and the summary from `ChangeStats`. There is no toolbar: the summary's hint tells a first-time user what to do; the welcome view (`gittan.welcome.pp`, shown while no repository is open) has Open Repository... with its key caps, Clone... and Init... in a row (under each other when the row does not fit; `OnClone`, `OnInit`) over the recent repositories. A folder that is not a repository, or a git failure, is shown in the empty view in the hint's place (`ShowError`), not in a dialog.
- `gittan.app.pp` holds `TGittanApp`, what every repository shares, one per process: the settings (read as it is created, which also sets the git to run, `SetGitExe`), the lexers (created there, loaded by the window, which takes `OnLoaded`), the application icon (`Icon`, MAINICON at every size, which the welcome view and the notice draw) and the check for a newer build. The window (`uwindow.pp`) creates it first in `FormCreate` (`CreateApp`) and frees it last in `FormDestroy` (`FreeApp`), after the frame; the code reaches it through `App` (`App.Settings`, `App.Lexers`). It is the first step towards several repositories open in one window, each in a frame of its own, with the app shared.
- `gittan.settings.pp` holds `TGittanSettings`, an ini file in a folder named `Gittan` next to the one `GetAppConfigDir` gives (`~/.config/Gittan/gittan.ini` on Unix; `ConfigDir` keeps the folder off `Application.Title`, which `GetAppConfigDir` would name it after): the window bounds and state (with none, or none on a screen now, `PlaceWindow` in `uwindow.pp` opens the window in the middle of the main screen's work area, `FirstShare` of it, at least the designed size and at most `FirstMaxWidth` by `FirstMaxHeight` at 96 DPI), the tree width, the editor font and zoom, the width of a tab (`TabSize`, 0 for `DefaultTabSize`, 8, git's own; `FTabSize` in the frame, set on every editor in `SetupEditor` and changed through `ApplyTabSize`, written as 0 when it is the default), the view options (word wrap, hidden unchanged lines, context lines, side by side, blame), an external editor command, a terminal command (File > Open in Terminal (Cmd+Alt+T) and the status bar's menu run it with the repository root appended, and a command of the Commands page marked for the terminal with the root and then its command line, `OpenTerminal` in `umain.actions.inc`, see repo-commands.md; empty opens the platform's terminal: `open -a Terminal` on macOS, Windows Terminal or `cmd.exe` on Windows, the first of `x-terminal-emulator`, `gnome-terminal`, `konsole`, `xfce4-terminal` and `xterm` on PATH elsewhere, started in the root), the path of git to run in place of the one found on PATH (`GitPath`, section `Tools`; empty for the found one), whether the open repository is fetched in the background and how many minutes apart (`AutoFetch`, on by default, and `AutoFetchMinutes`, `DefaultAutoFetchMinutes` 10, kept within 1 to 240; on the Tools page under git, see commit-and-remote.md), whether the GitHub features are on and the gh they run (`GitHubEnabled`, on by default, and `GhPath`, empty for the gh found; section `GitHub`, a section per service that hosts repositories, with `Enabled` and `Cli`, and whether the GitHub page looks for clones beside the recent repositories, `CloneSiblings`, off by default; an older file's `Gh` in `Tools` is read as `GhPath` and taken out on save, tested in `TestOldGhPath`), whether the AI features show, the agent they run (Claude Code or GitHub Copilot) and each agent's command and model (section `AI`; ai.md), the recent repositories, and the commands files trusted (`[Trust]`, `CommandsTrusted`, `TrustCommands`; repo-commands.md). The editor font has no fixed default: with none picked (`FontName` empty, `FontSize` 0) it is `DefaultFontName` (Menlo on macOS, Consolas on Windows, Monospace elsewhere) at `DefaultFontSize` for the height of the screen the window opens on in logical pixels (9 on macOS, 10 elsewhere, one more from 1200 and another from 1600; `FDefaultFontSize`; the LCL's Cocoa makes a size a third larger than a native point, so 9 is Terminal's and Xcode's 12), and the frame's `FormClose` writes the name and size only when they differ from these, so the default keeps following the screen; the Courier New 9 earlier versions wrote (ATSynEdit's own default, never picked) is read as no choice. `ApplySettings` in `umain.actions.inc` applies it before the menu is built, `FormClose` saves it. The settings dialog (`gittan.settingsdlg.pp`, `EditSettings`, from `MenuSettingsClick`; Cmd+, in the application menu on macOS, which the LCL builds from `CocoaConfigMenu.appMenu.customMenus` when the menu is set, and Tools > Settings with Ctrl+, elsewhere) has five pages (`TSettingsPage`) picked in a sidebar of the main window's kind (a `TGittanSideNav` with the icons `niEditor`, `niTools`, `niForge`, `niAI` and `niAbout`, colored with `ThemeSideNav` on `SidebarShade`, which `ColorSidebar` in `umain.pp` uses too; each page is an autosized panel in the content beside it, shown one at a time by `ShowPage`, all held at the tallest one's height from `DoShow`, the preferred height of each page not shown, so the dialog keeps its size): Editor edits the editor font and its size (View > Font has the font too; both go through `ApplyEditorFont`), the tab width and the syntax theme (View > Syntax Theme too; both go through `SetSyntaxTheme`); Tools edits the editor and terminal commands, each with a hint for what an empty field does, and the path of git, with a note under it that says what will run: where the tool is found on PATH, or that it is not, or whether the path typed exists; Hosting has a block per service that hosts repositories under its name in bold, GitHub alone so far (another service, GitLab with glab, is another block and section): Turn on the GitHub features (`FGitHubBox`, `GitHubChange`) with a note on what they are, and gh's path with the same kind of note (for gh that the GitHub features are off when none is found), then Look for clones beside the recent repositories (`FSiblingsBox`, `CloneSiblings`) with a note, both enabled only with the switch on; AI turns the AI features on and picks the agent, with its command's path and its model (see ai.md); About, the last, which Gittan > About Gittan on macOS (before Settings in `customMenus`) and Tools > About Gittan elsewhere open (`MenuAboutClick`; `OpenSettings` takes the page, `EditSettings` its `APage`), shows the icon (`LoadAppIcon`: `Application.Icon`, empty under Cocoa, else `MAINICON` from the executable's resources, the .ico's largest image, resampled with BGRABitmap's `rfBestQuality` in `AppIconPaint` to a square as wide as its box in the screen's pixels, in the middle of the box's height, which `alLeft` makes that of the text beside it), the name, the tagline and the build (`CurrentBuild`, or a local build with its compile date), a Check for Updates of its own (a `TGittanUpdateJob` the dialog owns; one still running when the dialog closes is dropped and goes to `GUpdateZombies`, freed once it has finished, so closing does not wait for curl, which gives up after `FetchSeconds`; its answer is beside the button, past the snooze: a link to download a newer build, a link to the latest release when this build cannot be compared with it, this is the latest build, or why GitHub could not be asked), what Gittan runs on and with (`ReadVersions`, queued the first time the page shows, so git, gh and the agent are run after it is drawn, and again when the page shows after a tool field, a switch or the agent changed (`FVersionsRead`, dropped by `ToolChange`, `GitHubChange` and `AIChange`), since the lines name the tools as the fields have them: the build, `git --version`, `gh --version` (or that the GitHub features are off) and the agent's `--version` as the fields name them now, or that the AI features are off, the system with its version (`sw_vers`, the Windows version, `/etc/os-release`), the CPU and the widgetset, Free Pascal and the LCL) with Copy, which puts those lines on the clipboard for a bug report, links to gittan.app and the source, and the licenses of Gittan and what it is built with. While About shows, OK keeps the focus, since a focused button becomes the default under Cocoa and Return would check for updates. `EditSettings` takes the values besides the font as a `TSettingsValues`. The other view options stay in the View menu. The font, the theme and the tab width are previewed in the editor itself: the dialog calls `PreviewSettings` on every change, and `MenuSettingsClick` puts back the font, theme and tab width it had when the dialog is cancelled. The dialog also has a read-only sample editor of its own (`FSampleEdit`, with its own `TATAdapterEControl`) under buttons for Pascal, C++, JavaScript, TypeScript and Python (`Samples`), so the colors show whatever the main editor holds and wherever the dialog sits: it takes the lexers from `FLexers` and the colors and zoom from `Edit`, and `StyleSample` sets its lexer again after every change, since `TGittanLexers.ApplyTheme` recolors the lexers every editor shares in place (so the sample can only show the theme the main editor has, which is why the main editor previews too). As in `SetEditorLexer`, assigning the lexer needs `DoEventChange(0)` to start the parse. The dialog opens with its bottom right corner near the editor's, so the code at the left stays in view (placed in `DoShow`, once its autosized size is known); opened on About (`FCentered`), which has nothing to preview, it is centered over the main window, as the other dialogs are (`poMainFormCenter`). The dialog changes `FSettings` only; the file is written on close as before, so an edit of the ini while Gittan runs is still lost. With no argument on the command line Gittan reopens the most recent repository. The argument or that repository (`StartRepository`) opens in `OpenAtStartAsync`, queued from the frame's `Init`, so the window is shown and painted first, with the welcome view already saying what opens (`SetBusy`) rather than offering its buttons for that moment; the repository's git work then runs in a thread (`TGittanOpenJob`, see git-core.md). A folder or file dropped on the Dock icon at launch that is open or opening by then stays (the repository is open, an open job runs, or the view is no longer the empty summary). The ini is written only on a normal close; a killed process keeps the previous one. TIniFile trims every value and takes a pair of quotes around one off as it reads, so `KeepEdges` writes a string that starts or ends with a space or a double quote inside quotes of its own (a quoted editor path such as `"C:\Program Files\Code\Code.exe"` stays quoted); the commit draft goes through `EscapeLines` first, which writes a line end as `\n` and a backslash as `\\`. Tested in `tests/testsettings.pp` (`TestQuotesAndSpaces`).
- Tools > Install CLI Command (`MenuInstallCliClick`, `gittan.cli.pp`) installs a `gittan` command that opens a folder or file in Gittan, the current folder when none is given. It is a script naming the running executable by its full path (`Application.ExeName`), so installing again after moving Gittan updates it. macOS: `/usr/local/bin/gittan` runs `open -a <bundle>` (`MacBundleOf`: the bundle the executable is in, or `Gittan.app` beside it, since a build's bundle holds a link to `./Gittan` and a Gittan started as that file gets no Dock icon or menu bar; the plain Unix script only when there is no bundle), so a running Gittan gets the path through Cocoa's open-files event, which the LCL hands to `FormDropFiles`; `/usr/local/bin` belongs to root, so the copy then goes through `osascript ... with administrator privileges`, and a Gittan run from a disk image or translocated by Gatekeeper is refused. Windows: `%LOCALAPPDATA%\Gittan\bin\gittan.cmd` runs `start`, and that folder is added to the user's `Path` in `HKCU\Environment` (then `WM_SETTINGCHANGE`, so only new terminals see it). Elsewhere: `~/.local/bin/gittan` starts the executable with `nohup` in the background, and the message says how to add the folder to PATH when it is missing. Every script carries a marker line (`IsGittanScript`); a `gittan` without it is someone else's and is neither replaced nor removed. Tools > Uninstall CLI Command (`UninstallCli`) removes the script (as an administrator on macOS when needed) and on Windows the empty bin folder and its PATH entry (`PathListRemove`); the item is enabled only while the script is there (`CliInstalled`, checked in the Tools menu's `OnClick`, which runs as it opens). The script texts, the PATH helpers and the marker check are tested in `tests/testcli.pp`; installing and removing are not.
- `gittan.update.pp` (no LCL, tested in `tests/testupdate.pp`) looks for a newer Gittan, as Trndi does: `TGittanUpdateJob` runs curl (`FetchUrl`; Gittan links no TLS library) for GitHub's `releases/latest` in a thread, `ParseRelease` reads the tag, title and page, and `IsNewerRelease` compares the tag's number (`BuildOfTag`, build-<n>) with `CurrentBuild`, the compiled-in `GittanBuild`; a local build (-1) is never told about one. `TGittanApp` (`gittan.app`) starts a check `UpdateFirstCheck` ms after start and every `UpdatePoll` ms after that, only in a build with a number, and tells the window through `OnUpdateChecked` (`UpdateChecked` in `umain.update.inc`); a newer release puts the badge in the status bar (`ShowUpdateBadge`) with a hint, unless `UpdateSnoozedUntil` in the settings (section `Update`, a yyyy-mm-dd day) is still ahead (`UpdateDue`). A click on it opens `UpdateDialog`: Download opens the release's page, Remind Me in 14 Days (`UpdateSnoozeDays`, `SnoozeUpdate`) sets the snooze and hides the badge, Not Now closes it. Tools > Check for Updates (`App.CheckForUpdate(True)`) always answers in a dialog, past the snooze: the same dialog for a newer build, else up to date, a local build with the latest release named, or curl's message. The app keeps the last finished job until the next check or until it is freed, since the job is still in its thread as it reports.
- `UpdateStatus` fills the repository parts whenever one is open, since the header names the file and its lexer; without one the name is the path of a plain file. It leaves the message and the position alone. `UpdateStatusPosition` (from `UpdateChangeNav`, so on every caret move) shows "Ln 12, Col 4" in the change view and a plain file: the file's line from `FileLineOfRow`, or the old side's number with "(old)" for a deleted line; nothing in the summary, the repository diff or the history. A note goes through `StatusNote` (`StatusNoteSeconds`, `StatusErrorSeconds` in red) and clears itself; a message that says something is under way ("Looking for ...", "Loading history...", fetching a pull request) is shown with `ShowMessage(..., 0)`, which stays, and the code that finishes the work calls `ClearMessage`. A repository that fails to load keeps its error in red until the next message. `UpdateStatus` also checks the Syntax menu: Automatic (the lexer from the file name; `FManualLexer` is set by a manual pick and cleared when the view changes), and the lexer in use, found through the item's `Hint`, which keeps the name without accelerator ampersands.
- `UpdateCaption` names the window after the repository, or after the file when none is open; the header names the file, so the title does not change with the selection.

# Submodules

Read this when touching `gittan.submodules`, `gittan.subpage`, `umain.submodules.inc`, submodule actions.

- The Submodules section (`umain.submodules.inc`, `gittan.submodules.pp`, the latter without LCL and tested in `tests/testsubmodules.pp`) sits under the Config section, built like it (`FSubPanel`, `FSubHeader`, `FSubTree`; folded or not in `SubmodulesOpen`, unfolded by default; `LayoutRepoFiles` sizes both, each up to a third of the tree panel while both show, and within what the page rows, the headers and the Commit section leave the tree of changed files, which keeps at least 80 px: a list with no room for a row is hidden, since a tree view laid out 0 px high never draws its rows on Cocoa, even once it has room; the panels grow and shrink at their top edge, so alBottom keeps their order). `FillSubmodules` (from `ApplySnapshot`) runs `ListSubmodules`: `git config -z -f .gitmodules --get-regexp ^submodule\.` read by `ParseSubmoduleConfig` (name, path, URL, branch) and the recorded commits from `git ls-files -s -z` through `ApplyIndexEntries` (a gitlink in stages 1-3 is a conflict, "ours" standing for the recorded commit); nothing when there is no `.gitmodules`. When `SubmoduleKey` (the paths, recorded commits, branches, URLs and the kind git status gives a submodule whose checkout moved) changed, `StartSubmoduleJobs` starts one `TGittanSubmoduleJob` per submodule, so a slow remote holds up only its row; View > Refresh starts them always, and `FSubTimer` again `SubmodulePoll` (5 min) after the last job of a round finished (`StartSubmoduleJobs(True)`, which keeps the rows' results while the jobs run; `AbandonSubmoduleJobs` stops the timer, and a finished job redraws the shown view only when `SubmoduleInfoKey` changed, so a poll leaves the caret alone). A job runs `CheckSubmodule`: the checked-out commit (`rev-parse HEAD` in the submodule, when it has a `.git`), then `git ls-remote` for `SubmoduleRemoteRef` (HEAD, or `refs/heads/<branch>` from .gitmodules, the repository's own branch for ".") against the submodule's `origin`, or for one not initialized against the URL in .gitmodules (`ResolveSubmoduleUrl` makes a relative one absolute from the repository's origin). Nothing is fetched. The result (`TGittanSubmoduleInfo`) is `smUpToDate` when the remote's commit is the recorded one, `smNotFetched` when the submodule does not have the remote's commit, else `smBehind`, `smAhead` or `smDiverged` from `rev-list --left-right --count`, with the incoming commits (`MaxIncoming`, `git log recorded..tip`), the remote's commit described when the submodule has it (`TipCommit`) and, when the recorded commit is past it, the commits the remote's branch lacks (`Outgoing`, `git log tip..recorded`) and the remote-tracking branches that have the recorded commit (`Holding`, `HoldingBranches`: `for-each-ref --contains` over refs/remotes, origin/HEAD left out, at most `MaxHolding`, as of the submodule's last fetch); `smFailed` keeps git's message. Finished jobs go to `FBlameZombies`. A row is the path with the folder icon (dotted in the kind's color when git status reports the submodule) and "↓3", "↓?" (new commits not fetched, so not counted), "↑2", or "⚠"; the header's detail counts the submodules and the ones with new commits on their remote ("9 · 3 behind", `rsSubmodulesNewer`). A row says what its mark means as a hint after the hint pause (`SubmoduleHint`, from `SubTreeMouseMove` through `SetTreeHint`, which the tree of changed files uses too, with `FTreeHintTree` naming the tree): how many commits the remote's branch (or its default branch) has that the recorded commit lacks and that Update brings it there, how far the recorded commit is past it, both, that they are not fetched, that it is where the remote is, or why the remote could not be asked, then how the submodule moved in the work tree when it did. For each submodule git status reports, `FillSubmodules` also runs `CompareSubmodule` against the sides of `TGittanRepo.DiffSides` into `FSubChanges`: the commit the left side records (`git ls-tree`, `ParseGitlink`), the one the right side records or, for the work tree, the one checked out (the recorded one when not initialized), and when the submodule has both, the commits added and dropped between them (`rev-list --left-right --count`, at most `MaxIncoming` of each listed); only local objects are read. A click shows the view `gvSubmodule` (`ShowSubmodule`), from the Submodules section, a changed submodule's node in the file tree or its row in the summary: the submodule's page, `TGittanSubPage` (`gittan.subpage.pp`, `FSubPage`, painted like the summary in the same scroll box, under the file header, which stays shown for it), with the name, the URL (a web address a link, through `RemoteWebUrl`) and the branch it follows, then cards (a disc in the state's color: green up to date, blue new commits on the remote, amber not checked out or past the remote, red in conflict or when the remote could not be asked) and, for a submodule that moved, a card "Changed  b0193be → 2844a79" with how many commits; then the recorded, checked-out and remote commits in labeled rows and the lists of commits it moved on to, the ones it no longer has, the new ones on the remote and the ones not on the remote's branch (`Outgoing`; the card past the remote then names the branches that have them and suggests setting one in .gitmodules, else says they may not be pushed or be on another branch) (the new ones left out when the moved-to commit is the remote's, as the list above has them), each on a line with a dot per commit as the summary's recent commits. A click on a commit copies its id (`SubPageCopyCommit`, "Copied 2844a79" in the status bar). The header names the path with an Open pill that opens the submodule as a repository (`OpenShownSubmodule`), and has no lexer name. The page keeps its scroll position while it shows the same submodule (a finished job or a refresh shows it again), and the snapshot leaves the summary hidden under it. `SelectShownSubmodule` keeps the shown submodule selected in the tree it was picked in, after a refresh (which empties both) in the file tree when it is changed, else in the section. A finished job redraws the view when it shows its submodule; `RefreshRepository` shows it again, or the summary when it is gone. `RunGitIn` in `gittan.git.pp` runs git as `TGittanRepo.RunGit` does without a repository object, for the jobs.
- Submodule actions (end of `umain.submodules.inc`, `gittan.submoduledlg.pp`): File > Submodules has Update Submodules, Sync Submodule URLs (both off without submodules) and Add Submodule...; the Submodules section's right-click menu (`FSubPopup`, a right click selects the row) has Update, Sync URL, Open as Repository (once checked out) and Copy Path for its row, and a shown submodule that is not checked out, or is checked out at another commit than the recorded one, has an Update pill before Open (`FSubUpdatePill`, read by `HeaderAction`). All are off while a commit or remote job runs (`CanSubmoduleAction`, `UpdateSubmoduleItems` from `UpdateRemoteItems` and `FillSubmoduleTree`). An update runs in the remote job (`rkSubmoduleUpdate`, `TGittanRepo.UpdateSubmodules`: `git submodule update --init --recursive --progress [-- <path>]` with `RemoteEnvironment`, the job's `Arg` the path, empty for all) with its notice; before it `UpdateSubmodulesAsk` asks, Cancel the default, when `MovedSubmodules` (`git submodule status`, the "+" lines read by `ParseMovedSubmodules`) finds a submodule it would move back, listing each with the commit checked out and the recorded one, since that is what a user who moved a submodule to record it does not want. A sync runs on the main thread (`SyncSubmodulesNow`, `TGittanRepo.SyncSubmodules`, `git submodule sync --recursive [-- <path>]`), its result in the status bar or a red banner. Add Submodule... opens `ChooseSubmodule`, built in code like the clone dialog: the URL (the clipboard's when `LooksLikeCloneUrl` takes it), the path, which follows the URL (`CloneFolderName`) in the folder every submodule shares (`SubmoduleFolder`, vendor/ when they are vendor/a and vendor/b) until it is typed in, with the whole path under it, and the branch (empty for the remote's default); Add is off, the reason in red, while the path leaves the repository (absolute, `..`, `.git`), is a submodule or inside one, or exists and is not empty. The red line is given a `Top` above the buttons each time it is shown again, since an alTop control made visible goes last. The add runs in the remote job (`rkSubmoduleAdd`: `Arg` the URL, `Path` and `Branch` set before `Start`; `TGittanRepo.AddSubmodule`, `git submodule add [-b <branch>] -- <url> <path>`, without `--progress`, which git 2.30 takes for an update only), its notice shown at once. `RemoteJobDone` hands both to `SubmoduleRemoteDone` after the refresh, which asks the remotes again (`RecheckSubmodules`, as View > Refresh) and says it in a green banner, a new submodule shown and named with a reminder to commit it with .gitmodules (git stages both); a failure is told in the notice with Update Again, or for an add Try Again, which opens the dialog again with what failed (`FRetryPath`, `FRetryBranch`), since git removes what a failed add made. Tested in `tests/testsubmodules.pp` (`TestParseMoved`, `TestSubmoduleFolder`, `TestUpdateSyncAdd`, which allows local folders as remotes through `GIT_CONFIG_COUNT` with `SetTestVariable` from testgit, since TGittanRepo runs git itself).

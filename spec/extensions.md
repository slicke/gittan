# Extensions

Read this when touching `gittan.ext.*`, `gittan.exthost`, `umain.ext.inc`, the Extensions menu, the Extensions page of the settings, `externals/quickjs/`, the libraries beside the executable, an event the extensions get, or what the extensions add to the forge view (its Extensions menu, their tabs in `gittan.extpage`, their Batch operations in `gittan.batchpage`, `uforge`).

## What an extension is

- A JavaScript file (ES2023, run by quickjs-ng) in the user's extensions folder, `extensions` beside the settings files (`TGittanSettings.ExtensionsDir`; `~/.config/Gittan/extensions` on macOS and Linux). Every `*.js` at the top of the folder is one extension; subfolders hold ES modules an extension imports, confined to the folder and to its subfolders: a file at the top is an extension of its own and only its own context imports it, as a module extension's bootstrap does (`gittan.ext.modules`, `ResolveModuleSpecifier`'s `Entry`). The engine, the manifest, the permissions, the module loader and the promise bridge came from Trndi's extension engine (`units/trndi/ext` there), with its dialogs and settings swapped for a host class, so `src/core` builds them without the LCL and the tests run them.
- The file starts with a manifest in a comment: `/* @name ... @copyright ... @version ... @description ... @homepage ... @license ... @perms net, exec */` (`gittan.ext.perm`, `ParseExtManifest`; a UTF-8 BOM and one `"use strict";` line may come first; an unknown directive or permission keeps the file from loading). Its id is the file's name without `.js` in lower case (`ExtIdFromPath`); two files that differ in case alone collide, and the second is refused. `@repos` keeps the extension to some repositories (`TExtManifest.Repos`, kept in `TExtContextInfo.Repos` and `TGittanExtInfo.Repos`; every repository when empty, an empty `@repos` keeps the file from loading): patterns separated by commas, on one line or several; a pattern starting with `/`, `~` (the home folder), `\\` or a drive is a root, any other is matched with each remote's `RemoteUrlKey` (host and path in lower case, no scheme, user, port, trailing slash or `.git`, so the scp form and https agree), with `*` and `?` (`IsWild`; a root without regard to case where file names are so, `FileNameCaseSensitive`). `ExtRepoInScope` (`gittan.ext.perm`) decides, against the frame's root and `FRemoteUrls` (the snapshot's `RemoteUrls`). The frame fires through the engine's scoped `Fire(AEvent, Json, Root, RemoteUrls, Msg)` and asks `Listens` rather than the registry's `HasListener`, so an extension left out gets no event and costs no payload; `RebuildExtMenu` leaves out the commands of an extension `ExtInScope` says no to, and is queued when the frame opens a repository and when its remotes change. The unscoped `Fire` (the tests, `unload`) calls every listener. It is a filter, not a permission: the `repo.*` reads, the cards and `exec` work as before. `@forges` keeps it to forges by name (`TExtManifest.Forges`, `TExtContextInfo.Forges`, `TGittanExtInfo.Forges`, in lower case; an empty one, and a name no registered forge has, keep the file from loading: `CheckForges` in the loader, since `gittan.ext.perm` knows no forge): the engine's `InScope` takes `@repos` and then, for an extension with `@forges`, the forge of the remotes (`ForgeClassFor`, asked only then) against them (`ExtForgeInScope` in `gittan.ext.perm`, False for a repository on no forge), so `Listens`, `Fire` and `ExtInScope` leave a repository on another forge out; where no repository decides, the forge view's menu and tabs, `TGittanExtEngine.ExtForgeInScope(id, forge)` asks with the view's forge. The id is the key of the extension's object in settings.json and of its grant in state.json, so a name that `ValidExtKey` refuses (a tab, a line end or another control character) keeps the file from loading; `=`, `;`, `[` and `]` are fine.
- Permissions are groups (`TExtPermGroup`): `ui` (dialogs, cards, messages, commands, the extension's own storage and settings page) and `timers` always granted (`PermBaseline`); `data` (the repositories' files and their content, diffs, history), `net` (fetch), `exec` (git and programs, which run in the shown repository unless `repo` or `cwd` says another, so `exec` gets that root too), `forge` (the forge's tool with the user's account: `Gittan.forge`, `Gittan.forges`; no other program, and of the tool only what its forge's `CliAllows` lets through, so it is apart from `exec`) and `settings` (Gittan's own settings) only when `@perms` names them and the user said yes (`PermPromptable`). Without `data` an event's listener gets `ok`, `kind`, `mode` and `amend` alone, not the root, the files, the message or the commits (`ContentFreePayload` in `Fire`). The grant is kept with the file's SHA-256 (`gittan.ext.grant`; `ExtPerm` in the settings, `extensionGrants.<id>` in state.json with `hash`, `granted`, `author`), with every file in the subfolders hashed in when there is one (`ModulesDigest` in the loader: their paths and content, not through a link), since a module runs under its importer's grant; so an edited file, or an added or edited module, asks again (every extension with a promptable grant, as the loader cannot tell whose a module is); a no is not kept and the file is skipped until the next load. A native an extension was not granted is not defined in its context, so `typeof Gittan.git === "undefined"` says what it may do, and `Gittan.permissions.require("net")` throws a readable error.

## The engine (`src/core`)

- `gittan.ext.quickjs` is the binding to quickjs-ng through Trndi's C shim (`externals/quickjs/tq_shim.c`): a JSValue is a 16-byte struct, so every value crosses by pointer, and every native is a plain Pascal procedure reached through one trampoline by its `magic`. The libraries are `libqjs` and `tqshim`, linked at link time (`{$LINKLIB}` on macOS, the `Libraries` path of `Gittan.lpi`, `-Fl` for the tests) and loaded from beside the executable: an rpath of `@loader_path` on macOS and `$ORIGIN` (and `$ORIGIN/../lib/gittan` for the packages) on Linux, set as `Conditionals` in both build modes; Windows looks beside the executable anyway. `make`, `make debug` and `make rebuild` copy them from `externals/quickjs/prebuilt/<cpu>-<os>` (`QJS_DIR`, FPC's names, aarch64 for Apple Silicon) into the project root before the link and into `Gittan.app/Contents/MacOS` after it (`stage_qjs`); `make test` copies them beside the test binary; `make packages` installs them in `/usr/lib/gittan`; CI copies them into the tar, the bundle (signed ad hoc each, since `codesign --deep` leaves loose dylibs alone), the zip and the installer (`dist/windows/gittan.iss`). On Linux the engine ships as `libqjs.so.<version>` and the `libqjs.so.0` and `libqjs.so` links are made by `qjs-links` and `stage_qjs` (git keeps no symlinks that survive NTFS). `.gitignore` lets the prebuilt libraries in. The macOS libraries were built with a minimum of macOS 11.0 (`clang -mmacosx-version-min=11.0`), the Intel ones cross-built on Apple Silicon (`build.sh mac-x86_64`); a rebuild of the engine is `externals/quickjs/build.sh` (needs cmake), see its README.
- `gittan.ext.engine` is `TGittanExtEngine`, one for the process (`Instance`; `Existing` never makes one; `ReleaseInstance` at the end, after which none can be made): one runtime, a context of its own per extension (`NewExtensionContext`), the `Gittan` class in each, the baseline natives (`alert`, `confirm`, `prompt`, `select`, `console.*`, `setTimeout` and the timers over `TFPTimer`, `performance.now` and `crypto` over `gittan.ext.sys`), the ES polyfills, the module loader, the promise bridge (`gittan.ext.promise`: a `TJSAsyncTask` thread runs a native marked threaded and settles the promise on the main thread through `Synchronize`), a 50 ms timer that drains the job queue (`PumpJobs`, public, which the tests call), a watchdog that aborts a script after 10 s of continuous JS (a native that waits, a dialog, restarts the budget) and a 64 MB heap for all contexts. `UnloadExtensions` tears every context down (the registry's values first) and keeps the runtime, which is what Reload does.
- `gittan.ext.host` is what the engine asks of the program: `TGittanExtHost` with the dialogs (`Alert`, `Confirm`, `Prompt`, `Select`, `Message`, `ShowLog`), `ReportError`, `AskPermission`, the message loop (`Pump`, `Terminated`), the repositories (`ActiveRoot`, `RepoFor`, `StatsFor`) and the window (`AddCard`, `ClearCards`, `SetStatus`, `Notify`, `OpenFile`, `CommandsChanged`). `ExtHost` is the one in place, a default that answers nothing until `SetExtHost`; the window gives `TGittanExtUIHost` (`gittan.exthost`, over `gittan.askdlg` and the frames through `TRepoWindow.FrameForRoot`, `ShownFrame`, `FrameAt`) in its `FormCreate` and takes it back in `FormDestroy`, before the frames go; the tests give `TFakeExtHost` (`tests/testextengine.pp`).
- `gittan.ext.registry` keeps what the extensions registered: the commands (`Gittan.commands.register`: an id, a title, where it shows, the function), the listeners (`Gittan.on`) and the declared settings (`Gittan.settings.define`), each function a value the registry owns and frees with its context. The engine calls them by value (`RunCommand`, `Fire`), never by a global's name, so two extensions with the same function name do not collide.
- `gittan.ext.loader` finds and loads: `TGittanExtLoader.Load` reads the folder in name order, parses each manifest, hashes the file, skips one turned off (`ExtEnabled`, `extensions.<id>.enabled` false in settings.json), asks for its permissions, makes its context, lets `OnProvision` register Gittan's natives in it (`gittan.ext.api`) and runs it; what it found is `Infos` (`TGittanExtInfo`: the manifest, what was granted, whether it loaded, else why) for the settings page. `Reload` unloads (their cards go too) and loads again. The host's `CommandsChanged` is told once at the end (`Loading` is on meanwhile). `App.Extensions` is the loader; the window queues the first load after it is up, before the repositories open, so a permission prompt comes over the window and `repo.opened` reaches the listeners.
- `gittan.ext.api` is the API an extension sees. The natives of the `Gittan` class answer JSON text, and a facade evaluated in the context parses it into `Gittan.repo`, `.git`, `.exec`, `.forge`, `.forges`, `.net`, `.ui`, `.storage`, `.settings` and `.app`; a namespace whose natives were not granted is left out. The reads run on the main thread against the window's repository; `git.run`, `exec.run` and `fetch` run on the promise thread with strings alone (`RunGitEnv`, `RunCli`, `gittan.http`), never the window's objects. `{input}` of `git.run` and `exec.run` goes to the program's standard input, written by a thread of its own while the output is read (`TToolInputWriter` in `RunTool`), so a program that writes as it reads cannot fill both pipes, and one that ends before reading it all does not end Gittan (SIGPIPE is blocked on that thread).

| `Gittan.settings.define([{key, type, label, default, options, note}])`, `.get(key)` | ui | the fields of its settings page (`type` bool, string, number or choice); `get` is the value set there, else the default |
| `Gittan.app.setting(name)` | settings | `GitPath`, `EditorCommand`, `TerminalCommand`, `AIEnabled`, `HostingEnabled`, `ExtensionsDir`, `<Forge>Cli` |

The events (`GittanExtEvents`), each with `repo` in its argument for a listener with `data` (without it, only `ok`, `kind`, `mode` and `amend`): `repo.opened` (`branch`, `head`), `repo.changed` (the snapshot), `commit.before` (`message`, `paths`, `amend`), `commit.after` (`ok`, `error`, `id`, `amend`), `push.before` (`branch`, `remote`, `ref`, `kind`: push, force, branch or tag; for a plain push or force push the upstream's remote and branch, else the remote it would be set to and the branch), `push.after` (`ok`, `error`, `kind`), `pull.before` (`branch`, `mode`), `pull.after` (`ok`, `error`) and `unload`. A `before` listener stops what is about to happen by returning `false`, a string (the reason) or `{cancel: true, message}`: the frame shows "An extension stopped it" with the reason and starts nothing (`ExtFire`, `umain.ext.inc`; `StartCommit`, `StartFixupCommit`, `StartRemote`); every listener is called even after one stopped it, a listener that throws is reported and stops nothing, and a promise is not waited for. A payload is built only when the event has a listener (`ExtListens`, the registry's `HasListener`), since `repo.changed`'s snapshot costs a JSON of every file and `push.before`'s destination git runs on the main thread. The frame raises them (`ExtEmit`) from `OpenJobDone` (`repo.opened`, then `repo.changed`; `FExtOpening` keeps `ApplySnapshot`'s own out meanwhile, reset in a finally), the end of `ApplySnapshot`, `CommitJobDone` and `RemoteJobDone`, all on the main thread.

## The window

- The Extensions menu (`FExtMenu`, after Tools) holds the commands registered for the menu, then Reload Extensions, Open Extensions Folder and Extensions Settings...; the command palette lists them as "Extensions: ...". The popups get theirs after a separator, tagged `ExtItemTag`. `RebuildExtMenu` builds them again from the registry, queued (`QueueRebuildExtMenu`, from `TRepoWindow.ExtensionsChanged`, which the host's `CommandsChanged` calls in every frame, and from a click on a command that is gone): the registry changes from a click on one of these items, Reload Extensions or Extensions Settings..., and the rebuild frees the item clicked; a click is `ExtCommandClick`, which gives the command the repository, the file (the popup's for a popup, else the one shown), the line under the editor's popup or the caret, and the selection. The forge view has an Extensions menu of its own (`FExtMenu` in `uforge`, after Tools, built by `RebuildExt`): the commands registered for `"forge"` of the extensions whose `@forges` has the view's forge, then Reload Extensions and Open Extensions Folder; a click runs the command with `{forge, login}`.
- The Extensions page of the settings (`pgExtensions`, `gittan.settingsdlg`): the extensions found, ticked while they load, what the one picked is, its permissions, the repositories of its `@repos` (Runs for:) or why it did not load, Open Folder, Reload (loads the extensions again and lists what is found now, through `TSettingsValues.ExtReload`, the frame's `ExtReloadForSettings`), Reset Permissions (asks again at the next load) and the fields the extension declared; OK writes the values (`SetExtValue`, kept as they are; a field emptied stays in the list as `name=`, since `Values[] := ''` would drop the pair and keep the old value, so the value goes and `get` gives the default again), the ids turned off (`SetExtEnabled`) and the resets (`ClearExtPerm`), and reloads when one was turned on or off or reset (`OpenSettings`, `umain.actions.inc`). The dialog gets it all through `TSettingsValues` (`ExtInfos`, `ExtDefs`, the lists) and names no unit of the engine.
- Errors reach the shown frame's banner (`ReportError`): a manifest that is wrong, a script that fails to load (the engine's `ExtError`), a native that raises; `alert` and `confirm` are dialogs headed by the extension's name (`ExtensionNameForContext`: `@name`, else the file's id) with "From the extension <name>" beside the buttons (`AskDlgFrom`), and so is `console.log`'s, headed console.log (`ShowLog` takes the name, as `console.pop`'s headed Console output does); an alert with no extension behind it (an unhandled promise rejection) is headed "Extension" and says "From an extension".

## The forge view

- What the extensions add to the forge view (`uforge`) is kept in the registry beside the commands (`TGittanExtCommandWhere`: `cwForge` for its menu, `cwForgeTab` for a tab, `cwBatch` for an operation, with `Note` for the description), registered by natives of their own (`registerForgeTab`, `registerBatch`, so `commands.register` cannot make one) and found by a key with a mark (`KindKey`; a command's, `CommandKey`, has its own, `cmd:`, so a command named `tab:x` is not the tab `x`; the keys live only while Gittan runs, none is kept in the settings), so a tab, an operation and a command may share an id and `commands.unregister` takes the command alone. The function kept is the shim's (`COMMANDS_SHIM` in the engine): it takes `seq` (and for a tab `kind`, `action`, `row`) off the context, calls the extension's `render`, `action` or `run` through a promise, and gives `{value}` or `{error}` to `_deliver(seq, json)`, which the shim takes out of reach; always once: a value JSON cannot carry (a BigInt, a cycle) is an error, and an answer that has not come within 300 seconds (`ANSWER_SECONDS`, a timer) is one, the late answer then dropped, so a run or a tab never waits for ever; the native gives it to the host (`Deliver`), the window to the view (`TRepoWindow.ExtDeliver`), which takes only the answer of the request it waits for (`NextExtSeq`, and the extension's id). `gittan.ext.views` (no LCL, `tests/testextviews.pp`) reads the answers: `ReadExtAnswer`, `ExtTabModelOf`, `ExtBatchResultOf`.
- A tab (`FExtTabs`, the `cwForgeTab` entries whose extension `ExtForgeInScope` takes for the view's forge) follows the Batch tab in the strip (`Tabs`, `TabCount`, `CurrentTab`); shown, it is the tab page (`TGittanExtTabPage`, `gittan.extpage`, in the box in the forge page's place; it shares the batch page's painting through `TGittanCardPage`, `gittan.cardpage`: the palette, links and hover, pills, wrapped text and the height measured before it is shown) and its `render` is asked with `{seq, kind: "render", forge, login}` (`RenderExtTab`) as it is shown, as the view is shown again and on Refresh (the page's pill or Cmd+R). The answer is the model: `{text, empty, rows: [{title, detail, tag, url, repo, severity, actions: [{id, title}]}]}` (an object with any of those keys, whatever their values, so `{text: ""}` clears the tab), a list of rows or a string; a row's head opens its `url` in the browser (a web address only, `ExtWebUrl`: anything but http and https is dropped when the model is read, so a row cannot open a file, an app or another scheme's handler) or its `repo` in Gittan, a pill runs `action(id, row, ctx)` (the row as the extension gave it, `RowJson`), whose answer is the new model or, when it has none, a render again. The pills of a row's actions wrap as the Batch page's operations do, the card measured with the same test. Loading or Working shows while a request runs, an error in the error color. A render asked for while an action runs (Refresh, the view shown again, the job's answer) waits for the action's answer and follows it (`RenderExtTabSoon`, `FExtTabRenderAfter`), so that answer is still taken. A reload of the extensions (another context behind the tab's function, told by the context's generation, `GenerationForContext` and `FExtTabGen`, a number each new context takes and never reused, since a new context may get a freed one's address) asks again, dropping a render or an action still to come; a tab gone shows the first section. Another account (`AccountChanged`, `ForgetAnswers`) drops the tab's rows and any answer still to come, an action's too, and asks again once the job says who is logged in (`FExtTabStale`), so no row of the old account's runs an action as the new one; a tab rendered while the job had not said who is logged in yet is asked again when it does (`OldLogin <> FLogin` in `JobDone`).
- An operation (`TGittanBatchExtOp`, `SetExtOps`: every extension's, as `@forges` is asked per repository) is a pill after Maintenance (wrapping when they do not fit); Run (`OnExtRun`, `BatchExtRun`) calls `run({seq, repo, name, forge, login})` for each picked repository in turn, one run at a time (`RunExtStep`, the next from the message loop once the answer came, since it may come while `RunCommand` is still on the stack, and after each one left out, so many left out keep the window alive), leaving out those `ExtInScope` says no to with their remotes; while one runs every other operation's Run is off and says why. The page (`StartExtRun`, `SetExtResult`, `FinishExtRun`) shows a card per repository the operation had something to say of (a string or a number other than 0, or `{text, severity, url}`, `url` a web address only; null, false, true, 0 and an empty string say nothing), its head opening it and its link opening `url`, then the quiet ones and the left-out ones on a line each; an error is the repository's result in the error color. A reload stops a run whose function is gone or in another context (`FExtRunGen`, the context's generation as for a tab); another account (`ForgetAnswers`) stops it too ("The account changed, which stopped the run."), its answer still to come dropped, so no later step runs the forge's tool as the new account. The operation shown is kept by its key (`OperationKey`, `BatchOperation`), so an extension's, not there yet when the page is made, is shown once `SetExtOps` brings it, unless another was picked meanwhile.
- What an extension added is marked with a puzzle piece (`gittan.puzzle`: a square body with a knob on its top and on its right, `PuzzleParts` for the Cocoa strip's one path, `PaintPuzzle` on an LCL canvas): before its tab's name in the strip (`SetTabs`' `AExts` in `gittan.toolbar` and `gittan.owntitlebar`, from the view's `Tabs`, whose `AHints` give the tooltip "From the extension <name>", `ExtNameOf`), in its operation's pill on the Batch tab, and before the line "From the extension <name>" under its tab's head and its operation's description (`TGittanBatchExtOp.Source`). So a user sees what is not Gittan's own, and which extension it is, before running it.
- While the forge view is shown an extension's `Gittan.ui.notify` and `.error` are a dialog, as the frame's banner is under the view.

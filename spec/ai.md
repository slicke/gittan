# AI features through Claude Code, GitHub Copilot or an OpenAI-compatible API

Read this when touching `gittan.ai`, `gittan.agentcli`, `gittan.openai`, `umain.ai.inc`, the AI review's cards in the change view, the sparkle in the filter field, Resolve with the agent in a conflict's list, File > Split Changes into Commits, Fix on a finding's card, Go > Explain Line History with AI, the AI page of the settings, AI in the Commit header, File > Write Commit Message, `RunAgentCli` or `ChatComplete`.

- The AI features ask an agent, one active at a time (`TGittanAgent`: `gaClaude`, `gaCopilot`, `gaOpenAI`; `AgentNames` for the interface, `AgentCommands` for the settings key, which is the command's name for a tool and `openai` for the API; `AgentOfKey` back, Claude Code for an unknown key). Each agent is a class of `TGittanAI` (`gittan.ai`) that its own unit registers as it loads (`RegisterAI` from the unit's initialization, `AIClassOf` for the class of a kind, nil for none; `Gittan.lpr` uses the units, as it does `gittan.github`, so they are linked), as the forges register with `gittan.forge` (forges.md): the command line tools in `gittan.agentcli`, `TGittanClaude` for Claude Code's `claude` (`claude -p`) and `TGittanCopilot` for GitHub Copilot's `copilot` (the prompt on its input), which work with the user's own login, plan and settings and read the repository's own instructions (both read CLAUDE.md and AGENTS.md; Copilot also `.github/copilot-instructions.md`), both `TGittanAgentCli`; and `TGittanOpenAI` in `gittan.openai`, a model at an OpenAI-compatible API (OpenAI's own, OpenRouter, a local Ollama) asked with the user's key through `gittan.http` (app-shell.md), a `TGittanApi`, the base in `gittan.ai` for any API (a server as its path, a key and a model, which it needs; `DefaultUrl` when the settings name no server) that a later provider with another request shape would share. A `TGittanAI` is made from the settings' fields (`Create(APath, AKey, AModel)`) and changes nothing after, so a job may hold its own copy (`Clone`) from another thread; its class says what it is (`Kind`, `Name`, `IsApi`, `ReadsFiles`: a tool reads the repository's files itself, a model at an API sees what it is sent alone, which the prompts and the find go by), finds it from the setting (`Find`: the path as given, else the command on ToolSearchPath, which has `~/.local/bin`, where Claude Code's installer puts claude, Homebrew's folders and nvm's node for an npm install, and for claude else `~/.claude/local/claude`, the local install of earlier versions; for an API the setting else `DefaultUrl`), and an instance says whether it can be asked (`Available`: the command found; the server and a model set), its name for a message (`Title`: the agent's, or the model's for an API, since that is who answers), its prompt (`Prompt`, `TaskPrompt` as it reads files or not), answers a task (`Ask(ARoot, ATask, AInput, ACancel)`: a tool run with its `Args` and `Input` for the task and read with `ReadAnswer`, the API asked with `ChatComplete`; told to stop, a tool is ended and a request to the API given up) and gives a line for About (`About`: the tool and its version from `--version`, `VersionOf`, empty when it printed none; the model at its server, `rsAboutApi`). Nothing of the features shows until the settings turn them on: the AI page of the settings dialog (`TGittanSideNav` row with `niAI`, a sparkle) has Turn on the AI features (`AIEnabled`, section `AI`, key `Enabled`, off by default, since the changes go to the agent's provider) with a note that says so, the agent (`AIAgent`, key `Agent`: claude, copilot or openai) in a list, and the picked agent's command path and model, each agent keeping its own (`ClaudePath`/`ClaudeModel`, keys `Claude` and `ClaudeModel`; `CopilotPath`/`CopilotModel`, keys `Copilot` and `CopilotModel`; for the API its server, key and model, `OpenAIUrl`/`OpenAIKey`/`OpenAIModel`, keys of the same names, the key in the settings file as it is, which `Save` makes readable by its owner alone on macOS and Linux while a key is set): the dialog keeps the paths and models in `FAgentPaths` and `FAgentModels` (the API's server as its path) and the key in `FKeyEdit`, and `ShowAgent` puts the picked one's in the fields, with labels, hints and notes naming it (the path's note as for git and gh, the command found by the class's `Find`; the model's "an alias such as haiku or sonnet" for Claude Code, "auto to let Copilot pick" for Copilot). For an API (`ApiAgent`, the class's `IsApi`) the command field is labelled Server with the class's default server as its hint and a note naming OpenRouter's and Ollama's URLs, the API key field with its label and note (the key shown as asterisks, "kept in Gittan's settings file", empty for a local server) is visible for it alone, the server's note says it is a URL while what is typed starts with neither http:// nor https:// or has nothing after it, and the model's note says the API needs one, or that it is missing while the field is empty (`ToolChange`, which the model field raises too; a tool's model is not looked for). The fields are disabled while the switch is off. About makes the agent from the fields and lists its `About` line in `TVersionsJob` (the job's own `AI`), "not found" when it is empty. The frame makes the agent from the settings at start and after the dialog (`FindAI`: the picked agent's three fields, the class's `Find`, into `FAI`, freed with the frame); `AIAvailable` is the switch and `FAI.Available`; `AgentName` is `FAI.Title`, what the hints, the status bar and the banners say. Tested in `tests/testsettings.pp`, `tests/testagentcli.pp` and `tests/testopenai.pp`.
- The API (`gittan.openai`): `ChatComplete` posts a chat completion to `ChatEndpoint` (the server's base with `/chat/completions`, a trailing slash dropped) with `Content-Type: application/json`, `Accept` and, when the key is not empty, `Authorization: Bearer`, through `HttpRequest` with `ChatTimeout` (180 s; a model reviews a long diff slowly) and the job's cancel, which gives the request up (app-shell.md). The body (`ChatRequestBody`, fpjson) names the model and carries two messages, the task's prompt as the system message and the input (the changes, the question) as the user's. `ParseChatAnswer` takes the first choice's message content (a string, or the text of parts), trimmed, else the API's error (`error.message`, or an error string), else "the model answered with no text" when there are choices; no JSON or no choices is no answer, and `ChatComplete` then says the status (`HttpFailure`) or shows the body's start. The model has no tools: `TaskPrompt(ATask, AReadsFiles)` (`gittan.ai`) gives the prompt for each task (`TGittanAITask`: `atMessage`, `atReview`, `atFind`, and `atLocate`, the second round of a find for such a model, below), the same text with a note that differs: an agent that reads files may (the commit message only when the diff leaves the change unclear; the review to check a finding; the find to be sure), one that sees what it is sent is told it cannot (the review says so in a finding that would need the rest of the file; the find judges by the file list that follows the question, `RepoFileList`: `git ls-files --cached --others --exclude-standard`, cut at `MessageDiffKeep`, in `FindListInput`, which `TGittanFindJob` gives an agent whose class does not read files). The three jobs share `TGittanAgentJob` (the repository and its own copy of the agent, `AI`; `AgentName` is its `Title`) and its `Ask(ATask, AInput)`, the agent's `Ask` with `Cancelled` as what it may ask, False once the job was stopped; a stopped command is ended and a request to the API given up, so neither keeps the reaper waiting when the frame or Gittan closes. The commit message job cleans the answer with `CleanCommitMessage` and reports no answer when nothing is left. The tests (`tests/testopenai.pp`) cover the agent (its registration, default server, title by its model, that it needs one, its prompt and About line), the endpoint, the request body (quotes, line ends and UTF-8 through) and the answers and errors of OpenAI's and OpenRouter's shape; no server is asked (`ChatComplete` was tried by hand against a fake server). The test runner sets the UTF-8 code page on every platform, as LazUTF8 does in the app, since fpjson's strings are `UTF8String` and a `string` is converted on the way otherwise.
- `RunAgentCli` (`gittan.git.pp`) runs the command through `RunTool` with Gittan's environment and ToolSearchPath as PATH, writes its input to standard input before closing it (both agents read all of it before they write, so any length goes), keeps stdout on failure too (with `--output-format json` claude says why there and exits 1) and stderr in the error, and asks `ACancel` on every pass of the reading loop: True ends the agent (`TProcess.Terminate`), so a job told to stop does not wait for its answer.
- The commit message: "✦ AI" at the right end of the Commit section's header (the header's action, `Action`, a link in the accent color underlined under the mouse, with its own hint only over it, `ActionHint`; a click on it raises `OnAction` and neither folds nor unfolds; dimmed and inert while not `ActionEnabled`), and File > Write Commit Message (Shift+Cmd+K, `FMessageItem`), both `MessageActionClick`; the hint and the texts below name the agent. The action shows while `AIAvailable`, nothing is in progress (`FOperation` empty: a merge or a rebase has its message) and the boxes choose (`CommitChoosing`), and is enabled with files ticked or Amend on, and no commit running; the menu item is there while `AIAvailable` and enabled as the action is (`UpdateMessageAction`, from `UpdateCommitState`). Either unfolds the section and starts a `TGittanMessageJob` (`StartMessageJob`, the status bar saying the agent is writing) for the ticked files (`ChosenCommitPaths`) and Amend, keeping the field's text in `FMessageFrom`; while it runs the action says Stop and the menu item Stop Writing Commit Message, and either ends the agent (`AbandonMessageJob`). The job (`gittan.ai.pp`, a `TGittanAgentJob` that may be given up) collects the changes with `CommitChanges` and asks the agent (`Ask`; a tool's `Args` and `Input` are what its command gets, `gittan.agentcli`). Claude Code gets `-p` with the prompt (the message alone, no preamble, fences or trailers, and short whatever the repository's own messages are like: a subject of at most 72 characters and a body of a few lines only when the change needs explaining, what changed and why rather than each file, the style taken from the recent subjects, the files read only when the diff leaves the change unclear; told only to follow the conventions, a model wrote pages), `--output-format json`, `--tools Read,Grep,Glob`, `--no-session-persistence` and `--max-turns` `MessageMaxTurns` (10, `TaskTurns` per task), with the changes on its input, and `--model` when one is set. Copilot ignores its input when `-p` is given, so it gets the prompt and then the changes on its input, with `-s` (its answer alone), `--no-color`, `--stream=off`, `--no-ask-user`, `--available-tools=view,grep,glob` and `--allow-all-tools` (which a run without a terminal needs, and which the three read-only tools make safe), and `--model=` when one is set. Either may read the repository for context but has no tool that writes, runs a command or goes to the network. `ReadAnswer` reads a command's answer: claude's JSON with `ParseClaudeResult` whatever the exit (the last line that starts an object, so a warning before it does no harm; `is_error` or a subtype other than success is the error, `error_max_turns` said as such), Copilot's whole output when it exited with 0; without an answer the reason is stderr, else what was printed, else that the agent gave none (`TGittanAgentCli.ReadAnswer`, which both fall back on). `CleanCommitMessage` trims the message and takes off a code fence around the whole of it.
 `MessageJobDone` puts the message in the field when the field is as it was at the start, else says in the status bar that it was not used; a failure (not logged in, an unknown option of an old version) is an error banner, "Claude Code wrote no message" or "GitHub Copilot wrote no message". The job is abandoned when another repository opens and when Gittan quits, and when the settings turn the features off.
- `CommitChanges(ARoot, APaths, AAmend)` is what the agent gets: the recent subjects (`MessageSubjects`, 10, `git log --format=%s`), a line saying the commit amends HEAD when it does, the summary (`diff --stat=100`) and the diff (`--no-ext-diff -M`), cut at a line end after `MessageDiffKeep` bytes (80000) with a line saying how much was left out. The diff is made in a temporary index (`GIT_INDEX_FILE` in the temp folder: `read-tree HEAD`, or `--empty` before the first commit, then `add -A` of the paths from a NUL-separated file under `--literal-pathspecs`), so an untracked ticked file shows as the commit would take it and the real index is left alone; it is compared with HEAD, or HEAD's parent for an amend (the empty tree when there is none). The changes left out of a file (file-actions.md) and the old path of a rename are not reflected: the file is described as it is on disk. No change gives an empty text, which the job reports as nothing to describe. Tested in `tests/testai.pp` against a temporary repository (chosen paths only, an untracked file, before the first commit, amend, nothing to describe, a long diff cut), and in `tests/testagentcli.pp` on each tool's arguments, input and answers, on claude's JSON, where a tool is found and `VersionOf`; no agent is run in the tests.
- The review: View > Review Changes with AI (Alt+Cmd+R, `FAIReviewItem`; Stop AI Review while it runs) and Clear AI Review (`FAIClearItem`, enabled while there are findings for what is compared) show while `AIAvailable` (`UpdateAIReviewItems`, from `UpdateMessageAction`). `StartAIReview` starts a `TGittanAIReviewJob` with the repository's base, whether it is a range, every changed file (`FStats`) and `AIReviewKey` (the root, the base and `WholeTree`), the status bar saying the agent is reviewing; `ReviewChanges` gives the agent what the change view compares: a range diffed as it is (`git diff -M A..B`), else the work tree's changed files against the base (HEAD when empty) through the temporary index `IndexDiff` makes (named by the process id and a counter; a file and lock of that name an earlier process left are removed first), which `CommitChanges` uses too, so untracked files are in it; the diff's lines are numbered as the view numbers them (`NumberDiff`: "N12 +text" for a context or added line in the new side, "O7 -text" for a removed one in the old side, headers as they are), so the agent names lines without counting in a hunk. The review prompt (`TaskPrompt`, in a tool's `Args` or `Input`) asks for only real problems, bugs, wrong results, crashes, data loss, security holes, races, missed edge cases; no style, naming, formatting, praise or summaries; at most 10, none a fine answer; files may be read to check a finding; a JSON array alone of path, line, side new or old, severity bug, risk or question, and a body in Markdown), with `ReviewMaxTurns` (20) for claude. `Ask` reads the answer as for a message, without cleaning it, and `ParseReviewFindings` reads the array from its first bracket to its last (so a fence or a sentence around it does no harm), dropping an `a/` or `b/` before a path and a finding without path, line or body, at most `ReviewMaxFindings` (10): each is a `TGittanReviewThread` with `Agent` and `Severity` set, its line the view's own (old side with `LeftSide`) and one comment by the agent, with no address and made now. An answer with no array is an error banner with its start; tested in `tests/testai.pp`. `AIReviewDone` keeps the findings in `FAIThreads` with the job's key in `FAIThreadsKey`, says in the status bar how many there are ("found nothing to point out", "one thing", "N things"), and rebuilds the view; a failure is an error banner, "Claude Code could not review the changes". The findings replace the last review's; Clear AI Review, opening another repository and turning the features off drop them, and the job is abandoned with the repository, on quitting and when the features go off.
- The change view shows the findings as it shows a pull request's threads (github.md): the threads it shows are `FShown` (`CollectShownThreads`): the pull request's (`FThreads`) while they apply (`PullThreadsShown`: View > Review Comments on, a pull request's threads held, and the view's new side the work tree or the pull request's own diff), then `FAIThreads` while `FAIThreadsKey` is `AIReviewKey`, so the findings show for the comparison they were made for and come back when it is compared again. `FThreadRows`, the gaps' Tags, the cards, the clicks and the tree's bubbles (`FileThreads`) index `FShown`; the status bar's pull request chip and its hint count `FThreads` alone. `PlaceThreads` places a finding on the view's own lines, without `MapLine` (an old-side one whatever the base, since the view's old side is what the agent saw); the lines are those of the review's moment, so an edit of the work tree since moves the code under a card. A finding's card has the agent's name after a sparkle (`ThreadAuthor`), its severity as the note over it (`SeverityLabel`: Bug, Risk, Question, or the agent's own word), a violet stripe while open (`AgentColor`) in place of the link color, and in place of "GitHub ↗" the link `CardLink` gives (`HasLink` in `EditDrawGap`, drawn in the violet for a finding, and `EditClickGap` hits it where it is drawn): "✦ Fix" while the finding is open (not `Resolved`), `AIAvailable` and the view's new side is the work tree (not a range), "Stop Fixing" while the agent fixes it, none otherwise; a click elsewhere folds it as any card.
- Where something is: while `AIAvailable` the filter field over the tree shows a sparkle left of its cross (`TGittanSearchBox.ShowAction`, `UpdateFindAction`, from `SetupTreeFilter` and `SettingsChanged`), its hint "Ask Claude Code which files hold what you type" only over it (`ActionHint`). A click on it, or Cmd+Enter in the field (Ctrl+Enter elsewhere; `TreeFilterKeyDown`), is `SearchBoxAction`: with the field empty a status note says to type first, else `StartFindJob` starts a `TGittanFindJob` with the field's text, the status bar saying the agent is looking for it and the sparkle lit (`ActionBusy`); a click while it runs stops it. The find prompt (`TaskPrompt`) asks for the files that define, implement or handle what is asked, searched and read to be sure, only files that are there; a JSON array alone of path, line, 0 for the whole file, and why, the best first, at most 10, none a fine answer, with `FindMaxTurns` (20) for claude, the user's words on the input (and the file list for a model that cannot search, above). Such a model has only named files by their paths, so the job then asks it a second round (`atLocate`, `TGittanFindJob.LocateLines`): `FindLinesInput` gives the question and the files it named that the first round's list names and that are in the work tree (a file not in the list, an ignored one such as `.env`, is left out, as is a path out of the work tree, absolute or with .., or through a symbolic link, the file or a folder on the way, `ThroughLink`, since a link may lead out of it), each with its lines numbered ("12: text") and cut at its share of `MessageDiffKeep` with a line that says so (the budget split among the files that are there, and only that much of a file read; the cut is at a line end, `CutAt`, or where the share ends when it holds none), a binary file (a NUL in what is read) named without its text, and the locate prompt asks for the line in each file where it is, a JSON array as the first's; `MergeFoundLines` puts the lines, and a why given, into the first answer's files by path, in its order, a line only when it is one of those the file was given (`FindLinesInput`'s counts); the first answer's lines were guessed from the paths and are dropped, so a file not named again, or with a line past its text, has 0, and a second answer that fails leaves the files without lines. `ParseFoundFiles` reads the array as `ParseReviewFindings` does, keeping each item with a path (`./` taken off, backslashes made /), a missing or negative line 0, at most `FindMaxFiles` (10); tested in `tests/testai.pp`. `FindJobDone` keeps the files that are in the work tree (`RepoFileExists`) in `FFoundFiles` and drops them in `FFindPopup` from the field under the header `Files for "<question>"`: the path with `:line`, cut at its start to keep the file's name, and the why dimmed, cut to a part of the list's width, since the list cuts a caption at its end and gives the detail its whole width. None is a status note, a failure an error banner ("Claude Code could not find it"). A pick empties the field (the question was not a filter) and shows the file at its line with `ShowFileLine`, queued (`ShowFoundAsync`, with the file picked kept in `FFoundPick`, since another find may be done before the call) so the focus the list gives back to the field does not take it from the editor; `ShowFileLine` sets the top line from the editor's height when the editor has not been painted since it was shown (`LineBottom` 0), and passes the caret on (`EditChangeCaretPos`), since ATSynEdit's `DoGotoPos` on an editor not yet painted only places the caret, neither scrolling nor raising the caret event, and the view stayed at its top with the status bar's line and the header's symbol from before. The job is abandoned with the repository, on quitting and when the features go off.
- Resolving a conflict: while `AIAvailable` the list a conflict's button drops down (`ResolveConflictAt`, conflicts.md) has a last item after the four picks, "Resolve with Claude Code" (`rsResolveAI`, the sparkle as its detail, its index in `FConflictAIItem`, -1 without it), "Stop Claude Code Resolving" while a resolution runs; a pick of it is `StartConflictJob` (or `AbandonConflictJob`) from `ConflictPopupPick`. One at a time: `StartConflictJob` takes the conflict as `ResolveBlock` gives it (its lines as the file holds them, markers included, and where it is; the pick's lines dropped) and starts a `TGittanConflictJob` with the path, `FOperation` and whether it is a rebase, the status bar saying the agent is resolving the conflict at line N. The job gives the agent `ConflictInput`: the path, what git is doing and which side of the markers is the user's own (the `>>>>>>>` one in a rebase, which replays the user's commits onto the upstream), `ConflictCommits` (the first of MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD and REBASE_HEAD there is; its whole message unless it is a merge's head, which is only a branch's tip; and the subjects since the merge base of HEAD and it that changed the file on either side, `MessageSubjects` each), `ConflictAround` (20) lines of the file before and after, and the conflict. The resolve prompt (`atResolve`, `TaskPrompt`) asks to keep what each side meant to change, combining them where they change different things and following the commits where they contradict, to keep the file's indentation and style and change nothing outside the conflict (a tool may read the repository to see how the code is used; a model is told it sees the lines alone), and to answer with the lines between a line `<resolved>` and a line `</resolved>`, then a sentence on what it kept between `<why>` and `</why>`; `ResolveMaxTurns` (10) for claude. `ParseResolution` takes the lines between the first `<resolved>` and the last `</resolved>` (case ignored; the line ends next to the tags are theirs, a blank line at the end is kept, none is an answer that drops both sides, a code fence around them is taken off) and the why on one line, and refuses an answer without the tags or with a `<<<<<<<` or `>>>>>>>` line in it. The lines become the block's `OldLines`; `ConflictJobDone` writes the block with `WriteConflictBlock`, which `ApplyConflictPick` uses for a pick too (`DiscardBlock`, refused when the file no longer holds the conflict, kept in `FDiscards` so File > Undo Discard puts it back, and the file marked resolved when it was the last), the status bar saying what the agent kept (`rsResolvedAI`, `rsResolvedAILast`; "File > Undo Discard puts it back" when it gave no why); it moves on to the next conflicted file only when the file is the one shown, and refuses while the file is being edited. A failure is an error banner, "Claude Code could not resolve the conflict". The job is abandoned with the repository, on quitting and when the features go off. Tested in `tests/testai.pp` (`TestParseResolution`; `TestConflictInput` and `TestConflictJob` against a merge that conflicts).
- Splitting the changes into commits: File > Split Changes into Commits... (`FSplitItem`, after Write Commit Message, no shortcut) shows while `AIAvailable` (`UpdateSplitItem`, from `UpdateMessageAction`), enabled with nothing in progress (`FOperation` empty), the boxes choosing, no commit running and two files or more to choose from (`ChoosablePaths`: the changed files but the conflicts), or a plan held; "Stop Splitting into Commits" while the job runs, which ends it (`AbandonSplitJob`). `MenuSplitClick` shows the plan held (`ShowPlan`), pruned first (`PrunePlan`: the files no longer changed dropped, as after a commit, and a commit left with none), else starts a `TGittanSplitJob` with every choosable path (`StartSplitJob`, the status bar saying the agent is splitting the changes). The job gives the agent `SplitInput`: `CommitChanges` of them all (the recent subjects, the summary and the diff in the temporary index, so untracked files are in it) and the paths, a line each, since the summary cuts a long one. The split prompt (`atSplit`, `TaskPrompt`) asks for a few commits a reviewer can follow, each a refactoring, a fix, a feature or a dependency bump with its tests, in the order they should be made, every listed file in exactly one, one commit for the whole a fine answer, each with a message as the commit message's prompt asks for one; a JSON array alone of files and message, at most 8; `SplitMaxTurns` (10) for claude. `ParseCommitPlan` reads the array as `ParseReviewFindings` does, keeping only the paths it was given (`./`, and `a/` or `b/` when the path without it is one, taken off), in the list's spelling when the agent's differs in case only, each in the first commit that names it, the message cleaned with `CleanCommitMessage`, a commit with no file left dropped, at most `SplitMaxCommits` (10), and puts the paths no commit took into one more commit with no message, so the plan holds every file (`TGittanCommitPlan` of `TGittanPlannedCommit`). `SplitJobDone` keeps it in `FCommitPlan` (the agent's name in `FPlanAgent`); a plan of one commit is applied at once and the status bar says the agent sees the changes as one commit; more drop `FPlanPopup` from the Commit header: "Commits planned by Claude Code" as its header, each commit's subject numbered with how many files it takes ("(the files left over)" for the one with no message), a divider and Plan Again (which asks again). A pick is `ApplyPlannedCommit`: every choosable file is ticked when it is in the commit and unticked otherwise (`SetCommitChosen`), the changes left out of each dropped (`DropLeftOut`, the plan took files whole), the message put in the field when the commit has one, and the section unfolded with the field focused (`MenuCommitClick`); the status bar says which commit of how many was ticked. The user commits it, and the menu item shows the rest. The plan is dropped on opening a repository and when the features go off; a failure is an error banner, "Claude Code could not split the changes". The job is abandoned with the repository, on quitting and when the features go off. Tested in `tests/testai.pp` (`TestParseCommitPlan`, `TestSplitJob`).
- Fixing a finding: a click on a card's Fix is `FixFindingClick`: while a fix runs, the same card's Stop Fixing ends it (`AbandonFixJob`) and another card's Fix says in the status bar to stop it first (`rsFixBusy`); else it starts a `TGittanFixJob` with the repository's base and the finding (`FFixKey` is its `FindingKey`: the path, the agent's line and the text, which tells it apart from the others), the status bar saying the agent is fixing the finding at line N, and the cards repainted. The job reads the file as it is (`ReadFileBytes`, `SplitLf`, `BareLine`) and gives the agent `FixInput`: the finding (its line, "of the old side (a line the change removed)" for one there, its severity and text), the file's diff against the base (HEAD when empty; none for an untracked file) and the file with its lines numbered, all cut at `MessageDiffKeep`. The fix prompt (`atFix`, `TaskPrompt`) asks to change as little as needed, keep the file's style and change no other file (a tool may read the repository to check the finding), and to answer with edits, each the lines to replace between a line `<find>` and a line `</find>` (whole lines as they are, without their numbers, enough of them to be found once) and the lines to put in their place between `<replace>` and `</replace>`, then a sentence between `<why>` and `</why>`; a finding that is wrong or needs no change gets the why alone. `FixMaxTurns` (15) for claude. Edits by the lines they replace rather than a patch, whose hunk headers and counts a model gets wrong. `ParseFixEdits` reads the pairs in turn (the tags' line ends and a fence taken off as for a resolution, `TagLines`; an empty replace drops the lines) and the why (`WhyOf`), and refuses an answer with neither, an empty find or a find with no replace. `ApplyFixEdits` makes them in turn, each on what the one before left: an edit's lines must be in the file once, compared as they are, else with the spaces at the ends of the lines ignored, else with a line number ("12: ") the agent copied taken off each (`FindLines`); none or more than one place fails with which edit it was. `FixBlock` makes the block from the file before and after: the lines between those both begin and end with, as a `TGittanDiscard` whose write puts the fix in and whose undo takes it out; a fix that only inserts lines keeps the line before them in the block (the line after at the top of the file), so the write has a line to check. A finding whose path goes through a symbolic link (`ThroughLink`) is refused before the agent is asked (`rsFixLink`), since the write would follow it. `FixJobDone` writes it with `DiscardBlock` (refused when the file changed since it was read, and while it is being edited: `EditingRepoPath`, the path made a full name as `FEditPath` is, as for a conflict's resolution) and keeps it in `FDiscards`, so File > Undo Discard takes the fix back; the finding is marked `Resolved` in `FAIThreads`, which folds its card and takes its Fix away, and the status bar says what the agent changed (`rsFixed`; "File > Undo Discard puts it back" when it gave no why). An answer with no edits says the agent's why in the status bar (`rsFixNone`); a failure, edits that do not fit the file included, is an error banner, "Claude Code could not fix it". The job is abandoned with the repository, on quitting and when the features go off. Tested in `tests/testai.pp` (`TestParseFixEdits`, `TestApplyFixEdits`, `TestFixBlock` with its write and undo, `TestFixJob`).
- Explaining lines: Go > Explain Line History with AI (`FWhyItem`, after Time-lapse, no shortcut) and the editor menu's item of the same name (`FWhyEditItem`, after Copy Hash, shown in the change view, enabled on a row of the new side's editor while the file is not being edited) show while `AIAvailable` (`UpdateAIReviewItems`, `EditPopupPopup`); while a job runs both say "Stop Explaining Line History" and end it. The lines are the selection's rows when it spans more than one row and holds the row (the caret's for the Go menu, the one the menu opened on for the editor's), else that row alone (`WhyRows`; a selection that ends at the start of a row does not take it). `StartWhyJob` needs the change view of a file (`rsWhyNeedsChanges` otherwise), takes the lines in the commit the history starts from as Code History does (`ChunkLines`, `HistoryRef`; rows all new have none, `rsNoHistoryYet`), keeps where the card goes in `FWhyThread` (the last of the rows with a line: its new-side line, else its old-side one with `LeftSide`) and the comparison in `FWhyKey` (`AIReviewKey`), and starts a `TGittanWhyJob` with the path, the ref and the lines, the status bar saying the agent is reading their history. The job gives the agent `WhyInput`: the lines as the ref has them (`git show ref:path`), then `git log --no-color -n WhyCommits (10) -L from,to:path --format=commit %h, Author, Date (%as) and the whole message (%B)` with the diff of the lines each, cut at `MessageDiffKeep`; git failing or an empty history (`rsNoLineHistory`) is a failure. The why prompt (`atWhy`, `TaskPrompt`) asks what the lines do, how and why they came to be so and what the changes that shaped them were for, each commit named by its short hash, saying so where the history gives no reason rather than guessing, as at most three short paragraphs of Markdown, the history first (a tool may read the repository to see how the lines are used); `WhyMaxTurns` (10) for claude. The answer, trimmed with its line ends made LF, becomes an AI thread (`WhyJobDone`): the agent as its agent and its comment's author, `WhySeverity` ("history", which `SeverityLabel` shows as Line history and `CardLink` gives no Fix), put in `FAIThreads` for `FWhyKey` (the review's findings for another comparison dropped, an explanation for the same line replaced; but while the findings held are for the comparison shown and the explanation was asked in another, it is dropped instead of them) and shown as the findings are, under the lines; Clear AI Review and a new review drop it with them. A failure is an error banner, "Claude Code could not explain the lines". The job is abandoned with the repository, on quitting and when the features go off. Tested in `tests/testai.pp` (`TestWhyInput` against a repository with three commits, `TestWhyJob`).

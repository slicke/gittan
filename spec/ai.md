# AI features through Claude Code or GitHub Copilot

Read this when touching `gittan.ai`, `umain.ai.inc`, the AI review's cards in the change view, the sparkle in the filter field, the AI page of the settings, AI in the Commit header, File > Write Commit Message or `RunAgentCli`.

- Gittan links no model API: the AI features run an agent's own command line tool without a session in the repository root, Claude Code's `claude` (`claude -p`) or GitHub Copilot's `copilot` (the prompt on its input), so they work with the user's own login, plan and settings, and the agent reads the repository's own instructions (both read CLAUDE.md and AGENTS.md; Copilot also `.github/copilot-instructions.md`). One agent is active at a time (`TGittanAgent`: `gaClaude`, `gaCopilot`; `AgentNames` for the interface, `AgentCommands` for the command and the settings key, `AgentOfKey` back, Claude Code for an unknown key). Nothing of them shows until the settings turn them on: the AI page of the settings dialog (`TGittanSideNav` row with `niAI`, a sparkle) has Turn on the AI features (`AIEnabled`, section `AI`, key `Enabled`, off by default, since the changes go to the agent's provider) with a note that says so, the agent (`AIAgent`, key `Agent`: claude or copilot) in a list, and the picked agent's command path and model, each agent keeping its own (`ClaudePath`/`ClaudeModel`, keys `Claude` and `ClaudeModel`; `CopilotPath`/`CopilotModel`, keys `Copilot` and `CopilotModel`): the dialog keeps both in `FAgentPaths` and `FAgentModels` and `ShowAgent` puts the picked one's in the fields, with labels, hints and notes naming it (the path's note as for git and gh; the model's "an alias such as haiku or sonnet" for Claude Code, "auto to let Copilot pick" for Copilot). The fields are disabled while the switch is off. `FindAgent` takes the setting, else `FindTool` (ToolSearchPath has `~/.local/bin`, where Claude Code's installer puts claude, Homebrew's folders and nvm's node for an npm install), and for claude else `~/.claude/local/claude`, the local install of earlier versions. `FindAgentCli` keeps the agent, its command and model in `FAgent`, `FAgentCli` and `FAgentModel` at start and after the dialog; `AIAvailable` is the switch and the command found. Tested in `tests/testsettings.pp`.
- `RunAgentCli` (`gittan.git.pp`) runs the command through `RunTool` with Gittan's environment and ToolSearchPath as PATH, writes its input to standard input before closing it (both agents read all of it before they write, so any length goes), keeps stdout on failure too (with `--output-format json` claude says why there and exits 1) and stderr in the error, and asks `ACancel` on every pass of the reading loop: True ends the agent (`TProcess.Terminate`), so a job told to stop does not wait for its answer.
- The commit message: "✦ AI" at the right end of the Commit section's header (the header's action, `Action`, a link in the accent color underlined under the mouse, with its own hint only over it, `ActionHint`; a click on it raises `OnAction` and neither folds nor unfolds; dimmed and inert while not `ActionEnabled`), and File > Write Commit Message (Shift+Cmd+K, `FMessageItem`), both `MessageActionClick`; the hint and the texts below name the agent. The action shows while `AIAvailable`, nothing is in progress (`FOperation` empty: a merge or a rebase has its message) and the boxes choose (`CommitChoosing`), and is enabled with files ticked or Amend on, and no commit running; the menu item is there while `AIAvailable` and enabled as the action is (`UpdateMessageAction`, from `UpdateCommitState`). Either unfolds the section and starts a `TGittanMessageJob` (`StartMessageJob`, the status bar saying the agent is writing) for the ticked files (`ChosenCommitPaths`) and Amend, keeping the field's text in `FMessageFrom`; while it runs the action says Stop and the menu item Stop Writing Commit Message, and either ends the agent (`AbandonMessageJob`). The job (`gittan.ai.pp`, a `TGittanJob` that may be given up) collects the changes with `CommitChanges` and runs the agent with `CommitMessageArgs` and `CommitMessageInput`. Claude Code gets `-p` with the prompt (the message alone, no preamble, fences or trailers, and short whatever the repository's own messages are like: a subject of at most 72 characters and a body of a few lines only when the change needs explaining, what changed and why rather than each file, the style taken from the recent subjects, the files read only when the diff leaves the change unclear; told only to follow the conventions, a model wrote pages), `--output-format json`, `--tools Read,Grep,Glob`, `--no-session-persistence` and `--max-turns` `MessageMaxTurns` (10), with the changes on its input, and `--model` when one is set. Copilot ignores its input when `-p` is given, so it gets the prompt and then the changes on its input, with `-s` (its answer alone), `--no-color`, `--stream=off`, `--no-ask-user`, `--available-tools=view,grep,glob` and `--allow-all-tools` (which a run without a terminal needs, and which the three read-only tools make safe), and `--model=` when one is set. Either may read the repository for context but has no tool that writes, runs a command or goes to the network. `ReadAgentAnswer` reads the answer: claude's JSON with `ParseClaudeResult` whatever the exit (the last line that starts an object, so a warning before it does no harm; `is_error` or a subtype other than success is the error, `error_max_turns` said as such), Copilot's whole output when it exited with 0; without an answer the reason is stderr, else what was printed, else that the agent gave none. `CleanCommitMessage` trims the message and takes off a code fence around the whole of it. `MessageJobDone` puts the message in the field when the field is as it was at the start, else says in the status bar that it was not used; a failure (not logged in, an unknown option of an old version) is an error banner, "Claude Code wrote no message" or "GitHub Copilot wrote no message". The job is abandoned when another repository opens and when Gittan quits, and when the settings turn the features off.
- `CommitChanges(ARoot, APaths, AAmend)` is what the agent gets: the recent subjects (`MessageSubjects`, 10, `git log --format=%s`), a line saying the commit amends HEAD when it does, the summary (`diff --stat=100`) and the diff (`--no-ext-diff -M`), cut at a line end after `MessageDiffKeep` bytes (80000) with a line saying how much was left out. The diff is made in a temporary index (`GIT_INDEX_FILE` in the temp folder: `read-tree HEAD`, or `--empty` before the first commit, then `add -A` of the paths from a NUL-separated file under `--literal-pathspecs`), so an untracked ticked file shows as the commit would take it and the real index is left alone; it is compared with HEAD, or HEAD's parent for an amend (the empty tree when there is none). The changes left out of a file (file-actions.md) and the old path of a rename are not reflected: the file is described as it is on disk. No change gives an empty text, which the job reports as nothing to describe. Tested in `tests/testai.pp` against a temporary repository (chosen paths only, an untracked file, before the first commit, amend, nothing to describe, a long diff cut), on each agent's arguments, input and answers, and on claude's JSON; no agent is run in the tests.
- The review: View > Review Changes with AI (Alt+Cmd+R, `FAIReviewItem`; Stop AI Review while it runs) and Clear AI Review (`FAIClearItem`, enabled while there are findings for what is compared) show while `AIAvailable` (`UpdateAIReviewItems`, from `UpdateMessageAction`). `StartAIReview` starts a `TGittanAIReviewJob` with the repository's base, whether it is a range, every changed file (`FStats`) and `AIReviewKey` (the root, the base and `WholeTree`), the status bar saying the agent is reviewing; `ReviewChanges` gives the agent what the change view compares: a range diffed as it is (`git diff -M A..B`), else the work tree's changed files against the base (HEAD when empty) through the temporary index `IndexDiff` makes, which `CommitChanges` uses too, so untracked files are in it; the diff's lines are numbered as the view numbers them (`NumberDiff`: "N12 +text" for a context or added line in the new side, "O7 -text" for a removed one in the old side, headers as they are), so the agent names lines without counting in a hunk. `ReviewArgs`/`ReviewInput` give the review prompt (only real problems, bugs, wrong results, crashes, data loss, security holes, races, missed edge cases; no style, naming, formatting, praise or summaries; at most 10, none a fine answer; files may be read to check a finding; a JSON array alone of path, line, side new or old, severity bug, risk or question, and a body in Markdown) and `ReviewMaxTurns` (20) for claude. `ReadAgentText` reads the answer as `ReadAgentAnswer` does without making it a message, and `ParseReviewFindings` reads the array from its first bracket to its last (so a fence or a sentence around it does no harm), dropping an `a/` or `b/` before a path and a finding without path, line or body, at most `ReviewMaxFindings` (10): each is a `TGittanReviewThread` with `Agent` and `Severity` set, its line the view's own (old side with `LeftSide`) and one comment by the agent, with no address and made now. An answer with no array is an error banner with its start; tested in `tests/testai.pp`. `AIReviewDone` keeps the findings in `FAIThreads` with the job's key in `FAIThreadsKey`, says in the status bar how many there are ("found nothing to point out", "one thing", "N things"), and rebuilds the view; a failure is an error banner, "Claude Code could not review the changes". The findings replace the last review's; Clear AI Review, opening another repository and turning the features off drop them, and the job is abandoned with the repository, on quitting and when the features go off.
- The change view shows the findings as it shows a pull request's threads (github.md): the threads it shows are `FShown` (`CollectShownThreads`): the pull request's (`FThreads`) while they apply (`PullThreadsShown`: View > Review Comments on, a pull request's threads held, and the view's new side the work tree or the pull request's own diff), then `FAIThreads` while `FAIThreadsKey` is `AIReviewKey`, so the findings show for the comparison they were made for and come back when it is compared again. `FThreadRows`, the gaps' Tags, the cards, the clicks and the tree's bubbles (`FileThreads`) index `FShown`; the status bar's pull request chip and its hint count `FThreads` alone. `PlaceThreads` places a finding on the view's own lines, without `MapLine` (an old-side one whatever the base, since the view's old side is what the agent saw); the lines are those of the review's moment, so an edit of the work tree since moves the code under a card. A finding's card has the agent's name after a sparkle (`ThreadAuthor`), its severity as the note over it (`SeverityLabel`: Bug, Risk, Question, or the agent's own word), a violet stripe while open (`AgentColor`) in place of the link color, and no "GitHub ↗" (`HasLink` in `EditDrawGap`, and `EditClickGap` looks for the link only on a thread with an address); a click folds it as any card.
- Where something is: while `AIAvailable` the filter field over the tree shows a sparkle left of its cross (`TGittanSearchBox.ShowAction`, `UpdateFindAction`, from `SetupTreeFilter` and `SettingsChanged`), its hint "Ask Claude Code which files hold what you type" only over it (`ActionHint`). A click on it, or Cmd+Enter in the field (Ctrl+Enter elsewhere; `TreeFilterKeyDown`), is `SearchBoxAction`: with the field empty a status note says to type first, else `StartFindJob` starts a `TGittanFindJob` with the field's text, the status bar saying the agent is looking for it and the sparkle lit (`ActionBusy`); a click while it runs stops it. `FindArgs`/`FindInput` give the prompt (the files that define, implement or handle what is asked, searched and read to be sure, only files that are there; a JSON array alone of path, line, 0 for the whole file, and why, the best first, at most 10, none a fine answer) and `FindMaxTurns` (20) for claude, the user's words on the input. `ParseFoundFiles` reads the array as `ParseReviewFindings` does, keeping each item with a path (`./` taken off, backslashes made /), a missing or negative line 0, at most `FindMaxFiles` (10); tested in `tests/testai.pp`. `FindJobDone` keeps the files that are in the work tree (`RepoFileExists`) in `FFoundFiles` and drops them in `FFindPopup` from the field under the header `Files for "<question>"`: the path with `:line`, cut at its start to keep the file's name, and the why dimmed, cut to a part of the list's width, since the list cuts a caption at its end and gives the detail its whole width. None is a status note, a failure an error banner ("Claude Code could not find it"). A pick empties the field (the question was not a filter) and shows the file at its line with `ShowFileLine`, queued (`ShowFoundAsync`) so the focus the list gives back to the field does not take it from the editor; `ShowFileLine` sets the top line from the editor's height when the editor has not been painted since it was shown (`LineBottom` 0), where `DoGotoPos` took the row for one in sight. The job is abandoned with the repository, on quitting and when the features go off.

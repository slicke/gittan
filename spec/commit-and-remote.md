# Commit, fetch, pull, push, clone and remotes

Read this when touching `TGittanRepo.Commit`, `gittan.commitjob`, `gittan.remotejob`, `umain.commit.inc`, `umain.remote.inc`, `umain.clone.inc`, the notice panel, or the Commit section.

- `TGittanRepo.Commit` (tested in `tests/testgit.pp`) commits the chosen paths as they are in the work tree, as the views show them against HEAD, whatever the index holds: `git commit --only` with the paths, so the other files and their staged changes stay out and hooks and signing run as configured (a `commit-tree` of our own would skip them). The paths go in files (`--pathspec-from-file`, NUL separated, git 2.26 or later) under `--literal-pathspecs`, so no command line grows with them and `br[a].txt` is no pattern. `--only` knows only tracked paths, so the chosen untracked ones are added first and taken out of the index again (`rm --cached`) when the commit fails, a hook's refusal say, whose output is the error. The tree lists a rename under its new path alone, and committing that alone would keep the old file, so `Commit` reads `git status` itself and adds the old path. git refuses a commit of some paths during a merge, cherry-pick or revert (`Operation`): the chosen paths are then added (not one whose deletion is staged, which `git add` would not match) and the whole index committed. Any file in conflict refuses the commit before anything is touched. The message goes in with `-F` byte for byte (a line starting with # is kept); `HeadMessage` gives HEAD's for an amend, and an amend without paths changes only the message. `AParts` (`TGittanCommitPart`: a path and the text to commit for it) are chosen files committed with other text than the work tree's, the changes left out (see file-actions.md): the commit is then made from a temporary index (`CommitThroughIndex`: `read-tree HEAD`, or `--empty` before the first commit, `add -A` of the paths, then each part written over its path with `hash-object -w --path=<path>`, so the path's filters apply as `git add` would, and `update-index --cacheinfo` with the mode `ls-files -s` gives, the work tree's) through `GIT_INDEX_FILE`, so hooks and signing run as for any commit and nothing else the real index holds goes in, and afterwards `git reset` of the paths gives the real index the committed text, so what was left out shows as not staged, as `git commit --only` leaves it; a failed commit leaves the real index untouched. During a merge, a cherry-pick or a revert the parts are written into the real index after the paths are added. A chosen file git rm --cached took out of the index but left on disk is committed through the temporary index as well, taken out of it with `rm --cached`, and its untracked entry is not added (see Renaming and removing files in file-actions.md).
- `gittan.commitjob.pp` (no LCL, tested in `tests/testcommitjob.pp`) holds `TGittanCommitJob`, a thread that runs `Commit` on a `TGittanRepo` of its own, since hooks can take their time, and calls `OnDone` in the main thread with `Ok`, `Id` and `Error`. A commit is never broken off: `Stop` only drops the handler (`Stop(True)` also waits, for quitting), and the thread is not terminated for it (a `TGittanJob` without `AEndOnStop`, see git-core.md), since FPC never runs `Execute` for a thread terminated before it started.
- The Commit section (`umain.commit.inc`) is the last panel of the tree panel (`FCommitPanel`, `alBottom` with `Top` at `MaxInt div 2`, since alBottom orders by the bottom edge and a section shown later would otherwise go under it; `AutoSize`, so folding hides `FCommitBox` and the panel follows): a `TGittanSectionHeader` ("Commit", the detail "3 of 5"; `CommitOpen` in the settings; before the detail a check box from the tree's `FCheckImages`, off, on or mixed as none, all or some of the files are chosen (`CheckIndex`, set in `UpdateCommitState`, none while not choosing), whose click (`OnCheck`, `CommitHeaderCheck`, the header's other clicks still fold) chooses every file that can be, the filter's hidden ones too, or none when all were (`SetAllChosen`, which drops the changes left out as a folder's box does); Tick All Files and Untick All Files at the end of the file menu do the same, shown over the tree while it chooses, `FChosenCount` and `FChoosableCount` enabling them), a native `TMemo` for the message (Cmd+Enter commits; its `TextHint` "Message (⌘↩ to commit)", which Cocoa does not draw for a memo, is a label of `gittan.memohint.pp` (CocoaAll only, used behind `LCLCocoa`): `SetMemoPlaceholder` from `CommitHintAsync` once the handle exists puts a borderless `NSTextField` that ignores the mouse, in `placeholderTextColor` and the view's font, where the text view's first line starts, and `ShowMemoPlaceholder` from `CommitMemoChange` hides it while there is text; NSTextView's private `placeholderAttributedString` takes a text but draws nothing on recent macOS), the length of the first line by the Commit button once it is past `SubjectSoftLimit` (50) as "58/72", in amber past `SubjectHardLimit` (72), where git log --oneline and GitHub cut it (`FSubjectCount`, `UpdateSubjectCount`), Amend (fills an empty field with `HeadMessage` and gives it back when turned off unchanged) and the Commit button, with a note under them saying why the button is off (a `TGittanHintBox`, `gittan.hintbox.pp`: wrapped text in a box with rounded corners tinted with the boxes' accent, red for conflicts (`Warn`), with an icon from an image list or a status bar marker before it: the tree's ticked box before "Tick the files to commit.", the conflict badge before the conflicts, `HintBranch` before the note about HEAD, none for the rest; a `Link` on a line of its own under the text, in `LinkColor` and underlined under the mouse, raises `OnLink`: under the conflicts it is "Next Conflict (F6)", which `CommitNoteLink` sends to `GoToConflict`): not compared with HEAD (`CommitChoosing`: against another base the tree is not what would be committed), a rebase in progress, conflicts, nothing ticked; during a merge, cherry-pick or revert it says everything staged goes in too. The tree's check boxes are its `StateImages` (`FCheckImages`, drawn by `FillCheckIcons` in `gittan.icons`: off, on, mixed for a folder or a file with changes left out of the commit); `ApplyCommitChecks` (end of `FillFileTree`) sets every node's `StateIndex`, none for a conflict or while not choosing. A file is chosen unless git does not track it; only the flips are kept, by path (`FCommitOn`, `FCommitOff`), so they outlive the watcher's refreshes and the filter, and are dropped after a commit or on opening a repository. The form's `TTreeView` is an interposer class in `umain.pp` whose `MouseDown` sends a left click on a state image to `OnStateClick` without selecting the row, so ticking files does not load each diff; Space flips the selected row (`FileTreeKeyDown`), and a folder's box ticks all its files, or none when all were. `StartCommit` asks for a name and e-mail first when git has none (`EnsureIdentity`, kept in the global config), commits every chosen file of `FStats` (not only those the filter shows) through a `TGittanCommitJob`, and `CommitJobDone` shows git's reason in a banner, keeping the message, or on success, when the branch can be pushed as it is (an upstream, not behind it, not an amend, which is left to Force Push, and Push enabled), a green banner "Committed abc1234" with the subject and a Push action (`CommitPushClick`, `StartRemote(rkPush)`), which stays `BannerActionSeconds` (20); otherwise it notes "Committed abc1234: subject" in the status bar. The message is kept in the settings (`CommitDraft`, `CommitDraftRepo`: one slot, line ends escaped) and comes back for that repository only. A commit still running when another repository is opened goes on in `FDroppedCommits` with `DroppedCommitDone` as its handler, and quitting waits for it as for the current one; once one is made, `ForgetCommitted` clears the slot and the field where they still hold its message, since leaving the repository saved it as the draft. File > Commit... (Cmd+K) unfolds the section and focuses the field. Cocoa makes the first text view of a new window its first responder, so `FocusTreeAsync` gives the tree the keys once the window is up. Every git call runs with `GIT_OPTIONAL_LOCKS=0`, so the watcher's `git status` never holds `index.lock` when a commit starts.
- Fetch, pull and push (`umain.remote.inc`): File > Pull (Shift+Cmd+L), Push (Shift+Cmd+P) and Fetch (Alt+Cmd+F), and the same in a `TGittanPopupList` (`FSyncPopup`) that drops up from the status bar's "↑2 ↓5" with the counts as details (Push says "new on the remote" without an upstream) and Commit Graph last; the summary's sync line ("↑ 3 not pushed · ↓ 2 not pulled", or "In sync"; for a branch without an upstream in a repository with a remote "↑ 2 not on the remote yet", or "branch not on the remote yet" with none: the snapshot's `NotOnRemote` from `TGittanRepo.NotOnRemotes`, `rev-list --count HEAD --not --remotes`, which also lists the recent commits with those dotted as not pushed (`RecentCommits` falls back to them without an upstream), and the status bar's track counts them as ↑; tested in `TestBehindDefault`) is a chip under the mouse that drops the same list (`TGittanSummary.OnSyncClick`, `FSyncRect` set by `PaintSync`; `SummarySyncClick`). `TGittanRepo.Fetch` is `fetch --all --prune`. `Pull(pmAuto)` runs a plain `pull --no-edit` when the config says how to pull (`pull.rebase`, `pull.ff`, `branch.<name>.rebase`) and `pull --ff-only` otherwise, so a diverged branch is never merged or rebased unasked: `ADiverged` (git's "Not possible to fast-forward" or "divergent branches") makes `RemoteJobDone` ask Merge (`pull --no-rebase --ff --no-edit`, past a `pull.ff=only`) or Rebase (`pull --rebase --autostash`). `Push` pushes HEAD to the branch's upstream from `branch.<name>.remote` and `.merge` (`push <remote> HEAD:<ref>`, whatever push.default says), or with `-u` to the same name on `RemoteFor('')` without one; `ARejected` ("[rejected]", "fetch first", "non-fast-forward") offers to pull first, and when the refreshed counts show the upstream has commits the branch lacks (`FBehind`, as after a rebase or amend of pushed commits) the question offers Force Push too. `ForcePush` (File > Force Push (with Lease)..., Shift+Alt+Cmd+P, enabled with an upstream; and Force Push in the sync list while the branch is both ahead and behind, "replaces ↓3") is `push --force-with-lease --force-if-includes <remote> HEAD:<ref>` over the upstream: `ForcePushAsk` names how many of the upstream's commits are taken off (a plain push when there are none), a refusal because the remote moved since the last fetch (`AStale`, "stale info", the job's `Stale`) offers a fetch, and one because the upstream has commits a fetch brought in that were never in the branch's reflog (`AUnseen`, "remote ref updated since checkout", the job's `Unseen`; what `--force-if-includes` guards against, since a fetch alone moves the lease along) offers a pull. Tested in `TestForcePush`. The remote job also clones (`rkClone`, see Clone, init and remotes), updates and adds submodules (`rkSubmoduleUpdate`, `rkSubmoduleAdd`, see Submodule actions in submodules.md), fetches a pull request to compare with (`rkFetchPull`, see github.md) and runs `PushBranch` (`push -u <remote> refs/heads/<b>:refs/heads/<b>`, `rkPushBranch`), `PushTag` (one tag, or `--tags` with none, `rkPushTag`) and `DeleteRemoteTag` (`rkDeleteRemoteTag`), each with the job's `Remote`; a pre-push hook gets the notice at once for all the pushes. They run through `RunGitEnv` with `RemoteEnvironment`: `GIT_SSH_COMMAND=ssh -o BatchMode=yes` unless the user runs ssh their own way (`GIT_SSH_COMMAND`, `GIT_SSH`, `core.sshCommand`), so a key that needs its passphrase or an unknown host fails at once instead of waiting at a terminal nobody sees; a key in the agent still works. `TGittanRemoteJob` (`gittan.remotejob.pp`, tested in `tests/testcommitjob.pp`) runs one in a thread like the commit job, never broken off; only one job of the two kinds runs at a time (`UpdateRemoteItems`, `UpdateCommitState`). The three run with `--progress`, so git counts its objects without a terminal, and the job keeps what git and the hooks write in `Progress` (under a critical section, the newest `ProgressKeep` bytes, with `AppendTerminalText` resolving the carriage returns of a progress line as it comes; tested) and raises `OnOutput` in the main thread, one notification at a time. `TGittanNotice` (`gittan.notice.pp`) is the notice this feeds: a panel in the middle of the form like the commit graph (`FNotice`, a child of the form, `Recenter` from `EditorPanelResize`, the theme's colors from `ApplyTheme`), with the application icon over a title whose dots move while it is busy and the last eight lines of a detail text under it in the editor's font (`DetailFont`), closed by its close button or a click outside it (not by the application going to the background, so a long hook is still in view on coming back), and never taking the focus, so a commit message being typed goes on; `Popup(title, detail, busy, kind)`, `Title`, `Detail`, `SetButtons` (`OnButton` with the index, the first the default, filled in the accent, at the right end) and `Close` make it reusable for other messages. Busy, it follows the end of the detail; not busy it is wider, shows up to 18 lines with the end in view, scrolls with the wheel (a thin bar shows where), and `nkBad` colors the title red. `StartRemote` shows it at once for a push when `TGittanRepo.HasHook('pre-push')` (a file of that name in `rev-parse --git-path hooks`, so husky's `core.hooksPath` counts; tested) with the title "Running the pre-push hook" and the status bar saying the same, since a hook may run the tests, and otherwise `FNoticeTimer` shows it after `NoticeDelay` (1 s), so a quick fetch flashes none; `RemoteJobOutput` puts `Progress` in it and, once `PushTransferStarted` finds git's own object counts or the remote's answer in the output (tested), turns the title into "Pushing"; `RemoteJobDone` and `StopRemoteJob` close it. A failure that is no divergence or rejection (those still ask) is told in the notice, not a dialog (`ShowRemoteFailure`): the job's `Error` (a hook's output, then git's reason) under a red title, "The pre-push hook failed" when the push had a hook and git reported nothing of its own, else "The push failed" and the like, with Push Again (Pull Again, Fetch Again, Try Again; `FRetryKind`, `FRetryMode` and `FRetryArg` run the same job again) and Copy Output (`NoticeButton`); `OpenRepository` closes it, and Try Again for anything but a clone does nothing when the open repository is not the one the job ran in (`FRetryRoot`), so a failed push, force push or remote delete is never run again on another repository, and the status bar says the title in red for a while. A pre-push hook (husky sets `core.hooksPath` to `.husky/_`, which git honours on its own) runs inside git's push with `ToolSearchPath` as its PATH, so it finds node; its refusal is a plain failure with its output in the error, not a rejection (`TestPushHook`). Tested against a bare repository and a second clone in `tests/testgit.pp` (`TestPushFetchPull`, `TestPullDiverged`, `TestRemoteEnvironment`).
- Clone, init and remotes (`umain.clone.inc`): File > Clone Repository... and Clone... in the welcome view open `ChooseClone` (`gittan.clonedlg.pp`, built in code): the URL (the clipboard's when `LooksLikeCloneUrl` takes it), the folder (`CloneParent`: the last clone's, else the one the most recent repository is in, else home; Choose... opens a folder dialog) and the name of the new folder, which follows the URL as git names it (`CloneFolderName`, tested) until it is typed in, with the whole path under them and Clone the submodules too (on by default, kept for the session); Clone is off, with the reason in red, while the folder is missing or the new folder exists and is not empty. The dialog keeps its width (`Constraints.MinWidth` and `MaxWidth` with `AutoSize`), so a long path is cut at the edge. The clone runs in the remote job (`rkClone`: `CloneRepository`, `git clone --progress [--recurse-submodules] -- <url> <target>` in the parent folder with `RemoteEnvironmentIn` of that folder, so the user's `core.sshCommand` counts; the job's `Root` is the target, `Arg` the URL, `Submodules` set before `Start`), its notice shown at once by `StartClone`; `RemoteJobDone` hands a clone to `CloneDone` before any refresh, which opens it with a green banner, or shows the failure in the notice with Clone Again (`FRetryRoot`, `FRetrySubmodules`). File > Init Repository... and Init... pick a folder with the form's `DirDialog` (titled Init Repository for the while) and run `InitRepository` (`git init` in it), then open it; a folder with a `.git` of its own is just opened, one inside another repository is asked about first, and a failure shows in the welcome view with no repository open, else in the banner. File > Remotes... (`FRemotesItem`, off while a remote or commit job runs) and Edit Remotes... at the right of the Repository page's Remotes heading (`TGittanRepoPage.OnEditRemotes`, a link with the URL `EditRemotesLink`) open `EditRemotes` (`gittan.remotesdlg.pp`): a native `TListView` of the remotes (`ReadRemotes` in `gittan.repoinfo.pp`, `ParseRemotes` now keeping the push URL too, shown after the URL when it differs), the URL column sized from the list's outer `Width` (on Cocoa `ClientWidth` follows the columns) and `ScrollBars := ssAutoVertical` (Cocoa keeps a horizontal scroller otherwise), the first row selected again in `DoShow` (a selection made before the list shows does not stick on Cocoa). Add..., Edit... (also a double click or Return) and Remove... (also Delete) under it: Add and Edit open `TRemoteForm` with the name, the URL and the push URL (empty pushes to the URL) and, when adding, Fetch from it after adding (the first remote is named origin, the URL from the clipboard when it looks like one); each change runs at once (`TGittanRepo.AddRemote`, `RenameRemote`, `RemoveRemote`, `SetRemoteUrls`, which unsets every `pushurl` and sets one only when it differs from the URL; `--` before the names), a refusal shown in red in the dialog it came from, which stays open. Remove asks first, naming how many remote-tracking branches go. When the dialog closes after a change the repository is refreshed, and a remote added with its fetch asked for is fetched (`fetch --all`). Tested in testgit (`TestCloneFolderName`, `TestLooksLikeCloneUrl`, `TestCloneAndInit`, `TestEditRemotes`) and testrepoinfo (`TestRemotes`).

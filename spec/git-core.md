# The git wrapper, comparisons and the repository state

Read this when touching `gittan.git`, `TGittanRepo`, `FindTool`, git/gh paths, the compare base (`Base`, ranges, merge base, snapshots), the watcher, or `ChangeStats`.

- Gittan supports git 2.30 and later (`MinGitMajor`, `MinGitMinor`; 2.30 is the first with `push --force-if-includes`). `ParseGitVersion` reads `git --version` ("git version 2.30.1.windows.1" too), `GitVersion` asks the git `GitExe` runs (`GitVersionOf` one given by path, for the settings' About page, which names the git in its field before it is saved) and `GitVersionSupported` compares (tested in `TestParseGitVersion`); `CheckGitVersion` in `umain.actions.inc` says an older one in a red banner (the version, what is needed and the path), at the end of `FormCreate`, after the repository is opened since that clears the banners, and when the settings name another git. A git that cannot be run is left to the errors of the git calls: one that cannot be started answers `GitNotRunMessage` (git not found, or the path that could not be run, and that another can be set under Tools in the settings), and the `/usr/bin/git` of a Mac without the Command Line Tools, which only stands in for theirs and writes "No developer tools were found" or "invalid active developer path" (`IsMissingDeveloperTools`), answers `MissingDeveloperToolsMessage` (`xcode-select --install`); both show where the repository would, in the empty view and the status bar (tested in `TestGitNotRun`). Nothing is refused for an old git: what needs a newer one fails with git's own message.
- `gittan.git.pp` wraps the `git` command line tool (found by `FindTool`, see below) through a `TProcess` from fcl-process; it does not link libgit2. Every call runs with `LC_ALL=C` (so the one message `Open` matches on is always English), `GIT_TERMINAL_PROMPT=0`, `-c core.quotepath=false` and `-c diff.suppressBlankEmpty=false` (with the user's `true` git writes a blank context line as an empty line, which the readers of a hunk, the change view, discard, keep, leave out and code history, would drop; `TestSuppressBlankEmpty`); a failed call's `Error` is what git wrote on stdout and then on stderr, since a pre-push hook's output (husky's "pre-push script failed", the tests it ran) goes to the one and git's own "failed to push some refs" to the other; `RunGitEnv` reads both pipes as git writes (through `RunTool`, its own loop, not `RunCommandLoop`, which `RunCli` runs a forge's tool such as gh through too, with `JoinFailure` for the error of either; between reads `WaitForGit` waits with `select` on the pipes on Unix, which git's exit wakes, and on the process handle for 10 ms at most on Windows, so a short call does not sleep past its end) and closes git's input at once, since nothing is written to it and a hook or alias that reads it would wait for ever (`TestInputClosed`) and tells an `AOnOutput` of each piece, which `TGittanRepo.OnOutput` gets for a fetch, pull or push (`RunRemote`), and `ResolveReturns` reads a progress line written over with carriage returns as the terminal last showed it, and the list commands (`status`, `diff --numstat`, `diff --name-status`) are read with `-z`, since the line form quotes a path with a space or a quote C-style. `TGittanRepo.Open` resolves any folder to its work tree root with `rev-parse --show-toplevel`.
- An app started from the Finder gets a PATH of `/usr/bin:/bin:/usr/sbin:/sbin` alone. `ToolSearchPath` in `gittan.git.pp` (made once, in the unit's initialization) is Gittan's PATH followed by the folders missing from it where package and version managers put commands (Homebrew, `/usr/local/bin`, `~/.local/bin`, Cargo, Volta, asdf and mise shims, Nix, Linuxbrew, snap, bun, deno, yarn, `~/.npm-global/bin`, pnpm's home from `PNPM_HOME` or its platform's default), those that exist, and the node of nvm and fnm, which lives in a folder named after its version: `NvmNodeBin` (tested) follows nvm's `alias/default` through the alias files (`lts/*` → `lts/krypton` → `v24.21.0`, a bare `20` meaning the newest v20) under `NVM_DIR` or `~/.nvm`, else takes the newest version installed, and `FnmNodeBin` takes fnm's `aliases/default` under `FNM_DIR` or its default folder, else the newest installed; Windows keeps its PATH. `FindTool(name)` looks a command up on it, node included; git itself is run by the path it gives (plain `git` when none), and `CopyEnvironment` gives every git and gh process it as its PATH, so the hooks git runs find node, npx or pre-commit too (tested: a hook writes its PATH). The environment is read through `EnvironmentVariable` and `EnvironmentStrings` in `gittan.git.pp`, never `GetEnvironmentVariable` or `GetEnvironmentString`: on Windows FPC 3.2.4's read the ANSI environment and label it as the OEM code page, so the ö of `USERPROFILE=C:\Users\Björn` (F6 in Windows-1252) reached git as ÷ (F6 in code page 850) and `git config --global`, which Gittan runs to set the identity before a first commit, could not lock `C:/Users/Bj÷rn/.gitconfig`; the two read the Unicode environment as UTF-8 (tested: `TestEnvironmentUtf8` sets a variable with an ö and a git alias run by its shell prints it). git runs by the path `GitPath` in the settings when one is given, else by what `FindTool('git')` gives (`SetGitExe`, `GitExe`; the earlier paths are kept alive, so a thread starting git during the change copies a live string). The forge is found likewise: `FindForge` takes `GhPath` from the settings, else `FindTool` of `TGittanGitHubForge.CliName` (gh), and makes `FForge`, a `TGittanGitHubForge` with that path (see github.md for the forge classes), kept while the path stays the same; none (`FForge` nil) while there is no gh or `GitHubEnabled` is off (the Hosting page's switch), which hides the GitHub features as a missing gh does (gh is optional throughout: nothing else needs it). Features that need the forge check `Assigned(FForge)` and go through it; nothing outside `gittan.github` runs gh, which it does through `RunCli` (a `TProcess` like `RunGit`, sharing `CopyEnvironment`) with `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`. Open on GitHub and Copy GitHub URL in the file menu and the editor menu, Open Commit on GitHub in the editor menu and the pull request items of the status bar's menu are always built (`BuildPopups`, `AddForgeItem`, their separators too) and kept in `FForgeItems`, their captions formats with the forge's name in place of `%s` in `FForgeCaptions`; `UpdateForgeItems` shows them while there is a forge and hides them otherwise, names them, the View menu's item, the sidebar's row (`SetRowCaption`) and the pages after the forge (`ForgeName`), and enables View > Review Comments likewise; the Compare With menu and a commit's menu are built as they open and look themselves. A change of either path, or of the GitHub switch, in the settings dialog applies at once: `SetGitExe`, `FindForge`, `UpdateForgeItems`, what a forge that is gone had found dropped (the pull request, the review threads), then `MenuRefreshClick`. `ForgeUrl` in `umain.actions.inc` asks the forge for the address of a `TGittanWebTarget` (`WebUrl`; GitHub's runs `gh browse --no-browser`), putting the tool's message in the status bar when it fails (no GitHub remote, say); `OpenOnForge` opens it with `OpenURL`, Copy GitHub URL puts it in the clipboard. `FileWebTarget` gives the target for a path, at a line when one is known (`FileLineOfRow`: the new side's line in the change view, the row in a plain file, none elsewhere), at the right commit of a range, else on the branch, since the work tree has no page (`FileTarget`; GitHub's `--commit` or `--branch`, `GitHubWebArgs`, tested); a commit is opened by its hash (`CommitTarget`).
- `gittan.watch.pp` holds `TGittanWatcher`, a thread that polls the open repository every two seconds (`WatchInterval` in `umain.pp`), every ten while another application is in front (`WatchIdleInterval`: `AppDeactivate` sets the watcher's `Interval`, `AppActivate` sets it back and calls `Poll`, which wakes the thread for a tick at once; `StartWatcher` takes the pace from `Application.Active` through `WatchPace`), and fires `OnChange` in the main thread (through `TThread.Queue`) when `TGittanRepo.Fingerprint` changed: the branch, the commit ids of HEAD and the base, the status of every changed file, and the size, time and MD5 of every changed file on disk (no diff is run for the poll). The thread has its own `TGittanRepo`, so git never runs on the main thread for the poll. A poll that raises (a file gone between git's listing and the read) is tried again on the next tick: the fingerprint is kept only once the snapshot is taken, and the thread goes on. A snapshot that fails (`Snapshot` false) keeps no fingerprint either, so the next tick tries again; the form hears of the failure once (`FFailed`), not on every tick it goes on failing. `Stop` clears the handler before `WaitFor`, because `WaitFor` on the main thread runs the queued calls while it waits. `gittan.watch.pp` also holds `TGittanOpenJob` (a `TGittanJob`, tested in `tests/testwatch.pp`): `OpenRepository` empties the views (`ClearRepositoryViews`), closes `FRepo`, puts the welcome view in its busy state ("Opening <name>..." under the title in place of the error, the buttons and the recent list, which take no clicks then; `TGittanWelcome.SetBusy`, cleared by `ShowWelcome`) and starts the job, which opens the repository and takes its snapshot through a `TGittanRepo` of its own (with `IgnoreWhitespace` as the form has it, see change-view.md), since that is some twenty git commands one after the other and took seconds on Windows; an exception out of the open or the snapshot is a failed open with its message, so `Done` is reached and the form does not wait for the job for ever. `OpenJobDone` takes the repository with `TGittanRepo.OpenAt` (the root and git directory the job found, no git run), draws the snapshot (`ApplySnapshot`), restarts the watcher and calls the `AOnOpened` given to `OpenRepository`, which the clone and init flows use for their notes, since the repository is not open when `OpenRepository` returns. Opening another one abandons a job still running (`AbandonOpenJob`). The snapshot holds the branches and tags too (`Refs`, from `TGittanRepo.Refs`), which `RebuildCompareMenu` lists from `FRefs`, so the watcher's refresh does not run those three `for-each-ref` on the main thread either. `RefreshRepository` in `umain.pp` (also View > Refresh, Cmd+R) reloads the tree, summary and status bar through `LoadRepository` and restores the view from `FView`: the expanded folders, the selected file with its caret and top line, or the repository diff. A selected file that is no longer changed falls back to the summary, which says so in a notice line under its header (`TGittanSummary.Notice`, cleared when the user picks a view). The file shown is `FCurrentPath` when the tree selects nothing, as when the tree filter hides it (`TreeFilterChange` refills the tree without selecting); while `FStats` still lists it, it is shown again (`ShowChanges`) without a node to select, rather than said to be no longer changed.
- `gittan.job.pp` holds `TGittanJob`, the base of the background jobs (commit, remote, blame, history, pull requests, review threads, repository info, submodules, the update check; tested in `tests/testjob.pp`): a thread created suspended that does one piece of work and ends `Execute` with `Done`, which queues `OnDone` for the main thread unless the job was told to end. `Stop(AWait)` drops the handler (`Detach`, which the remote job extends to `OnOutput`), ends the thread when the job was made with `AEndOnStop` (work that may be given up), and waits when asked, but never for a thread that was not started. A commit or a push is made without `AEndOnStop`, so its git runs to the end. `Destroy` detaches first, since `WaitFor` in the main thread lets queued calls through while it waits, then waits, and only then do the descendants free what the thread works with. The watcher is not one: it reports through `Synchronize` on every change.
- Compare With > "origin/main (Merge Base)" compares the work tree with the commit the branch left the default branch at, what a pull request from it would hold plus the changes not committed yet. `TGittanRepo.DefaultBranch` is the remote-tracking branch the remote's HEAD points at (`symbolic-ref refs/remotes/<remote>/HEAD`, the remote from `RemoteFor('')`), else main or master on that remote; `MergeBase` runs `git merge-base <ref> HEAD`. `LoadRepository` keeps both in `FDefaultBranch` and `FMergeBase`, `RebuildCompareMenu` lists the merge base as a radio item right after HEAD (Working Tree), and `BaseLabel` names it "vs origin/main (merge base)". `AheadBehind` (`rev-list --left-right --count @{upstream}...HEAD`) gives the status bar's "↑2 ↓5" after the branch name, each only when above zero and only with an upstream (`FHasUpstream`, `FAhead`, `FBehind`). A click on the counts opens the commit graph (`ShowCommitGraph`, see commit-graph.md). `TGittanRepo.SyncCommits` (`git log --format=%H%x1f%h%x1f%s @{upstream}..HEAD`, or `HEAD..@{upstream}` for the ones behind, at most `AMax`) lists those commits; it is tested, but nothing in the app calls it since the graph took the place of the list it filled.
- What git is in the middle of is shown after the branch in the summary ("main · merging") and as an amber badge in the status bar, with the conflicted files as a red badge there. `TGittanRepo.Operation` looks in the git directory (`GitDir`, `rev-parse --absolute-git-dir`, which `IndexPath` uses too) for rebase-merge or rebase-apply ("rebasing", or "applying patches" for git am), MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD and BISECT_LOG. HEAD is detached while a rebase stops, so `LoadRepository` names the branch from `RebaseBranch` (the `head-name` file of the rebase) then, and only then: the snapshot's `Detached` (from `Branch(out ADetached)`, symbolic-ref failing) says so, since a checkout in a terminal while the rebase stands leaves the rebase behind with HEAD on another branch (a stray rebase, see conflicts.md), whose name is then the branch; `FOperation`, `FRebaseBranch` and `FConflictFiles` are read there.
- `ChangeStats` in `gittan.git.pp` joins `ChangedPaths` with `git diff --numstat --no-renames <base>` (or without a base before the first commit) into a `TGittanFileStats` array: path, change kind, added and deleted lines, or `Binary` when numstat prints `-`, and `Staged`/`Unstaged` from the two status columns. How full a file's badge is tells how much of the change the index holds (`StatIcon`): none gets the tinted badge from `ChangeIcon` (the kind's color translucent under the letter in that color, so it suits a light and a dark tree), part of it the tint in a ring of the color and all of it the solid badge with a white letter (`StagedIcon` in `gittan.icons.pp`, with `APartly`), and the summary row and the file header say "staged" or "partly staged" (`SetStage`).
- `TGittanRepo.Base` is the commit the work tree is compared against, empty for HEAD; `RunDiff` puts it into every `git diff` call (before the `--` of a path list) and falls back to the empty tree (`EmptyTree`, the id depends on the repository's hash function) when HEAD does not exist, so everything staged before the first commit shows as added. With a base set, `ChangedFiles` builds the status lines from `git diff --name-status` plus the untracked files from `git status`, so the tree, the counts, the file diffs and the watcher (which gets the base in its constructor) all follow it. View > Compare With lists `Refs` (local branches, remote branches, tags, most recent commit first, symbolic refs such as origin/HEAD left out; rebuilt by `LoadRepository`) and Other… asks for any ref, or for a range: `main...feature` (what feature changed since it left main, through git's merge base) or `v1..v2` compares two commits, and git diff takes either as one argument. With a range (`IsRange`, the ends from `SplitRange`, HEAD for one left out) the right side is the second commit, not the work tree, and the left side the views read a file's old version from (`DiffSides`: images, binaries, translations, blame, submodules) is, for `A...B`, the merge base of A and B, what git diffs B against, not A (`TestBlame`): `ChangedFiles` asks git status for nothing, `FileChanges` reads a file without a diff from the right commit with `git show`, `Fingerprint` resolves both ends and skips the files on disk, and `BaseLabel` in `umain.actions.inc` shows the range itself where the summary, the status bar and the repository diff otherwise say "vs base". `SetBase` restarts the watcher and keeps the previous base, with the error as the summary's notice, when git rejects the new one.
- View > Compare With > Take Snapshot (Cmd+Shift+N) records the work tree as it is, untracked files included, and compares against it, so the views show only what changes from here on (the use is watching someone or something else edit the tree). `TGittanRepo.TakeSnapshot` copies the repository's index to a temporary file (`GIT_INDEX_FILE`, an optional argument of `RunGit`; `CopyIndex` deletes the file when the repository has no index yet, since on Windows `GetTempFileName` has made it and git refuses an empty index; `TestSnapshotNoIndex`), runs `add -A` and `write-tree` on the copy and `commit-tree` (parent HEAD when there is one) for a commit no branch points at (`CommitTree`, with Gittan's own identity, since commit-tree refuses to run without one; `StashRange` makes its commit the same way; commit-tree signs only with `-S`, so `commit.gpgSign` does not reach it); the repository's own index and status are left as they were. The commit is reachable from nothing, so `git gc` prunes it two weeks or more after it was made. `git diff <commit>` only lists the paths of the index, so a snapshot is compared with `TGittanRepo.WholeTree` set: `CompareIndex` keeps a second temporary index per `TGittanRepo` (the watcher's has its own), refreshed with `add -A -N` (intent to add: no object is written) before each diff, and `ChangedFiles` then takes the untracked files from the diff instead of `git status`, so a file the snapshot holds unchanged is no change and one it lacks is added (`ChangeKind` reads an A in the work tree column as added, as `--name-status` puts it). `WholeTree` has no effect against HEAD or in a range. The snapshots of a repository (`gittan.snapshots.pp`, `TGittanSnapshots`: id and time, newest first, at most `MaxSnapshots`) are kept in `IndexCacheDir` as `<md5 of root>.snapshots`; `LoadSnapshots` in `umain.actions.inc` drops the ones git has pruned (`HasCommit`) when the repository is opened. The Compare With menu lists them as "Snapshot 14:32" (the day before the time when it is not today, `TGittanSnapshots.Caption`), radio items with `Tag` 1, and `SetBase(ARef, ASnapshot)` sets `WholeTree` with the base; `BaseLabel` shows "vs snapshot 14:32", and the summary says "No changes vs ..." instead of "Working tree clean" whenever a base is set.
 An untracked file is counted by `CountNewFile` with git's own rule (a NUL in the first 8000 bytes makes it binary); one gone or unreadable since git listed it counts nothing. `Branch` is `git symbolic-ref --short HEAD`, which also names an unborn branch, or the short commit id when HEAD is detached.

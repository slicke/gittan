# Image, binary and translation views

Read this when touching `gittan.imagediff`, `gittan.binaryview`, `gittan.pofile`, `umain.translations.inc`.

- A changed image (`IsImagePath` in `gittan.imagediff.pp`: every format BGRABitmap reads, png, jpg, jpeg, gif, bmp, ico, cur, tga, tif, tiff, pcx, webp, psd, pdd, xpm, pnm, pbm, pgm, ppm, xwd, ora, pdn, lzp, oxo, and avif only when libavif loads (`AvifReadable`, tried once); SVG is text and keeps the text diff) is shown side by side instead of as text: `ShowChanges` hands it to `ShowImageChanges`, which reads both versions with `TGittanRepo.FileBlob` (`git cat-file blob <ref>:<path>`, or the work tree file when the ref is empty, the refs from `DiffSides`; tested) and sets the view to `gvImage`, with `FImageDiff`, a `TGittanImageDiff`, in the editor's place under the file header (the editor keeps its text and is hidden; `ChangeBlocks` gives nothing in that view, so the navigator hides and F7 steps to the next file; the header names the format through `ImageFormatName`). The control decodes both with `DecodeImage` (the format told from the bytes: a WebP by LazInk's `TInkWebP`, which needs no library, anything else, and a WebP it cannot decode, by BGRABitmap, with the OpenRaster, Paint.NET and PhoXo readers registered in the unit's initialization, since they register only when asked) and paints them at one scale, so a change of size shows: a whole number up to `MaxZoom` (8) with nearest neighbour while they fit, a smooth reduction otherwise; a checkerboard behind each shows transparency, a frame in the diff's red and green marks the old and the new side, each caption gives the size in pixels and bytes and the zoom, the new side how many pixels differ when the sizes match (two fully transparent pixels count as the same), and a side without a version, or one that cannot be decoded, says so in a dotted box. `RefreshRepository` treats it as the change view.
- Any other binary file (`Binary` in its stat: numstat's "-", or for an untracked file a NUL in its first 8000 bytes) is shown by `ShowBinaryChanges` in `FBinaryView`, a `TGittanBinaryView` (`gittan.binaryview.pp`, view `gvBinary`), in the editor's place as an image is: a page drawn on the canvas (so it stays sharp on Retina) with the extension on it (BIN without one), "Binary file" and the sizes, "4.9 KB → 8.8 KB", "New file · …" or "Deleted · …" (`TGittanRepo.FileSize`, `git cat-file -s` or the work tree file, without reading it; tested). `ShowChanges` does not ask git for the diff of a binary file at all, since an untracked one was read as text. `OpenFile` shows a file that `IsBinaryFile` (in `gittan.git.pp`, git's rule, tested) finds binary the same way with its size (`ShowBinaryFile`). `ChangeBlocks` gives nothing in that view, and Go > Next/Previous File go to the first change only when the file has one: `GoToChange` steps on to the next file in a file without changes, so an image or a binary file used to be skipped.
- A file in Git LFS is what it stands for, not the pointer git holds in its place (`ParseLfsPointer` in `gittan.git.pp`: under 1024 bytes, the version line, `oid sha256:` and `size`; tested). `RunDiff` passes `-c diff.lfs.binary=true`, so a file with the attribute `diff=lfs` (what `git lfs track` writes) is binary in the stats and every diff, not the pointers' changed oid and size lines; `format-patch` and the AI's and the reviews' own diffs keep git's text. `FileBlob` reads a pointer's object from the local store (`LfsObjectFile`: `lfs/objects/<2>/<2>/<oid>` in the common git directory, which a linked worktree's `commondir` names, or under `lfs.storage`; the folder is found once per open, `LfsStore`, so a later `lfs.storage` counts from the next open), in a commit or in the work tree, and gives the pointer itself when the object is not downloaded; it never runs git-lfs or reaches the network. `FileSize` gives a pointer's size, and its overload also whether the object is missing from the one read of the pointer, which the binary view uses for both. So the image view, the binary view's sizes and the Files page show the real file. Tested in `TestLfsFiles` without git-lfs, the pointer committed as it is and the object put in the store by hand. A version not downloaded says so: the image view's side reads "Not downloaded (Git LFS)" with the pointer's size (`SetImages` finds the pointer itself, so the Files page's image does too), the binary view adds the line "Not downloaded from Git LFS" (`SetNote`, from `TGittanRepo.LfsMissing`), and the Files page shows such a file as binary with its size. In the change view the header then has Download (`FLfsSides`, the refs of the sides missing, the work tree's empty), which runs `TGittanRepo.LfsDownload` in the remote job (`rkLfsFetch`, `StartLfsDownload`, the refs in the job's `Refs`): `git lfs fetch --include=<path> <PushRemote> <refs>` (the work tree as HEAD) and, for the work tree, `git lfs checkout -- <path>`, which replaces only a pointer. git-lfs reads both as patterns, --include as a list between commas with no escape for one, so `LfsPattern` puts `?` for each comma and wildcard of the path (tested with `a,b [v2].psd`). Without Git LFS (`LfsInstalled`), or without a remote, it fails with a message of its own. When it is done the file is shown again ("Downloaded <name>" in the status bar); a failure is the remote notice with Try Again (`FRetryRefs`). `TestLfsDownload` downloads from a remote in a folder when git-lfs is installed (GitHub's runners have it), else checks the message.
- Where a repository stands with Git LFS is read once per commit checked out: `ApplySnapshot` calls `CheckLfs` (umain.remote.inc), which starts a `TGittanLfsCheckJob` (gittan.watch.pp, tested in `tests/testwatch.pp`) unless the root and HEAD are those it last read (`FLfsChecked`; a snapshot of another commit while a check runs clears it, so `LfsCheckDone` reads again, and so does a check that failed, Track with Git LFS and Stop Tracking, and saving a `.gitattributes` in the editor (`SaveEdit`), which may make files lockable or put them in Git LFS without a new commit; HEAD is the snapshot's `Head`, kept in `FSnapHead`, so no git runs on the main thread for the key), so a pull, a switch or a checkout from a terminal reads it again and a snapshot of the same commit does not. The job runs `TGittanRepo.LfsState` (tested): `Files`, the files with filter=lfs (`ls-files -- ':(attr:filter=lfs)'`), `Pointers`, those of them whose work tree file is a pointer (read only under `LfsPointerMax`, 1024 bytes; a file that cannot be read, locked on Windows, counts as neither), and, when there are files, `Lockable` (the files in Git LFS and those with the attribute `lockable`, `ls-files -- ':(attr:lockable)'`, sorted, which git-lfs makes read-only until they are locked), and, when there are files to lock, `Installed` (`LfsInstalled`: git-lfs on the tool path, else `git lfs version`, which finds it in git's exec path as Git for Windows keeps it; once found it is not asked again) and `SetUp` (`filter.lfs.process` or `.smudge` in git's config). `LfsCheckDone` shows a banner, the worst first: not installed (red, "Get Git LFS" opens git-lfs.com), not set up (red, Set Up runs `LfsInstall` in the remote job, `rkLfsInstall`: `git lfs install`, which writes the filter in the user's global config and the hooks in the repository, then `git lfs checkout`), both since committing such a file would put its content in git itself; else, with pointers, a note "2 files from Git LFS are not downloaded" with Download All (`LfsPull`, `rkLfsPull`: `git lfs pull`). A banner closed is not shown again until what it says changes (`FLfsShown`, cleared with `FLfsChecked` on opening a repository). The LFS jobs of the remote job (download, pull, install) end in a green banner or the status bar, show the file of an image or binary view again, and read the state again; a failure is the remote notice with Try Again. `StopRemoteJob` drops a check still running.
- Git LFS locks (`gittan.lfslocks.pp`, no LCL, tested in `tests/testlfslocks.pp`; `umain.lfslocks.inc`): who holds which file on the LFS server. `ReadLfsLocks` runs `git lfs locks --verify --json` with `RemoteEnvironmentIn`, which splits them into the user's (`ours`) and everyone else's (`theirs`); a server that cannot verify, or one whose `--verify` answer is a plain list rather than that split (`ParseLfsLocks`' `AVerified`), gets the plain `--json` list, the user's own then those this clone locked (`--local`, matched by id and path, `MarkLocalLocks`: the clone's list keeps a lock someone else force unlocked, so the path alone would make a later lock of another user's look like the user's; a `--local` that fails fails the read, so what was known stays rather than the user's own looking like another user's). `ParseLfsLocks` reads either form into `TGittanLfsLock` (id, path from the root, owner's name, `LockedAt` in UTC or 0, `Ours`); git-lfs lists none, and succeeds, in a repository without a remote. `TGittanLfsLocksJob` reads them on a thread: `LfsCheckDone` keeps the check's `Lockable` in `FLfsLockable` and `Installed` in `FLfsInstalled` and, with git-lfs installed, starts it (`StartLfsLocks`, which runs nothing without git-lfs; one asked for while it runs reads again when it is done, `FLfsLocksAgain`), as do a fetch, the background fetch, a lock and an unlock, and opening the list; a failure (offline, a server without locks) keeps what was known (`FLfsLocks`). The job is dropped, not waited for, with the remote jobs (`StopLfsLocks`), and ends git-lfs as it runs (`ReadLfsLocks`' `ACancel`, through `RunGitEnv`, asked as the job's `Cancelled`), so a server that does not answer keeps neither a frame that closes nor quitting waiting. The file menu has, under the Git LFS items, Lock File (Git LFS) for a file of `FLfsLockable` no one holds while git-lfs is installed (without it the banner says it is missing, and the lock would only fail), and for a locked file Unlock File when it is the user's or Force Unlock (Locked by <owner>)... (`UpdateLockItems`, both off while a remote job or a commit runs); `TGittanRepo.LfsLock` (`git lfs lock -- <path>`) and `LfsUnlock` (`git lfs unlock [--force] -- <path>`, the `--` for a path that starts with -) run in the remote job (`rkLfsLock`, `rkLfsUnlock`, `rkLfsForceUnlock`), a forced one asked first (`UnlockAsk`). `LfsLockJobDone` says it in the status bar, or shows the remote notice with Try Again on a failure (held by someone else, changes not committed), and reads the locks again. The header says "Locked by <owner>" in its note for the file shown when another user holds it (`LockNote`, from `ShowChanges` and `OpenFile`, when the locks are read and when the Git LFS check ends, which drops them without git-lfs; `ShownLockPath` is `FCurrentPath`, or the file open on its own; a note of its own, `FLockNote`, is cleared when the lock goes, another note is left, and the note it took the place of, the file changed on disk, comes back, `FLockNoteWas`). File > Git LFS Locks... (`FLfsLocksItem`, shown while git-lfs is installed and there are files to lock or locks) drops a list (`FLfsLocksPopup`, under the status bar's branch, as the reflog) of the locks as last read, the user's first, each with its owner ("you") and age; a pick shows the file (`ShowRepoFile`), a right click offers Show File and the unlock (`FLfsLocksMenu`, `LfsLocksMenuClick`). A file of HEAD on the Files page that may be locked or is gets a third pill after Open and Save As... (`BlobActions`, again when the locks are read and when the Git LFS check ends; no Lock without git-lfs): Lock, Unlock or Force Unlock (`BlobLockAction`), so a file is locked before it is changed, which the change tree, holding only changed files, cannot offer; `ShownLockPath` is then `FBlobPath`. A commit of files another user holds is asked first (`LockedCommitAsk` from `StartCommit`, with the locks as last read; an amend keeps what HEAD changed in the commit, so its paths are checked too, `TGittanRepo.HeadPaths`: `git diff-tree HEAD^ HEAD`, against the first parent also for a merge, `--root HEAD` for the first commit, which git 2.30 can both do, a rename as both paths, tested): git-lfs's pre-push hook refuses the push while they hold them, so the question names the file and its owner, or counts the files and lists up to eight, with Commit Anyway and Cancel, Cancel the default.
- View > Translations (Cmd+Alt+L, `Translations` in the settings, on by default) shows a gettext file (`.po`, `IsPoPath`; a `.pot` template has no translations and keeps the text view) as its entries, the original on the left and the translation on the right (`umain.translations.inc`, view `gvTranslation`). `gittan.pofile.pp` (no LCL, tested in `tests/testpofile.pp`) reads the entries (`ParsePo`: context, msgid, plural, each msgstr form unescaped and joined from its continuation lines, the fuzzy flag, obsolete `#~` entries, the line each keyword is on) and lays them out (`PoRows`, the header and obsolete entries left out): the context in brackets (marked in `Context`; `ShowTranslation` dims it to the gutter's color with a `tagPoContext` attribute, which `RecolorWords` recolors on a theme change, since a Lazarus project's .po files give every entry the resource string's name as its context), the original and its plural on the left, the translation on the right with `[n] ` before each plural form, the text split at its line breaks, the shorter side padded with blank rows and a blank row between entries. `ShowTranslation` puts the two sides in `FEditOld` and `Edit` as the side-by-side change view does (`SidesShown` makes `ApplyLayout` show the old side, and keeps word wrap off), without a lexer; the numbers (`SetRowNumbers`) are the file lines the original and each translation start on. A fuzzy entry is tinted amber (`bmFuzzy`, its numbers amber too through `LineNumberColor`, and its translation's first number has `FuzzyMark`, "! ", before it in the decor text), one with a form left empty red (`bmUntranslated`), on both sides. In the change view the old version is read too and `ChangedEntries` pairs the entries by context and original (`EntryKey`): an entry that is new, or whose plural, translation or fuzzy flag differ, gets the diff's green strip on the new side, the header counts them ("5 changed · …") and its first row is one of `FPoBlocks`, which `ChangeBlocks` answers in this view, so the navigator and F7 step through the changes; in the file view, and for a new or deleted file, the blocks are the entries that need work (fuzzy or untranslated). Entries removed since the old version are not shown. F7 goes on to the next changed file past the last (`ShowsChangedFile`). The header shows the counts (`FPoStats`) where it names the lexer. A changed file (`ShowTranslationChanges`, from `ShowChanges`) shows its new version through `FileBlob`, the old one when it is deleted, and a refresh shows it again; a file with a conflict keeps the change view, since its markers break the entries. A file from File > Open (`ShowTranslationFile`, from `OpenFile`) shows its text on disk. Toggling the item shows the file again the other way. Find searches the translations, the right side.

# GitHub and the forges: pull requests and review comments

Read this when touching `TGittanForge` or adding a forge, `gittan.github`, `gittan.reviews`, `umain.reviews.inc`, `gittan.pullpage`, `umain.pulls.inc`, `gittan.forge`, `gittan.forgepage`, `umain.forge.inc`, the pull request chip, the Pull Requests page, the GitHub page or Compare With > Pull Requests.

- A forge is the service that hosts a repository; Gittan reaches it through `TGittanForge` in `gittan.forge.pp` (no LCL, tested in `tests/testforge.pp`), and nothing outside the forge's own unit names it or runs its tool. The class has the forge's `Name` ("GitHub", for menus, links and the sidebar), `CliName` and `Cli` (the tool and its path), `Version` (for About), three factories of jobs, each an abstract job of `gittan.forge` or `gittan.reviews` with its forge-specific part virtual: `PullJob` (`TGittanPullRequestJob`: `AskBranchPull`, `AskOpenPulls`, `AskReviewPulls`, `AskLogin`; the base runs them in order, filters with `WithoutReviewed` and finds the gone upstreams), `ReviewJob` (`TGittanReviewJob`: `Ask` fills the threads, the notes and the head commit) and `AccountJob` (`TGittanForgeJob`: `Ask` gives the login and the two lists; the base filters with `StillToReview`), `WebUrl` (the address of a `TGittanWebTarget`: a file at a line in a commit or on a branch, a commit, or an issue) and `PullRef` (the ref a remote serves a pull request's head at, which `FetchPullRequest` fetches). A job takes what it needs from the forge when it is made, so it may outlive the forge (the settings change while it runs). The records are the forge's too: `TGittanPullRequest`, `TGittanForgePull`, and their states as kinds, never a forge's words (`TGittanPullState`, `TGittanReviewDecision`, `TGittanReviewVerdict`, `TGittanChecksState`), with `PullRequestStatus`, `PullRequestNote`, `PullRequestChecks`, `ReviewDecisionNote`, `IssueNumber`, `WithoutReviewed`, `NeedsMyReview`, `StillToReview` and `WithFeedback`. GitHub is `TGittanGitHubForge` in `gittan.github.pp` (tested in `tests/testgithub.pp`), the only forge so far: its jobs (in the unit's implementation), the JSON gh prints read into the forge's records and kinds, and `RunGh`, through which every gh runs. The form holds one forge in `FForge` (see git-core.md for `FindForge`). Another forge is a unit of its own beside `gittan.github` with a class of `TGittanForge`; what is left then is choosing a forge per repository by its remotes, and a page of the user's pull requests per forge.
- `gittan.github.pp` (no LCL, tested in `tests/testgithub.pp`) reads what gh prints with `--json` into `TGittanPullRequest` (`gittan.forge`; number, repository as owner/name from its address, state, review decision, URL, head and base branch, author, draft) through `ParsePullRequest` and `ParsePullRequests` (fpjson), `PullRequestStatus` gives the one-line "PR #12 · Approved" (the status bar's hint; the bar itself draws the parts, see the status bar in window-chrome.md, with the state from `PullRequestNote`) (Merged, Closed, Draft, Changes requested, Review required, or the number alone) followed by the checks of the head commit when there are any (`PullRequestChecks`, from `statusCheckRollup`: "checks ✓", "2 checks failing" or "3 checks pending"; a CheckRun counts by its conclusion once completed, a StatusContext by its state), and `RepoPathOfUrl` the "owner/repo" of a GitHub address, which the parser puts in the record's `Repo`, the path the rest of Gittan uses. GitHub's pull request job (`TGittanPullRequestJob`, from the forge's `PullJob`) runs `gh pr view` (no selector: gh takes the checked-out branch and knows its fork), `gh pr list --state open --limit 50` and, when the list came, `gh pr list` again with `--search review-requested:@me` (GitHub's own search, which knows who gh is logged in as and the teams they are on) for the open pull requests waiting for the user's review (`ReviewPulls`, empty when gh could not list them), less the ones the user has already reviewed: a review given clears a personal request but not one made of a team the user is on, so the job asks gh for the login (`gh api user --jq .login`, once: `Login` after the job, which `FPullLogin` hands to the next one, cleared when gh goes) and `WithoutReviewed` (tested) leaves out a pull request whose latest review by that login (`latestReviews`, read into `Reviews` as login and verdict) approved it or asked for changes, keeping one only commented on or whose review was dismissed, and one the login is asked for again in person after their review (`reviewRequests`, the users' logins in `Requested`); in a thread, like the blame job. `StartPullJob` in `umain.actions.inc` runs it from `LoadRepository` once per repository and branch (`FPullKey`), from View > Refresh always, and from `FPullTimer`, which `PullJobDone` sets after every job that gh answered: `PullPollPending` (30 s) while the pull request has checks pending, else `PullPollIdle` (5 min), so the status bar follows the checks, a review and a new pull request; a poll keeps the data shown while gh runs (`AKeep`), and `AbandonPullJob` stops the timer; `PullJobDone` keeps the result (`FHasPull`, `FPull`, `FPulls`, `FPullError`), and the finished job goes to `FBlameZombies`. `UpdateStatus` adds the branch's pull request after the base label; the status bar's menu gets Open Pull Request and Copy Pull Request URL with gh. View > Compare With > Pull Requests (with gh) lists the open pull requests as radio items (`RebuildPullMenu`: "Loading...", gh's message or "No open pull requests" while there is nothing to list); choosing one (`MenuComparePullClick`, `ComparePull`) runs `TGittanRepo.FetchPullRequest` as a remote job (`rkFetchPull`, `StartPullFetch`; the number in `Arg`, the base in `Branch`, the fetched ref back in `HeadRef`), so the window goes on while it fetches and the status bar says "Fetching pull request #N..."; `PullFetchDone` compares, and a failure gets the remote job's notice with git's reason and Try Again; `git fetch --no-tags <remote> <base> +refs/pull/N/head:refs/gittan/pr/N` (the source ref from the forge's `PullRef`, given to the remote job as `PullRef`), with the remote `RemoteFor` finds for the pull request's owner/repo (else origin, else the first; `HasRemoteFor`, tested, says whether one holds the path at all, for the GitHub page), and sets the base to the three-dot range `<remote>/<base>...refs/gittan/pr/N` (kept in `FPullRange`, numbered `FPullNumber`), which `BaseLabel` names "vs PR #N" and `RebuildCompareMenu` leaves out of the ref list. A failed fetch is a summary notice.
- The Pull Requests page (`TGittanPullPage`, `gittan.pullpage.pp`, painted like the Repository page in the same box, `FView = gvPulls`; `umain.pulls.inc`) lists the open pull requests the job read (`FPulls`), from the sidebar's Pull Requests row (`navPulls`, `niPull`, a branch's commit meeting the trunk), View > Pull Requests (Cmd+6, `FPullsItem`) and All Pull Requests in the list the status bar's chip drops (`paList`); the row (`TGittanSideNav.SetRowVisible`) and the item show only while gh is found (`UpdateForgeItems`, which also leaves the page for the summary when gh goes). The page has the repository's name with "Pull Requests" after it and under them the "owner/repo" of the first pull request (`Repo`, else the root), with "Asking GitHub…" (the forge's name, `SetForge`) after it while the job runs (`SetPulls` with `ALoading`, keeping what it had). The branch's own pull request (`SetBranchPull`, `FHasPull`, `FPull`) stands first under "This branch", also when it is merged or closed; then "Open pull requests" with the count and Refresh at the right (`OnRefresh`: `StartPullJob(True, True)`, not while one runs), gh's message in the error color when it failed, or "No open pull requests". A card per pull request: the number dimmed and the title in bold, at the right the state as a chip (`PullRequestNote`: Merged in the link color, Approved in the ok color, Changes requested in the error color, Draft, Closed and Review required dimmed) and the checks as one ("✓ checks", "2 failing", "3 pending" in the ok, error and warning colors), under them who opened it, "head → base", when it was opened and, when later, last changed (`ReviewAge` against `LocalTimeToUniversal(Now)`), "+120 −30 in 4 files" and its labels, with "GitHub ↗" (`OnOpenUrl`) at the right end; one waiting for the user's review has a "Needs your review" chip in the warning color before the state (`SetReviewPulls` with the job's `ReviewPulls`, kept in `FReviewPulls` and handed over by `UpdatePullPage`; `NeedsReview` looks its number up). For these gh is asked for `createdAt`, `updatedAt`, `additions`, `deletions`, `changedFiles` and `labels` too (`PullRequestFields`; `Created` and `Updated` in UTC, `Labels` the names joined with ", ", tested). A card fills under the mouse and a click compares with its pull request (`OnCompare`, `ComparePull`, as the menu does); the one compared against (`SetComparing` with `FPullNumber` while the base is `FPullRange`, from `UpdatePullPage` and `UpdateStatus`) has a stripe in the link color and a Comparing chip, and a click on it goes back to the working tree (`OnWorkingTree`, `SetBase('')`). `UpdatePullPage` hands the job's state to the page when a job starts and ends and when the page is shown; showing the page asks gh again (`ShowPulls`). The content is painted on a measuring canvas first (`Layout`, as the Commands page does) so the height is known before the page is shown.
- The summary (Home) counts the pull requests waiting for the user's review in one row under the conversation, so they are seen as the repository opens without taking the room a card each took: the pull request icon and "3 pull requests need your review" (`TGittanSummary.SetReviewPulls`, from `PullJobDone` with the job's `ReviewPulls`; cleared when a job starts afresh and when gh goes; nothing with none), a chip with a dimmed chevron while `OnReviewClick` is set, filled with the hover color under the mouse. A click drops `FReviewPopup` from the chip (`SummaryReviewClick` in `umain.pulls.inc`): "Needs your review" as its header, a row per pull request with "#12 Title" and, dimmed, who opened it, when and "draft" for one (`ReviewPullLine` in `gittan.summary.pp`; the branches are left out, since the list is at most 440 wide and the detail takes its room from the title), the one compared against checked, then All Pull Requests; a pick compares with its pull request (`ReviewPopupPick`, `ComparePull`, as a card of the page does), which puts its review comments in the change view, and All Pull Requests opens the page (`ShowPulls`). The row's height goes into the layout before the paint (`LayoutReview`), as the conversation's does, a clean tree with the row is not centered (`CentersClean`), and the job's result is compared with what is shown (`SamePulls`) so a poll that finds the same does not repaint.
- The change view shows the findings of an AI review among these threads, in a list of its own with them (`FShown`; see ai.md). View > Review Comments (Cmd+Shift+M, `ReviewComments` in the settings, on by default) shows the review threads of a pull request in the change view, each in a card under the line it is on (`umain.reviews.inc`, `gittan.reviews.pp`, the latter without LCL and tested in `tests/testreviews.pp`). GitHub's review job (`TGittanReviewJob`, from the forge's `ReviewJob`) asks gh for them with `gh api graphql` (`ReviewThreadsQuery` in `gittan.github`, a page of 100 threads at a time, owner and name from the pull request's URL) and `ParseReviewThreads` (`gittan.github`) reads each thread's path, line (or start line, original line, side), resolved, outdated and file-level state and comments. `ReviewTarget` picks the pull request: the one compared against (Compare With > Pull Requests), whose diff is the one the comments were made on, else the branch's own while the new side is the work tree; `PullJobDone` asks again at the pull request's poll, `SetBase` when the comparison changes, and `ThreadsKey` keeps a poll that finds the same from rebuilding the view. `PlaceThreads` (from `BuildChangeView`, once the lines are numbered) finds each thread's diff line in `FThreadRows`: in the pull request's own diff as it is, else the head's line mapped onto the work tree with `MapLine` over `git diff -U0 <head> -- path` (kept in `FMapDiff` until the file is shown again); a comment on a removed line only where the old side is the pull request's base (its diff, or the merge base with the default branch). One that cannot be placed (outdated, on the whole file, on a removed line not shown) goes to the top of the file. Hide Unchanged Lines keeps a commented line. The cards are the editor's gaps (`TATGaps`, `ApplyReviewGaps`): room under a line painted by `OnDrawGap` (`EditDrawGap`), outside the text, so the lexer, the numbers and `FRows` are untouched; a gap's Tag is the thread, and side by side the other editor gets an empty gap of the same height (Tag -1) so the rows stay in step, with `MatchScrollPixels` putting the old side at the same pixel, since `LineTop` alone loses the part of a tall gap scrolled into. `ReviewLayout` lays a card out in the interface font at the width its last paint had (`FReviewWidths`, laid out again when it changes), measured on `FReviewMeasure`. A comment's body is Markdown, drawn as the Markdown preview's LazInk draws it, but on the canvas, since a card is a gap and not a control: `CommentParts` (`gittan.reviews`, tested) first cuts the body at its `<details>` blocks, each a part with its summary and depth (a block holds the deeper parts after it), and makes Markdown of the HTML bots write (CodeRabbit's): HTML comments go, an `<img>` becomes its alt text, an `<a href>` a Markdown link, block tags a line break or a blank line, a heading bold text; code, fenced or in backticks, is left alone. `CommentMarkdown` joins the top parts with each block folded to "▸" and its summary (the folded card's first line). `ReviewSegments` (kept by the body in `FReviewSegments`) cuts the parts at the fences, each line's kind, depth, block and comment packed in its Objects (`ReviewRow`, `RowKind`, `RowDepth`, `RowDetail`, `RowComment`): a block's summary is an `rlDetails` line, dimmed after "▸", or after "▾" with the lines in it, indented `ReviewIndent` per level with a rule down the left of each, when it is open; a click on it opens or closes it when the button comes up, as a card folds (`DetailsKey`, the thread's id, the comment and the part, kept in `FThreadFlips`). The text between fences is one `rlMarkup` line in LazInk's inline markup (`MarkdownToInk` with `imoInlineHTML`, so only the inline tags it trusts pass), measured (`ReviewRowHeight`, `HTMLTextExtentOpt`) and drawn (`HTMLDrawOpt`) at the card's width through one layout cache (`FReviewInk`), links in the link color; a fence's lines are code in the editor's font, a suggestion block labeled. A folded card shows the first line of text without its markup. A resolved or outdated thread starts folded to one line; a click on a card folds or unfolds it (`FThreadFlips` by the first comment's URL, applied in `EditMouseUp` so the card does not change height under the button), a click on "GitHub ↗" opens it, one on a link in a comment that goes to the web opens the link (`HTMLHitTest`). Three editor quirks are worked around: the gutter of a line spans its gaps and gutter decor centers the change view's numbers in that height, so `DrawGapGutter` (from `OnDrawEditor`) paints the gutter over the gaps plain and puts the number back at its line; the block staples, drawn down a block of code after the text, run through the cards under its lines, so `DrawGapGutter` paints the cards again over them (`EditDrawGap` with the gaps' rects, under the last row of a wrapped line); and a gap before the first line shows only at scroll position -1, which every `LineTop := 0` leaves, so `RevealTopGapAsync` moves a view at its top up onto it. The status bar's pull request chip shows a speech bubble after its checks, with the number of open threads, dimmed when all are resolved or outdated (`SetPullThreads`, from `UpdateStatus` while the threads are the chip's pull request's), and its hint counts them (`ReviewHint`, the `HintComment` bubble). In the tree a file with threads gets the same bubble at the right end of its row with the number of open ones, gray when all are resolved or outdated (`FileTreeAdvancedCustomDrawItem` at `cdPostPaint`, `FileThreads`), and its hint says how many (`FileThreadsHint`). What is on no line, the pull request's own comments and the text a review was submitted with (what a reviewer writes with Request changes or Approve; such a review has no thread unless it also commented on lines), comes in the same query (`reviews(last:100)` and `comments(last:100)`, read from the first page by `ParsePullNotes` into `TGittanPullNotes`, oldest first; a review that only commented on lines, or is still pending, is left out, an approval, a request for changes or a dismissal is kept without text) and is shown in the summary under the header (`TGittanSummary.SetNotes`, from `ReviewJobDone`, cleared by `ClearReviews`): "Conversation of pull request #N", then a card per note with a stripe in the outcome's color (green approved, red requested changes), the author, what they did and when, a "GitHub ↗" link (`OnOpenUrl`) and the text, its Markdown drawn as a review card's is (`CommentParts`, each part through `MarkdownToInk` and `HTMLDrawOpt` in the summary's own layout cache, `FInk`, a row of `TGittanSummaryNoteBox.Rows`) at the card's width, a `<details>` block as its summary after "▸" that a click opens (after "▾", the parts in it indented `NoteIndent` per level with a rule, `FNotesOpen` by the note's address and the part, `NoteDetailsAt`, the hand cursor over it), at most `NoteMaxLines` lines high with an ellipsis after unless a block in it is open; a link in it that goes to the web opens through `OnOpenUrl` (`TextLinkAt`, the hand cursor over it).
- The GitHub page (`TGittanForgePage`, `gittan.forgepage.pp`, painted like the Pull Requests page in the same box, `FView = gvForge`; `umain.forge.inc`) shows the user's pull requests across every repository: from the sidebar's GitHub row (`navForge`, `niForge`, a globe) and View > GitHub (Cmd+7, `FForgeItem`), both shown only while gh is found (`UpdateForgeItems`, which also leaves the page for the summary when gh goes). It is written for more than one forge: `gittan.forge.pp` has `TGittanForgePull` (the repository as "owner/name", number, title, URL, author, branches, state, review decision, the head commit's checks as one word, the state of the user's latest review of it, whether they are asked for one in person now, and `Feedback`: whether someone other than its author, and not a bot, has commented on it or reviewed it, among its last thirty comments and last thirty reviews; a deleted user counts as someone else) and `TGittanForgeJob`, a thread whose forge-specific part is `Ask`; GitHub's (from the forge's `AccountJob`) runs `gh api graphql` with `ForgeQuery` (`gittan.github`), one query for the viewer's login and two searches, `is:pr is:open author:@me` and `is:pr is:open review-requested:@me`, fifty each, newest changed first, each node with `viewerLatestReview`, `viewerLatestReviewRequest`, the authors (`__typename` and login) of its last thirty `comments` and `reviews` and the last commit's `statusCheckRollup`; `ParseForgeAnswer` reads it (the first GraphQL error's message as the error). The review search keeps a pull request asked of a team the user is on after their review, so `NeedsMyReview` keeps one the user is asked for in person now (a request made again after their review) or whose latest review by them neither approved it nor asked for changes, and `StillToReview` filters the list by it in the job. Another forge adds its own `AccountJob`, filling the same records. `StartForgeJob` in `umain.forge.inc` runs the job, one at a time, when the page is shown (`ShowForge`) and on Refresh; `ForgeJobDone` keeps the login, the two lists and the error (`FForgeLogin`, `FForgeMine`, `FForgeReview`, `FForgeError`, kept across repositories since they are the user's, cleared when gh goes), gives `FPullLogin` the login when the pull request job has not asked yet, and `UpdateForgePage` hands them to the page; the done job goes to `FBlameZombies`. The page has the forge's name with "Pull requests" after it, the login under them with "Asking GitHub…" while the job runs and Refresh at the right, the error in the error color, then two columns, "Your open pull requests" and "Waiting for your review" with their counts, under each other when the page is narrower than `TwoColumnsMin` (760); a column with nothing says so once the forge has answered. Under the left heading, while the user has open pull requests, a checkbox, "Hide the ones without feedback" (painted: a rounded box filled in the link color with a check when on, the caption underlined under the mouse), leaves out the ones without `Feedback` (`HideWithoutFeedback`, `WithFeedback`, tested; the cards shown kept in `FShownMine`, which a click picks from), the heading then counting "1 of 3 open" and, when it hides them all, saying "Nobody has commented on or reviewed any of them yet."; `OnHideChange` (`ForgePageHideChange`) keeps it in the settings, `HideWithoutFeedback` in `[GitHub]`, off by default, and the page starts from it. A card per pull request: the number dimmed and the title in bold, at the right the state (Draft, Approved, Changes requested, Review required) and the checks ("✓ checks", "checks failing", "checks pending") as chips in the Pull Requests page's colors and "Asked again" in the warning color on one the user reviewed and is asked for again, under them the repository, who opened it (left out when it is the user), when it was opened and, when later, last changed, with "GitHub ↗" (`OnOpenUrl`) at the right end. A card fills under the mouse and a click raises `OnPick`; `ForgePagePick` compares with the pull request (`ComparePull`, the record turned into a `TGittanPullRequest`) when the open repository has a remote for its repository (`TGittanRepo.HasRemoteFor`), else opens it on GitHub. The content is painted on a measuring canvas first (`Layout`) so the height is known before the page is shown.

# GitHub: pull requests and review comments

Read this when touching `gittan.github`, `gittan.reviews`, `umain.reviews.inc`, `gittan.pullpage`, `umain.pulls.inc`, the pull request chip, the Pull Requests page or Compare With > Pull Requests.

- `gittan.github.pp` (no LCL, tested in `tests/testgithub.pp`) reads what gh prints with `--json`: `TGittanPullRequest` (number, title, state, review decision, URL, head and base branch, author, draft) through `ParsePullRequest` and `ParsePullRequests` (fpjson), `PullRequestStatus` gives the one-line "PR #12 · Approved" (the status bar's hint; the bar itself draws the parts, see the status bar in window-chrome.md, with the state from `PullRequestNote`) (Merged, Closed, Draft, Changes requested, Review required, or the number alone) followed by the checks of the head commit when there are any (`PullRequestChecks`, from `statusCheckRollup`: "checks ✓", "2 checks failing" or "3 checks pending"; a CheckRun counts by its conclusion once completed, a StatusContext by its state), and `RepoPathOfUrl` the "owner/repo" of a GitHub address. `TGittanPullRequestJob` runs `gh pr view` (no selector: gh takes the checked-out branch and knows its fork), `gh pr list --state open --limit 50` and, when the list came, `gh pr list` again with `--search review-requested:@me` (GitHub's own search, which knows who gh is logged in as and the teams they are on) for the open pull requests waiting for the user's review (`ReviewPulls`, empty when gh could not list them), less the ones the user has already reviewed: a review given clears a personal request but not one made of a team the user is on, so the job asks gh for the login (`gh api user --jq .login`, once: `Login` after the job, which `FGitHubLogin` hands to the next one, cleared when gh goes) and `WithoutReviewed` (tested) leaves out a pull request whose latest review by that login (`latestReviews`, read into `Reviews` as login and state) approved it or asked for changes, keeping one only commented on or whose review was dismissed; in a thread, like the blame job. `StartPullJob` in `umain.actions.inc` runs it from `LoadRepository` once per repository and branch (`FPullKey`), from View > Refresh always, and from `FPullTimer`, which `PullJobDone` sets after every job that gh answered: `PullPollPending` (30 s) while the pull request has checks pending, else `PullPollIdle` (5 min), so the status bar follows the checks, a review and a new pull request; a poll keeps the data shown while gh runs (`AKeep`), and `AbandonPullJob` stops the timer; `PullJobDone` keeps the result (`FHasPull`, `FPull`, `FPulls`, `FPullError`), and the finished job goes to `FBlameZombies`. `UpdateStatus` adds the branch's pull request after the base label; the status bar's menu gets Open Pull Request and Copy Pull Request URL with gh. View > Compare With > Pull Requests (with gh) lists the open pull requests as radio items (`RebuildPullMenu`: "Loading...", gh's message or "No open pull requests" while there is nothing to list); choosing one (`MenuComparePullClick`, `ComparePull`) runs `TGittanRepo.FetchPullRequest` as a remote job (`rkFetchPull`, `StartPullFetch`; the number in `Arg`, the base in `Branch`, the fetched ref back in `HeadRef`), so the window goes on while it fetches and the status bar says "Fetching pull request #N..."; `PullFetchDone` compares, and a failure gets the remote job's notice with git's reason and Try Again; `git fetch --no-tags <remote> <base> +refs/pull/N/head:refs/gittan/pr/N`, with the remote `RemoteFor` finds for the pull request's owner/repo (else origin, else the first), and sets the base to the three-dot range `<remote>/<base>...refs/gittan/pr/N` (kept in `FPullRange`, numbered `FPullNumber`), which `BaseLabel` names "vs PR #N" and `RebuildCompareMenu` leaves out of the ref list. A failed fetch is a summary notice.
- The Pull Requests page (`TGittanPullPage`, `gittan.pullpage.pp`, painted like the Repository page in the same box, `FView = gvPulls`; `umain.pulls.inc`) lists the open pull requests the job read (`FPulls`), from the sidebar's Pull Requests row (`navPulls`, `niPull`, a branch's commit meeting the trunk), View > Pull Requests (Cmd+6, `FPullsItem`) and All Pull Requests in the list the status bar's chip drops (`paList`); the row (`TGittanSideNav.SetRowVisible`) and the item show only while gh is found (`UpdateGitHubItems`, which also leaves the page for the summary when gh goes). The page has the repository's name with "Pull Requests" after it and under them the "owner/repo" of the first pull request's address (`RepoPathOfUrl`, else the root), with "Asking GitHub…" after it while the job runs (`SetPulls` with `ALoading`, keeping what it had). The branch's own pull request (`SetBranchPull`, `FHasPull`, `FPull`) stands first under "This branch", also when it is merged or closed; then "Open pull requests" with the count and Refresh at the right (`OnRefresh`: `StartPullJob(True, True)`, not while one runs), gh's message in the error color when it failed, or "No open pull requests". A card per pull request: the number dimmed and the title in bold, at the right the state as a chip (`PullRequestNote`: Merged in the link color, Approved in the ok color, Changes requested in the error color, Draft, Closed and Review required dimmed) and the checks as one ("✓ checks", "2 failing", "3 pending" in the ok, error and warning colors), under them who opened it, "head → base", when it was opened and, when later, last changed (`ReviewAge` against `LocalTimeToUniversal(Now)`), "+120 −30 in 4 files" and its labels, with "GitHub ↗" (`OnOpenUrl`) at the right end; one waiting for the user's review has a "Needs your review" chip in the warning color before the state (`SetReviewPulls` with the job's `ReviewPulls`, kept in `FReviewPulls` and handed over by `UpdatePullPage`; `NeedsReview` looks its number up). For these gh is asked for `createdAt`, `updatedAt`, `additions`, `deletions`, `changedFiles` and `labels` too (`PullRequestFields`; `Created` and `Updated` in UTC, `Labels` the names joined with ", ", tested). A card fills under the mouse and a click compares with its pull request (`OnCompare`, `ComparePull`, as the menu does); the one compared against (`SetComparing` with `FPullNumber` while the base is `FPullRange`, from `UpdatePullPage` and `UpdateStatus`) has a stripe in the link color and a Comparing chip, and a click on it goes back to the working tree (`OnWorkingTree`, `SetBase('')`). `UpdatePullPage` hands the job's state to the page when a job starts and ends and when the page is shown; showing the page asks gh again (`ShowPulls`). The content is painted on a measuring canvas first (`Layout`, as the Commands page does) so the height is known before the page is shown.
- The summary (Home) counts the pull requests waiting for the user's review in one row under the conversation, so they are seen as the repository opens without taking the room a card each took: the pull request icon and "3 pull requests need your review" (`TGittanSummary.SetReviewPulls`, from `PullJobDone` with the job's `ReviewPulls`; cleared when a job starts afresh and when gh goes; nothing with none), a chip with a dimmed chevron while `OnReviewClick` is set, filled with the hover color under the mouse. A click drops `FReviewPopup` from the chip (`SummaryReviewClick` in `umain.pulls.inc`): "Needs your review" as its header, a row per pull request with "#12 Title" and, dimmed, who opened it, when and "draft" for one (`ReviewPullLine` in `gittan.summary.pp`; the branches are left out, since the list is at most 440 wide and the detail takes its room from the title), the one compared against checked, then All Pull Requests; a pick compares with its pull request (`ReviewPopupPick`, `ComparePull`, as a card of the page does), which puts its review comments in the change view, and All Pull Requests opens the page (`ShowPulls`). The row's height goes into the layout before the paint (`LayoutReview`), as the conversation's does, a clean tree with the row is not centered (`CentersClean`), and the job's result is compared with what is shown (`SamePulls`) so a poll that finds the same does not repaint.
- The change view shows the findings of an AI review among these threads, in a list of its own with them (`FShown`; see ai.md). View > Review Comments (Cmd+Shift+M, `ReviewComments` in the settings, on by default) shows the review threads of a pull request in the change view, each in a card under the line it is on (`umain.reviews.inc`, `gittan.reviews.pp`, the latter without LCL and tested in `tests/testreviews.pp`). `TGittanReviewJob` asks gh for them with `gh api graphql` (`ReviewThreadsQuery`, a page of 100 threads at a time, owner and name from the pull request's URL) and `ParseReviewThreads` reads each thread's path, line (or start line, original line, side), resolved, outdated and file-level state and comments. `ReviewTarget` picks the pull request: the one compared against (Compare With > Pull Requests), whose diff is the one the comments were made on, else the branch's own while the new side is the work tree; `PullJobDone` asks again at the pull request's poll, `SetBase` when the comparison changes, and `ThreadsKey` keeps a poll that finds the same from rebuilding the view. `PlaceThreads` (from `BuildChangeView`, once the lines are numbered) finds each thread's diff line in `FThreadRows`: in the pull request's own diff as it is, else the head's line mapped onto the work tree with `MapLine` over `git diff -U0 <head> -- path` (kept in `FMapDiff` until the file is shown again); a comment on a removed line only where the old side is the pull request's base (its diff, or the merge base with the default branch). One that cannot be placed (outdated, on the whole file, on a removed line not shown) goes to the top of the file. Hide Unchanged Lines keeps a commented line. The cards are the editor's gaps (`TATGaps`, `ApplyReviewGaps`): room under a line painted by `OnDrawGap` (`EditDrawGap`), outside the text, so the lexer, the numbers and `FRows` are untouched; a gap's Tag is the thread, and side by side the other editor gets an empty gap of the same height (Tag -1) so the rows stay in step, with `MatchScrollPixels` putting the old side at the same pixel, since `LineTop` alone loses the part of a tall gap scrolled into. `ReviewLayout` lays a card out in the interface font (code between ``` fences in the editor's, a suggestion block labeled) at the width its last paint had (`FReviewWidths`, laid out again when it changes), measured on `FReviewMeasure`. A resolved or outdated thread starts folded to one line; a click on a card folds or unfolds it (`FThreadFlips` by the first comment's URL, applied in `EditMouseUp` so the card does not change height under the button), a click on "GitHub ↗" opens it. Three editor quirks are worked around: the gutter of a line spans its gaps and gutter decor centers the change view's numbers in that height, so `DrawGapGutter` (from `OnDrawEditor`) paints the gutter over the gaps plain and puts the number back at its line; the block staples, drawn down a block of code after the text, run through the cards under its lines, so `DrawGapGutter` paints the cards again over them (`EditDrawGap` with the gaps' rects, under the last row of a wrapped line); and a gap before the first line shows only at scroll position -1, which every `LineTop := 0` leaves, so `RevealTopGapAsync` moves a view at its top up onto it. The status bar's pull request chip shows a speech bubble after its checks, with the number of open threads, dimmed when all are resolved or outdated (`SetPullThreads`, from `UpdateStatus` while the threads are the chip's pull request's), and its hint counts them (`ReviewHint`, the `HintComment` bubble). In the tree a file with threads gets the same bubble at the right end of its row with the number of open ones, gray when all are resolved or outdated (`FileTreeAdvancedCustomDrawItem` at `cdPostPaint`, `FileThreads`), and its hint says how many (`FileThreadsHint`). What is on no line, the pull request's own comments and the text a review was submitted with (what a reviewer writes with Request changes or Approve; such a review has no thread unless it also commented on lines), comes in the same query (`reviews(last:100)` and `comments(last:100)`, read from the first page by `ParsePullNotes` into `TGittanPullNotes`, oldest first; a review that only commented on lines, or is still pending, is left out, an approval, a request for changes or a dismissal is kept without text) and is shown in the summary under the header (`TGittanSummary.SetNotes`, from `ReviewJobDone`, cleared by `ClearReviews`): "Conversation of pull request #N", then a card per note with a stripe in the outcome's color (green approved, red requested changes), the author, what they did and when, a "GitHub ↗" link (`OnOpenUrl`) and the text wrapped to the width, at most `NoteMaxLines` lines.

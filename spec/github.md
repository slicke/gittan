# GitHub and the forges: pull requests and review comments

Read this when touching `TGittanForge` or adding a forge (with forges.md, the contract a new one fills in), `gittan.github`, `gittan.reviews`, `umain.reviews.inc`, `gittan.pullpage`, `umain.pulls.inc`, `gittan.forge`, `gittan.forgepage`, `uforge`, the pull request chip, the Pull Requests page, the forge view (the GitHub view) or Compare With > Pull Requests.

- A forge is the service that hosts a repository; Gittan reaches it through `TGittanForge` in `gittan.forge.pp` (no LCL, tested in `tests/testforge.pp`), and nothing outside the forge's own unit names it or runs its tool: the unit registers its class as it loads (`RegisterForge` in its `initialization`; `Gittan.lpr` lists the forges' units so they are linked), and the rest of Gittan makes one through `ForgeClass` (the first registered, nil while none is; `TGittanForgeClass`, the constructor virtual) and asks it for `CliName` the same way, so no unit in `src/ui` uses `gittan.github` (tested in `tests/testgithub.pp`). Another forge is a unit beside it that inherits `TGittanForge` and registers itself; a repository frame gets the forge of its remotes: the snapshot carries their URLs as git reaches them (`RemoteUrls`, from `ResolvedRemoteUrlsIn`: the remotes and the `url.<base>.insteadOf` rules in one `git config`, each URL rewritten by the longest rule it starts with, `ApplyInsteadOf`, tested; read in the watcher's thread), and when they change `ApplySnapshot` has the frame look again (`ReFindForge`: `FindForge`, true when the forge changed, then what the old one had found dropped and the menu items following), `ForgeClassFor` giving the first registered forge whose `HostsRemote` takes the host of one of them (`RemoteHost`: "github.com" of an https, ssh or user@host:path URL, '' of a local path; both tested with a forge on example.org in `tests/testforge.pp`), the remotes in order, the host of an ssh URL that no forge takes looked up in the user's `~/.ssh/config` and asked again (`SshHostName`, `UserSshConfig`, the config read only when the hosts as they are gave no forge and one of them is an ssh remote's, and then only the aliases looked up, `ForgeClassIn`: the HostName of the first Host block whose patterns match, with `*`, `?`, `!` and `%h`, a value in double quotes taken without them, Match blocks and Include not followed; tested), so `git@github-work:org/repo` with `Host github-work` / `HostName github.com` is GitHub, as gh itself takes it, nil when none does, so a repository without a remote, or with its remotes only on GitLab or Bitbucket, has no forge and shows none of the GitHub features (they would fail there); none without a repository either. GitHub's `HostsRemote` takes github.com (and www., ssh.) and the GitHub Enterprise hosts gh is logged in to, the top-level keys of its `hosts.yml` (`GhHosts`, tested; read from disk again only when the file's age or path changed, `GhLoggedHosts`, since every remote asks) in `GhConfigDir` (`GH_CONFIG_DIR`, else `GitHub CLI` in AppData on Windows, else `gh` in `XDG_CONFIG_HOME` or `~/.config`), and the host `GH_HOST` names when gh's environment gives the token gh takes for it, as gh logs in through the environment with no `hosts.yml` entry (`GhEnvHost`, tested: `GH_ENTERPRISE_TOKEN` or `GITHUB_ENTERPRISE_TOKEN` for an Enterprise Server, `GH_TOKEN` or `GITHUB_TOKEN` for a host under ghe.com). The forge view, which no repository decides, takes the first registered forge that is on and whose tool is found (`TForgeView.FindForge`), so turning GitHub off leaves the globe to the next forge; `App.ForgeCli` takes the forge class whose tool it finds (`ForgeClass` when none is given). The hosting features have one switch for every forge, `HostingEnabled` in `[Hosting]` (on unless turned off; a forge acts only on a repository with a remote on it, so a switch per forge would add little), and each registered forge its tool in a section of its own named after it (`[GitHub]` `Cli`, empty for the one found), which `TGittanSettings` reads and writes for every forge in `RegisteredForges` (`ForgeCliPath`, `SetForgeCliPath`, by the forge's `Name`, a class function; an older `[Tools]` key named after the tool, gh's `Gh`, and an older `Enabled` in a forge's section, GitHub's, are read once and dropped; tested). `App.ForgeCli` gives '' while the switch is off. The settings dialog's Hosting page has the switch, "Turn on the hosting features", with what it means, then a block per registered forge built in a loop (`FForges`, `FForgeEdits`, `FForgeNotes`: its name and its tool's field, the captions formatted with the forge's `Name` and `CliName`), then the clones' switch; the tools and the clones' switch follow the hosting switch (`HostingChange`), and About lists each forge's tool's version, or that the hosting features are off. `TSettingsValues` carries `HostingEnabled` and `ForgePaths`, the latter in the order of `RegisteredForges`. The class has the forge's `Name` ("GitHub", for menus, links and the sidebar), `CliName` and `Cli` (the tool and its path), `Version` (for About), three factories of jobs, each an abstract job of `gittan.forge` or `gittan.reviews` with its forge-specific part virtual: `PullJob` (`TGittanPullRequestJob`: `AskBranchPull`, `AskOpenPulls`, `AskReviewPulls`, `AskLogin`; the base runs them in order, filters with `WithoutReviewed` and finds the gone upstreams), `ReviewJob` (`TGittanReviewJob`: `Ask` fills the threads, the notes and the head commit) and `AccountJob` (`TGittanForgeJob`: `Ask` gives the login and the two lists; the base filters with `StillToReview`), `WebUrl` (the address of a `TGittanWebTarget`: a file at a line in a commit or on a branch, a commit, an issue, or a new pull request) and `PullRef` (the ref a remote serves a pull request's head at, which `FetchPullRequest` fetches). A job takes what it needs from the forge when it is made, so it may outlive the forge (the settings change while it runs). The records are the forge's too: `TGittanPullRequest`, `TGittanForgePull`, and their states as kinds, never a forge's words (`TGittanPullState`, `TGittanReviewDecision`, `TGittanReviewVerdict`, `TGittanChecksState`), with `PullRequestStatus`, `PullRequestNote`, `PullRequestChecks`, `ReviewDecisionNote`, `IssueNumber`, `WithoutReviewed`, `NeedsMyReview`, `StillToReview` and `WithFeedback`. GitHub is `TGittanGitHubForge` in `gittan.github.pp` (tested in `tests/testgithub.pp`), the only forge so far: its jobs (in the unit's implementation), the JSON gh prints read into the forge's records and kinds, and `RunGh`, through which every gh runs. A repository frame holds one forge in `FForge` (see git-core.md for `FindForge`), and the forge view of the window (`uforge.pp`) one of its own, found the same way. Another forge is a unit of its own beside `gittan.github` with a class of `TGittanForge`; what is left then is choosing a forge per repository by its remotes, and a forge view per forge.
- `gittan.github.pp` (no LCL, tested in `tests/testgithub.pp`) reads what gh prints with `--json` into `TGittanPullRequest` (`gittan.forge`; number, repository as owner/name from its address, state, review decision, URL, head and base branch, author, draft) through `ParsePullRequest` and `ParsePullRequests` (fpjson), `PullRequestStatus` gives the one-line "PR #12 · Approved" (the status bar's hint; the bar itself draws the parts, see the status bar in window-chrome.md, with the state from `PullRequestNote`) (Merged, Closed, Draft, Changes requested, Review required, or the number alone) followed by the checks of the head commit when there are any (`PullRequestChecks`, from `statusCheckRollup`: "checks ✓", "2 checks failing" or "3 checks pending"; a CheckRun counts by its conclusion once completed, a StatusContext by its state), and `RepoPathOfUrl` the "owner/repo" of a GitHub address, which the parser puts in the record's `Repo`, the path the rest of Gittan uses. GitHub's pull request job (`TGittanPullRequestJob`, from the forge's `PullJob`) runs `gh pr view` (no selector: gh takes the checked-out branch and knows its fork), `gh pr list --state open --limit 50` and, when the list came, `gh pr list` again with `--search review-requested:@me` (GitHub's own search, which knows who gh is logged in as and the teams they are on) for the open pull requests waiting for the user's review (`ReviewPulls`, empty when gh could not list them), less the ones the user has already reviewed: a review given clears a personal request but not one made of a team the user is on, so the job asks gh for the login (`gh api user --jq .login`, once: `Login` after the job, which `FPullLogin` hands to the next one, cleared when gh goes) and `WithoutReviewed` (tested) leaves out a pull request whose latest review by that login (`latestReviews`, read into `Reviews` as login and verdict) approved it or asked for changes, keeping one only commented on or whose review was dismissed, and one the login is asked for again in person after their review (`reviewRequests`, the users' logins in `Requested`); in a thread, like the blame job. `StartPullJob` in `umain.actions.inc` runs it from `LoadRepository` once per repository and branch (`FPullKey`), from View > Refresh always, and from `FPullTimer`, which `PullJobDone` sets after every job that gh answered: `PullPollPending` (30 s) while the pull request has checks pending, else `PullPollIdle` (5 min), so the status bar follows the checks, a review and a new pull request; a poll keeps the data shown while gh runs (`AKeep`), and `AbandonPullJob` stops the timer; `PullJobDone` keeps the result (`FHasPull`, `FPull`, `FPulls`, `FPullError`), and the finished job goes to `FBlameZombies`. `UpdateStatus` adds the branch's pull request after the base label; the status bar's menu gets Open Pull Request and Copy Pull Request URL with gh. View > Compare With > Pull Requests (with gh) lists the open pull requests as radio items (`RebuildPullMenu`: "Loading...", gh's message or "No open pull requests" while there is nothing to list); choosing one (`MenuComparePullClick`, `ComparePull`) runs `TGittanRepo.FetchPullRequest` as a remote job (`rkFetchPull`, `StartPullFetch`; the number in `Arg`, the base in `Branch`, the fetched ref back in `HeadRef`), so the window goes on while it fetches and the status bar says "Fetching pull request #N..."; `PullFetchDone` compares, and a failure gets the remote job's notice with git's reason and Try Again; `git fetch --no-tags <remote> <base> +refs/pull/N/head:refs/gittan/pr/N` (the source ref from the forge's `PullRef`, given to the remote job as `PullRef`), with the remote `RemoteFor` finds for the pull request's owner/repo (else origin, else the first; `HasRemoteFor`, tested, says whether one holds the path at all, for the GitHub page), and sets the base to the three-dot range `<remote>/<base>...refs/gittan/pr/N` (kept in `FPullRange`, numbered `FPullNumber`), which `BaseLabel` names "vs PR #N" and `RebuildCompareMenu` leaves out of the ref list. A failed fetch is a summary notice.
- The Pull Requests page (`TGittanPullPage`, `gittan.pullpage.pp`, painted like the Repository page in the same box, `FView = gvPulls`; `umain.pulls.inc`) lists the open pull requests the job read (`FPulls`), from the sidebar's Pull Requests row (`navPulls`, `niPull`, a branch's commit meeting the trunk), View > Pull Requests (Cmd+Option+6, Ctrl+Shift+6 elsewhere, `FPullsItem`) and All Pull Requests in the list the status bar's chip drops (`paList`); the row (`TGittanSideNav.SetRowVisible`) and the item show only while gh is found (`UpdateForgeItems`, which also leaves the page for the summary when gh goes). The page has the repository's name with "Pull Requests" after it and under them the "owner/repo" of the first pull request (`Repo`, else the root), with "Asking GitHub…" (the forge's name, `SetForge`) after it while the job runs (`SetPulls` with `ALoading`, keeping what it had). The branch's own pull request (`SetBranchPull`, `FHasPull`, `FPull`) stands first under "This branch", also when it is merged or closed; then "Open pull requests" with the count and Refresh at the right (`OnRefresh`: `StartPullJob(True, True)`, not while one runs), gh's message in the error color when it failed, or "No open pull requests". A card per pull request: the number dimmed and the title in bold, at the right the state as a chip (`PullRequestNote`: Merged in the link color, Approved in the ok color, Changes requested in the error color, Draft, Closed and Review required dimmed) and the checks as one ("✓ checks", "2 failing", "3 pending" in the ok, error and warning colors), under them who opened it, "head → base", when it was opened and, when later, last changed (`ReviewAge` against `LocalTimeToUniversal(Now)`), "+120 −30 in 4 files" and its labels, with "GitHub ↗" (`OnOpenUrl`) at the right end; one waiting for the user's review has a "Needs your review" chip in the warning color before the state (`SetReviewPulls` with the job's `ReviewPulls`, kept in `FReviewPulls` and handed over by `UpdatePullPage`; `NeedsReview` looks its number up). For these gh is asked for `createdAt`, `updatedAt`, `additions`, `deletions`, `changedFiles` and `labels` too (`PullRequestFields`; `Created` and `Updated` in UTC, `Labels` the names joined with ", ", tested). A card fills under the mouse and a click compares with its pull request (`OnCompare`, `ComparePull`, as the menu does); the one compared against (`SetComparing` with `FPullNumber` while the base is `FPullRange`, from `UpdatePullPage` and `UpdateStatus`) has a stripe in the link color and a Comparing chip, and a click on it goes back to the working tree (`OnWorkingTree`, `SetBase('')`). `UpdatePullPage` hands the job's state to the page when a job starts and ends and when the page is shown; showing the page asks gh again (`ShowPulls`). The content is painted on a measuring canvas first (`Layout`, as the Commands page does) so the height is known before the page is shown.
- Branch > Create Pull Request... (`FNewPullItem`, shown while there is a forge) and the same item in the status bar's menu (`FNewPullPopItem`) open the forge's page for a new pull request from the current branch (`CreatePull` in `umain.pulls.inc`), enabled by `CanCreatePull`: a forge, a branch, not the default branch (`FDefaultBranch` without its remote), no merge or rebase going on, no push or commit running, not a current branch whose pull request is open (`FHasPull` with `prOpen`; after one merged or closed another may follow) or another branch whose name on its remote is the head of one of the open pull requests listed (`FPulls`), and not the current branch before its first commit (`FSnapHead` empty). A branch with no upstream is asked whether to push it first (Push and Open: `rkPushBranch` to the remote `RemoteFor('')` gives, `push -u`); a branch with commits not pushed is asked the same, with Open Anyway beside it: the current one counted by the snapshot (`FAhead`, pushed with `rkPush`), another (the one a push banner offered) against its upstream (`CountCommits`, pushed with `rkPushBranch`; only while its upstream has its own name, the branch `rkPushBranch` pushes to). The push asked for is `FPullAfterPush`: when it works, `PushedBanner` shows its success and opens the page; when it fails, or another remote job ends first (any kind, a pull request's fetch or a clone included, `RemoteJobDone` dropping it before the kinds that end early), it is dropped. Any other push that works (`rkPush`, `rkPushBranch`) shows its success with Create Pull Request by it while `CanCreatePull` holds for the branch (`FPushedBranch`, `NewPullBannerClick`). `OpenNewPull` takes the branch as its upstream names it on its remote and the path of the repository the remote's push URL holds (`remote get-url --push`, `RemoteRepoPath` in `gittan.forge.pp`, tested in `TestRemoteRepoPath`) into a `NewPullTarget`, unless the push URL is on no host of the frame's forge (`ForgeClassFor` of it, the forge having been found by another remote), which gives a note in the status bar (`rsNewPullOtherHost`) and no page; GitHub's `WebUrl` asks gh for the repository's address (`gh browse --no-browser` with no target, which is gh's default repository, the parent of a fork when it is set) and `GitHubNewPullUrl` (tested in `TestNewPullUrl`) makes its compare page of it, `<repo>/compare/<branch>?expand=1`, the branch escaped and given as `owner:branch` when it is pushed to another repository.
- The summary (Home) counts the pull requests waiting for the user's review in one row under the conversation, so they are seen as the repository opens without taking the room a card each took: the pull request icon and "3 pull requests need your review" (`TGittanSummary.SetReviewPulls`, from `PullJobDone` with the job's `ReviewPulls`; cleared when a job starts afresh and when gh goes; nothing with none), a chip with a dimmed chevron while `OnReviewClick` is set, filled with the hover color under the mouse. A click drops `FReviewPopup` from the chip (`SummaryReviewClick` in `umain.pulls.inc`): "Needs your review" as its header, a row per pull request with "#12 Title" and, dimmed, who opened it, when and "draft" for one (`ReviewPullLine` in `gittan.summary.pp`; the branches are left out, since the list is at most 440 wide and the detail takes its room from the title), the one compared against checked, then All Pull Requests; a pick compares with its pull request (`ReviewPopupPick`, `ComparePull`, as a card of the page does), which puts its review comments in the change view, and All Pull Requests opens the page (`ShowPulls`). The row's height goes into the layout before the paint (`LayoutReview`), as the conversation's does, a clean tree with the row is not centered (`CentersClean`), and the job's result is compared with what is shown (`SamePulls`) so a poll that finds the same does not repaint.
- The change view shows the findings of an AI review among these threads, in a list of its own with them (`FShown`; see ai.md). View > Review Comments (Cmd+Shift+M, `ReviewComments` in the settings, on by default) shows the review threads of a pull request in the change view, each in a card under the line it is on (`umain.reviews.inc`, `gittan.reviews.pp`, the latter without LCL and tested in `tests/testreviews.pp`). GitHub's review job (`TGittanReviewJob`, from the forge's `ReviewJob`) asks gh for them with `gh api graphql` (`ReviewThreadsQuery` in `gittan.github`, a page of 100 threads at a time, owner and name from the pull request's URL) and `ParseReviewThreads` (`gittan.github`) reads each thread's path, line (or start line, original line, side), resolved, outdated and file-level state and comments. `ReviewTarget` picks the pull request: the one compared against (Compare With > Pull Requests), whose diff is the one the comments were made on, else the branch's own while it is open and the new side is the work tree (a merged or closed one shows neither threads nor its conversation: its review is over, and a long-lived branch such as develop always has one behind it, whose comments would land on today's lines); `PullJobDone` asks again at the pull request's poll, `SetBase` when the comparison changes, and `ThreadsKey` keeps a poll that finds the same from rebuilding the view. `PlaceThreads` (from `BuildChangeView`, once the lines are numbered) finds each thread's diff line in `FThreadRows`: in the pull request's own diff as it is, else the head's line mapped onto the work tree with `MapLine` over `git diff -U0 <head> -- path` (kept in `FMapDiff` until the file is shown again); a comment on a removed line only where the old side is the pull request's base (its diff, or the merge base with the default branch). One that cannot be placed (outdated, on the whole file, on a removed line not shown) goes to the top of the file. Hide Unchanged Lines keeps a commented line. The cards are the editor's gaps (`TATGaps`, `ApplyReviewGaps`): room under a line painted by `OnDrawGap` (`EditDrawGap`), outside the text, so the lexer, the numbers and `FRows` are untouched; a gap's Tag is the thread, and side by side the other editor gets an empty gap of the same height (Tag -1) so the rows stay in step, with `MatchScrollPixels` putting the old side at the same pixel, since `LineTop` alone loses the part of a tall gap scrolled into. `ReviewLayout` lays a card out in the interface font at the width its last paint had (`FReviewWidths`, laid out again when it changes), measured on `FReviewMeasure`. A comment's body is Markdown, drawn as the Markdown preview's LazInk draws it, but on the canvas, since a card is a gap and not a control: `CommentParts` (`gittan.reviews`, tested) first cuts the body at its `<details>` blocks, each a part with its summary and depth (a block holds the deeper parts after it), and makes Markdown of the HTML bots write (CodeRabbit's): HTML comments go, an `<img>` becomes its alt text, an `<a href>` a Markdown link, block tags a line break or a blank line, a heading bold text; code, fenced or in backticks, is left alone. `CommentMarkdown` joins the top parts with each block folded to "▸" and its summary (the folded card's first line). `ReviewSegments` (kept by the body in `FReviewSegments`, emptied by `ClearReviews`, when other threads come and in `ApplySnapshot`, since the paths it links are the files of the work tree) cuts the parts at the fences, each line's kind, depth, block and comment packed in its Objects (`ReviewRow`, `RowKind`, `RowDepth`, `RowDetail`, `RowComment`): a block's summary is an `rlDetails` line, dimmed after "▸", or after "▾" with the lines in it, indented `ReviewIndent` per level with a rule down the left of each, when it is open; a click on it opens or closes it when the button comes up, as a card folds (`DetailsKey`, the thread's id, the comment and the part, kept in `FThreadFlips`). The text between fences is one `rlMarkup` line in LazInk's inline markup (`MarkdownToInk` with `imoInlineHTML`, so only the inline tags it trusts pass), measured (`ReviewRowHeight`, `HTMLTextExtentOpt`) and drawn (`HTMLDrawOpt`) at the card's width through one layout cache (`FReviewInk`), links in the link color; a fence's lines are code in the editor's font, a suggestion block labeled. A folded card shows the first line of text without its markup. A resolved or outdated thread starts folded to one line; a click on a card folds or unfolds it (`FThreadFlips` by the first comment's URL, applied in `EditMouseUp` so the card does not change height under the button), a click on "GitHub ↗" opens it, one on a link in a comment that goes to the web opens the link (`HTMLHitTest`, `OpenCommentLink`). A path in a comment's text that is a file of the work tree (`RepoFileExists`) is a link to it: `LinkFilePaths` (`gittan.reviews`, tested) makes one of each path with a / or a . in it that its callback says is a file (`TGittanPathTest`), with the line when ":42", ":42-50" or "#L42" follows, and of a code span that holds only such a path, leaving links (a bracket whose own closing bracket, nested ones counted, is right before a parenthesis; a task's `[ ]` or an index is text), URLs, tags and fenced code alone, as `gittan-file:path#L42` (`FileLinkScheme`, read back by `FileOfLink`); a click on it shows the file when `RepoFileExists` still finds it (which takes no path that `..` leads out of the root, an absolute one read under it, since a comment can write such a link itself; else nothing happens, and it never goes to the browser) (`ShowFileLine`: `ShowRepoFile`, then the caret on the row of the new side holding the line, in the middle of the view, the gap hiding it opened), from a card once the button is up and the editor done with the click (`FGapLink`, `OpenGapLinkAsync` from `EditMouseUp`), since the new file would otherwise get the caret where the button came up. The forge's address of a file (`FileOfWebUrl`; GitHub's `GitHubFileOfUrl`, tested: `/owner/name/blob/<ref>/path#L10`) of a repository a remote holds (`HasRemoteFor`) is shown in Gittan the same way when the file is in the work tree, else opens in the browser. Three editor quirks are worked around: the gutter of a line spans its gaps and gutter decor centers the change view's numbers in that height, so `DrawGapGutter` (from `OnDrawEditor`) paints the gutter over the gaps plain and puts the number back at its line; the block staples, drawn down a block of code after the text, run through the cards under its lines, so `DrawGapGutter` paints the cards again over them (`EditDrawGap` with the gaps' rects, under the last row of a wrapped line); and a gap before the first line shows only at scroll position -1, which every `LineTop := 0` leaves, so `RevealTopGapAsync` moves a view at its top up onto it. The status bar's pull request chip shows a speech bubble after its checks, with the number of open threads, dimmed when all are resolved or outdated (`SetPullThreads`, from `UpdateStatus` while the threads are the chip's pull request's), and its hint counts them (`ReviewHint`, the `HintComment` bubble). In the tree a file with threads gets the same bubble at the right end of its row with the number of open ones, gray when all are resolved or outdated (`FileTreeAdvancedCustomDrawItem` at `cdPostPaint`, `FileThreads`), and its hint says how many (`FileThreadsHint`). What is on no line, the pull request's own comments and the text a review was submitted with (what a reviewer writes with Request changes or Approve; such a review has no thread unless it also commented on lines), comes in the same query (`reviews(last:100)` and `comments(last:100)`, read from the first page by `ParsePullNotes` into `TGittanPullNotes`, oldest first; a review that only commented on lines, or is still pending, is left out, an approval, a request for changes or a dismissal is kept without text) and is shown in the summary under the header (`TGittanSummary.SetNotes`, from `ReviewJobDone`, cleared by `ClearReviews`): "Conversation of pull request #N", then a card per note with a stripe in the outcome's color (green approved, red requested changes), the author, what they did and when, a "GitHub ↗" link (`OnOpenUrl`) and the text, its Markdown drawn as a review card's is (`CommentParts`, each part through `MarkdownToInk` and `HTMLDrawOpt` in the summary's own layout cache, `FInk`; the parts and their markup are made once per `SetNotes`, `FNoteParts` and `FNoteMarkup`, so a new width lays them out again without parsing them or asking for the files again; a row of `TGittanSummaryNoteBox.Rows`) at the card's width, a `<details>` block as its summary after "▸" that a click opens (after "▾", the parts in it indented `NoteIndent` per level with a rule, `FNotesOpen` by the note's address and the part, `NoteDetailsAt`, the hand cursor over it), at most `NoteMaxLines` lines high with an ellipsis and "Show more" after unless a block in it is open, a click on which shows the whole text with "Show less" under it (`NoteMoreAt`, the note's key with part -1 in `FNotesOpen`); a link in it that goes to the web, or to a file of the repository (`LinkFilePaths` through `OnFileExists`, as in a review card), goes to `OnOpenUrl` (`TextLinkAt`, the hand cursor over it), which is `OpenCommentLink`.
- The forge view (`TForgeView`, `uforge.pp`) shows the user's pull requests across every repository of the forge, in the window over the repository frames rather than in one of them, since they are the user's and not a repository's: one for the window (`FForgeView` in `uwindow.pp`), made after the first frame and shown from the globe at the right end of the window's top chrome (the tab strip on macOS, the own title bar on Windows and GTK 3; window-chrome.md), which is there only while there is a forge (`UpdateForgeChrome`, `TForgeView.HasForge`; `App.ForgeCli` gives gh's path, '' while GitHub is off or gh is not found, and the view's `FindForge` makes its forge of it (the first registered forge whose tool is found, kept through `KeepForge` as a frame's is), again on `SettingsChanged`, where a forge that changed drops what the old one found and the job it ran, and asks the new one at once while the view is shown, and a forge that is gone takes the view and the globe with it). `ShowForgeView` puts the view over the frame shown with its own menu (and the application menu's items on macOS), the forge's name as the caption and the title bar's shade whole, puts the view's own tabs in the strip in place of the frames' (below) and counts the frame as in the background (`IsActive` is false for it, so it leaves the chrome alone and marks its news); the globe again, Escape, File > Close GitHub (Cmd+W) or a repository opening hides it (`HideForgeView`, `ActivateFrame`), and the frame takes the window back (`Activated`). The view's menu has the items that mean something without a repository, New Tab, Open Repository..., Open Recent (built as the File menu opens), Close GitHub, Refresh (Cmd+R), Next and Previous Tab (the view's tabs), Settings..., Check for Updates... and About; the ones that need the window or a dialog go through `TRepoWindow` (`AskOpenRepository`, `ShowSettings`, `ShowAbout`), which runs them in the frame under the view (its `MenuOpenRepoClick`, `MenuSettingsClick`, `MenuAboutClick`, public for it). The view holds the page (`TGittanForgePage`, `gittan.forgepage.pp`, painted like the Pull Requests page) in a scroll box of its own under the title bar's strip (`BorderSpacing.Top`), in the page's palette for the appearance (`SetTheme`, the colors the Pull Requests page has; a timer follows the appearance while the view is shown, as a frame's `ThemeTimer` does). It is written for more than one forge: `gittan.forge.pp` has `TGittanForgePull` (the repository as "owner/name", number, title, URL, author, branches, state, review decision, the head commit's checks as one word, the state of the user's latest review of it, whether they are asked for one in person now, and `Feedback`: whether someone other than its author, and not a bot, has commented on it or reviewed it, among its last thirty comments and last thirty reviews; a deleted user counts as someone else) and `TGittanForgeJob`, a thread whose forge-specific part is `Ask`; GitHub's (from the forge's `AccountJob`) runs `gh api graphql` with `ForgeQuery` (`gittan.github`), one query for the viewer's login and two searches, `is:pr is:open author:@me` and `is:pr is:open review-requested:@me`, fifty each, newest changed first, each node with `viewerLatestReview`, `viewerLatestReviewRequest`, the authors (`__typename` and login) of its last thirty `comments` and `reviews` and the last commit's `statusCheckRollup`; `ParseForgeAnswer` reads it (the first GraphQL error's message as the error). The review search keeps a pull request asked of a team the user is on after their review, so `NeedsMyReview` keeps one the user is asked for in person now (a request made again after their review) or whose latest review by them neither approved it nor asked for changes, and `StillToReview` filters the list by it in the job. Another forge adds its own `AccountJob`, filling the same records. `TForgeView.StartJob` runs the job, one at a time, when the view is shown (`Shown`) and on Refresh, with the user's folder as gh's working directory, since no repository is needed; `JobDone` keeps the login, the two lists and the error (`FLogin`, `FMine`, `FReview`, `FError`, cleared when gh goes) and `UpdatePage` hands them to the page; a done or abandoned job goes to the view's own zombie list (`FZombies`, a `TGittanJobReaper` as the frame's `FBlameZombies`), freed once its thread has ended and waited for on the way out. The page's content is no wider than `MaxContentWidth` (960), centered in a wider page. Its head has the login's initial in a disc of the link color (empty in the hover fill before the forge has answered), the forge's name with "Pull requests" after it and Refresh (↻ in a round button, filled under the mouse) after that, a dot pulsing in Refresh's place while the job runs (`FPulse`), and under them the login with "2 open · 1 to review", or "Asking GitHub…" while the job runs; then the error in the error color, then one section (`Section`, `fsMine` or `fsReview`): "Your open pull requests" or "Waiting for your review" with its count. The sections are the view's tabs, which the window's tab strip (the macOS toolbar's, the own title bar's on Windows and GTK 3) shows in place of the frames' while the view is shown, as fixed tabs, without crosses or a plus (`SetTabs`' `AFixed`): "Open" and "Waiting for review" (`SectionCaption`, `SectionCount`; another section is another tab), the latter with the news dot while something waits for the user's review (`TForgeView.Tabs`); `UpdateTabs` in `uwindow.pp` takes them from the view, whose `OnTabsChange` (on every `UpdatePage` and tab change) has the strip follow. A click on one, Cmd+digit, Ctrl+Tab and Go > Next and Previous Tab change the section (`SelectTab`, `StepTab`; the window's `TabSelect`, `FormKeyDown` and `StepTab` hand them to the view while it is shown), which the view keeps until the app quits. A column with nothing says so, once the forge has answered (the view starts the job before it updates the page, so the lists of before are not taken as the answer), in a card of its own with a large dim glyph: a pull request's for the Open section, a check in a ring and "All caught up" for the other. At the right of a section's heading, or on a line of their own under it when they do not fit there, while the section has pull requests, its filters are chips (a rounded outline with the caption dim, filled under the mouse; on, a tint of the link color with the caption and the outline in it): "With feedback", "Needs attention", "No drafts" and "Stale" on Open, "Asked of me" and "No drafts" on Waiting for review (`MineChips`, `ReviewChips`). They are `TGittanForgeFilter`s in `gittan.forge` (`ffFeedback`: `Feedback`; `ffAttention`: `NeedsAttention`, changes requested or checks failing; `ffNoDrafts`; `ffAskedOfMe`: `Requested`, asked in person, not only through a team; `ffStale`: `IsStale`, unchanged for `StaleDays` (30) by its last change, else its opening, to clean up), every one on must pass at the time given (`FilterPulls`, tested); a click on a chip turns it on or off (`MineFilters`, `ReviewFilters`; the cards shown kept in `FShownMine` and `FShownReview`, which a click picks from), the heading then counting "1 of 3 open" and, when they leave none, the empty card saying "None of them match the filters."; `OnFilterChange` (`TForgeView.PageFilterChange`) keeps them in the settings, a flag each in `[GitHub]`: `HideWithoutFeedback`, `OnlyNeedsAttention`, `HideDrafts`, `OnlyAskedOfMe`, `HideReviewDrafts`, `OnlyStale`, off by default, which the page starts from (`LoadFilters`). A card per pull request: a pull request glyph (painted, in the ok color, dimmed for a draft), the number dimmed and the title in bold, at the right the state (Draft, Approved, Changes requested, Review required) and the checks ("✓ checks", "checks failing", "checks pending") as chips in the Pull Requests page's colors and "Asked again" in the warning color on one the user reviewed and is asked for again, under them the repository in the text color, then dimmed who opened it (left out when it is the user), how long ago it was opened and, when later, last changed (`RelativeAge` in `gittan.reviews`, tested: `ReviewAge` up to a month, then months and years rather than the date), with "GitHub ↗" (`OnOpenUrl`) at the right end while the card is under the mouse (its place a link all the same; the card and its links are under the mouse together, so the card stays filled on them). A pull request with a local clone has a third line with "Open ~/path/to/clone" under that link (`ShortPath`, in `gittan.textfit`, its path cut at its start to the card), left out when the clone is the repository `SetOpenRoot` names (the view names none, since several may be open). The clone comes from the job: `StartJob` gives it the recent repositories (`Clones`, newest first, the open one among them), and after the forge has answered `FindClones` (`gittan.forge`, tested against repositories made for the test) puts in each pull request's `Clone` the first of them one of whose remotes holds its repository, in the job's thread: `RemoteUrlsIn` (`gittan.git`) reads a repository's remotes with one git, and `RemoteUrlsHold` matches "owner/name" as `HasRemoteFor` and `RemoteFor` do, after a slash or the colon of `user@host:` and followed by nothing, `.git` or a slash, so `notme/bar` is not `me/bar` (on any remote, so a fork's clone with the original as `upstream` counts; a folder gone or no repository is passed over). Beyond the recent list it looks only while `CloneSiblings` is on (the Hosting page's Look for clones beside the recent repositories, off by default; the job's `Siblings`): `AddSiblingRepositories` (tested) then adds after them the folders beside each, in its parent folder, that hold a `.git` (a folder, or the file a worktree has), in name order, one level down and not again beside those. A card fills under the mouse and a click raises `OnPick`, as a click on its clone's link does; `TForgeView.PagePick` asks the window (`TRepoWindow.ComparePullRequest`, the record turned into a `TGittanPullRequest` by `PullRequestOf` in `gittan.forge`, tested) to compare with the pull request in the frame that has a remote for its repository (`TRepoFrame.HasRemoteFor`, `ComparePull`), which the window shows, else, when it has a clone still there, to open the clone (`OpenRepository` with `ForgeCloneOpened`, the pull request kept in the window's `FForgeClonePull`) and compare with it there once it is open; when the window can do neither, the view opens it on GitHub. The content is painted on a measuring canvas first (`Layout`) so the height is known before the page is shown.

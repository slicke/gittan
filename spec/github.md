# GitHub: pull requests and review comments

Read this when touching `gittan.github`, `gittan.reviews`, `umain.reviews.inc`, the pull request chip or Compare With > Pull Requests.

- `gittan.github.pp` (no LCL, tested in `tests/testgithub.pp`) reads what gh prints with `--json`: `TGittanPullRequest` (number, title, state, review decision, URL, head and base branch, author, draft) through `ParsePullRequest` and `ParsePullRequests` (fpjson), `PullRequestStatus` gives the one-line "PR #12 · Approved" (the status bar's hint; the bar itself draws the parts, see the status bar in window-chrome.md, with the state from `PullRequestNote`) (Merged, Closed, Draft, Changes requested, Review required, or the number alone) followed by the checks of the head commit when there are any (`PullRequestChecks`, from `statusCheckRollup`: "checks ✓", "2 checks failing" or "3 checks pending"; a CheckRun counts by its conclusion once completed, a StatusContext by its state), and `RepoPathOfUrl` the "owner/repo" of a GitHub address. `TGittanPullRequestJob` runs `gh pr view` (no selector: gh takes the checked-out branch and knows its fork) and `gh pr list --state open --limit 50` in a thread, like the blame job. `StartPullJob` in `umain.actions.inc` runs it from `LoadRepository` once per repository and branch (`FPullKey`), from View > Refresh always, and from `FPullTimer`, which `PullJobDone` sets after every job that gh answered: `PullPollPending` (30 s) while the pull request has checks pending, else `PullPollIdle` (5 min), so the status bar follows the checks, a review and a new pull request; a poll keeps the data shown while gh runs (`AKeep`), and `AbandonPullJob` stops the timer; `PullJobDone` keeps the result (`FHasPull`, `FPull`, `FPulls`, `FPullError`), and the finished job goes to `FBlameZombies`. `UpdateStatus` adds the branch's pull request after the base label; the status bar's menu gets Open Pull Request and Copy Pull Request URL with gh. View > Compare With > Pull Requests (with gh) lists the open pull requests as radio items (`RebuildPullMenu`: "Loading...", gh's message or "No open pull requests" while there is nothing to list); choosing one (`MenuComparePullClick`, `ComparePull`) runs `TGittanRepo.FetchPullRequest` as a remote job (`rkFetchPull`, `StartPullFetch`; the number in `Arg`, the base in `Branch`, the fetched ref back in `HeadRef`), so the window goes on while it fetches and the status bar says "Fetching pull request #N..."; `PullFetchDone` compares, and a failure gets the remote job's notice with git's reason and Try Again; `git fetch --no-tags <remote> <base> +refs/pull/N/head:refs/gittan/pr/N`, with the remote `RemoteFor` finds for the pull request's owner/repo (else origin, else the first), and sets the base to the three-dot range `<remote>/<base>...refs/gittan/pr/N` (kept in `FPullRange`, numbered `FPullNumber`), which `BaseLabel` names "vs PR #N" and `RebuildCompareMenu` leaves out of the ref list. A failed fetch is a summary notice.
- View > Review Comments (Cmd+Shift+M, `ReviewComments` in the settings, on by default) shows the review threads of a pull request in the change view, each in a card under the line it is on (`umain.reviews.inc`, `gittan.reviews.pp`, the latter without LCL and tested in `tests/testreviews.pp`). `TGittanReviewJob` asks gh for them with `gh api graphql` (`ReviewThreadsQuery`, a page of 100 threads at a time, owner and name from the pull request's URL) and `ParseReviewThreads` reads each thread's path, line (or start line, original line, side), resolved, outdated and file-level state and comments. `ReviewTarget` picks the pull request: the one compared against (Compare With > Pull Requests), whose diff is the one the comments were made on, else the branch's own while the new side is the work tree; `PullJobDone` asks again at the pull request's poll, `SetBase` when the comparison changes, and `ThreadsKey` keeps a poll that finds the same from rebuilding the view. `PlaceThreads` (from `BuildChangeView`, once the lines are numbered) finds each thread's diff line in `FThreadRows`: in the pull request's own diff as it is, else the head's line mapped onto the work tree with `MapLine` over `git diff -U0 <head> -- path` (kept in `FMapDiff` until the file is shown again); a comment on a removed line only where the old side is the pull request's base (its diff, or the merge base with the default branch). One that cannot be placed (outdated, on the whole file, on a removed line not shown) goes to the top of the file. Hide Unchanged Lines keeps a commented line. The cards are the editor's gaps (`TATGaps`, `ApplyReviewGaps`): room under a line painted by `OnDrawGap` (`EditDrawGap`), outside the text, so the lexer, the numbers and `FRows` are untouched; a gap's Tag is the thread, and side by side the other editor gets an empty gap of the same height (Tag -1) so the rows stay in step, with `MatchScrollPixels` putting the old side at the same pixel, since `LineTop` alone loses the part of a tall gap scrolled into. `ReviewLayout` lays a card out in the interface font (code between ``` fences in the editor's, a suggestion block labeled) at the width its last paint had (`FReviewWidths`, laid out again when it changes), measured on `FReviewMeasure`. A resolved or outdated thread starts folded to one line; a click on a card folds or unfolds it (`FThreadFlips` by the first comment's URL, applied in `EditMouseUp` so the card does not change height under the button), a click on "GitHub ↗" opens it. Two editor quirks are worked around: the gutter of a line spans its gaps and gutter decor centers the change view's numbers in that height, so `DrawGapGutter` (from `OnDrawEditor`) paints the gutter over the gaps plain and puts the number back at its line; and a gap before the first line shows only at scroll position -1, which every `LineTop := 0` leaves, so `RevealTopGapAsync` moves a view at its top up onto it. The status bar's pull request chip shows a speech bubble after its checks, with the number of open threads, dimmed when all are resolved or outdated (`SetPullThreads`, from `UpdateStatus` while the threads are the chip's pull request's), and its hint counts them (`ReviewHint`, the `HintComment` bubble). In the tree a file with threads gets the same bubble at the right end of its row with the number of open ones, gray when all are resolved or outdated (`FileTreeAdvancedCustomDrawItem` at `cdPostPaint`, `FileThreads`), and its hint says how many (`FileThreadsHint`). What is on no line, the pull request's own comments and the text a review was submitted with (what a reviewer writes with Request changes or Approve; such a review has no thread unless it also commented on lines), comes in the same query (`reviews(last:100)` and `comments(last:100)`, read from the first page by `ParsePullNotes` into `TGittanPullNotes`, oldest first; a review that only commented on lines, or is still pending, is left out, an approval, a request for changes or a dismissal is kept without text) and is shown in the summary under the header (`TGittanSummary.SetNotes`, from `ReviewJobDone`, cleared by `ClearReviews`): "Conversation of pull request #N", then a card per note with a stripe in the outcome's color (green approved, red requested changes), the author, what they did and when, a "GitHub ↗" link (`OnOpenUrl`) and the text wrapped to the width, at most `NoteMaxLines` lines.

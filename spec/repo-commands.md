# The Commands page and .gittan/commands.toml

Read this when touching `gittan.repocommands`, `gittan.commandpage`, `umain.commands.inc`, the Commands row of the sidebar, the shortcuts that run a command, or the `.gittan` folder. The kinds of project (Rust, Go, Python, Lazarus) whose commands the page lists are in project-kinds.md.

- A repository's own commands are buttons on the Commands page: the fourth row of the sidebar (`navCommands`, between Repository and Files; `niCommands`, a terminal with a prompt), View > Commands (Cmd+Option+4, Ctrl+Shift+4 elsewhere), and on macOS a click on "Gittan" after the traffic lights (`TGittanToolbar.OnName`; the label is an `NSButton` without a border). `TGittanCommandPage` (`gittan.commandpage.pp`) is painted like the Repository page in the same scroll box (`FView = gvCommands`; `ShowCommands` in `umain.commands.inc`), the repository's name and root over three sections of tiles, each tile a command on one line: a run mark (a triangle, in the link color under the mouse and while it runs), its name in bold, and at the right its shortcut as a chip and a terminal (`PaintTerminalIcon`, the sidebar's Commands icon; in the link color under the mouse, with the hint Run in Terminal). What runs is the tile's hint (the shell line, a script's text for package.json, `make <target>` for a target, with " · in a terminal" for one that opens there and " · asks first" for one with `confirm`), under the command's `description` when the file gives one, so the tiles stay short. Inside a section the commands are grouped by name (`SplitCommandName` in `gittan.repocommands`): a command's group is what comes before the first `:` in its name (`build` for `build:run` and `build:test`, npm's way), or before the first `-` for a Makefile target (`build-linux`; a target cannot have a colon), and a name with no separator is a group of its own name, so `build` belongs with `build:run`. A group of two or more is listed under its name as a sub-heading (`PaintSubheading`, bold in the text color, no divider) with the rest of each name on the tiles (`PaintGrid` with `AShort`; the hint then starts with the full name), the bare name first; the commands of no group come first in the section, under no heading, by name. Each grid is sorted by name (case-insensitive; the page sorts, so `OnRun`'s index is still the index into the commands) in one grid that every group shares (`ColumnCount`: as many as fit at `TileMinWidth`), so a group of one has a tile as wide as the others (`ShortcutPrefix`, "⌃⌘" on macOS, "Ctrl+Alt+" elsewhere). A tile fills with the hover color under the mouse and `OnRun` runs it; its terminal raises `OnRunInTerminal`, which runs it as a command with `terminal = true` is run (`RunRepoCommand` with `AInTerminal`), for one that keeps running (`npm run dev`, a watch), and leads while another command runs on the page too, as the terminal is not the page's job; a file's command still waits for the file to be trusted. The groups are the commands files' (`TGittanCommandsFiles`, which `SetCommands` takes): `.gittan/commands.toml` under the heading "Commands" (its path as the detail, and at the right Edit… when the file exists, else Create…, `OnEditFile`: `CommandPageEditFile` opens it in the editor as a Config file, writing a commented example first when there is none), then each `.toml` file of `.gittan/commands/` in a section of its own, its name without `.toml` as the heading and its path as the detail (`PaintFileSection`; a file's command has the file's path as its `Project`, so `PaintTiles`, `GroupCount` and `IsRun` tell the files apart as they tell the kinds); a file that is no TOML gives no commands and shows the reader's message in the error color under its heading ("Not read: Expected token type … at line 2, column 1"), the scripts of `package.json` ("Scripts", with the package manager as the detail), the targets of a Makefile ("Targets") and then one section per kind of project the root's files tell (`gittan.project`, project-kinds.md: the kind's name as the heading, "Rust", "Go", with the file that told it as the detail, "Cargo.toml", "Polyglot.lpi"; `SetCommands` takes the kinds with the commands, `TGittanProjects`, in the order the page shows them, and `PaintTiles` and `GroupCount` take the kind's name beside the source, since every kind's commands are `csProject`; a kind the `project =` line of commands.toml asked for whose file is missing has "named in commands.toml" as its detail). With none of them the page says so and offers Create…. Gittan's own `.gittan/commands.toml` is the example: keys for the Makefile's targets and a `log` command (git's colors need `-c color.ui=always`, since a program not writing to a terminal turns them off unless told; the job sets `FORCE_COLOR` for the tools that honor it).
- The commands come from `gittan.repocommands.pp` (no LCL, tested in `tests/testrepocommands.pp`). `DiscoverRepoCommands(ARoot)` reads them in that order: `ReadCommandsFiles` reads `.gittan/commands.toml` and then the `.toml` files of `.gittan/commands/` by name (byte order, `CompareOrdinal`, the same in every locale; the extension in any case, `CI.TOML` too, found by listing every name and not by a mask, which is case-sensitive on Unix; a hidden file, one whose name starts with a dot as an editor's or macOS's `._` ones do, and other files there are left alone; a file that cannot be read gives no commands and the error as its message, as one that is no TOML does), each parsed by `ParseCommandsToml` with toml-fp (`vendor/toml-fp`, TOML 1.1; its units `TOML.Types` and `TOML.Parser` are on the unit path of `Gittan.lpi`'s build modes and of `make test`, no package to register): a table per command under `[commands]`, `[commands.test]`, with `run =` the shell line, `key =` one letter or digit for its shortcut (a string, or a number 0 to 9), `terminal = true` for one that opens in the terminal, `description =` a line for the tile's hint (trimmed), `confirm = true` or a question of its own (`Confirm`, `ConfirmText`; an empty string asks nothing) and `hidden = true`; `run` may be a table of lines per system instead of a string, `run = { windows = "...", unix = "..." }` or `run.macos = "..."`: `ParseCommandsToml` takes the line of its `ASystem` (`CommandsSystem` by default: macos, windows, linux, freebsd, haiku, else unix; `CommandsSystemTitle` names it for the page), else `unix`'s on any system but Windows, else `default`'s, and with none of them the command has no `Command` and `Elsewhere` set: the page shows it dimmed with the hint "no command for macOS", its key runs nothing, and it takes no script or target of its name; a string as the value, `lint = "npm run lint"` under `[commands]`, is the run line alone; a name with a colon is quoted, `[commands."build:run"]`; a value of another type than these counts as missing, and other keys are left alone. A table with no `run` and the name of a script, a target or a kind's command gives that one its key, terminal flag, description, `confirm` and `hidden`, so a repository can give `make test` or `cargo test` a shortcut without writing it again. TOML keeps no order of keys (toml-fp's tables are dictionaries), so a file's commands come sorted by name, which also settles which of two asking for one key keeps it. `project = ["rust", "go"]` (or a string, `"rust, go"`) before the first table of commands.toml, `ParseCommandsTomlProjects`, keeps the kinds of project to those named, `"none"` to none, when the files would tell another (see project-kinds.md); in the files of `.gittan/commands/` it is not read. There is no other format: a `.gittan/commands.ini` of an earlier build is not read. `ParsePackageScripts` the `scripts` of `package.json` (fpjson; run as `npm run <name>`, or through pnpm, yarn or bun when their lock file is in the root, `PackageRunner`), `ParseMakefileTargets` the targets of `Makefile`, `makefile` or `GNUmakefile` (a rule line's names before the colon, each a plain name: no `.` first, no `/`, `%`, `$` or `=`; recipe lines, assignments and pattern rules are left out; run as `make <target>`), and last each kind of project's commands (`ProjectsOfRoot`, then the kind's `Commands`; `Source = csProject` with `Project` the kind's name; the overload with `out AProjects` gives the kinds to the caller, which `LoadRepoCommands` keeps in `FRepoProjects` for the page). A hidden command (`hidden = true` on its own table or on the one that names it) is left out of the list `DiscoverRepoCommands` gives, so it has no tile and its key runs nothing; a hidden table with no `run` that names nothing is still listed, dimmed, as a misspelling would be. A key is kept as a capital; the first command with a key keeps it when two ask for the same. A section with no command line that names no script or target (a misspelling, or a target since dropped) is kept among the file's commands with an empty `Command`: the page shows it dimmed with the hint "no script or target named …", it leads nowhere, and its key runs nothing (`CommandByKey` skips it). A script, target or kind's command takes the first such section that names it (commands.toml before the folder's files); a later one of the same name is kept the same way, with `Overlaps` the line of what it names, and its hint says so instead ("an earlier file already names test (make test)"); which of the two wins is the order, nothing of the later one is merged in. `FormKeyDown` (umain.pp; `KeyPreview` is on so the editor does not take them) runs the command whose key is pressed with Ctrl+Cmd on macOS and Ctrl+Alt elsewhere (`CommandKey`; a key the system takes first on macOS, Ctrl+Cmd+Q, F, D or Space, never arrives; on Windows, which reports AltGr as Ctrl+Alt, a key with the right Alt down is left to the layout's character), from any view.
- A committed file could make a key on this computer run what a clone says, so the files' commands run only once the user has trusted them: `CommandsFileHash` (`CommandsHashOf` for files already read) is the SHA-256 of each file's path, the length of its text and its text, one after the other (so a file added to `.gittan/commands/`, even an empty one, asks again) (`gittan.sha256`, from Trndi's `slicke.sha256`, since FPC 3.2.2 has none; tested in `tests/testsha256.pp`; empty without a file), so trusted files cannot be swapped for others of the same hash, and the settings keep the roots trusted in `trust` in state.json (the root as the key, the hash as the value; `CommandsTrusted`, `TrustCommands`). Until then the page shows the files' commands dimmed under one card that says why, under the Commands heading, with Trust Commands (`OnTrust`); their keys do nothing, and a change of any file asks again. The scripts and targets are run by a click as they would be in a terminal and need no trust, but a key a file gives them is the file's and waits with it.
- A command with `confirm` asks before it runs (`RunRepoCommand`, so a tile, its key, its terminal and Run Again all ask, and a Project page button whose kind's command is on the page with the same line, which `ProjectPageRun` runs as that one; `RunCommandRecord`, which a button of no such command reaches, does not): `AskDlg` titled with its name, the file's question or "Run build?", the shell line under it, Run and Cancel, Cancel the default, after the trust check.
- A command runs in `TGittanCommandJob` (`gittan.repocommands.pp`, a `TGittanJob`) through the user's shell as a login shell (`$SHELL -l -c`, `/bin/sh` without one; `cmd.exe /c` on Windows) in the repository root, in its own process group on Unix (the child calls `setsid` from `OnForkEvent`), with Gittan's environment, PATH set to `ToolSearchPath` outside Windows and `FORCE_COLOR` and `CLICOLOR_FORCE` set so tools keep their colors, both streams in one pipe (`poStderrToOutPut`) read as it writes: `Output` keeps the text (the newest `OutputKeep` bytes), `OnOutput` tells the main thread of each piece and `OnDone` of the end, with `ExitCode`, `ElapsedMs`, and `Started` false when the shell could not start. `Kill` ends it: SIGTERM to the process group on Unix (the shell alone when it has not reached `setsid` yet), and SIGKILL to it when it is still running `KillGraceMs` (3 s) later, as a command that ignores SIGTERM would be, the shell or else what is left of its group (`GroupLives`: a child that ignores SIGTERM under a shell that ended), which the loop waits for until then; asked on every pass of the reading loop so a command that writes all the time still ends; `taskkill /T /F` on Windows, so the shell's children (node under npm) go with it. One command runs at a time (`FCommandJob`; a click while one runs is ignored, the tile shows its time so far where the chip was, its border in the link color; the running command and the one that ran last are known by name, source and kind, `IsRun`, `FCommandProject` in the frame, so a reload keeps them and a kind's `build` is told from a script's). Under the groups the output is a panel (`PaintOutput`): a bar in the card color with the state as a pill in its own color (Running with a dot that pulses, Stopping… once Stop is clicked, Done with a tick in the ok color, Failed · exit code n and Could not start with a cross in the error color, Stopped with a square), the command's name and its time, which counts while it runs (`FTimer`, every `PulseMs`), and at the right Stop (filled in the error color) while it runs, else Run Again (the same command by name and source, `RunIndex`, so a script and a target of one name are told apart; not while the file is untrusted) and Copy. Under the bar a `TGittanConsole` (the editor's font; `FollowEnd` while it runs) fills the box down to its bottom, at least `ConsoleMinHeight`; the tile that ran last has its run mark in the state's color. A run scrolls the box only as far as the panel's end needs (`RunRepoCommand`), so with room for the console the tiles stay in place and the output shows under them. The job keeps running when another view is shown, and its output arrives to the page meanwhile; it is killed when the repository changes (`LoadRepoCommands` with another root), the welcome view shows, or Gittan quits (`AbandonCommandJob(True)` in `FormClose`). A command with `terminal = true` runs through Repository > Open in Terminal's command instead, with the command line appended after the root, so an interactive one (a watch, a REPL) gets a terminal: with a terminal command set in the settings it is run with the root and the line as its two arguments; without one macOS runs `osascript` telling Terminal to `cd` into the root and run the line, Windows `wt.exe` or `cmd.exe /K` in the root, and Linux the first terminal found with `sh`, `-c` and the line as arguments of their own (after `--` for gnome-terminal, `-x` for xfce4-terminal, `-e` for the rest), the root quoted for sh (`gittan.cli.ShellQuote`), so the terminal stays open after it.
- `LoadRepoCommands` runs `DiscoverRepoCommands` (a few small files, so it is synchronous) from `ApplySnapshot`, so the watcher keeps the commands and the keys current after an edit of a file or a pull, keeps the files read in `FCommandsFiles` and their hash in `FCommandsHash`, and hands them to the page with whether they are trusted. The Config section lists the files under `.gittan` after those under `.github`, folders walked (`RepoFolders` in `gittan.repofiles.pp`), so every commands file opens in the editor from the sidebar too, and `IsRepoFile` lets it be edited and saved.

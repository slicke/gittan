# The Commands page and .gittan/commands.ini

Read this when touching `gittan.repocommands`, `gittan.commandpage`, `umain.commands.inc`, the Commands row of the sidebar, the shortcuts that run a command, or the `.gittan` folder.

- A repository's own commands are buttons on the Commands page: the fourth row of the sidebar (`navCommands`, between Repository and Files; `niCommands`, a terminal with a prompt), View > Commands (Cmd+Option+4, Ctrl+Shift+4 elsewhere), and on macOS a click on "Gittan" after the traffic lights (`TGittanToolbar.OnName`; the label is an `NSButton` without a border). `TGittanCommandPage` (`gittan.commandpage.pp`) is painted like the Repository page in the same scroll box (`FView = gvCommands`; `ShowCommands` in `umain.commands.inc`), the repository's name and root over three groups of tiles, each tile a command: a run mark (a triangle, in the link color under the mouse and while it runs), its name, under it what runs dimmed in the editor's font (`CodeFont`; the shell line, a script's text for package.json, `make <target>` for a target), and at the right of the name its shortcut as a chip. Each group's tiles are sorted by name (case-insensitive; the page sorts, so `OnRun`'s index is still the index into the commands), in one grid that every group shares (`ColumnCount`: as many as fit at `TileMinWidth`), so a group of one has a tile as wide as the others (`ShortcutPrefix`, "⌃⌘" on macOS, "Ctrl+Alt+" elsewhere). A tile fills with the hover color under the mouse and `OnRun` runs it. The groups are the file's commands (heading "Commands", detail `.gittan/commands.ini`, and at the right Edit… when the file exists, else Create…, `OnEditFile`: `CommandPageEditFile` opens the file in the editor as a Config file, writing a commented example first when there is none), the scripts of `package.json` ("Scripts", with the package manager as the detail) and the targets of a Makefile ("Targets"). With none of the three the page says so and offers Create…. Gittan's own `.gittan/commands.ini` is the example: keys for the Makefile's targets and a `log` command (git's colors need `-c color.ui=always`, since a program not writing to a terminal turns them off unless told; the job sets `FORCE_COLOR` for the tools that honor it).
- The commands come from `gittan.repocommands.pp` (no LCL, tested in `tests/testrepocommands.pp`). `DiscoverRepoCommands(ARoot)` reads them in that order: `ParseCommandsFile` takes `.gittan/commands.ini` (a `[name]` section per command with `command =` the shell line, `key =` one letter or digit for its shortcut, and `terminal = true` for one that opens in the terminal; `;` and `#` start comments; a section with no `command` and the name of a script or a target gives that one its key and terminal flag, so a repository can give `make test` a shortcut without writing it again), `ParsePackageScripts` the `scripts` of `package.json` (fpjson; run as `npm run <name>`, or through pnpm, yarn or bun when their lock file is in the root, `PackageRunner`), and `ParseMakefileTargets` the targets of `Makefile`, `makefile` or `GNUmakefile` (a rule line's names before the colon, each a plain name: no `.` first, no `/`, `%`, `$` or `=`; recipe lines, assignments and pattern rules are left out; run as `make <target>`). A key is kept as a capital; the first command with a key keeps it when two ask for the same. A section with no command line that names no script or target (a misspelling, or a target since dropped) is kept among the file's commands with an empty `Command`: the page shows it dimmed, "no script or target named …", it leads nowhere, and its key runs nothing (`CommandByKey` skips it). `FormKeyDown` (umain.pp; `KeyPreview` is on so the editor does not take them) runs the command whose key is pressed with Ctrl+Cmd on macOS and Ctrl+Alt elsewhere (`CommandKey`; a key the system takes first on macOS, Ctrl+Cmd+Q, F, D or Space, never arrives; on Windows, which reports AltGr as Ctrl+Alt, a key with the right Alt down is left to the layout's character), from any view.
- A committed file could make a key on this computer run what a clone says, so the file's commands run only once the user has trusted the file: `CommandsFileHash` is the SHA-256 of its text (`gittan.sha256`, from Trndi's `slicke.sha256`, since FPC 3.2.2 has none; tested in `tests/testsha256.pp`; empty without a file), so a trusted file cannot be swapped for another of the same hash as MD5's collisions would allow (a file trusted under the MD5 Gittan once kept is asked about again), and the settings keep a `[Trust]` section of the roots trusted (the MD5 of the root as the key, the file's hash as the value; `CommandsTrusted`, `TrustCommands`). Until then the page shows the file's commands dimmed under a card that says why, with Trust Commands (`OnTrust`); their keys do nothing, and a change of the file asks again. The scripts and targets are run by a click as they would be in a terminal and need no trust, but a key the file gives them is the file's and waits with it.
- A command runs in `TGittanCommandJob` (`gittan.repocommands.pp`, a `TGittanJob`) through the user's shell as a login shell (`$SHELL -l -c`, `/bin/sh` without one; `cmd.exe /c` on Windows) in the repository root, in its own process group on Unix (the child calls `setsid` from `OnForkEvent`), with Gittan's environment, PATH set to `ToolSearchPath` outside Windows and `FORCE_COLOR` and `CLICOLOR_FORCE` set so tools keep their colors, both streams in one pipe (`poStderrToOutPut`) read as it writes: `Output` keeps the text (the newest `OutputKeep` bytes), `OnOutput` tells the main thread of each piece and `OnDone` of the end, with `ExitCode`, `ElapsedMs`, and `Started` false when the shell could not start. `Kill` ends it: SIGTERM to the process group on Unix (the shell alone when it has not reached `setsid` yet), asked on every pass of the reading loop so a command that writes all the time still ends, `taskkill /T` on Windows, so the shell's children (node under npm) go with it. One command runs at a time (`FCommandJob`; a click while one runs is ignored, the tile says it is running). The page's Output heading names the command and its state (running; exit 0 and the time in the ok color; another exit code in the error color; "could not start") with Stop while it runs, else Copy, over a `TGittanConsole` (the editor's font; `FollowEnd` while it runs) that fills the rest of the box, at least `ConsoleMinHeight`. The job keeps running when another view is shown, and its output arrives to the page meanwhile; it is killed when the repository changes (`LoadRepoCommands` with another root), the welcome view shows, or Gittan quits (`AbandonCommandJob(True)` in `FormClose`). A command with `terminal = true` runs through File > Open in Terminal's command instead, with the command line appended after the root, so an interactive one (a watch, a REPL) gets a terminal: with a terminal command set in the settings it is run with the root and the line as its two arguments; without one macOS runs `osascript` telling Terminal to `cd` into the root and run the line, Windows `wt.exe` or `cmd.exe /K` in the root, and Linux the first terminal found with `sh`, `-c` and the line as arguments of their own (after `--` for gnome-terminal, `-x` for xfce4-terminal, `-e` for the rest), the root quoted for sh (`gittan.cli.ShellQuote`), so the terminal stays open after it.
- `LoadRepoCommands` runs `DiscoverRepoCommands` (three small files, so it is synchronous) from `ApplySnapshot`, so the watcher keeps the commands and the keys current after an edit of the file or a pull, and hands them to the page with whether the file exists and is trusted. The Config section lists the files under `.gittan` after those under `.github` (`RepoFolders` in `gittan.repofiles.pp`), so `commands.ini` opens in the editor from the sidebar too, and `IsRepoFile` lets it be edited and saved.

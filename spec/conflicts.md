# Conflicts

Read this when touching `gittan.conflicts`, `umain.conflicts.inc`, the merge editor (`gittan.merge`, `gittan.mergeview`, `umain.merge.inc`), merge/rebase state in the Commit section, or the conflict navigator.

- A conflicted file (`ckConflict`) is shown with its conflicts tinted by role. git's diff of it against HEAD shows our side as unchanged and the base and their side as added, so the diff colors would mislead. `gittan.conflicts.pp` (no LCL, tested in `tests/testconflicts.pp`) gives every diff line a role with `ConflictRoles`: a marker (`<<<<<<<`, `|||||||` of the diff3 and zdiff3 styles, `=======`, `>>>>>>>`, seven signs then the end of the line or a space), our side, the base, their side, or none; a deleted line is never one. `ShowChanges` keeps the roles in `FConflictRoles` for a conflicted file, and `FillChangeEditor` marks those rows of the new side with bookmark kinds `bmConflictMarker` to `bmConflictTheirs` instead of the diff's (violet, blue, grey and amber in `EditCalcBookmarkColor`), the marker lines bold through `MarkHeader`, without word marks. The rows of a conflict are contiguous, so `ChangeBlocks` counts each conflict as one block for the navigator and F7.
- Resolving conflicts (`umain.conflicts.inc`): a conflicted file's header has the pills Use Mine, Use Theirs and Mark Resolved (`ShowChanges` sets them; `HeaderAction` sends them to `ConflictHeaderAction`), and the file menu has Resolve Using Mine/Theirs and Mark as Resolved, shown only for a conflict. Mine is the user's own work (`TGittanConflictSide`): git's ours, except in a rebase, which replays the user's commits onto the upstream, where it is git's theirs. `TGittanRepo.ResolveConflict` checks out that side (`checkout --ours/--theirs`) and adds it, or `git rm`s the file when that side deleted it (no stage 2 or 3 in `ls-files -u`); taking a side asks first, since the file's edits are lost. `MarkResolved` adds the file as it is, or removes it when it is gone from disk; when it still has markers (`MarkersLeft` runs `ConflictRoles` over the file) it asks first. One conflict at a time: `ShowChanges` keeps the diff line of each conflict's `<<<<<<<` in `FConflictStarts` (`ConflictStarts` in `gittan.conflicts.pp`) and `FindConflictRows` (in `BuildChangeView`) their rows, and `FConflictEnds` the line each ends on (`ConflictEnd`: the `>>>>>>>`, or the last line of one open at the end), with `FConflictEndRows` their rows; and while `CanResolveBlocks` (the change view of a conflicted file with markers, not against a range, not being edited) the conflict band (`gutterTagDiscard`, `umain.discard.inc`) shows a fork button on each of those rows, with `rsResolveBlockHint`, and a bar in the conflict color (`KindColor(ckConflict)`) down the band's left edge from each conflict's first row to its last, so a conflict stands out from the ordinary changes of a long file. A conflicted file also gets a conflict navigator: `TGittanFileHeader.SetConflicts` (from `UpdateChangeNav`, counted over `FConflictRows` as the changes are) shows the header's second `TGittanChangeNav` (`ConflictNav`, anchored left of the change navigator, its `Suffix` "conflicts" so it reads "1 / 3 conflicts", in violet from `ApplyTheme`), shown in the file header on every widgetset, left of the change navigator (`UpdateChangeNav` sets it in `FHeader`; the macOS toolbar and the own title bar hold the tabs). Its arrows and Go > Next/Previous Conflict (F6, Shift+F6) run `GoToConflict`, which goes to the next (or previous) conflict from the caret as `GoToChange` does, on to the next (or previous) conflicted file in the tree past the last (`NextConflictFile`, which `ShowNextConflict` uses too), and wraps around in the file when there is no other. A click on it, File > Resolve Conflict... (Cmd+Shift+R, for the conflict the caret is in, `ConflictAtRow` by the line's role; `UpdateResolveItems` from `UpdateDiscardItems`) or the editor menu's item of the same name (shown for a conflicted file, for the row it opened on) calls `ResolveConflictAt`, which drops `FConflictPopup` (a `TGittanPopupList`) down from the button: "Conflict 2 of 3" as its header, then Use Mine, Use Theirs, Use Both, Mine First and Use Both, Theirs First, the first two with the names git wrote on the markers as their details (`ConflictSides`, `MarkerName`), mine being git's theirs in a rebase as above (`FConflictPicks` maps the rows to `TGittanConflictPick`), and while the AI features are on Resolve with the agent (ai.md). `ApplyConflictPick` and the agent's resolution write through `WriteConflictBlock`. `ApplyConflictPick` builds the block with `ResolveBlock`: `NewLines` the conflict's lines as the file holds them (the markers, both sides and the base; a deleted diff line is skipped, it is not in the file), `OldLines` the pick, `Line` where it is, and writes it with `DiscardBlock`, so a file that changed since the diff is left alone, and keeps it in `FDiscards`, so File > Undo Discard puts the conflict back. When `MarkersLeft` then finds none the file is marked resolved (`MarkResolved`), and the discard is flagged `Resolved`: undoing it writes the markers back and puts the file in conflict again (`TGittanRepo.Unresolve`, `git update-index --unresolve`, from the stages git keeps when a conflict is added or removed; tested in `TestUnresolve`), so Commit Merge and Continue refuse it as before, and when git kept nothing the status bar says the file still counts as resolved and `ShowNextConflict` shows the next conflicted file in the tree, round the end; with none left it goes to the Commit section instead (`MenuCommitClick` for a merge, which focuses the message; the section unfolded and the Continue button focused in `ContinueMode`) and the status bar says so. Resolving a whole file (`ResolvePath`, the pills and the file menu) moves on the same way, when the resolved file was the one shown. The status bar's conflict badge (`ConflictBadgeClick`) drops the same list down with the conflicted files, each with the conflicts left in it (`ConflictDetail`: "3 conflicts", "no markers left", or "deleted" when one side removed it), the shown one checked; a pick shows the file. Tested in `tests/testconflicts.pp` (the starts, the names, the block for each pick, deleted lines skipped, an open conflict, and a write and its undo through `gittan.discard`). The Commit section follows what git is in the middle of: during a merge the button is Commit Merge, the field is filled once with git's message (`MergeMessage`, MERGE_MSG without its comment lines; it goes with the merge unless edited) and the whole index is committed as before; during a rebase, cherry-pick, revert or am (`ContinueMode`) the field is disabled, the tree has no boxes, and the buttons are Abort, Skip and Continue. `ContinueOperation` refuses while `ls-files -u` lists a conflict (`git add -u` would take one with its markers as resolved), stages the tracked files' changes (`add -u`; a rebase does not go on with a change left unstaged) and runs `<command> --continue` with `GIT_EDITOR=:` (the shell's no-op, so git's message stays); a rebase that stops again at a later commit with conflicts of its own counts as done, and the status bar says it stopped again. Before that `ContinueOperationClick` asks (Other Changes, with Take Them Too and Cancel, the default) when `TGittanRepo.ContinueExtras` lists files: the tracked files changed besides the conflicts resolved at this stop (`diff --name-only` less the paths of `ls-files --resolve-undo`, which git empties when it goes on), so an unrelated edit is not folded into the replayed commit unasked; at a stop without conflicts, such as an edit stop, the list is empty and Continue takes the changes as before. Tested in `TestContinueExtras` and `TestRebaseInteractiveEdit`. `SkipOperation` (`--skip`, not for a merge) and `AbortOperation` (`--abort`) ask first. They run on the main thread: local and quick. Tested in `tests/testgit.pp` (`TestResolveMerge`, `TestResolveRebase`, `TestMarkResolvedAndAbort`, `TestSkip`). A stray rebase (`StrayRebase`): a rebase that stopped, whose conflicts were resolved, and a checkout in a terminal (which git allows then) put HEAD on another branch, maybe with commits made there; git still counts the rebase as going on (rebase-merge stays until it is continued, aborted or quit, and `git status` says so), of the branch in `FRebaseBranch` while `FBranch` is HEAD's. The summary and the status bar say "main · rebasing feature" (`OperationLabel`, `rsOperationOf`); `ContinueMode` is off, since `rebase --continue` would set the rebased branch to HEAD and lose its commits, so the Commit section commits as usual with the note `rsStrayRebaseNote` and the Abort button; Abort then asks with `rsStrayAbortAsk` and offers, besides Abort (which checks the rebased branch out again as it was; the other branch keeps its commits), Forget the Rebase: `TGittanRepo.QuitOperation`, `<command> --quit` (not for a merge), which keeps HEAD, the index and the files and only ends the rebase. Tested in `TestRebaseStray`.
- The merge editor (`umain.merge.inc`, `gittan.mergeview.pp`, the model in `gittan.merge.pp`, no LCL, tested in `tests/testmerge.pp`) resolves a conflicted file line by line in three panes: mine and theirs side by side above, the result across the width under them. It opens from the header's fourth pill, Merge Editor (shown while the file has markers, `ConflictHeaderAction` index 3), File > Open in Merge Editor (Cmd+Shift+E, `FMergeEditorItem`, enabled by `CanOpenMerge` in `UpdateResolveItems`; it closes the editor while shown) or the last item of the conflict's list (`FConflictMergeItem`). `FMergeMode` then stays on: `ShowChanges` shows every conflicted text file with markers in it (`ShowMergeView`, `FView` `gvMerge`, `FMergeView` in the editor's place under the file header) until its Close pill; a file without markers, an image, or one no longer in conflict gets the change view. `TGittanMerge` reads the file (`ReadMergeFile`, split as `DiscardBlock` splits it, CR taken off) into chunks with `ConflictRoles`: runs both sides agree on and conflicts, each with the lines of mine and theirs (mine is git's theirs in a rebase, as above), the names on the markers, and which lines of each side are picked (`Picked`, `Taken`; a side with no lines can be taken whole, which resolves the conflict as its deletion; `TheirsFirst` when theirs was taken first, which puts it first). `Rows` lays the panes above out row for row: a header row per conflict ("Conflict 1 of 2 · HEAD", drawn by the view over an empty line), then its lines with the shorter side padded (`bmFiller`); the rows take the conflict's bookmark kinds (`SetKinds`: `bmConflictOurs`, `bmConflictTheirs`, `bmConflictMarker`, `bmFiller`, `bmGap`), so `EditCalcBookmarkColor` colors them through `Restyle`, which also copies the editor's font, zoom and tab size (`RestyleMergeView`, with `ApplyEditorColors` per editor; from `ShowMergeView` and `ApplyTheme`). A band of boxes (`gutterTagPick`) in place of the line numbers holds a box per line of a conflict and one on its header for the whole side (a dash when only some lines are picked); a click on the box, or anywhere on a header row, ticks it. `Output` is the result: the agreed lines, the picked lines of each conflict with a side taken, and every other conflict as git wrote it, markers and all, tinted by `Origins`. The two panes above scroll together and the result follows to the chunk at their top (`OutputStarts`). The result can be typed in; from the first key the boxes are off (dimmed, the caption says so) and the pills All Mine, All Theirs, Save, Close become Reset, Save, Close (`SetMergeActions`, `MergeHeaderAction`). Save (`SaveMerge`) writes the result as one block, the file as read against the result from line 1 (`ResultBlock`), with `DiscardBlock`, so a file changed since it was read is left alone, and keeps it in `FDiscards`, so File > Undo Discard puts the conflicts back; with no markers left the file is marked resolved, the block flagged `Resolved` (the undo unresolves it) and `ShowNextConflict` goes on as for a pick; with some left the editor reads the file again. A refresh while the file is unchanged on disk keeps the ticks (`ShowMergeView` compares the lines); leaving the file with ticks or edits not saved (`MergeDirty`; `ShowChanges` of another path, `LeaveEditorViews`, opening a repository) asks Save or Don't Save (`FlushMerge`, which writes without a refresh). Go > Next/Previous Conflict step through the editor's conflicts first (`TGittanMergeView.GoToConflict`), then on to the next file. Tried in the app on a merge with diff3 markers: the pills, the boxes, Save, Undo Discard and an edit with Reset.

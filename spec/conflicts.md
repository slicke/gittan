# Conflicts

Read this when touching `gittan.conflicts`, `umain.conflicts.inc`, merge/rebase state in the Commit section, or the conflict navigator.

- A conflicted file (`ckConflict`) is shown with its conflicts tinted by role. git's diff of it against HEAD shows our side as unchanged and the base and their side as added, so the diff colors would mislead. `gittan.conflicts.pp` (no LCL, tested in `tests/testconflicts.pp`) gives every diff line a role with `ConflictRoles`: a marker (`<<<<<<<`, `|||||||` of the diff3 and zdiff3 styles, `=======`, `>>>>>>>`, seven signs then the end of the line or a space), our side, the base, their side, or none; a deleted line is never one. `ShowChanges` keeps the roles in `FConflictRoles` for a conflicted file, and `FillChangeEditor` marks those rows of the new side with bookmark kinds `bmConflictMarker` to `bmConflictTheirs` instead of the diff's (violet, blue, grey and amber in `EditCalcBookmarkColor`), the marker lines bold through `MarkHeader`, without word marks. The rows of a conflict are contiguous, so `ChangeBlocks` counts each conflict as one block for the navigator and F7.
- Resolving conflicts (`umain.conflicts.inc`): a conflicted file's header (and the toolbar on macOS, the title bar on Windows) has the pills Use Mine, Use Theirs and Mark Resolved (`ShowChanges` sets them; `HeaderAction` sends them to `ConflictHeaderAction`), and the file menu has Resolve Using Mine/Theirs and Mark as Resolved, enabled for a conflict. Mine is the user's own work (`TGittanConflictSide`): git's ours, except in a rebase, which replays the user's commits onto the upstream, where it is git's theirs. `TGittanRepo.ResolveConflict` checks out that side (`checkout --ours/--theirs`) and adds it, or `git rm`s the file when that side deleted it (no stage 2 or 3 in `ls-files -u`); taking a side asks first, since the file's edits are lost. `MarkResolved` adds the file as it is, or removes it when it is gone from disk; when it still has markers (`MarkersLeft` runs `ConflictRoles` over the file) it asks first. One conflict at a time: `ShowChanges` keeps the diff line of each conflict's `<<<<<<<` in `FConflictStarts` (`ConflictStarts` in `gittan.conflicts.pp`) and `FindConflictRows` (in `BuildChangeView`) their rows, and `FConflictEnds` the line each ends on (`ConflictEnd`: the `>>>>>>>`, or the last line of one open at the end), with `FConflictEndRows` their rows; and while `CanResolveBlocks` (the change view of a conflicted file with markers, not against a range, not being edited) the conflict band (`gutterTagDiscard`, `umain.discard.inc`) shows a fork button on each of those rows, with `rsResolveBlockHint`, and a bar in the conflict color (`KindColor(ckConflict)`) down the band's left edge from each conflict's first row to its last, so a conflict stands out from the ordinary changes of a long file. A conflicted file also gets a conflict navigator: `TGittanFileHeader.SetConflicts` (from `UpdateChangeNav`, counted over `FConflictRows` as the changes are) shows the header's second `TGittanChangeNav` (`ConflictNav`, anchored left of the change navigator, its `Suffix` "conflicts" so it reads "1 / 3 conflicts", in violet from `ApplyTheme`), and `HeaderControlsChange` hands the position to the toolbar on macOS (`SetConflicts` there puts a purple counter and a second segmented control, `ConflictNavTag`, before the change navigator's items) and to the title bar on Windows (`ConflictNav`, laid out left of `Nav`). Its arrows and Go > Next/Previous Conflict (F6, Shift+F6) run `GoToConflict`, which goes to the next (or previous) conflict from the caret as `GoToChange` does, on to the next (or previous) conflicted file in the tree past the last (`NextConflictFile`, which `ShowNextConflict` uses too), and wraps around in the file when there is no other. A click on it, File > Resolve Conflict... (Cmd+Shift+R, for the conflict the caret is in, `ConflictAtRow` by the line's role; `UpdateResolveItems` from `UpdateDiscardItems`) or the editor menu's item of the same name (shown for a conflicted file, for the row it opened on) calls `ResolveConflictAt`, which drops `FConflictPopup` (a `TGittanPopupList`) down from the button: "Conflict 2 of 3" as its header, then Use Mine, Use Theirs, Use Both, Mine First and Use Both, Theirs First, the first two with the names git wrote on the markers as their details (`ConflictSides`, `MarkerName`), mine being git's theirs in a rebase as above (`FConflictPicks` maps the rows to `TGittanConflictPick`). `ApplyConflictPick` builds the block with `ResolveBlock`: `NewLines` the conflict's lines as the file holds them (the markers, both sides and the base; a deleted diff line is skipped, it is not in the file), `OldLines` the pick, `Line` where it is, and writes it with `DiscardBlock`, so a file that changed since the diff is left alone, and keeps it in `FDiscards`, so File > Undo Discard puts the conflict back. When `MarkersLeft` then finds none the file is marked resolved (`MarkResolved`) and `ShowNextConflict` shows the next conflicted file in the tree, round the end; with none left it goes to the Commit section instead (`MenuCommitClick` for a merge, which focuses the message; the section unfolded and the Continue button focused in `ContinueMode`) and the status bar says so. Resolving a whole file (`ResolvePath`, the pills and the file menu) moves on the same way, when the resolved file was the one shown. The status bar's conflict badge (`ConflictBadgeClick`) drops the same list down with the conflicted files, each with the conflicts left in it (`ConflictDetail`: "3 conflicts", "no markers left", or "deleted" when one side removed it), the shown one checked; a pick shows the file. Tested in `tests/testconflicts.pp` (the starts, the names, the block for each pick, deleted lines skipped, an open conflict, and a write and its undo through `gittan.discard`). The Commit section follows what git is in the middle of: during a merge the button is Commit Merge, the field is filled once with git's message (`MergeMessage`, MERGE_MSG without its comment lines; it goes with the merge unless edited) and the whole index is committed as before; during a rebase, cherry-pick, revert or am (`ContinueMode`) the field is disabled, the tree has no boxes, and the buttons are Abort, Skip and Continue. `ContinueOperation` refuses while `ls-files -u` lists a conflict (`git add -u` would take one with its markers as resolved), stages the tracked files' changes (`add -u`) and runs `<command> --continue` with `GIT_EDITOR=:` (the shell's no-op, so git's message stays); a rebase that stops again at a later commit with conflicts of its own counts as done, and the status bar says it stopped again. `SkipOperation` (`--skip`, not for a merge) and `AbortOperation` (`--abort`) ask first. They run on the main thread: local and quick. Tested in `tests/testgit.pp` (`TestResolveMerge`, `TestResolveRebase`, `TestMarkResolvedAndAbort`, `TestSkip`).

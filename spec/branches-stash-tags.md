# Interactive rebase, branches, stashes, tags, reflog, bisect and patches

Read this when touching `umain.rebase.inc`, `umain.branches.inc`, `umain.stash.inc`, `umain.tags.inc`, `umain.reflog.inc`, `umain.bisect.inc`, `umain.patches.inc`.

- Interactive rebase (`umain.rebase.inc`, `gittan.rebase.pp`, `gittan.rebasedlg.pp`): Rebase Interactively from Here... in the commit menu (on a commit in HEAD's history other than HEAD itself) lists the commits after it, and Choose Commits... in the question Rebase <branch> onto... asks lists those the rebase would replay, both through `RebaseInteractiveAsk`. `TGittanRepo.RebaseSteps` reads them (`git log --reverse` over `<onto>..HEAD`, read as `GraphCommits` reads, `Pushed` set for those on the upstream; a merge commit among them is reported, and refused, since a plain `rebase -i` would flatten it) as `TGittanRebaseSteps`: oldest first as git replays them, each with an action (`TGittanRebaseAction`: pick, reword, edit, squash, fixup, drop) and the message to commit it with. `EditRebase` (`TRebaseForm`, built in code like the settings dialog) shows them newest first in a native `TListView` (Action, Commit, Author, Id; the Commit column takes what the others leave), with the highlighted commit's action in a combo box, Move Up and Move Down (Alt+Up and Alt+Down; up is later in the replay) and its message in a memo: a Pick whose message is changed becomes a Reword and back (`MessageUnchanged`, line ends and trailing blanks aside); P, R, E, S, F, D and Delete set the action in the list; a squash or fixup with no kept commit below it to fold into is said under the list and keeps Rebase off (`CheckRebaseSteps`); a note says how many of the commits are pushed already. `BuildRebaseTodo` (tested in `tests/testrebase.pp`) writes git's todo list so that no editor is needed while the rebase runs: a `pick`, `edit` or `drop` line per step, a squash or fixup as a `fixup` line (git keeps the earlier commit's message without asking), and when a step's message is not the commit's own, or squashes fold into it, an `exec git commit --amend --allow-empty -F "<file>"` line after them with the message (the folded messages joined by blank lines, as git's squash joins them, `JoinedMessage`) in a file `msg-<n>.txt`; `ShellQuote` quotes the path for sh, which git runs exec lines with on every platform. `TGittanRepo.RebaseInteractive` writes the todo and the files to `gittan-rebase` in the git directory (they stay until the rebase is over, since an exec line reads its file when its turn comes, maybe after a stop; the folder goes when the rebase ends, there or in `ContinueOperation`, `SkipOperation` and `AbortOperation`) and runs `git rebase -i --autostash --empty=keep <onto>` with `GIT_SEQUENCE_EDITOR=cp "<todo>"` (git runs the sequence editor through sh with the todo's path after it; `cp` is there on every platform, Git for Windows' sh included) and `GIT_EDITOR=:`; `--empty=keep` so that a commit whose patch is upstream already stays, and the exec line amends the commit it was written for and not the one before. A stop at an edit ends with exit code 0, so the result is read from the repository afterwards: `Operation` still rebasing with files in conflict is `AConflicts`, without is `AStopped` (an edit, or a failed exec line, with git's words in `Error`). `RebaseStoppedAt` gives the commit of an edit stop (the last line of the rebase's `done` file is an `edit` line; stopped-sha and amend are written for a conflicted fixup too), which the status bar and the note under the Commit button name ("Stopped at abc1234 to edit it..."); Continue (`rebase --continue` after `add -u`) amends the changes into it and goes on, and the status bar says so again when the rebase stops at a later edit. Continue, Skip and Abort clear the banner of the stop they get past (`FBanner.Clear`), and a rebase, merge, cherry-pick or revert that finishes says so in a green banner (`BannerSuccess`), as a rebase from the dialog that goes through does. Started from the graph, a rebase that went through opens it again. Tested in `tests/testgit.pp` (`TestRebaseInteractive`, `TestRebaseInteractiveEdit`, `TestRebaseInteractiveConflicts`).
- Branch management (`umain.branches.inc`): the branch list starts with New Branch... (a name, `CreateBranch` at HEAD, switched to; not while git is in the middle of something) and, when local branches other than the current one track a branch deleted on its remote, Delete Gone Branches... with their count (`FGoneToDelete`); these rows are `BranchNew` and `BranchGone` in `FBranchNames` (no branch name holds a colon), and `FBranchRefs` holds per row the remote-tracking branch of a remote row. `TGittanPopupList.OnContext` (a right click, or the Menu key) shows `FBranchMenu` for a branch: Switch to, Merge into the current branch (`MergeIntoCurrent`, `MergeRef`), Rebase <current> onto <branch> (`RebaseOntoAsk`: `CommitsToRebase` counts the commits replayed, `rev-list --count onto..HEAD`, and how many of them the upstream already has, so the dialog says the next push must be forced; then `RebaseOnto`, `rebase --autostash`, through `RunCommitting` like a merge, so one that stops with conflicts goes to the Commit section's Continue and Abort; Choose Commits... in the question opens the interactive rebase's dialog with the same commits instead), Show What <branch> Changed Since <current> (`CompareSince`: `SetBase` with the range `current...branch`, through their merge base, as a pull request from it would show; `HEAD...branch` while git is in the middle of something), Show What <current> Changed Since <branch> (`CompareCurrentSince`, the range `branch...current`, as a pull request to it would show; `BaseLabel` reads such a range as "current since branch") and Compare with Working Tree (`SetBase` with the branch) for any but the current one, Rename... (`RenameBranch`, `branch -m`, the upstream going along) and Delete... for a local one, Set Upstream... for a local one (`ShowUpstreamList`, `FUpstreamPopup`, also Branch > Set Upstream of <current>..., which says so in the status bar while HEAD is on no branch: per remote without a branch of that name Push to <remote>/<branch>, which pushes it there and tracks it as a remote job, Stop Tracking <upstream> (`SetUpstream` with nothing, `branch --unset-upstream`), then the remote-tracking branches, the upstream checked, a pick tracking it without a push, `branch --set-upstream-to`; `FUpstreamRows` holds per row '+remote', '-' or '=ref'), and Delete <upstream> on the Remote... for a local branch with an upstream (`Upstream`, `%(upstream:short)`) or a remote row. Deleting asks, runs `branch -d`, and when git says the branch is not fully merged (`ANotMerged`) asks again before `-D`, since its commits are then only in the reflog; Delete Gone Branches deletes the merged ones and asks again for the rest, listing them. Deleting on the remote is `push <remote> --delete <branch>` (`DeleteRemoteBranch`; `SplitRemoteRef` finds the remote by the repository's remotes, so one with a slash in its name works) and runs as a remote job (`rkDeleteRemote`, with the ref in `Arg`). The Branch menu (`BuildMenu`, items updated by `UpdateBranchItems` as it opens and from `UpdateRemoteItems` and `ShowSummary`, so the shortcut follows) puts the verb first: Switch to Branch... (Cmd+B), New Branch..., Merge into <current>..., Rebase <current> onto..., Show What a Branch Changed Since It Left <current>... and Show What <current> Changed Since It Left... each drop the branch list from the status bar's branch (`PartScreenRect(spBranch)`) through `ShowBranchList` in a `TGittanBranchListMode` (`FBranchListMode`): in any but `blSwitch` the header says what the pick does, the current branch and the New/Delete Gone rows are left out, nothing is checked, and `BranchPopupPick` merges, rebases or compares with the picked branch (a remote row by its remote-tracking ref). Acting on what is compared: while the base is a branch compared through the merge base with the current one (`current...branch` or `HEAD...branch`, what merging it would bring; `BaseActionRef` gives the branch, '' for a pull request's or a blame range, another range, or while git is in the middle of something or a job runs), the base label is a chip with a chevron in the summary (`TGittanSummary.BaseClickable`, `OnBaseClick`, drawn like the branch chip) and the status bar's base part answers a click (`SetBase` with `AClickable`, hint `rsBaseActionsHint`); both drop `FBasePopup` (`BaseClick`) with Merge <branch> into <current> and Rebase <current> onto <branch> (`BasePopupPick` runs `MergeIntoCurrent` or `RebaseOntoAsk` when the base is still that branch), and the base stays, so the summary then shows what is left of the difference. Tested in `tests/testgit.pp` (`TestBranchManagement`, `TestRebaseOnto`, `TestRebaseOntoConflicts`).
- Behind the default branch (`umain.branches.inc`): `TGittanRepo.BehindDefault` counts the commits of `DefaultBranch` (origin/main, as of the last fetch) HEAD lacks, 0 when that is the branch's upstream or its own name on the remote (the sync line and a pull cover those), and `Snapshot` puts it in `BehindDefault` (0 on a detached HEAD; tested in `TestBehindDefault`). `ApplySnapshot` gives it to the summary (`SetBehind`, none while git is in the middle of something), which shows a row under the header, "↓ 5 commits behind origin/main" with Rebase and Merge pills, whether the tree is clean or not. A pill raises `OnBehindAction`: `SummaryBehindAction` fetches first (`StartRemote(rkFetch)`, the ref, the branch and the choice kept in `FAfterFetchRef`, `FAfterFetchBranch` and `FAfterFetchRebase`), since the count may be old, and `RemoteJobDone` hands a fetch that went through to `AfterFetch`, which runs `RebaseOntoAsk` (its question, which says when the next push must be forced) or `MergeIntoCurrent` when the branch is still the one it was for; any other job's end, a failed fetch or `StopRemoteJob` drops the wait.
- Stashes (`umain.stash.inc`): the Stash menu has Stash Changes... (Cmd+Alt+S; asks for a message, which may be left empty, and runs `TGittanRepo.Stash`, `git stash push -u`, so untracked files go along), Stash Ticked Files... (the files the tree's boxes choose, `ChosenCommitPaths`, through `Stash` with paths, in a file with `--pathspec-from-file` as a commit's go; `--literal-pathspecs` only then, since without paths it keeps the untracked files out of the stash), Pop Latest Stash (Cmd+Alt+Shift+S), Apply Latest Stash and Stashes..., which drops the stash list from the status bar's stash chip, where a click drops it too: the chip shows a box and the count (`SetStashes`, part `spStash`, after the sync part; hidden with none). `TGittanRepo.Stashes` (`git stash list` with the id, the parents, the time and the reflog subject; `ParseStashSubject` reads the branch and the message out of "On main: message" and "WIP on main: 1234abc subject") comes with every `Snapshot`, so `ApplySnapshot` keeps them in `FStashes` and a stash made or dropped in a terminal shows up through the watcher (`Fingerprint` lists the stash ids); a stash made with -u has a third parent also when nothing was untracked, so `Untracked` compares its tree with the empty tree, in one `git log --no-walk` for all of them. The list (`ShowStashList`, `FStashPopup`, `FStashRows` with the index of each row's stash in `FListedStashes`, a copy of `FStashes` taken as the list opens, so a snapshot that lists the stashes again while it is up, after a `git stash` in a terminal, does not move a row onto another stash) starts with Stash Changes... while there are changes, then a row per stash, newest first, with the branch, the age (`BlameAge`) and "with untracked files" as its detail, the compared one checked; a pick shows the stash (`CompareStash`: `SetBase` with the range `TGittanRepo.StashRange` gives, from the commit the stash was made on to the stash, or, for one with untracked files, to a commit made for the view whose tree is the stash's with them added through a temporary index, `read-tree -i -m <empty tree> <stash> <stash>^3`, since the untracked files are in a commit of their own; it is reachable from nothing, like a snapshot's), kept in `FStashRange` with the stash's id in `FStashRangeId` (`ComparingStash`, `StashOfBase`), and `BaseLabel` names it "vs stash: message". A right click (or the Menu key) on a row drops `FStashMenu`: Apply, Pop (Apply and Drop), Create Branch from Stash... (`StashBranch`, `git stash branch`, after a name), Show the Stash and Drop... (asks first). While a stash is compared against, the base chip in the summary and the status bar drops Apply, Pop and Drop (`StashBaseClick`, `StashBasePick`, through `FBasePopup` with `FBaseStashId`), as a compared branch drops Merge and Rebase. `StashApply` (`git stash apply` or `pop`) and `StashDrop` name the stash by its place in the list, looked up by its id (`StashIndex`) when they run, since the places shift; `ApplyStash` goes back to the work tree when a stash was compared against, so the changes brought in are what the views show, and a stash whose changes clash is kept by git, which leaves the files in conflict (`AConflicts`, `ls-files -u`, no operation in progress): the banner says so and the conflict pills and the Commit section take over as after a merge. The stash comes by value into the procedures that refresh, since `FStashes[i]` is gone with the array once the snapshot lists them again (an access violation otherwise), and git's reason is kept before the refresh, whose own git calls may replace `Error`. Stashing and applying are off while git is in the middle of something or a commit, fetch, pull or push runs (`StashBusy`, `UpdateStashItems`), and stashing while a file is in conflict. Tested in `tests/testgit.pp` (`TestStashes`, `TestStashConflicts`).
- Tags (`umain.tags.inc`): Branch > Tags... drops the tag list (`ShowTagList`, `FTagPopup`) from the status bar's branch: New Tag at HEAD... (a name and an optional message, which makes it annotated, as Create Tag Here... in the commit graph asks), then the tags newest first from `TGittanRepo.Tags` (`for-each-ref refs/tags` sorted by creatordate, then by version for one second, in `TagFormat`, read by `ParseTags`: name, the commit an annotated tag peels to, the date and the subject of the tag's message or the commit's; tested), read as the list opens into `FTags`, each with the short id, the age and the subject, the ones on HEAD checked. A pick shows the commit (`ShowBlameCommit`); a right click (`TagContext`, `FTagMenu`) offers Show Commit, Compare with Working Tree (`SetBase` with `refs/tags/<name>`), Check Out... (`CheckoutTagAsk`: HEAD is detached then, which the question says, offering Create Branch Here... instead; `SwitchBranch` with `ADetach`, `Switch(..., ADetach)` being `switch --detach`, the blocked-by-changes question included), Create Branch Here... (`BranchAtAsk`, at the tag's commit), Push to <remote>, Copy Name, Delete... (`tag -d`) and Delete on <remote>... (asks first). The remote is `PushRemote`: the current branch's upstream remote, else `RemoteFor('')`. Branch > Push All Tags pushes every tag there. Not while git is in the middle of something or a job runs (`TagBusy`). Tested in `tests/testgit.pp` (`TestTags`, `TestParseTags`, with `TestForcePush` and `TestUpstream` for the pushes above).
- The reflog (`umain.reflog.inc`): Branch > Reflog... drops HEAD's reflog from the status bar's branch (`ShowReflogList`, `FReflogPopup`, the filter field reading "Filter the reflog") under the header "Where HEAD has been": a row per line, newest first, captioned with what git wrote of the move ("commit: subject", "reset: moving to HEAD~1", a full commit id in it cut to seven characters by `ShortenReflogIds`), with the commit's short id and age as its detail, the rows on HEAD's commit checked. `TGittanRepo.Reflog` reads the newest 1000 lines (`git log -g --date=unix` with `ReflogFormat`, the time taken from the selector `HEAD@{<unix>}`, read by `ParseReflog`; an unborn HEAD gives none) and marks `Lost` the commits that no ref and not HEAD reaches (`rev-list <commits> --not --all`, whose output holds the commits given that are reachable only from them, a hundred commits a call, since the thousand on one command line passed the length Windows allows; a failure leaves that hundred unmarked; `TestReflogMany`), which the row says as "only in the reflog": the commits Gittan's questions say are then only in the reflog, after a reset, an amend, a rebase or deleting a branch not merged, and the way back to them. A pick shows the commit (`ShowBlameCommit`); a right click (or the Menu key) drops `FReflogMenu` (`ReflogContext`, `FMenuReflog`): Show Commit, Compare with Working Tree (`SetBase` with the id), Create Branch Here... (`BranchAtAsk`, switched to), Reset <branch> to Here with Soft, Mixed and Hard (`ResetAsk` as in the commit menu, off while git is in the middle of something or a job runs) and Copy Commit Hash. The reflog is read when the list opens, not with every snapshot. Tested in `tests/testgit.pp` (`TestParseReflog`, `TestReflog`).
- Bisect (`umain.bisect.inc`): the commit menu's Bisect submenu starts one while git is in the middle of nothing, with Start Bisect: This Is Good, <branch> Is Bad (a commit in HEAD's history but not HEAD; git checks out the first commit to test at once) or Start Bisect: This Is Bad (it then waits for a good one); while git bisects it has Mark as Good, Mark as Bad, Skip: cannot be tested, and End Bisect instead, and the graph opens again after a mark until the bisect is done. `TGittanRepo.BisectStart`, `BisectMark` (`git bisect good|bad|skip <id>`, the commit by its id, since git reads HEAD~1 and the like from the commit being tested; the exit code 2 git gives when only skipped commits are left counts as marked) and `BisectEnd` (`git bisect reset`) run on the main thread with the watcher stopped (`RunBisect`), a refusal (a work tree change in the way of the checkout, a commit both good and bad) in a red banner. `BisectState` reads the marks (`for-each-ref refs/bisect`, `ParseBisectRefs`) and, once a bad and a good one are known, the commits between them (`rev-list <bad> --not <good>...`): `Left` is those still to test, without the bad one and the skipped ones; with none left, `Found` is the first bad commit with its `Subject`, or `Suspects` the commits it could be when skipped ones stand in the way. The snapshot carries it (`TGittanRepoSnapshot.Bisect`, read only while `Operation` is "bisecting") into `FBisect`. While git bisects, the Commit section has a box over the message (`FBisectBox`, `UpdateBisectState` from `UpdateCommitState`): a note saying what is still to mark, else the commit checked out to test with how many are left and about how many steps (`BisectSteps`), else the first bad commit or the suspects; Good, Bad and Skip on a row of their own mark HEAD, and under them Show Commit (once found) and End Bisect. A mark that finds the commit says it in a green banner, one that leaves only suspects in a blue one, else in the status bar. Tested in `tests/testgit.pp` (`TestParseBisectRefs`, `TestBisect`) and `tests/testgraph.pp` (`TestRefs`).
- Patches (`umain.patches.inc`, `gittan.patchdlg.pp`): Create Patch... in the commit menu (off on a merge commit) writes the commit as a patch file, and with another commit marked (Mark for Comparison) Create Patch Series with Marked <name>... writes every commit from the older of the two to the newer, both included (off unless one is in the other's history). `ChoosePatchSeries` lists the commits (`TGittanRepo.PatchCommits`: `git log --no-merges --reverse` over the newer without the older's parents, `rev-parse <older>^@`, so merges are left out as format-patch leaves them), the folder (`PatchFolder`: the last one's, else `<repository>-patches` beside it; format-patch makes it, the dialog refuses one whose parent is missing) and whether a cover letter comes first; `TGittanRepo.FormatPatches` runs `git format-patch -o <folder>` (`--root` when the older commit is a root, since format-patch reads a lone commit as "since it") and returns the files written, which are shown in Finder (or the file manager) with the count in the status bar; the graph stays open behind the dialog. File > Apply Patches... (`FApplyPatchesItem`, off while git is in the middle of something or a job runs, `CanApplyPatches`) picks files in an open dialog (`PickPatchFiles`, sorted by name, which is format-patch's order) and `ChooseApplyPatches` lists them with Add... and Remove and chooses Commit each patch (`git am --3way`, offered only while every file is a mail, `IsMailPatchFile`/`IsMailPatch`: an mbox `From ` line first, or a header with From: and Subject:) or Change the work tree only (`git apply`, a file at a time, retried with `--3way` when it does not fit, since `--3way` alone implies `--index` and refuses a file changed but not staged; the first that fails stops the rest). `TGittanRepo.ApplyPatches` counts what went in (for am the commits HEAD gained). An am that stops is the operation "applying patches", carried on by the Commit section's Continue, Skip and Abort as a rebase is; a work-tree patch with conflicts leaves them in the index with no operation. The folders and the choices last until another repository is opened. Tested in `tests/testgit.pp` (`TestIsMailPatch`, `TestPatches`).

# AGENTS.md

## Scope
This file applies to the Gittan repository root and its subdirectories.

## Working Rules
- Prefer the project Makefile instead of calling `lazbuild` directly. Run `make help` before inventing a new command or target.
- On macOS use `make` (or `gmake`); it finds lazbuild in `/Applications/lazarus` when it is not on PATH.
- Prefer the smallest relevant target: `make`, `make debug`, `make rebuild`, `make run`.
- `make test` builds `tests/gittantests.lpr` with plain `fpc` (no LCL) and runs it: fpcunit tests of `gittan.git` (parsing on its own, the rest against a temporary repository made with the real git), `gittan.worddiff` and `gittan.settings`. CI runs it on every leg. A new non-visual unit gets a `tests/test<name>.pp` registered in the runner.

## macOS linking
- Apple's ld from Xcode/CLT 27 rejects the Objective-C method lists FPC 3.2.x emits, and `-ld_classic` is gone. Darwin targets therefore link through LLVM's `ld64.lld` (`brew install lld`) via the shim in `tools/darwin-lld/ld`, taken from Trndi.
- `Gittan.lpi` adds `-FD$(ProjPath)/tools/darwin-lld` for `TargetOS='darwin'` only, so lazbuild and the Lazarus IDE both use it. Do not remove that conditional.
- Rebuilding the Lazarus IDE (for example after installing a package) also needs the shim:
  ```sh
  /Applications/lazarus/lazbuild --build-ide="-FD$PWD/tools/darwin-lld" --ws=cocoa
  ```
  Tools > Build Lazarus inside the IDE uses Apple's ld unless the build profile carries the same `-FD` option.
- Debug builds on macOS must use DWARF 2 (`-gw2`); FPC 3.2.x's DWARF 3 writer fails on Objective-C classes.

## CI
- `.github/workflows/build.yml` builds on every push to main and every PR: macOS arm64 (cocoa, `.dmg`), Windows x64 (win32, `.zip`) and Linux amd64 (qt6, `.tar.gz`), each with `lexlib/` beside the executable (in `Contents/Resources` for the bundle). The toolchain pins are Trndi's (Lazarus 4.8).
- The checkout fetches the submodules, and every leg registers the vendored `.lpk` files with `lazbuild --add-package-link` (the list is `VENDOR_PACKAGES` in the workflow, in dependency order). A new vendored package must be added there too.
- The macOS leg installs Homebrew's `lld` for the `tools/darwin-lld` shim, replaces the bundle's symlink with the binary and signs the bundle ad hoc. The Windows runner has no make, so that leg copies the lexers and calls lazbuild itself; keep it in step with `make lexlib`.
- Every push to main publishes a release, as in Trndi: the `version` job takes the next build number from the `build-<n>` tags (100 when there is none), and `publish` runs after the three builds, downloads the packages and creates the release `build-<n>` (tagged on the pushed commit by `gh release create`) with the commits since the previous build as its notes. A failed leg skips the release. PRs only upload artifacts. The website on the `gh-pages` branch links to `releases/latest`.

## Application icon
- `icons/gittan-source.png` is the artwork: a square image (1024) of a light blue document with the diff on a white background with a neutral gray drop shadow, cropped so the document fills most of the square. `make icons` runs `tools/makeicons.swift` (macOS only: CoreGraphics and `iconutil`), which writes two cut-outs. macOS (`icons/Gittan.icns`) gets the cut-out document, shrunk to 84%, on a dark rounded square (a superellipse with exponent 5, close to the continuous corners of macOS app icons) with a gradient from graphite at the top to nearly black at the bottom and a 6 pixel light outline, brighter at the top. Windows and Linux (`Gittan.ico`, `icons/gittan.png` at 1024 and `icons/png/gittan-<n>.png` at 16 to 512 for desktop files) get the document alone, as icons there take any shape: it is told from the background by its blue tint (blue minus red at least 3) and a flood fill from the border, the outline is cleaned with an opening and a closing and then smoothed (the fold's nearly white diagonal and stray tinted specks in the shadow leave it ragged otherwise), and the shadow's gray becomes black with matching alpha. A new artwork must keep a neutral background and a tinted subject, or the script needs another way to find the outline. Commit the generated files; other platforms only consume them.
- `Gittan.ico` beside `Gittan.lpi` is the project icon (`<Icon Value="0"/>` in the .lpi means it is set); Lazarus compiles it into the executable's resources, which the LCL uses for the window and taskbar icon on Windows and Linux. The .icns insets the rounded square to Apple's 824/1024 grid so it sits like other dock icons; the .ico and PNGs fill their canvas.
- Lazarus creates `Gittan.app` without an icon, so the Darwin build targets in the Makefile copy `icons/Gittan.icns` into `Contents/Resources` and add `CFBundleIconFile` to `Info.plist` after lazbuild. A bundle built from the Lazarus IDE lacks the icon until the next `make`. Finder caches icons; `touch Gittan.app` or a relaunch of Finder refreshes it.

## Vendored packages
- `vendor/` holds git submodules: ATSynEdit, its dependencies ATFlatControls and EncConv, and BGRABitmap; EControl and ATSynEdit_Ex for syntax highlighting; and CudaText-lexers, the lexer collection. Clone with `git clone --recursive` or run `git submodule update --init`.
- The Lazarus package links point at these copies, and the IDE is built with ATSynEdit and its dependencies. EControl and ATSynEdit_Ex are runtime-only packages, so changing them needs no IDE rebuild.
- Do not edit files under `vendor/`. Update a package by moving its submodule to a new commit; rebuild the IDE as above if it is one the IDE is built with.

## Syntax highlighting
- `gittan.lexers.pp` loads every EControl lexer (`*.lcf`) from one folder and picks a lexer by file name. 44 extensions are claimed by several lexers (`.inc` by Pascal and five assemblers, `.h` by C++ and CUDA, `.sql` by six dialects), and EControl takes the first by name, so `ForFile` passes it `ChooseLexer`: the lexers of the files beside the one in question (`SiblingExtensions` in `gittan.lexerpick.pp`, up to `MaxSiblings`) vote and the candidate with the most votes wins (`MostVoted`), a tie or an empty folder falls back to the table in `PreferredLexer`, then to EControl's order. A relative path needs the repository root (`ForFile(path, FRepo.Root)`) to find the folder. `gittan.lexerpick.pp` has no LCL dependency and is tested. `umain.pp` shows one read-only editor connected through a `TATAdapterEControl`; the Syntax menu changes its lexer.
- CudaText-lexers keeps one subfolder per lexer, but EControl loads from a flat folder. `make lexlib` copies the lexers (`*.lcf`) and their `*.cuda-lexmap` files into `lexlib/` (generated, gitignored); every build target runs it. EControl reads the lexmap beside a lexer on load: its `[ref]` section names the sub-lexers and its `[map]` section maps the lexer's style names to CudaText's theme style names (`ThemeMappingOfStyle`).
- At runtime the folder is found through `GITTAN_LEXLIB`, then `lexlib` beside the executable, then `Contents/Resources/lexlib` in a macOS bundle.
- After assigning a lexer, call the editor's `DoEventChange(0)`. Without it the adapter never parses and the text stays uncolored.
- `TGittanLexers.Load` normalizes every lexer style: `BgColor` is cleared so lexers only color text (line backgrounds are reserved for the diff colors), and a system font color such as `clWindowText` becomes `clNone`. Cocoa resolves system colors through the desktop theme, so in dark mode they turn white on the editor's light background and the text disappears (seen with the Delphi resources lexer on `.lfm`).
- The lexer files' own colors (clNavy, clMaroon and so on, a Delphi-like palette) are not what the editor shows. `gittan.syntaxthemes.pp` (no LCL, tested) holds the syntax themes: VS Code (Light+ and Dark+, the default), Delphi (RAD Studio's default colors, with a dark side made to match), GitHub (Primer), Solarized and Xcode. A theme does not list CudaText's theme style names (Id, Id1-4, IdKeyword, IdVar, String, Comment, Comment2 for preprocessor lines, Number, TagId, TextBold, ...) one by one: `StyleRoles` gives each style a role (`TThemeRole`: keyword, string, comment, type, ...), and a theme gives every role a color for light and for dark and names the roles it shows in bold or italics. `SyntaxThemeStyle` answers for one style. `TGittanLexers.ApplyTheme(ADark, ATheme)` looks up every format's `DisplayName` through the lexer's lexmap and sets the theme's color and font style; a style without a mapping (or mapped to `-`) keeps the lexer's own color and style, lightened for dark as described under Dark mode. The background styles (BracketBG, SectionBG1, ...) have no role, so they stay uncolored. View > Syntax Theme picks the theme (`FSyntaxTheme`, saved by name as `SyntaxTheme`); the menu is built from `SyntaxThemes`, so a new theme is one entry in that table. The themes color only the text: the editor's background and palette stay Gittan's own. There are no theme files to ship.
- After replacing the text through `Text` (not `LoadFromFile`), call `WrapInfo.Clear` and `Update(True)`. Setting `Text` skips the wrap rebuild while no fold ranges exist and never flags it, so once the lexer adds folds the old wrap items are reused and lines paint cut off or blank.

## Dark mode
- The empty view draws the application icon from `FAppIcon`, a `TIcon` the form loads from the `MAINICON` resource, not from `Application.Icon`: on Cocoa that one keeps to its first, 16 pixel image whatever `Current` is set to, and drawing any `TIcon` goes through its handle, made from that first image. So the summary sets `Current` on its own copy to the best size for the device pixels and copies that raw image into a `TBitmap` (`LoadFromRawImage`) it draws.
- The native controls (tree, status bar, menus) follow the desktop theme on their own; `Info.plist` does not set `NSRequiresAquaSystemAppearance`. Gittan only adapts what it colors itself.
- `gittan.theme.pp` holds `IsDarkMode` (the window system color darker than its text color, so it works with every widgetset), `ColorLuminance` and `LightenForDark`. Nothing forces an appearance the way Trndi's `nsutils.simpledarkmode` does.
- `ApplyTheme` in `umain.pp` resets `Edit.Colors` with `Init` and, in dark mode, sets a dark palette on top; `EditCalcBookmarkColor` picks dark or light diff colors from `FDark`. The LCL raises no event when the desktop theme changes (`OnActivate` does not fire reliably on Cocoa either), so `ThemeTimer` asks `IsDarkMode` every other second and reapplies the theme on a change; Cocoa reports the new system colors right away.
- The lexer collection uses colors tuned for a white background (clNavy, clMaroon, clBlack and so on). Most styles get the syntax theme's colors instead (see Syntax highlighting); for the rest `TGittanLexers.NormalizeStyles` remembers every style's color and font style, and `ApplyTheme(ADark)` restores them for light or runs the color through `LightenForDark` for dark: black becomes `clNone` so the editor's text color applies, every other dark color is blended toward white until it reaches a fixed brightness.

## Git
- `gittan.git.pp` wraps the `git` command line tool (found on PATH) through a `TProcess` from fcl-process; it does not link libgit2. Every call runs with `LC_ALL=C` (so the one message `Open` matches on is always English) and `GIT_TERMINAL_PROMPT=0`, and the list commands (`status`, `diff --numstat`, `diff --name-status`) are read with `-z`, since the line form quotes a path with a space or a quote C-style. `TGittanRepo.Open` resolves any folder to its work tree root with `rev-parse --show-toplevel`.
- `FindGitHubCli` in `gittan.git.pp` looks for `gh`, GitHub's command line tool, on PATH and then in `/opt/homebrew/bin`, `/usr/local/bin` and the usual Linux places (an app started from the Finder gets a PATH without Homebrew). `FormCreate` calls it once and keeps the path in `FGitHubCli` and the flag in `FHasGitHubCli`; features that need GitHub check the flag and run gh by that path through `RunGitHubCli` (a `TProcess` like `RunGit`, with `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`; both share `CopyEnvironment`). Open on GitHub in the file menu and the editor menu, and Open Commit on GitHub in the editor menu, exist only when gh is there (`BuildPopups`). `GitHubUrl` in `umain.actions.inc` runs `gh browse --no-browser` with the arguments and answers the printed address, putting gh's message in the status bar when it fails (no GitHub remote, say); `OpenOnGitHub` opens it with `OpenURL`, Copy GitHub URL puts it in the clipboard. `FileGitHubArgs` gives the arguments for a path, at a line when one is known (`FileLineOfRow`: the new side's line in the change view, the row in a plain file, none elsewhere), at the right commit of a range (`--commit`), else on the branch (`--branch`), since the work tree has no page; a commit is opened by its hash.
- `gittan.github.pp` (no LCL, tested in `tests/testgithub.pp`) reads what gh prints with `--json`: `TGittanPullRequest` (number, title, state, review decision, URL, head and base branch, author, draft) through `ParsePullRequest` and `ParsePullRequests` (fpjson), `PullRequestStatus` gives the status bar's "PR #12 · Approved" (Merged, Closed, Draft, Changes requested, Review required, or the number alone) followed by the checks of the head commit when there are any (`PullRequestChecks`, from `statusCheckRollup`: "checks ✓", "2 checks failing" or "3 checks pending"; a CheckRun counts by its conclusion once completed, a StatusContext by its state), and `RepoPathOfUrl` the "owner/repo" of a GitHub address. `TGittanPullRequestJob` runs `gh pr view` (no selector: gh takes the checked-out branch and knows its fork) and `gh pr list --state open --limit 50` in a thread, like the blame job. `StartPullJob` in `umain.actions.inc` runs it from `LoadRepository` once per repository and branch (`FPullKey`) and from View > Refresh always; `PullJobDone` keeps the result (`FHasPull`, `FPull`, `FPulls`, `FPullError`), and the finished job goes to `FBlameZombies`. `UpdateStatus` adds the branch's pull request after the base label; the status bar's menu gets Open Pull Request and Copy Pull Request URL with gh. View > Compare With > Pull Requests (with gh) lists the open pull requests as radio items (`RebuildPullMenu`: "Loading...", gh's message or "No open pull requests" while there is nothing to list); choosing one (`MenuComparePullClick`) runs `TGittanRepo.FetchPullRequest`, `git fetch --no-tags <remote> <base> +refs/pull/N/head:refs/gittan/pr/N`, with the remote `RemoteFor` finds for the pull request's owner/repo (else origin, else the first), and sets the base to the three-dot range `<remote>/<base>...refs/gittan/pr/N` (kept in `FPullRange`, numbered `FPullNumber`), which `BaseLabel` names "vs PR #N" and `RebuildCompareMenu` leaves out of the ref list. A failed fetch is a summary notice.
- File > Open Repository (Cmd+Shift+O) uses the `TSelectDirectoryDialog` on the form (a folder on the command line, `gittan <folder>`, a folder dropped on the window, or File > Open Recent opens one too), then `OpenRepository` in `umain.pp` fills the tree and the summary from `ChangeStats`. There is no toolbar: the summary's hint tells a first-time user what to do. A folder that is not a repository, or a git failure, is shown in the empty view in the hint's place (`ShowError`), not in a dialog.
- `gittan.settings.pp` holds `TGittanSettings`, an ini file in `GetAppConfigDir` (`~/.config/gittan/gittan.ini` on Unix): the window bounds and state, the tree width, the editor font and zoom, the view options (word wrap, hidden unchanged lines, context lines, side by side, blame), an external editor command, a terminal command (File > Open in Terminal (Cmd+Alt+T) and the status bar's menu run it with the repository root appended; empty opens the platform's terminal: `open -a Terminal` on macOS, Windows Terminal or `cmd.exe` on Windows, the first of `x-terminal-emulator`, `gnome-terminal`, `konsole`, `xfce4-terminal` and `xterm` on PATH elsewhere, started in the root), and the recent repositories. `ApplySettings` in `umain.actions.inc` applies it before the menu is built, `FormClose` saves it. With no argument on the command line Gittan reopens the most recent repository. The ini is written only on a normal close; a killed process keeps the previous one.
- Tools > Install CLI Command (`MenuInstallCliClick`, `gittan.cli.pp`) installs a `gittan` command that opens a folder or file in Gittan, the current folder when none is given. It is a script naming the running executable by its full path (`Application.ExeName`), so installing again after moving Gittan updates it. macOS: `/usr/local/bin/gittan` runs `open -a <bundle>`, so a running Gittan gets the path through Cocoa's open-files event, which the LCL hands to `FormDropFiles`; `/usr/local/bin` belongs to root, so the copy then goes through `osascript ... with administrator privileges`, and a Gittan run from a disk image or translocated by Gatekeeper is refused. Windows: `%LOCALAPPDATA%\Gittan\bin\gittan.cmd` runs `start`, and that folder is added to the user's `Path` in `HKCU\Environment` (then `WM_SETTINGCHANGE`, so only new terminals see it). Elsewhere: `~/.local/bin/gittan` starts the executable with `nohup` in the background, and the message says how to add the folder to PATH when it is missing. Every script carries a marker line (`IsGittanScript`); a `gittan` without it is someone else's and is neither replaced nor removed. Tools > Uninstall CLI Command (`UninstallCli`) removes the script (as an administrator on macOS when needed) and on Windows the empty bin folder and its PATH entry (`PathListRemove`); the item is enabled only while the script is there (`CliInstalled`, checked in the Tools menu's `OnClick`, which runs as it opens). The script texts, the PATH helpers and the marker check are tested in `tests/testcli.pp`; installing and removing are not.
- `umain.pp` is split: the class and the core (theme, menus, views, repository, tree) are in the unit, the change view building in `umain.diffview.inc` and the menu actions (settings, recent, find, zoom, view options, file stepping, context menus, compare) in `umain.actions.inc`.
- `gittan.watch.pp` holds `TGittanWatcher`, a thread that polls the open repository every two seconds (`WatchInterval` in `umain.pp`) and fires `OnChange` in the main thread (through `TThread.Queue`) when `TGittanRepo.Fingerprint` changed: the branch, the commit ids of HEAD and the base, the status of every changed file, and the size, time and MD5 of every changed file on disk (no diff is run for the poll). The thread has its own `TGittanRepo`, so git never runs on the main thread for the poll. `Stop` clears the handler before `WaitFor`, because `WaitFor` on the main thread runs the queued calls while it waits. `OpenRepository` restarts the watcher; `RefreshRepository` in `umain.pp` (also View > Refresh, Cmd+R) reloads the tree, summary and status bar through `LoadRepository` and restores the view from `FView`: the expanded folders, the selected file with its caret and top line, or the repository diff. A selected file that is no longer changed falls back to the summary, which says so in a notice line under its header (`TGittanSummary.Notice`, cleared when the user picks a view).
- Compare With > "origin/main (Merge Base)" compares the work tree with the commit the branch left the default branch at, what a pull request from it would hold plus the changes not committed yet. `TGittanRepo.DefaultBranch` is the remote-tracking branch the remote's HEAD points at (`symbolic-ref refs/remotes/<remote>/HEAD`, the remote from `RemoteFor('')`), else main or master on that remote; `MergeBase` runs `git merge-base <ref> HEAD`. `LoadRepository` keeps both in `FDefaultBranch` and `FMergeBase`, `RebuildCompareMenu` lists the merge base as a radio item right after HEAD (Working Tree), and `BaseLabel` names it "vs origin/main (merge base)". `AheadBehind` (`rev-list --left-right --count @{upstream}...HEAD`) gives the status bar's "↑2 ↓5" after the branch name, each only when above zero and only with an upstream (`FHasUpstream`, `FAhead`, `FBehind`).
- What git is in the middle of is shown after the branch in the status bar and the summary ("on main · merging"), with the number of conflicted files in the status bar. `TGittanRepo.Operation` looks in the git directory (`GitDir`, `rev-parse --absolute-git-dir`, which `IndexPath` uses too) for rebase-merge or rebase-apply ("rebasing", or "applying patches" for git am), MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD and BISECT_LOG. HEAD is detached while a rebase stops, so `LoadRepository` names the branch from `RebaseBranch` (the `head-name` file of the rebase) then; `FOperation` and `FConflictFiles` are read there.
- A conflicted file (`ckConflict`) is shown with its conflicts tinted by role. git's diff of it against HEAD shows our side as unchanged and the base and their side as added, so the diff colors would mislead. `gittan.conflicts.pp` (no LCL, tested in `tests/testconflicts.pp`) gives every diff line a role with `ConflictRoles`: a marker (`<<<<<<<`, `|||||||` of the diff3 and zdiff3 styles, `=======`, `>>>>>>>`, seven signs then the end of the line or a space), our side, the base, their side, or none; a deleted line is never one. `ShowChanges` keeps the roles in `FConflictRoles` for a conflicted file, and `FillChangeEditor` marks those rows of the new side with bookmark kinds `bmConflictMarker` to `bmConflictTheirs` instead of the diff's (violet, blue, grey and amber in `EditCalcBookmarkColor`), the marker lines bold through `MarkHeader`, without word marks. The rows of a conflict are contiguous, so `ChangeBlocks` counts each conflict as one block for the navigator and F7.
- View > Blame (Cmd+Shift+B) shows in the change view who last changed each line (`umain.blame.inc`, `gittan.blame.pp`). `TGittanRepo.Blame` runs `git blame --porcelain` for a path in a commit, or in the work tree when the commit is empty; `TGittanBlame.Parse` reads the output into the commits and the commit of each line, and `TGittanBlameJob` runs the two sides of a file (the base, and the work tree or the right commit of a range, from `DiffSides`) in a thread, since a long history takes a while. A line of the new side is blamed in that version, a deleted line in the base; the old side of the side-by-side view is blamed in the base throughout. The results are cached per commit and path and dropped by `ClearBlameCache` whenever `LoadRepository` runs, since a reload may mean a new HEAD or work tree; a job no longer wanted is abandoned (`AbandonBlameJob`) and freed later rather than waited for. The band is a gutter band of Gittan's own tag (`gutterTagBlame`), leftmost, which ATSynEdit sizes but does not paint: `DrawBlame` paints the author and the age (`BlameAge`: today, 3d, 2w, 5mo, 3y) at the first visible row of each run of rows with the same commit from `OnDrawEditor`, and `BlameHintAt` gives the hover hint (short hash, author, date, summary) that `EditMouseMove` shows through the hover timer. Uncommitted lines are shown as "Not committed" in italics. A click on a cell (`EditClickGutter`, through `OnClickGutter`) shows its commit: `ShowBlameCommit` sets Base to `TGittanRepo.CommitRange`, the range from the parent (or from the empty tree for a root commit), and `BaseLabel` names it "vs commit abc1234" while `FBlameRange` matches; Compare With > HEAD (Working Tree) goes back.
- Go > Code History (Cmd+Shift+H) shows how a piece of the shown file changed over its last commits (`umain.history.inc`, `gittan.history.pp`): the piece as it is now with the past of every line under it. The piece is the selection when it spans more than one row (a word selected by Go to Symbol is not it), else the innermost code tree range around the caret (`EnclosingRange`, the fold ranges with `DisplayInTree` as `CodeTree` reads them, the end row from the range's `EndIdx` token), else the whole file as the range 1..`WholeFileLines`, which git clamps. `ChunkLines` maps the editor rows to file lines in the commit the history starts from (`HistoryRef`: the right commit of a range, else the base, HEAD by default) through `FNewNum` or `FOldNum`, so lines added in the work tree do not shift the range; rows that are all new have no history. `TGittanRepo.LineHistory` runs `git log -L from,to:path [ref]` (or `git log -p -- path` with from 0) with `--format=%x01%H%x1f%an%x1f%at%x1f%s`, and `TGittanHistory.Parse` reads the commits with their hunks (`TGittanHistoryCommit`: a `TGittanBlameCommit` plus `TGittanHistoryHunk`s with the start lines from the `@@` header). `TGittanHistoryJob` runs it in a thread like the blame job (abandoned jobs share `FBlameZombies`), `HistoryStep` (5) commits at a time plus one to know whether there are older ones; the changes not committed yet come first as a commit of their own (`AddUncommittedHistory`, the file's diff against HEAD cut to the range, only while the base is HEAD). `TGittanHistory.Layers` (tested) chains the hunks newest first: the new side of the newest commit is the current text, a commit's deleted lines are paired in order with the added lines in their place as their earlier versions, unpaired deleted lines are removed lines kept after the line before them, and the old side of each commit is matched by text, in order, to the new side of the next older one. The result is `TGittanHistoryRow`s: a current line (with its number in the newest version), the older versions under it, and removed lines, each with the commit it comes from (-1 when older than the history). `BuildHistoryView` puts them into the change view's fields (`GapFrom` holds the row's commit, so the blame band, hint and click work through `CommitOfRow` in `umain.blame.inc` without a blame, and a band click goes through `ShowHistoryCommit`): a legend row per commit first (`rowCommit`, `bmCommit`, bold through `MarkHeader`, the text from `HistoryHeaderText`: a swatch colored by `MarkSwatch`, short hash, date, author, summary, lines added and deleted; the author and summary composed with `GetDarwinNormalizedFilename`, since macOS gives git a decomposed name the editor would paint as two characters), a filler, then the rows: each tinted by its commit through bookmark kind `bmHistoryBase` + commit (`EditCalcBookmarkColor` maps it to `HistoryColor`, one hue per commit spread by the golden angle, faint for rows and strong for the swatch and the words), an older version in italics and a removed line struck through (attribs tagged `tagHistoryStyle`), and the words that changed between a version and the one before it shaded in the strong tint (`MarkHistoryWords`, tag `tagHistoryWord` with the commit in `TagEx` so `RecolorWords` can follow the theme). A last `rowMore` row fetches `HistoryStep` more while git had more. `EditMouseUp` sends a click to `HistoryClick`: a legend row shows the commit against its parent and opens the file at the hunk's first line, the more row fetches more at the same scroll position. `RefreshRepository` runs the job again for the same piece. `ChangeBlocks` skips legend rows, so the navigator counts the tinted runs. Side by Side and Hide Unchanged Lines do not apply to the view. After a commit the stored line range may no longer match the function; the command is run again from the file then.
- `gittan.findbar.pp` holds `TGittanFindBar`, the row under the header that Go > Find (Cmd+F) shows: a native `TEdit`, a `TGittanChangeNav` pill reused as previous/next with the match counter, a "Not found" note and a close cross. It only raises `OnSearch`; `FindText` in `umain.actions.inc` searches the editor's lines itself (case-insensitive substring, up to `MaxMatches`), picks the first match after the caret (or the selection start, so retyping extends the match in place), selects it through `DoGotoPos` with the caret after the match, and answers with `SetMatches`. Hidden lines of the change view are skipped. Enter and Shift+Enter step, Escape closes; Find Next/Previous (Cmd+G, Cmd+Shift+G) work with the bar closed.
- Go > Go to Definition (F12) and Cmd+click (Ctrl+click elsewhere) in an editor jump to the definition of the word under the caret (`umain.gotodef.inc`). The lexer's code tree is the only symbol table: `CodeTree` walks the adapter's `AnClient.PublicData.FoldRanges` for the ranges whose rule has `DisplayInTree` (functions, methods, classes), names them with `GetRangeName` as CudaText's code tree does, and answers a flat `TGittanSymbols` (name, row and column of the identifier token, depth, line text; the record and `BestSymbol`, which ranks by `SymbolRank`, are in `gittan.symbols.pp`: the word must equal one of the name's identifiers; a hit before the first parenthesis, and in the same case, ranks higher; a lexer names a range in its own way, "TForm1.Foo", "func foo(int a)", "class Foo"). The lookup runs on the text of the clicked editor first (the symbol on the caret's own row is skipped, so a lookup from a definition goes on), then, for the old side, on the new side, then on the rest of the repository through `FindInRepo` (see the symbol index). A hit shows the file (`ShowRepoFile`) and runs the lookup again on the text the editor shows, so the rows of the change view need no mapping. A definition on a hidden row opens its gap (`ExpandGap`) and looks again. `JumpToDefinition` selects the word on the definition's line (`WordPos`), since the lexer's position is the range's header, which may start with a keyword. The parse runs in the adapter's thread: every adapter's `OnParseBegin` and `OnParseDone` set its `Tag` to 0 and 1 (`AdapterParseBegin`/`AdapterParseDone`), and `WaitForParse` polls it with `Application.ProcessMessages`, up to `ParseTimeout`. `SetupEditor` gives both editors `InitEditorMouseActions(..., True)`, so Cmd+click moves the caret instead of adding one, and `EditMouseUp` runs the lookup when the modifier is down and nothing is selected. A word without a definition leaves a note in the status bar.
- The word under the mouse shows its definition after `HoverPause` ms: `EditMouseMove` (both editors) maps the mouse to a text position (`ClientPosToCaretPos`) and the word there (`WordAt`); a new word restarts `FHoverTimer`, whose tick looks the word up like Go to Definition (the word's own row skipped, so a definition shows nothing for itself; other files through `FindInRepo`) and shows a hint through the editor's `Hint` and `Application.ActivateHint`: "file:line" (the change view's own number, `RowLabel`) and the definition's line. - The symbol index (`umain.index.inc`, `gittan.symbolindex.pp`) holds the code tree of every file of the repository that has a lexer, so Go to Definition and the hover reach past the changed files. `OpenRepository` calls `StartIndexing`: the index is read from its file (one per repository, named by the MD5 of the root, in `IndexCacheDir`: `~/Library/Caches/Gittan/index/` on macOS, `$XDG_CACHE_HOME` or `~/.cache/Gittan/index/` on Linux, `%LOCALAPPDATA%\Gittan\index\` on Windows; a cache, since it is rebuilt from the repository), the files `TGittanRepo.Files` lists (`git ls-files` with the untracked, not ignored files) are queued, entries of files no longer listed are dropped, and `IndexNext` walks the queue: a file whose size and time (`FileStamp`) match its entry is kept, one without a lexer or larger than `MaxIndexedSize` gets no symbols, the rest are parsed one at a time in `FIndexEdit`, a hidden editor with its own adapter, whose `OnParseDone` (`IndexParseDone`) collects the symbols with `CodeTree` and queues the next file through `Application.QueueAsyncCall`, so the window stays responsive; `FIndexTimer` (`ParseTimeout`) gives up on a parse that never reports. `UpdateStatus` shows "indexing N/M" every `IndexReportEvery` files. The index is written (`SaveIndex`, only when `FIndexSaveNeeded`) when the indexing ends and when the repository or the window closes. `FileSymbols` gives a changed file's symbols from the index when its stamp is current, else parses it at once in `FScratch`, so a lookup never waits for the indexer and an edited file is parsed again. `FindInRepo` searches the changed files first, in tree order, then the rest of the index; `ShowRepoFile` shows a hit through the tree, or through `OpenFile` for a file that is not changed. `AdapterOf` must know every hidden editor: a lexer set through it on the wrong adapter starts no parse. `gittan.symbolindex.pp` has no LCL dependency and is tested, as is `Files`.

Typing filters by substring (the names matched at the start of a word listed first, at most `MaxRows` rows, the rest counted in a last row), Up and Down move in the list from the field, Enter or a double click raises `OnPick` with the index into the list given, and `SymbolBarPick` jumps through `JumpToDefinition` with the name's identifier (`NameIdentifier` in `gittan.symbols.pp`). With two sides the wholly deleted ranges come from the old side (`OnOld`). `InnermostRange` finds the range around a row; `ChangeDetail` words a change for the symbol bar ("+3  −1", "added  +12", "moved here, changed", "renamed from X").

A parse can end while `BuildChangeView` is still filling the editors (one side's text replaced, the other's not), so the update is skipped while `FBuildingView` is set and the build calls it once at its end; it also skips while an editor's line count is not its rows plus the empty line the text ends with.
- Go > Callers of Changed Symbols... (Cmd+Shift+C; `MenuCallersClick`) shows the impact of the shown file's diff on the rest of the repository: the index knows definitions only, so the identifiers of the changed symbols (`ShownSymbolChanges`, shared with Changed Symbols; the old end of a move left out) go to one `TGittanRepo.Grep`, `git grep -z -n -w -F -I --untracked` over the work tree, with `-i` when `LexerIgnoresCase` says the shown file's lexer reads identifiers so (Pascal, SQL, Basic), run synchronously. `gittan.callers.pp` (no LCL, tested in `tests/testcallers.pp`) reads the output (`ParseGrep`: one `TGittanCaller` per identifier found as a whole word on a row, the rows of the changed files and the shown file left out, since their uses are in the diff), and the handler drops the rows of files without a lexer or with one for prose (`LexerIsProse`: Markdown and the like mention a symbol, they do not call it) and the rows the index knows as definitions of the same identifier (`IsDefinitionRow`). The status bar counts the files that use the changed symbols; without any, or without changed symbols, it says so and the bar stays hidden.

- `TGittanRepo.Base` is the commit the work tree is compared against, empty for HEAD; `RunDiff` puts it into every `git diff` call (before the `--` of a path list) and falls back to the empty tree (`EmptyTree`, the id depends on the repository's hash function) when HEAD does not exist, so everything staged before the first commit shows as added. With a base set, `ChangedFiles` builds the status lines from `git diff --name-status` plus the untracked files from `git status`, so the tree, the counts, the file diffs and the watcher (which gets the base in its constructor) all follow it. View > Compare With lists `Refs` (local branches, remote branches, tags, most recent commit first, symbolic refs such as origin/HEAD left out; rebuilt by `LoadRepository`) and Other… asks for any ref, or for a range: `main...feature` (what feature changed since it left main, through git's merge base) or `v1..v2` compares two commits, and git diff takes either as one argument. With a range (`IsRange`, the ends from `SplitRange`, HEAD for one left out) the right side is the second commit, not the work tree: `ChangedFiles` asks git status for nothing, `FileChanges` reads a file without a diff from the right commit with `git show`, `Fingerprint` resolves both ends and skips the files on disk, and `BaseLabel` in `umain.actions.inc` shows the range itself where the summary, the status bar and the repository diff otherwise say "vs base". `SetBase` restarts the watcher and keeps the previous base, with the error as the summary's notice, when git rejects the new one.
- View > Compare With > Take Snapshot (Cmd+Shift+N) records the work tree as it is, untracked files included, and compares against it, so the views show only what changes from here on (the use is watching someone or something else edit the tree). `TGittanRepo.TakeSnapshot` copies the repository's index to a temporary file (`GIT_INDEX_FILE`, an optional argument of `RunGit`), runs `add -A` and `write-tree` on the copy and `commit-tree` (parent HEAD when there is one) for a commit no branch points at; the repository's own index and status are left as they were. The commit is reachable from nothing, so `git gc` prunes it two weeks or more after it was made. `git diff <commit>` only lists the paths of the index, so a snapshot is compared with `TGittanRepo.WholeTree` set: `CompareIndex` keeps a second temporary index per `TGittanRepo` (the watcher's has its own), refreshed with `add -A -N` (intent to add: no object is written) before each diff, and `ChangedFiles` then takes the untracked files from the diff instead of `git status`, so a file the snapshot holds unchanged is no change and one it lacks is added (`ChangeKind` reads an A in the work tree column as added, as `--name-status` puts it). `WholeTree` has no effect against HEAD or in a range. The snapshots of a repository (`gittan.snapshots.pp`, `TGittanSnapshots`: id and time, newest first, at most `MaxSnapshots`) are kept in `IndexCacheDir` as `<md5 of root>.snapshots`; `LoadSnapshots` in `umain.actions.inc` drops the ones git has pruned (`HasCommit`) when the repository is opened. The Compare With menu lists them as "Snapshot 14:32" (the day before the time when it is not today, `TGittanSnapshots.Caption`), radio items with `Tag` 1, and `SetBase(ARef, ASnapshot)` sets `WholeTree` with the base; `BaseLabel` shows "vs snapshot 14:32", and the summary says "No changes vs ..." instead of "Working tree clean" whenever a base is set.

- `gittan.changenav.pp` holds `TGittanChangeNav`, a pill at the right end of the file header with a previous and a next arrow and a counter ("2 / 5", or "– / 5" before the caret has reached a change). It paints itself with `TCanvas` primitives in colors `ApplyTheme` sets through `SetColors`, because a native push button keeps its light bezel on a dark background on macOS (the bezel takes the window's white background) while a caption follows the theme's text color and turned white on white. The header anchors it to its right edge and centers it vertically, so it stays in place when it grows with its counter; `TGittanFileHeader.SetChanges` shows or hides it and repaints the header, whose room for the path depends on the pill's width.
- `ChangeBlocks` in `umain.pp` lists the first line of every block of added/deleted lines from the second bookmark list; `GoToChange` jumps to the next or previous block from the caret and scrolls it near the top. The Go menu binds them to F7 and Shift+F7. `UpdateChangeNav` hides the pill while the list is empty and sets the counter to the last block the caret has reached. It runs from the editor's `OnChangeCaretPos`, but through `Application.QueueAsyncCall`: the event fires inside the editor's own updates, and resizing a child there (the pill grows with its counter, and was the editor's child then) made the editor recompute its scroll position from a half-updated state and scroll sideways after a theme change.
- The gutter's line states band (3 px, between the numbers and the fold icons) is the diff's strip: `MarkLine` sets an added line to `TATLineState.Added` and a deleted one to `Changed`, and `ApplyTheme` sets `Colors.StateAdded` green and `Colors.StateChanged` red. ATSynEdit marks every line of a freshly set text as `Added`, so `ShowText` resets the states to `None` before the marks and shows the band through `SetLineStatesBand`; `OpenFile` and `FormCreate` hide it, since a plain file has no changes.
- The gutter's fold band is hidden (`SetupEditor` in `umain.pp`): in a viewer the fold icons are noise, and the change view hides lines through the folding mechanism (below), which a fold or unfold of a lexer range would disturb. Folding stays enabled (`OptFoldEnabled`): the wrap info skips hidden lines only then, and the adapter adds no fold ranges without it.
- The diff line colors in `EditCalcBookmarkColor` are faint tints of the editor background (GitHub's values for light, the same blended onto the dark palette), so the lexer's syntax colors still read on top of them.
- `gittan.worddiff.pp` holds `WordDiff`: for every run of deleted lines followed by added lines it tokenizes both runs (words, runs of spaces, single punctuation characters, a break token per line end), takes a longest common subsequence of the tokens, and returns the unmatched tokens as character spans per diff line (UTF-16 units, as the editor counts columns; adjacent spans and spans with only spaces between them are joined). A block whose sides share less than `MinCommon` of their text (rewritten, not edited) and a block over `MaxBlockLines` or `MaxCells` token pairs get no spans. `BuildChangeView` computes `FWordSpans` from `FChangeLines`, `FillChangeEditor` puts them on the shown rows through `MarkWords`, and `ShowRepoDiff` does the same on the raw diff with the spans shifted one column for the marker (its hunk and file header lines get a blank marker first). `MarkWords` uses the editor's attribs (`Attribs.Add` with a `TATLinePart` that sets only `ColorBG`, so the lexer's text color stays), tagged `tagWordAdded`/`tagWordDeleted`; `WordColor` gives the shade for the theme and `RecolorWords` in `ApplyTheme` recolors the existing marks. Setting `Text` clears the attribs, so `ShowText` needs nothing extra.
- View > Ignore Whitespace (Cmd+Alt+I, `IgnoreWhitespace` in the settings) sets `TGittanRepo.IgnoreWhitespace`, which `RunDiff` turns into `-w` on every `git diff`: the numstat counts, the file diffs and the repository diff all leave whitespace changes out, and `WordDiff` then treats two runs of spaces as equal. The toggle runs `RefreshRepository`. `FileChanges` with an empty diff asks `git ls-files` whether the file is tracked: a tracked file (its changes whitespace only, or a mode change) is shown with every line unchanged, an untracked one all added. The watcher's own repository runs without the flag; it only needs to notice a change.
- The editor is a viewer: `ModeReadOnly` is set in `FormCreate`. ATSynEdit silently ignores `Text` and `LoadFromFile` while read-only, so `ShowText` and `OpenFile` clear the mode around the load and set it again. Loading does not clear the second bookmark list, so they call `BookmarkDeleteAll_2` first. There is no Save command.

## Editing Guidance
- Keep changes focused and minimal. Avoid unrelated refactors or formatting-only edits.
- Unit files must use the `.pp` extension. Formatting follows `JCFSettings.xml` (JEDI Code Formatter).
- When a unit grows large (like a main form), break code out into `.inc` include files.
- PasDoc `{** ... }` comments on public APIs in interfaces; banner-style comments in implementations.
- Cross-platform gotcha: `{$IFDEF UNIX}` does not cover Haiku. Use `{$IF DEFINED(UNIX) OR DEFINED(HAIKU)}` where both apply.
- Do not edit `backup/` directories, `link*.res`, or other generated artifacts.
- Update documentation when behavior or workflow changes.

## Validation
- After code changes, run the narrowest relevant build target first.
- To check a language or RTL detail in isolation, run a snippet through `instantfpc` rather than adding a throwaway unit or project to the tree.

# AGENTS.md

## Scope
This file applies to the Gittan repository root and its subdirectories.

## Working Rules
- The units (`gittan.*.pp`) live in `src/`, split in two: `src/core/` holds the units without the LCL, which plain `fpc` builds and the tests use, and `src/ui/` the controls, the units that need the LCL or a widgetset, and the main form (`umain.pp`, `umain.lfm`, `umain.*.inc`). `Gittan.lpr` and `Gittan.lpi` stay in the root. A new unit goes in `src/core/` when it builds without the LCL. A unit keeps its dotted name as its file name, since FPC finds a unit by file name and does not map folders to names. The project's `OtherUnitFiles` is `src/core;src/ui`, and the test build (Makefile, make.ps1 and the CI workflow) has only `-Fusrc/core`, so a core unit that comes to use the LCL breaks `make test`.
- Prefer the project Makefile instead of calling `lazbuild` directly. Run `make help` before inventing a new command or target.
- On macOS use `make` (or `gmake`); it finds lazbuild in `/Applications/lazarus` when it is not on PATH.
- Prefer the smallest relevant target: `make`, `make debug`, `make rebuild`, `make run`.
- On Linux `make` builds with gtk3 and links against GTK 3 and its stack: `gtk3-devel` on Fedora, `libgtk-3-dev` on Debian and Ubuntu (what CI installs); without it the link stops at `libgtk-3.so.0`.
- On Windows, where there is no make, `.\make.ps1` has the same targets (build, debug, rebuild, run, lexlib, test, clean, help) and finds lazbuild as Trndi's does (LAZBUILD, PATH, `C:\lazarus`, `C:\fpcupdeluxe\lazarus`). A build from the Lazarus IDE (F9) does not copy the lexers: run `.\make.ps1 lexlib` once, or after the lexers change.
- `make test` builds `tests/gittantests.lpr` with plain `fpc` (no LCL) and runs it: fpcunit tests of `gittan.git` (parsing on its own, the rest against a temporary repository made with the real git), `gittan.worddiff` and `gittan.settings`. CI runs it on every leg. A new non-visual unit gets a `tests/test<name>.pp` registered in the runner.

## macOS linking
- Darwin targets link with Apple's ld. The first ld of Xcode/CLT 27 rejected the Objective-C method lists FPC 3.2.x emits ("malformed method list atom"), and Gittan linked through LLVM's `ld64.lld` for a while; ld-27037 (August 2026) links them again. On "malformed method list atom", update Xcode or the Command Line Tools.
- Debug builds on macOS must use DWARF 2 (`-gw2`); FPC 3.2.x's DWARF 3 writer fails on Objective-C classes.

## CI
- `.github/workflows/build.yml` builds on every push to main and every PR: macOS arm64 (cocoa, `.dmg`), Windows x64 (win32, `.zip`) and Linux amd64 (gtk3, `.tar.gz`), each with `lexlib/` beside the executable (in `Contents/Resources` for the bundle). The toolchain is Lazarus 5.0RC1 on every leg (FPC 3.2.4rc2 on macOS, 3.2.2 elsewhere).
- The checkout fetches the submodules, and every leg registers the vendored `.lpk` files with `lazbuild --add-package-link` (the list is `VENDOR_PACKAGES` in the workflow, in dependency order). A new vendored package must be added there too.
- The macOS leg replaces the bundle's symlink with the binary and signs the bundle ad hoc. The Windows runner has no make, so that leg copies the lexers and calls lazbuild itself; keep it in step with `make lexlib`.
- Every push to main publishes a release, as in Trndi: the `version` job takes the next build number from the `build-<n>` tags (100 when there is none), and `publish` runs after the three builds, downloads the packages and creates the release `build-<n>` (tagged on the pushed commit by `gh release create`) with the commits since the previous build as its notes. A failed leg skips the release. PRs only upload artifacts. The build job passes the number to every leg as `GITTAN_BUILD`, which `gittan.update.pp` compiles in (`{$I %GITTAN_BUILD%}`); a local or PR build has none. The website on the `gh-pages` branch links to `releases/latest`.

## Application icon
- The artwork is two finished square PNGs, both cut once out of 1024-pixel pictures on a dark background; a new artwork must likewise be cut out before `make icons`. `icons/gittan-source.png` (646 pixels) is the motif alone, a document of white rope with a red and a green strand under a magnifying glass, transparent around it: the background was modeled as a smooth gradient and taken away, the drop shadow under the motif with it, and the magnifier's grip, whose dark band and underside are close to the background's color, added as a capsule fitted to its edges. `icons/gittan-source-mac.png` (768 pixels) is the same motif on a dark tile with a glass rim, transparent outside the tile; the tile's corners are not a superellipse (the bottom ones are squarer than the top), so it was clipped along the rim's outer edge traced from the picture, 1.5 pixels inside it so none of the background shows. The tile's face inside the rim was then darkened (red, green and blue scaled by 0.62, 0.58 and 0.56, the motif left as it was) from slate blue to nearly black, about #1e2229 in the middle. `make icons` runs `tools/makeicons.swift` (macOS only: CoreGraphics and `iconutil`). Windows and Linux (`Gittan.ico`, `icons/gittan.png` at 1024 and `icons/png/gittan-<n>.png` at 16 to 512 for desktop files) get the motif filling its canvas. macOS (`icons/Gittan.icns`) gets the tile inset to Apple's 824/1024 grid over a soft drop shadow, so it sits like other dock icons. Commit the generated files; other platforms only consume them.
- `Gittan.ico` beside `Gittan.lpi` is the project icon (`<Icon Value="0"/>` in the .lpi means it is set); Lazarus compiles it into the executable's resources, which the LCL uses for the window and taskbar icon on Windows and Linux. The .icns insets the tile to Apple's 824/1024 grid; the .ico and PNGs have the motif without a tile, filling their canvas.
- Lazarus creates `Gittan.app` without an icon, so the Darwin build targets in the Makefile copy `icons/Gittan.icns` into `Contents/Resources` and add `CFBundleIconFile` to `Info.plist` after lazbuild. The `Info.plist` lazbuild writes into a new bundle has the project title as `CFBundleName` with a bare `&`, which PlistBuddy refuses to read (so CI, which always starts without a bundle, shipped no icon); the targets escape it, set `CFBundleName` to Gittan and check the result with `plutil -lint`. A bundle built from the Lazarus IDE lacks the icon until the next `make`. Finder caches icons; `touch Gittan.app` or a relaunch of Finder refreshes it.

## Vendored packages
- `vendor/` holds git submodules: ATSynEdit, its dependencies ATFlatControls and EncConv, and BGRABitmap; EControl and ATSynEdit_Ex for syntax highlighting; CudaText-lexers, the lexer collection; MetaDarkStyle, the dark mode of the LCL's native controls on Windows; and LazInk (slicke/LazInk, the commit trndi-multi uses), which draws HTML and Markdown on the canvas with no browser engine, for the Markdown preview. MetaDarkStyle ships no `.gitignore` for its `lib/`, so `.gitmodules` sets `ignore = untracked` for it. Clone with `git clone --recursive` or run `git submodule update --init`.
- The Lazarus package links point at these copies, and the IDE is built with ATSynEdit and its dependencies. EControl, ATSynEdit_Ex, MetaDarkStyle and LazInk are used at runtime only (LazInk's package is RunAndDesignTime, but the IDE needs no rebuild for it), so changing them needs no IDE rebuild.
- Do not edit files under `vendor/`. Update a package by moving its submodule to a new commit; rebuild the IDE as above if it is one the IDE is built with.

## Syntax highlighting
- `gittan.lexers.pp` loads every EControl lexer (`*.lcf`) from one folder and picks a lexer by file name. 44 extensions are claimed by several lexers (`.inc` by Pascal and five assemblers, `.h` by C++ and CUDA, `.sql` by six dialects), and EControl takes the first by name, so `ForFile` passes it `ChooseLexer`: the lexers of the files beside the one in question (`SiblingExtensions` in `gittan.lexerpick.pp`, up to `MaxSiblings`) vote and the candidate with the most votes wins (`MostVoted`), a tie or an empty folder falls back to the table in `PreferredLexer`, then to EControl's order. A relative path needs the repository root (`ForFile(path, FRepo.Root)`) to find the folder. `gittan.lexerpick.pp` has no LCL dependency and is tested. `umain.pp` shows one read-only editor connected through a `TATAdapterEControl`; the Syntax menu changes its lexer.
- CudaText-lexers keeps one subfolder per lexer, but EControl loads from a flat folder. `make lexlib` copies the lexers (`*.lcf`) and their `*.cuda-lexmap` files into `lexlib/` (generated, gitignored); every build target runs it. EControl reads the lexmap beside a lexer on load: its `[ref]` section names the sub-lexers and its `[map]` section maps the lexer's style names to CudaText's theme style names (`ThemeMappingOfStyle`).
- `lexers/` holds Gittan's own lexers in the same layout (one subfolder each, the `.lcf` and its `.cuda-lexmap`), and `make lexlib` copies them too; the Windows leg of CI copies from both folders. `Gitignore` covers `.gitignore` and the other ignore files in its syntax (`.dockerignore`, `.npmignore`, ...), claimed by full name: a `#` comment at the start of a line, the `!` that negates a pattern, the wildcards `*`, `**`, `?` and `[...]`, and backslash escapes. `Gitattributes` claims `.gitattributes`: the pattern first, colored as in `Gitignore`, then the attributes, told from it by the whitespace before them (a lookbehind), with the `-` or `!` that unsets or unspecifies one, the `=value` and an `[attr]` macro definition at the start of a line each in a style of their own. A lexer here must not share a name with one in CudaText-lexers, since both land in the same flat folder.
- At runtime the folder is found through `GITTAN_LEXLIB`, then `lexlib` beside the executable, then `Contents/Resources/lexlib` in a macOS bundle.
- After assigning a lexer, call the editor's `DoEventChange(0)`. Without it the adapter never parses and the text stays uncolored.
- `TGittanLexers.Load` normalizes every lexer style: `BgColor` is cleared so lexers only color text (line backgrounds are reserved for the diff colors), and a system font color such as `clWindowText` becomes `clNone`. Cocoa resolves system colors through the desktop theme, so in dark mode they turn white on the editor's light background and the text disappears (seen with the Delphi resources lexer on `.lfm`).
- The lexer files' own colors (clNavy, clMaroon and so on, a Delphi-like palette) are not what the editor shows. `gittan.syntaxthemes.pp` (no LCL, tested) holds the syntax themes: VS Code (Light+ and Dark+, the default), Delphi (RAD Studio's default colors, with a dark side made to match), GitHub (Primer), Solarized and Xcode. A theme does not list CudaText's theme style names (Id, Id1-4, IdKeyword, IdVar, String, Comment, Comment2 for preprocessor lines, Number, TagId, TextBold, ...) one by one: `StyleRoles` gives each style a role (`TThemeRole`: keyword, string, comment, type, ...), and a theme gives every role a color for light and for dark and names the roles it shows in bold or italics. `SyntaxThemeStyle` answers for one style. `TGittanLexers.ApplyTheme(ADark, ATheme)` looks up every format's `DisplayName` through the lexer's lexmap and sets the theme's color and font style; a style without a mapping (or mapped to `-`) keeps the lexer's own color and style, lightened for dark as described under Dark mode. The background styles (BracketBG, SectionBG1, ...) have no role, so they stay uncolored. View > Syntax Theme picks the theme (`FSyntaxTheme`, saved by name as `SyntaxTheme`); the menu is built from `SyntaxThemes`, so a new theme is one entry in that table. The themes color only the text: the editor's background and palette stay Gittan's own. There are no theme files to ship.
- On gtk3 `SetupEditor` sets `DoubleBuffered` on both editors: ATSynEdit paints into a bitmap of its own only where the widgetset can draw outside Paint (`EditorDoubleBufferedNeeded`, `lcCanDrawOutsideOnPaint`), which gtk3 cannot, and unbuffered every caret blink invalidated the editor, which GTK cleared to its background before the repaint, so a repository file open to edits flickered. The caret does not blink there either (`OptCaretBlinkEnabled` off): on a blink ATSynEdit inverts the caret on the control's canvas outside Paint before it invalidates, which gtk3 draws onto the window outside its frame, so the caret flashed out of step with the bitmap blitted after it.
- After replacing the text through `Text` (not `LoadFromFile`), call `WrapInfo.Clear` and `Update(True)`. Setting `Text` skips the wrap rebuild while no fold ranges exist and never flags it, so once the lexer adds folds the old wrap items are reused and lines paint cut off or blank.

## Markdown preview
- View > Preview (Cmd+Shift+V, `MarkdownPreview` in the settings, off by default) shows a Markdown, HTML or SVG file (`IsPreviewPath`: `IsMarkdownPath` for `.md`, `.markdown`, `.mdown`, `.mkd`, `.mkdn`, `IsHtmlPath` for `.html`, `.htm`, `IsSvgPath` for `.svg`) drawn beside the editor, in the change view (the new side: the diff lines that are not deleted ones) and in a file opened by itself (`umain.mdpreview.inc`). `TGittanMarkdownPreview` (`gittan.mdpreview.pp`) is a `TInkPage` from LazInk with the editor's colors (`SetColors` from `ApplyTheme`), its font size at the editor's zoom, raw HTML allowed (a README's badges and `<details>`) and images no wider than the column. The page is loaded with the file's `file://` URI as its base, so relative images load from the work tree; a link to a heading scrolls, one to a local file goes to `ShowRepoFile` (inside the repository) or `OpenFile`, anything else to the browser. Loading the same text again does nothing and the same file keeps its scroll, so a refresh after the file changed on disk does not jump to the top; a repository file open to edits follows typing after `MdPreviewPause`.
- `ShowFile` picks LazInk's `LoadMarkdown` or `LoadHTML` by the extension. LazInk draws no SVG, so `OnResource` (`PageResource`) draws it with BGRABitmap's `TBGRASVG` (`RenderSvg`) as a PNG: an SVG file is shown as an `<img>` of a `gittan-svg:<n>.png` URL, numbered per load since LazInk keeps a picture by its URL, a small one (an icon) a whole number of times larger, up to 256 pixels on its longer side or 8 times, and drawn at the screen's pixels; an `.svg` image a Markdown or HTML page links to is drawn at its own size.
- The file header has a Preview toggle (`SetToggle`, `OnToggle`), a pill left of the action pills tinted in the accent while on, which stays in the header when ShowControls hands the pills to the macOS toolbar. `UpdatePreviewToggle` (from `UpdateStatus` and both menu handlers) sets it for the file `PreviewTogglePath` names: a `.po` file in the change view without conflicts, opened by itself or in the translation view toggles View > Translations, a file the preview draws toggles View > Preview; any other view shows none, and `SetFile`/`SetTitle` take it away. Its tooltip names the menu item's shortcut.
- `FMdPreview` and `FMdSplitter` are `alRight` in `EditorPanel`, at `FMdRatio` of its width. `ShowEditor` calls `UpdateMarkdownPreview`, which shows or hides them; the views that hide the editor (summary, image, binary) call `HideMarkdownPreview`. The side-by-side view shares what is left (`SidesWidth`).

## Dark mode
- The empty view draws the application icon from `FAppIcon`, a `TIcon` the form loads from the `MAINICON` resource, not from `Application.Icon`: on Cocoa that one keeps to its first, 16 pixel image whatever `Current` is set to, and drawing any `TIcon` goes through its handle, made from that first image. So the summary sets `Current` on its own copy to the best size for the device pixels and copies that raw image into a `TBitmap` (`LoadFromRawImage`) it draws.
- The native controls (tree, menus) follow the desktop theme on their own on Cocoa and GTK 3 (Linux builds with gtk3: GTK decorates its own windows under Wayland, so a form can take the title bar and keep the shadow and the rounded corners, which a frameless Qt 6 window loses; the LCL calls its gtk3 widgetset beta, so the tree, the splitter, the popup lists and the dialogs want a check under GNOME Wayland); `Info.plist` does not set `NSRequiresAquaSystemAppearance`. Gittan only adapts what it colors itself. On Windows the LCL's controls would stay light, so `Gittan.lpr` applies MetaDarkStyle (`vendor/metadarkstyle`, Win32 only) before `Application.Initialize` with `PreferredAppMode := pamAllowDark`: when Windows is in dark mode at startup it swaps in dark widgetset classes and hooks `OpenThemeData`, `DrawThemeText` and the system colors, so trees, menus, edits, scroll bars and dialogs turn dark, the menus the title bar opens with `TrackPopupMenuEx` too. It decides once and does not follow a change while Gittan runs, so on Windows `IsDarkMode` returns its `IsDarkModeEnabled` instead of asking the theme, and the editor and what Gittan draws stay in step with the native controls until a restart. Checked on Windows 11 in both modes, title bar included.
- `gittan.theme.pp` holds `IsDarkMode` (`ThemeServices.IsDarkTheme`, from Lazarus 5: the appearance on Cocoa, `AppsUseLightTheme` in the registry on Windows 10 and later, the brightness of the system colors elsewhere), `ColorLuminance` and `LightenForDark`. Nothing forces an appearance the way Trndi's `nsutils.simpledarkmode` does.
- `ApplyTheme` in `umain.pp` resets `Edit.Colors` with `Init` and, in dark mode, sets a dark palette on top; `EditCalcBookmarkColor` picks dark or light diff colors from `FDark`. The LCL raises no event when the desktop theme changes (`OnActivate` does not fire reliably on Cocoa either), so `ThemeTimer` asks `IsDarkMode` every other second and reapplies the theme on a change; Cocoa reports the new system colors right away.
- The lexer collection uses colors tuned for a white background (clNavy, clMaroon, clBlack and so on). Most styles get the syntax theme's colors instead (see Syntax highlighting); for the rest `TGittanLexers.NormalizeStyles` remembers every style's color and font style, and `ApplyTheme(ADark)` restores them for light or runs the color through `LightenForDark` for dark: black becomes `clNone` so the editor's text color applies, every other dark color is blended toward white until it reaches a fixed brightness.

## Git
- Gittan supports git 2.30 and later (`MinGitMajor`, `MinGitMinor`; 2.30 is the first with `push --force-if-includes`). `ParseGitVersion` reads `git --version` ("git version 2.30.1.windows.1" too), `GitVersion` asks the git `GitExe` runs and `GitVersionSupported` compares (tested in `TestParseGitVersion`); `CheckGitVersion` in `umain.actions.inc` says an older one in a red banner (the version, what is needed and the path), at the end of `FormCreate`, after the repository is opened since that clears the banners, and when the settings name another git. A git that cannot be run is left to the errors of the git calls: one that cannot be started answers `GitNotRunMessage` (git not found, or the path that could not be run, and that another can be set under Tools in the settings), and the `/usr/bin/git` of a Mac without the Command Line Tools, which only stands in for theirs and writes "No developer tools were found" or "invalid active developer path" (`IsMissingDeveloperTools`), answers `MissingDeveloperToolsMessage` (`xcode-select --install`); both show where the repository would, in the empty view and the status bar (tested in `TestGitNotRun`). Nothing is refused for an old git: what needs a newer one fails with git's own message.
- `gittan.git.pp` wraps the `git` command line tool (found by `FindTool`, see below) through a `TProcess` from fcl-process; it does not link libgit2. Every call runs with `LC_ALL=C` (so the one message `Open` matches on is always English) and `GIT_TERMINAL_PROMPT=0`; a failed call's `Error` is what git wrote on stdout and then on stderr, since a pre-push hook's output (husky's "pre-push script failed", the tests it ran) goes to the one and git's own "failed to push some refs" to the other; `RunGitEnv` reads both pipes as git writes (its own loop, not `RunCommandLoop`) and tells an `AOnOutput` of each piece, which `TGittanRepo.OnOutput` gets for a fetch, pull or push (`RunRemote`), and `ResolveReturns` reads a progress line written over with carriage returns as the terminal last showed it, and the list commands (`status`, `diff --numstat`, `diff --name-status`) are read with `-z`, since the line form quotes a path with a space or a quote C-style. `TGittanRepo.Open` resolves any folder to its work tree root with `rev-parse --show-toplevel`.
- An app started from the Finder gets a PATH of `/usr/bin:/bin:/usr/sbin:/sbin` alone. `ToolSearchPath` in `gittan.git.pp` (made once, in the unit's initialization) is Gittan's PATH followed by the folders missing from it where package and version managers put commands (Homebrew, `/usr/local/bin`, `~/.local/bin`, Cargo, Volta, asdf and mise shims, Nix, Linuxbrew, snap, bun, deno, yarn, `~/.npm-global/bin`, pnpm's home from `PNPM_HOME` or its platform's default), those that exist, and the node of nvm and fnm, which lives in a folder named after its version: `NvmNodeBin` (tested) follows nvm's `alias/default` through the alias files (`lts/*` → `lts/krypton` → `v24.21.0`, a bare `20` meaning the newest v20) under `NVM_DIR` or `~/.nvm`, else takes the newest version installed, and `FnmNodeBin` takes fnm's `aliases/default` under `FNM_DIR` or its default folder, else the newest installed; Windows keeps its PATH. `FindTool(name)` looks a command up on it, node included; git itself is run by the path it gives (plain `git` when none), and `CopyEnvironment` gives every git and gh process it as its PATH, so the hooks git runs find node, npx or pre-commit too (tested: a hook writes its PATH). The environment is read through `EnvironmentVariable` and `EnvironmentStrings` in `gittan.git.pp`, never `GetEnvironmentVariable` or `GetEnvironmentString`: on Windows FPC 3.2.4's read the ANSI environment and label it as the OEM code page, so the ö of `USERPROFILE=C:\Users\Björn` (F6 in Windows-1252) reached git as ÷ (F6 in code page 850) and `git config --global`, which Gittan runs to set the identity before a first commit, could not lock `C:/Users/Bj÷rn/.gitconfig`; the two read the Unicode environment as UTF-8 (tested: `TestEnvironmentUtf8` sets a variable with an ö and a git alias run by its shell prints it). git runs by the path `GitPath` in the settings when one is given, else by what `FindTool('git')` gives (`SetGitExe`, `GitExe`; the earlier paths are kept alive, so a thread starting git during the change copies a live string). gh likewise: `FindGitHubCli` takes `GhPath` from the settings, else `FindTool('gh')`, and keeps the path in `FGitHubCli` and the flag in `FHasGitHubCli` (gh is optional throughout: nothing else needs it); features that need GitHub check the flag and run gh by that path through `RunGitHubCli` (a `TProcess` like `RunGit`, with `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`; both share `CopyEnvironment`). Open on GitHub and Copy GitHub URL in the file menu and the editor menu, Open Commit on GitHub in the editor menu and the pull request items of the status bar's menu are always built (`BuildPopups`, `AddGitHubItem`, their separators too) and kept in `FGitHubItems`, which `UpdateGitHubItems` shows when gh is there and hides otherwise, with View > Review Comments enabled likewise; the Compare With menu and a commit's menu are built as they open and look at the flag themselves. A change of either path in the settings dialog applies at once: `SetGitExe`, `FindGitHubCli`, `UpdateGitHubItems`, what a gh that is gone had found dropped (the pull request, the review threads), then `MenuRefreshClick`. `GitHubUrl` in `umain.actions.inc` runs `gh browse --no-browser` with the arguments and answers the printed address, putting gh's message in the status bar when it fails (no GitHub remote, say); `OpenOnGitHub` opens it with `OpenURL`, Copy GitHub URL puts it in the clipboard. `FileGitHubArgs` gives the arguments for a path, at a line when one is known (`FileLineOfRow`: the new side's line in the change view, the row in a plain file, none elsewhere), at the right commit of a range (`--commit`), else on the branch (`--branch`), since the work tree has no page; a commit is opened by its hash.
- `gittan.github.pp` (no LCL, tested in `tests/testgithub.pp`) reads what gh prints with `--json`: `TGittanPullRequest` (number, title, state, review decision, URL, head and base branch, author, draft) through `ParsePullRequest` and `ParsePullRequests` (fpjson), `PullRequestStatus` gives the one-line "PR #12 · Approved" (the status bar's hint; the bar itself draws the parts, see the status bar, with the state from `PullRequestNote`) (Merged, Closed, Draft, Changes requested, Review required, or the number alone) followed by the checks of the head commit when there are any (`PullRequestChecks`, from `statusCheckRollup`: "checks ✓", "2 checks failing" or "3 checks pending"; a CheckRun counts by its conclusion once completed, a StatusContext by its state), and `RepoPathOfUrl` the "owner/repo" of a GitHub address. `TGittanPullRequestJob` runs `gh pr view` (no selector: gh takes the checked-out branch and knows its fork) and `gh pr list --state open --limit 50` in a thread, like the blame job. `StartPullJob` in `umain.actions.inc` runs it from `LoadRepository` once per repository and branch (`FPullKey`), from View > Refresh always, and from `FPullTimer`, which `PullJobDone` sets after every job that gh answered: `PullPollPending` (30 s) while the pull request has checks pending, else `PullPollIdle` (5 min), so the status bar follows the checks, a review and a new pull request; a poll keeps the data shown while gh runs (`AKeep`), and `AbandonPullJob` stops the timer; `PullJobDone` keeps the result (`FHasPull`, `FPull`, `FPulls`, `FPullError`), and the finished job goes to `FBlameZombies`. `UpdateStatus` adds the branch's pull request after the base label; the status bar's menu gets Open Pull Request and Copy Pull Request URL with gh. View > Compare With > Pull Requests (with gh) lists the open pull requests as radio items (`RebuildPullMenu`: "Loading...", gh's message or "No open pull requests" while there is nothing to list); choosing one (`MenuComparePullClick`) runs `TGittanRepo.FetchPullRequest`, `git fetch --no-tags <remote> <base> +refs/pull/N/head:refs/gittan/pr/N`, with the remote `RemoteFor` finds for the pull request's owner/repo (else origin, else the first), and sets the base to the three-dot range `<remote>/<base>...refs/gittan/pr/N` (kept in `FPullRange`, numbered `FPullNumber`), which `BaseLabel` names "vs PR #N" and `RebuildCompareMenu` leaves out of the ref list. A failed fetch is a summary notice.
- View > Review Comments (Cmd+Shift+M, `ReviewComments` in the settings, on by default) shows the review threads of a pull request in the change view, each in a card under the line it is on (`umain.reviews.inc`, `gittan.reviews.pp`, the latter without LCL and tested in `tests/testreviews.pp`). `TGittanReviewJob` asks gh for them with `gh api graphql` (`ReviewThreadsQuery`, a page of 100 threads at a time, owner and name from the pull request's URL) and `ParseReviewThreads` reads each thread's path, line (or start line, original line, side), resolved, outdated and file-level state and comments. `ReviewTarget` picks the pull request: the one compared against (Compare With > Pull Requests), whose diff is the one the comments were made on, else the branch's own while the new side is the work tree; `PullJobDone` asks again at the pull request's poll, `SetBase` when the comparison changes, and `ThreadsKey` keeps a poll that finds the same from rebuilding the view. `PlaceThreads` (from `BuildChangeView`, once the lines are numbered) finds each thread's diff line in `FThreadRows`: in the pull request's own diff as it is, else the head's line mapped onto the work tree with `MapLine` over `git diff -U0 <head> -- path` (kept in `FMapDiff` until the file is shown again); a comment on a removed line only where the old side is the pull request's base (its diff, or the merge base with the default branch). One that cannot be placed (outdated, on the whole file, on a removed line not shown) goes to the top of the file. Hide Unchanged Lines keeps a commented line. - `TGittanRepo.Commit` (tested in `tests/testgit.pp`) commits the chosen paths as they are in the work tree, as the views show them against HEAD, whatever the index holds: `git commit --only` with the paths, so the other files and their staged changes stay out and hooks and signing run as configured (a `commit-tree` of our own would skip them). The paths go in files (`--pathspec-from-file`, NUL separated, git 2.26 or later) under `--literal-pathspecs`, so no command line grows with them and `br[a].txt` is no pattern. `--only` knows only tracked paths, so the chosen untracked ones are added first and taken out of the index again (`rm --cached`) when the commit fails, a hook's refusal say, whose output is the error. The tree lists a rename under its new path alone, and committing that alone would keep the old file, so `Commit` reads `git status` itself and adds the old path. git refuses a commit of some paths during a merge, cherry-pick or revert (`Operation`): the chosen paths are then added (not one whose deletion is staged, which `git add` would not match) and the whole index committed. Any file in conflict refuses the commit before anything is touched. The message goes in with `-F` byte for byte (a line starting with # is kept); `HeadMessage` gives HEAD's for an amend, and an amend without paths changes only the message. `AParts` (`TGittanCommitPart`: a path and the text to commit for it) are chosen files committed with other text than the work tree's, the changes left out (see below): the commit is then made from a temporary index (`CommitThroughIndex`: `read-tree HEAD`, or `--empty` before the first commit, `add -A` of the paths, then each part written over its path with `hash-object -w --path=<path>`, so the path's filters apply as `git add` would, and `update-index --cacheinfo` with the mode `ls-files -s` gives, the work tree's) through `GIT_INDEX_FILE`, so hooks and signing run as for any commit and nothing else the real index holds goes in, and afterwards `git reset` of the paths gives the real index the committed text, so what was left out shows as not staged, as `git commit --only` leaves it; a failed commit leaves the real index untouched. During a merge, a cherry-pick or a revert the parts are written into the real index after the paths are added. A chosen file git rm --cached took out of the index but left on disk is committed through the temporary index as well, taken out of it with `rm --cached`, and its untracked entry is not added (see Renaming and removing files).

- View > Blame (Cmd+Shift+B) shows in the change view who last changed each line (`umain.blame.inc`, `gittan.blame.pp`). `TGittanRepo.Blame` runs `git blame --porcelain` for a path in a commit, or in the work tree when the commit is empty; `TGittanBlame.Parse` reads the output into the commits and the commit of each line, and `TGittanBlameJob` runs the two sides of a file (the base, and the work tree or the right commit of a range, from `DiffSides`) in a thread, since a long history takes a while. A line of the new side is blamed in that version, a deleted line in the base; the old side of the side-by-side view is blamed in the base throughout. The results are cached per commit and path and dropped by `ClearBlameCache` whenever `LoadRepository` runs, since a reload may mean a new HEAD or work tree; a job no longer wanted is abandoned (`AbandonBlameJob`) and freed later rather than waited for. The band is a gutter band of Gittan's own tag (`gutterTagBlame`), leftmost, which ATSynEdit sizes but does not paint: `DrawBlame` paints the author and the age (`BlameAge`: today, 3d, 2w, 5mo, 3y) at the first visible row of each run of rows with the same commit from `OnDrawEditor`, and `BlameHintAt` gives the hover hint (short hash, author, date, summary) that `EditMouseMove` shows through the hover timer. - Go > Code History (Cmd+Shift+H) shows how a piece of the shown file changed over its last commits (`umain.history.inc`, `gittan.history.pp`): the piece as it is now with the past of every line under it. The piece is the selection when it spans more than one row (a word selected by Go to Symbol is not it), else the innermost code tree range around the caret (`EnclosingRange`, the fold ranges with `DisplayInTree` as `CodeTree` reads them, the end row from the range's `EndIdx` token), else the whole file as the range 1..`WholeFileLines`, which git clamps. `ChunkLines` maps the editor rows to file lines in the commit the history starts from (`HistoryRef`: the right commit of a range, else the base, HEAD by default) through `FNewNum` or `FOldNum`, so lines added in the work tree do not shift the range; rows that are all new have no history. `TGittanRepo.LineHistory` runs `git log -L from,to:path [ref]` (or `git log -p -- path` with from 0) with `--format=%x01%H%x1f%an%x1f%at%x1f%s`, and `TGittanHistory.Parse` reads the commits with their hunks (`TGittanHistoryCommit`: a `TGittanBlameCommit` plus `TGittanHistoryHunk`s with the start lines from the `@@` header). `TGittanHistoryJob` runs it in a thread like the blame job (abandoned jobs share `FBlameZombies`), `HistoryStep` (5) commits at a time plus one to know whether there are older ones; the changes not committed yet come first as a commit of their own (`AddUncommittedHistory`, the file's diff against HEAD cut to the range, only while the base is HEAD). `TGittanHistory.Layers` (tested) chains the hunks newest first: the new side of the newest commit is the current text, a commit's deleted lines are paired in order with the added lines in their place as their earlier versions, unpaired deleted lines are removed lines kept after the line before them, and the old side of each commit is matched by text, in order, to the new side of the next older one. The result is `TGittanHistoryRow`s: a current line (with its number in the newest version), the older versions under it, and removed lines, each with the commit it comes from (-1 when older than the history). `BuildHistoryView` puts them into the change view's fields (`GapFrom` holds the row's commit, so the blame band, hint and click work through `CommitOfRow` in `umain.blame.inc` without a blame, and a band click goes through `ShowHistoryCommit`): a legend row per commit first (`rowCommit`, `bmCommit`, bold through `MarkHeader`, the text from `HistoryHeaderText`: a swatch colored by `MarkSwatch`, short hash, date, author, summary, lines added and deleted; the author and summary composed with `GetDarwinNormalizedFilename`, since macOS gives git a decomposed name the editor would paint as two characters), a filler, then the rows: each tinted by its commit through bookmark kind `bmHistoryBase` + commit (`EditCalcBookmarkColor` maps it to `HistoryColor`: a fixed palette of six hues taken in turn, in three tones from `THistoryTone`, faint for the rows, stronger for the words and darker in light mode (lighter in dark) for the swatch, which is text and keeps 3.4:1 or more against the background; each tone is one OKLCH lightness and chroma, so no hue looks lighter than the others, and the hues keep away from the diff's red and green), an older version in italics and a removed line struck through (attribs tagged `tagHistoryStyle`), and the words that changed between a version and the one before it shaded in the strong tint (`MarkHistoryWords`, tag `tagHistoryWord` with the commit in `TagEx` so `RecolorWords` can follow the theme). A band of its own next to the text (`gutterTagInitial`, `InitialCols` wide, shown by `SetInitialBand` from `ApplyBlame` in the history view only, whatever View > Blame says) puts the author's initial on every row with a commit, legend rows included (`DrawInitials`, through `CommitOfRow`): the first letter of the composed name in upper case (`NameInitial`) on a flat rounded badge in the commit's row tint, the letter bold in its swatch tone; the changes not committed yet take the initial of `TGittanRepo.UserName` (`git config user.name`, read into `FHistoryUser` by `BuildHistoryView`), and a line older than the history gets none. A click or the hint on the band works as on the blame band. A last `rowMore` row fetches `HistoryStep` more while git had more. `EditMouseUp` sends a click to `HistoryClick`: a legend row shows the commit against its parent and opens the file at the hunk's first line, the more row fetches more at the same scroll position. `RefreshRepository` runs the job again for the same piece. `ChangeBlocks` skips legend rows, so the navigator counts the tinted runs. Side by Side and Hide Unchanged Lines do not apply to the view. After a commit the stored line range may no longer match the function; the command is run again from the file then.

- Go > Go to Definition (F12) and Cmd+click (Ctrl+click elsewhere) in an editor jump to the definition of the word under the caret (`umain.gotodef.inc`). The lexer's code tree is the only symbol table: `CodeTree` walks the adapter's `AnClient.PublicData.FoldRanges` for the ranges whose rule has `DisplayInTree` (functions, methods, classes), names them with `GetRangeName` as CudaText's code tree does, and answers a flat `TGittanSymbols` (name, row and column of the identifier token, depth, line text; the record and `BestSymbol`, which ranks by `SymbolRank`, are in `gittan.symbols.pp`: the word must equal one of the name's identifiers; a hit before the first parenthesis, and in the same case, ranks higher; a lexer names a range in its own way, "TForm1.Foo", "func foo(int a)", "class Foo"). The lookup runs on the text of the clicked editor first (the symbol on the caret's own row is skipped, so a lookup from a definition goes on), then, for the old side, on the new side, then on the rest of the repository through `FindInRepo` (see the symbol index). A hit shows the file (`ShowRepoFile`) and runs the lookup again on the text the editor shows, so the rows of the change view need no mapping. A definition on a hidden row opens its gap (`ExpandGap`) and looks again. `JumpToDefinition` selects the word on the definition's line (`WordPos`), since the lexer's position is the range's header, which may start with a keyword. The parse runs in the adapter's thread: every adapter's `OnParseBegin` and `OnParseDone` set its `Tag` to 0 and 1 (`AdapterParseBegin`/`AdapterParseDone`), and `WaitForParse` polls it with `Application.ProcessMessages`, up to `ParseTimeout`. `SetupEditor` gives both editors `InitEditorMouseActions(..., True)`, so Cmd+click moves the caret instead of adding one, and `EditMouseUp` runs the lookup when the modifier is down and nothing is selected. A word without a definition leaves a note in the status bar.
- `WaitForParse` waits for an adapter's parse with `Application.ProcessMessages`, so anything may happen to the adapter meanwhile: another file scrolled into the view sets a new lexer on `FAdapter`, and another lookup loads a file into the scratch editor (`ParseScratch` sets `Lexer := nil`); either frees the parser (`AnClient`) it had. `CodeRanges` and `EnclosingRange` take `AnClient` after the wait, never before: one taken before was freed under a hover's repository lookup while the user scrolled through a merge, an access violation in `TCriticalSection.Enter`. `FileSymbols` refuses a nested parse in the scratch editor (`FScratchBusy`; it finds nothing and caches nothing then) and caches only when the scratch editor still holds its file, and the hover timer does not start a lookup inside another (`FHoverBusy`, `HoverLookup`).
- The word under the mouse shows its definition after `HoverPause` ms: `EditMouseMove` (both editors) maps the mouse to a text position (`ClientPosToCaretPos`) and the word there (`WordAt`); a new word restarts `FHoverTimer`, whose tick looks the word up like Go to Definition (the word's own row skipped, so a definition shows nothing for itself; other files through `FindInRepo`) and shows a hint through the editor's `Hint` and `Application.ActivateHint`: "file:line" (the change view's own number, `RowLabel`) and the definition's line. While Cmd (Ctrl elsewhere) is held the word is underlined in `FLinkColor` through an attribute tagged `tagHoverLink` and the cursor is a hand, as a link. `ClearHover` drops hint, timer and underline; `EditMouseLeave` calls it.
- The symbol index (`umain.index.inc`, `gittan.symbolindex.pp`) holds the code tree of every file of the repository that has a lexer, so Go to Definition and the hover reach past the changed files. `OpenRepository` calls `StartIndexing`: the index is read from its file (one per repository, named by the MD5 of the root, in `IndexCacheDir`: `~/Library/Caches/Gittan/index/` on macOS, `$XDG_CACHE_HOME` or `~/.cache/Gittan/index/` on Linux, `%LOCALAPPDATA%\Gittan\index\` on Windows; a cache, since it is rebuilt from the repository), the files `TGittanRepo.Files` lists (`git ls-files` with the untracked, not ignored files) are queued, entries of files no longer listed are dropped, the queue is sorted by extension and then path (`CompareByExt`) so the files of one lexer come together, and `IndexNext` walks it: a file whose size and time (`FileStamp`) match its entry is kept, one without a lexer or larger than `MaxIndexedSize` gets no symbols, the rest are parsed one at a time in `FIndexEdit`, a hidden editor with its own adapter, whose `OnParseDone` (`IndexParseDone`) collects the symbols with `CodeTree` and queues the next file through `Application.QueueAsyncCall`, so the window stays responsive; `FIndexTimer` (`ParseTimeout`) gives up on a parse that never reports. The adapter keeps its lexer, and so its parser thread, from one file to the next when the adapter is idle and the file takes the same lexer: `LoadFromFile` starts the parse through the editor's change event. Otherwise (another lexer, or a parse still running after a timeout or a repository closed mid-parse) the lexer is dropped and set again, which ends the thread and starts a new one, up to a tenth of a second (the thread polls its event every 100 ms), and so is done as seldom as possible: indexing 300 files took 69 s with a new thread per file and 7 s without, and a done event of a parse still running is never taken for the next file's. `UpdateStatus` moves the status bar's progress bar ("Indexing N/M") every `IndexReportEvery` files. The index is written (`SaveIndex`, only when `FIndexSaveNeeded`) when the indexing ends and when the repository or the window closes. `FileSymbols` gives a changed file's symbols from the index when its stamp is current, else parses it at once in `FScratch`, so a lookup never waits for the indexer and an edited file is parsed again. `FindInRepo` searches the changed files first, in tree order, then the rest of the index; `ShowRepoFile` shows a hit through the tree, or through `OpenFile` for a file that is not changed. `AdapterOf` must know every hidden editor: a lexer set through it on the wrong adapter starts no parse. `gittan.symbolindex.pp` has no LCL dependency and is tested, as is `Files`.

The result (`TGittanSubmoduleInfo`) is `smUpToDate` when the remote's commit is the recorded one, `smNotFetched` when the submodule does not have the remote's commit, else `smBehind`, `smAhead` or `smDiverged` from `rev-list --left-right --count`, with the incoming commits (`MaxIncoming`, `git log recorded..tip`), the remote's commit described when the submodule has it (`TipCommit`) and, when the recorded commit is past it, the commits the remote's branch lacks (`Outgoing`, `git log tip..recorded`) and the remote-tracking branches that have the recorded commit (`Holding`, `HoldingBranches`: `for-each-ref --contains` over refs/remotes, origin/HEAD left out, at most `MaxHolding`, as of the submodule's last fetch); `smFailed` keeps git's message. Finished jobs go to `FBlameZombies`. A row is the path with the folder icon (dotted in the kind's color when git status reports the submodule) and "↓3", "↓" (not fetched), "↑2", or "⚠"; the header's detail counts the submodules and the ones with new commits. For each submodule git status reports, `FillSubmodules` also runs `CompareSubmodule` against the sides of `TGittanRepo.DiffSides` into `FSubChanges`: the commit the left side records (`git ls-tree`, `ParseGitlink`), the one the right side records or, for the work tree, the one checked out (the recorded one when not initialized), and when the submodule has both, the commits added and dropped between them (`rev-list --left-right --count`, at most `MaxIncoming` of each listed); only local objects are read. A click shows the view `gvSubmodule` (`ShowSubmodule`), from the Submodules section, a changed submodule's node in the file tree or its row in the summary: the submodule's page, `TGittanSubPage` (`gittan.subpage.pp`, `FSubPage`, painted like the summary in the same scroll box, under the file header, which stays shown for it), with the name, the URL (a web address a link, through `RemoteWebUrl`) and the branch it follows, then cards (a disc in the state's color: green up to date, blue new commits on the remote, amber not checked out or past the remote, red in conflict or when the remote could not be asked) and, for a submodule that moved, a card "Changed  b0193be → 2844a79" with how many commits; then the recorded, checked-out and remote commits in labeled rows and the lists of commits it moved on to, the ones it no longer has, the new ones on the remote and the ones not on the remote's branch (`Outgoing`; the card past the remote then names the branches that have them and suggests setting one in .gitmodules, else says they may not be pushed or be on another branch) (the new ones left out when the moved-to commit is the remote's, as the list above has them), each on a line with a dot per commit as the summary's recent commits. A click on a commit copies its id (`SubPageCopyCommit`, "Copied 2844a79" in the status bar). The header names the path with an Open pill that opens the submodule as a repository (`OpenShownSubmodule`), and has no lexer name. The page keeps its scroll position while it shows the same submodule (a finished job or a refresh shows it again), and the snapshot leaves the summary hidden under it. `SelectShownSubmodule` keeps the shown submodule selected in the tree it was picked in, after a refresh (which empties both) in the file tree when it is changed, else in the section. A finished job redraws the view when it shows its submodule; `RefreshRepository` shows it again, or the summary when it is gone. `RunGitIn` in `gittan.git.pp` runs git as `TGittanRepo.RunGit` does without a repository object, for the jobs.
- Submodule actions (end of `umain.submodules.inc`, `gittan.submoduledlg.pp`): File > Submodules has Update Submodules, Sync Submodule URLs (both off without submodules) and Add Submodule...; the Submodules section's right-click menu (`FSubPopup`, a right click selects the row) has Update, Sync URL, Open as Repository (once checked out) and Copy Path for its row, and a shown submodule that is not checked out, or is checked out at another commit than the recorded one, has an Update pill before Open (`FSubUpdatePill`, read by `HeaderAction`). The red line is given a `Top` above the buttons each time it is shown again, since an alTop control made visible goes last. The add runs in the remote job (`rkSubmoduleAdd`: `Arg` the URL, `Path` and `Branch` set before `Start`; `TGittanRepo.AddSubmodule`, `git submodule add [-b <branch>] -- <url> <path>`, without `--progress`, which git 2.30 takes for an update only), its notice shown at once. `RemoteJobDone` hands both to `SubmoduleRemoteDone` after the refresh, which asks the remotes again (`RecheckSubmodules`, as View > Refresh) and says it in a green banner, a new submodule shown and named with a reminder to commit it with .gitmodules (git stages both); a failure is told in the notice with Update Again, or for an add Try Again, which opens the dialog again with what failed (`FRetryPath`, `FRetryBranch`), since git removes what a failed add made. Tested in `tests/testsubmodules.pp` (`TestParseMoved`, `TestSubmoduleFolder`, `TestUpdateSyncAdd`, which allows local folders as remotes through `GIT_CONFIG_COUNT` with `SetTestVariable` from testgit, since TGittanRepo runs git itself).
- A block of changed lines can be discarded: put back to how it is in the version compared against (`umain.discard.inc`, `gittan.discard.pp`, the latter without LCL and tested in `tests/testdiscard.pp`). It is offered while `CanDiscard`: the change view of a tracked text file that is modified, renamed or deleted (not a new file, whose one block would empty it, nor a conflict or a binary), against a commit or a snapshot but not a range, since the right side is not the work tree then. Every changed row of `Edit` is live across the text: `DiscardAt` (from `EditMouseMove`) gives the block and the row the mouse is on (or the kept change, see below), `SetHotDiscard` keeps them (`FHotDiscard`, `FHotRow`; cleared by `EditMouseLeave`, a scroll of `Edit` and `BuildChangeView`, since the blocks are counted anew) and, once the mouse has rested on the row (`FPillTimer`, `PillPause`; at once while they are already up, so a mouse passing through the diff raises none), `ShowDiscardPills` shows `FDiscardPills` at the right end of the row, a `TGittanHoverPills` (`gittan.hoverpills.pp`: a strip of pills in a font a size under the form's, a child of the form like the popup lists, placed at the right end of an anchor rectangle, `OnPick` on a click, `OnLeave` when the mouse leaves it, colored by `SetColors` from `ApplyTheme`, each pill with a hint the strip shows itself under it after `Application.HintPause` in a `THintWindow`, and a pill with the discard arrow set `DiscardGap` apart from the ones before it, since it is the one that loses work), Reviewed (`rsKeepPill`, the keep, see below) after a check mark and Discard after an arrow going back round a circle, both for the block the row is in. The word hover goes on under them. The mouse going from the rows onto the pills keeps the block (`MouseOnDiscardPills` in `EditMouseLeave`) and going back from the pills onto the rows too (`MouseOnDiscardRows` in `DiscardPillsLeave`). `DiscardPillsPick` runs `KeepBlockAt` or `DiscardBlockAt`, which File > Discard Change (Cmd+Shift+Backspace) also uses for the block the caret is in (`BlockAtRow`; `UpdateDiscardItems`, from `UpdateChangeNav` and when the File menu opens, enables the two items). `DiscardThis` asks (`rsDiscardAsk` with `DiscardBackText`: how many lines go back to what, HEAD or the base as `BaseLabel` names it) and writes. A conflicted file has a gutter band of its own instead, `gutterTagDiscard`, added rightmost in `SetupEditor` and shown by `SetDiscardBand` (from `ApplyBlame`, so every view change and zoom sets it) on `Edit` only while `CanResolveBlocks` (see Resolving conflicts): `DrawDiscard` (from `EditDrawEditor`) paints a fork button on each conflict's first row in view, the one under the mouse on a disc, with its hint and the hand cursor through the blame hint's path (`FHoverBlame`), and `EditClickGutter` sends a click on it to `ResolveConflictAt`. `DiffBlock` reads the block out of `FChangeLines` (its deleted lines, its added lines, and the 1-based line the added lines start at in the file as it is, one past the last line for lines deleted at the end) and `DiscardBlock` writes the deleted lines over the added ones by line number, not from the diff's text, since the diff may have been taken with whitespace ignored: it reads the file as bytes, splits at LF, checks that the lines at that place are the block's added lines (`rsDiscardStale` otherwise, so a file that changed since the diff was taken is left alone), keeps the file's line end (that of its first line) and whether it ends with a newline, and makes a missing file for a block of deleted lines at line 1 (a deleted file comes back). The blocks discarded are kept in `FDiscards` (cleared by `OpenRepository`), and File > Undo Discard (Cmd+Alt+Z) writes the latest back through `Swapped` (the same block with old and new exchanged, checked against the file the same way), showing its file when another is shown; a discard that fails is dropped from the list too. Both refresh the repository (`RefreshRepository`) and say what they did in the status bar. The index is not touched: a staged change discarded in the work tree stays staged, as `git status` then shows.
- A block can be left out of the commit (`umain.leaveout.inc`, `gittan.leaveout.pp`, the latter without LCL and tested in `tests/testleaveout.pp`). While `CanLeaveOut` (`CanDiscard` while the tree's boxes choose, `CommitChoosing`, and no commit runs) the hover pills are Reviewed, Skip in Commit and Discard (`FPillChoose`, the middle one without an icon, `'k d'`); on a block left out, or any block of a file not ticked, the middle pill is Include in Commit (`LeaveOutCaption`, its hint from `LeaveOutHint`). File > Leave Change Out of Commit (Cmd+Alt+K, `FLeaveOutItem`, `MenuLeaveOutClick`) does the same for the block the caret is in, and `UpdateLeaveOutItem` (from `UpdateDiscardItems`) enables it and names it Include Change in Commit where the pill reads Include in Commit. The changes left out are pairs of a block, as keeps are, held in `FLeftOut` (a second `TGittanKeeps`, by path, cleared by `OpenRepository` and after a commit) and matched to the shown diff by `MatchKeeps` in `gittan.keep` (both lines of a pair get the index; `ApplyKeeps` uses it too): `ApplyLeftOut` (from `ShowChanges` once `FView` is set, and `RebuildKeeps`) first drops those the raw diff no longer holds (`TGittanKeeps.Prune`) and fills `FLeftOutOf` for `FChangeLines`. `BuildRows` gives a line left out the muted tint `bmLeftOutAdded` or `bmLeftOutDeleted` with its strip and no word shades. Leaving out a block's pairs that leaves nothing of the file (`AllLeftOut` over the raw diff) unticks the file instead; Include on a block of a file not ticked ticks it with every other block shown left out, so a kept line goes in, and Keep includes the pairs it keeps (`IncludeKept`), since a kept line has nothing to show it is left out. A ticked file with changes left out has a mixed box (`ApplyCommitChecks`) and the header the pill Include All (`FHeaderInclude`, `IncludeFile`); a click on a file's box takes it whole, in or out, and drops its changes left out (`DropLeftOut`). `StartCommit` turns them into commit parts (`CommitParts`): the file's diff against HEAD again (`FileChanges`, so with whitespace ignored when that is on, whose whitespace-only changes then go in) and `LeaveOutText`, which writes the work tree's bytes with each left out pair's deleted line put back and its added line taken out, by line as `DiscardBlock` does: the added lines are checked against the file (`rsDiscardStale`, which stops the commit with a banner), context lines are not, since `-w` may show them as HEAD has them, line ends and a missing final newline are kept, and a line put back gets the CR when the file's first line has one. A file whose changes left out are all gone goes in whole.
- A block can also be kept: shown as plain code for the rest of the session, once the user has looked at it and accepted it (`gittan.keep.pp`, no LCL, tested in `tests/testkeep.pp`; the Reviewed pill, `KeepBlockAt`, named for what the user means by it, since "Keep" read as keeping the change in the file). Neither the file nor git is touched: `FKeeps` (a `TGittanKeeps`, cleared by `OpenRepository`) holds the keeps of every file by path, and `ShowChanges` keeps the diff as git gave it in `FRawChangeLines` and applies them to `FChangeLines` (`FKeeps.Apply`), which the view is built from, so a kept line has no color, no strip and no button, the navigator does not count it, Hide Unchanged Lines folds it away, and `DiffBlock` still finds the right lines for a discard of the blocks left (a kept added line counts as a line of the file, as it is). A keep is one pair of a block (`TGittanKeep`: the k-th deleted line with the k-th added line, as the side-by-side view puts them next to each other, a deleted line past the added ones, or an added line past the deleted ones; `BlockPairs`), kept by its content and found again in a fresh diff by it (`ApplyKeeps`: each keep takes the nearest unkept pair with its text, by `Line`, where it was), so it survives the diff being taken again after the file changed elsewhere and goes by itself when its lines are gone; keeping a block keeps every pair of it. `ApplyKeeps` drops a kept pair's deleted line and makes its added line a context line, and gives `FKeptOf`, the keep each line of the rewritten diff comes from (-1 for none): the mouse resting on a kept line (`DiscardAt` reports it as `FHotKeep`) gets a Not Reviewed pill (`UnkeepAt`), and the header gets a "Show n Reviewed" pill (`SetChangeActions`, which also sets Edit for one of the repository's own files; `FHeaderUnkeep` is its index, and `HeaderAction` runs `UnkeepFile`). `RebuildKeeps` applies the keeps to the raw diff again and rebuilds the view at the same place (`RebuildIfChanges`), with the headings found again, since the blocks are others now. The old side's numbers after a kept block are those of the rewritten diff, not the old file's: the kept lines count as if the old file had them. The tree's counts and badges come from git and show the whole change, and a commit takes the whole file as before.
- Reverting files (`umain.revert.inc`): Revert Changes... in the file menu (`FRevertItem`; the tree, the summary's rows, the file header) puts a changed file back as HEAD has it, or, on a folder of the tree (`FContextFolder`, the menu's only enabled item then), every changed file under it; File > Revert File... (Cmd+Alt+Backspace) does it to the file shown. It asks first, and is offered only while the work tree is compared with HEAD (`CanRevert`) and no commit or remote job runs: Discard is one block against the version compared with, Revert whole files against HEAD. `TGittanRepo.RevertFiles` adds a rename's old path (from `git status`), saves every file on disk as a blob first (`hash-object -w --no-filters`; `ASaved` gets the path, a NUL and the id, empty for a file that was not there), then runs `restore --source=HEAD --staged --worktree` for the paths HEAD has and `rm --cached --ignore-unmatch` plus a delete for the rest (added and untracked files); a submodule is left alone. File > Undo Revert (`FRevertUndo`, latest last, cleared by `OpenRepository`) writes the saved blobs back with `RestoreReverted` and deletes again a file that was not there; the index is not brought back. Tested in `tests/testgit.pp` (`TestRevertFiles`).
- Renaming and removing files (`umain.movefiles.inc`): Rename or Move... and Remove from Git... in the file menu (`FMoveItem`, `FRemoveItem`; the tree, the summary's rows, the file header) act on a file the index holds (`TGittanRepo.IsTracked`, `ls-files`), not a folder, while no commit or remote job runs (`CanMoveFiles`; Rename also needs the file on disk). Rename asks the new path from the top of the repository (`InputQuery`, the old path filled in; backslashes become slashes, and one that is absolute or holds `..`, `.git` or a colon is refused in the status bar) and runs `MovePath` (`git mv -- <old> <new>`, the new folder made first since git mv makes none), so git shows a staged rename. Remove asks, Cancel the default, Stop Tracking (`RemovePaths` with `AKeep`: `git rm --cached`, the file kept on disk) or Delete (`git rm`, which refuses a file with changes not committed; its message goes in a red banner). `ChangedFiles` lists a file taken out of the index but kept once, as the staged deletion, not also as untracked, and `Commit` commits it through the temporary index (`Untrack`: a chosen path whose deletion is staged and whose file is on disk is taken out of that index with `rm --cached` too), since `commit --only` would take it as the work tree has it and see no change. Tested in `tests/testgit.pp` (`TestMoveAndRemove`).
- Clean (`umain.clean.inc`, `gittan.cleandlg.pp`), with a preview: File > Clean... - The change view numbers its lines itself (`SetRowNumbers`): the editor's own numbering would count the deleted lines kept in the text, so every line below a deletion showed a number too high. ATSynEdit has no hook for the number text, but its gutter decor (`GutterDecor`) draws a text per line in the bookmark band. So the number band is hidden, the bookmark band is widened to the widest number (`OptGutterWidthBookmarks`, reapplied by the editor on every update, so the option is set rather than the band), and each row gets its number as decor text; a deleted line (in the unified view), a gap, a filler and a hidden row get none. An added line's number takes the strip's green (the decor's `Tag` keeps the kind, `LineNumberColor` maps it). `ResetLineNumbers` restores the editor's numbering for the file view and the repository diff, `ApplyTheme` recolors the decor, and `OnChangeZoom` resizes the band. The number style is `All` so both views look alike. `UpdateNumberWidth` measures the character width itself (`EditorCharWidth`, a bitmap canvas with the editor's font at its zoom): the editor's `TextCharSize` is a placeholder until its next paint, and the first change view is built before the editor has ever painted (the summary hides it until then), so a band sized from it cut the numbers once the editor reapplied it.
- `gittan.changenav.pp` holds `TGittanChangeNav`, a pill at the right end of the file header with a previous and a next arrow and a counter ("2 / 5", or "– / 5" before the caret has reached a change). It paints itself with `TCanvas` primitives in colors `ApplyTheme` sets through `SetColors`, because a native push button keeps its light bezel on a dark background on macOS (the bezel takes the window's white background) while a caption follows the theme's text color and turned white on white. The header anchors it to its right edge and centers it vertically, so it stays in place when it grows with its counter; `TGittanFileHeader.SetChanges` shows or hides it and repaints the header, whose room for the path depends on the pill's width.
- `ChangeBlocks` in `umain.pp` lists the first line of every block of added/deleted lines from the second bookmark list; `GoToChange` jumps to the next or previous block from the caret and scrolls it near the top. The Go menu binds them to F7 and Shift+F7. `UpdateChangeNav` hides the pill while the list is empty and sets the counter to the last block the caret has reached. It runs from the editor's `OnChangeCaretPos`, but through `Application.QueueAsyncCall`: the event fires inside the editor's own updates, and resizing a child there (the pill grows with its counter, and was the editor's child then) made the editor recompute its scroll position from a half-updated state and scroll sideways after a theme change.
- The gutter's line states band (3 px, between the numbers and the fold icons) is the diff's strip: `MarkLine` sets an added line to `TATLineState.Added` and a deleted one to `Changed`, and `ApplyTheme` sets `Colors.StateAdded` green and `Colors.StateChanged` red. ATSynEdit marks every line of a freshly set text as `Added`, so `ShowText` resets the states to `None` before the marks and shows the band through `SetLineStatesBand`; `OpenFile` and `FormCreate` hide it, since a plain file has no changes.
- The gutter's fold band is shown where `FoldingShown` allows: in the file view, and in the unified change view while View > Hide Unchanged Lines is off (`SetFoldBand`, from `ShowEditor` and `BuildChangeView`), its icons only under the mouse (`OptGutterShowFoldAlways` off). A click folds the lexer's range (a function, a class, a section) to its first line, drawn dimmed in a grey frame (`CollapseMark*`). View > Folding has Fold and Unfold at the caret (Cmd+Alt+-, Cmd+Alt++) and Fold All and Unfold All (with Shift), the editor's own fold commands by the item's `Tag` (`MenuFoldClick`); the menu is enabled, and the shortcuts act, only where `FoldingShown`. A find, a Go to Definition (`FoldAction`) or F7 that lands in a folded line unfolds it there; elsewhere a hidden line is the diff's and stays hidden. A refresh or a view option rebuilds the text: `KeepFolds` remembers the folded ranges by the file line they start on (`FileLineOfRow`: the row in the file view, `FNewNum` in the change view) and `RestoreFolds`, from `AdapterParseDone`, folds them again once the lexer has parsed the same file. Hide Unchanged Lines, Side by Side and the history view keep the band hidden: they hide lines through the folding mechanism (below), which a fold or unfold of a lexer range would disturb, or line up two editors row by row. Folding stays enabled (`OptFoldEnabled`): the wrap info skips hidden lines only then, and the adapter adds no fold ranges without it.
- The diff line colors in `EditCalcBookmarkColor` are faint tints of the editor background (GitHub's values for light, the same blended onto the dark palette), so the lexer's syntax colors still read on top of them.
- `gittan.worddiff.pp` holds `WordDiff`: for every run of deleted lines followed by added lines it tokenizes both runs (words, runs of spaces, single punctuation characters, a break token per line end), takes a longest common subsequence of the tokens, and returns the unmatched tokens as character spans per diff line (UTF-16 units, as the editor counts columns; adjacent spans and spans with only spaces between them are joined). A block whose sides share less than `MinCommon` of their text (rewritten, not edited) and a block over `MaxBlockLines` or `MaxCells` token pairs get no spans. `BuildChangeView` computes `FWordSpans` from `FChangeLines`, `FillChangeEditor` puts them on the shown rows through `MarkWords`, and `ShowRepoDiff` does the same on the raw diff with the spans shifted one column for the marker (its hunk and file header lines get a blank marker first). `MarkWords` uses the editor's attribs (`Attribs.Add` with a `TATLinePart` that sets only `ColorBG`, so the lexer's text color stays), tagged `tagWordAdded`/`tagWordDeleted`; `WordColor` gives the shade for the theme and `RecolorWords` in `ApplyTheme` recolors the existing marks. Setting `Text` clears the attribs, so `ShowText` needs nothing extra.
- View > Ignore Whitespace (Cmd+Alt+I, `IgnoreWhitespace` in the settings) sets `TGittanRepo.IgnoreWhitespace`, which `RunDiff` turns into `-w` on every `git diff`: the numstat counts, the file diffs and the repository diff all leave whitespace changes out, and `WordDiff` then treats two runs of spaces as equal. The toggle runs `RefreshRepository`. `FileChanges` with an empty diff asks `git ls-files` whether the file is tracked: a tracked file (its changes whitespace only, or a mode change) is shown with every line unchanged, an untracked one all added. The watcher's own repository runs without the flag; it only needs to notice a change.
- The editor is a viewer: `ModeReadOnly` is set in `FormCreate`. ATSynEdit silently ignores `Text` and `LoadFromFile` while read-only, so `ShowText` and `OpenFile` clear the mode around the load and set it again. Loading does not clear the second bookmark list, so they call `BookmarkDeleteAll_2` first. There is no Save command.

## Editing Guidance
- Keep changes focused and minimal. Avoid unrelated refactors or formatting-only edits.
- Unit files must use the `.pp` extension. Formatting follows `JCFSettings.xml` (JEDI Code Formatter).
- When a unit grows large (like a main form), break code out into `.inc` include files.
- PasDoc `{** ... }` comments on public APIs in interfaces; banner-style comments in implementations.
- Cross-platform gotcha: `{$IFDEF UNIX}` does not cover Haiku. Use `{$IF DEFINED(UNIX) OR DEFINED(HAIKU)}` where both apply.
- Do not edit `backup/` directories, `link*.res`, or other generated artifacts.
- Update documentation when behavior or workflow changes.

## Validation
- After code changes, run the narrowest relevant build target first.
- To check a language or RTL detail in isolation, run a snippet through `instantfpc` rather than adding a throwaway unit or project to the tree.

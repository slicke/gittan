# AGENTS.md

## Scope
This file applies to the Gittan repository root and its subdirectories.

## Working Rules
- The units (`gittan.*.pp`) live in `src/`, split in two: `src/core/` holds the units without the LCL, which plain `fpc` builds and the tests use, and `src/ui/` the controls, the units that need the LCL or a widgetset, and the main window (`uwindow.pp`, `uwindow.lfm`) with the repository frame it holds (`umain.pp`, `umain.lfm`, `umain.*.inc`). `Gittan.lpr` and `Gittan.lpi` stay in the root. A new unit goes in `src/core/` when it builds without the LCL. A unit keeps its dotted name as its file name, since FPC finds a unit by file name and does not map folders to names. The project's `OtherUnitFiles` is `src/core;src/ui`, and the test build (Makefile, make.ps1 and the CI workflow) has only `-Fusrc/core`, so a core unit that comes to use the LCL breaks `make test`.
- Prefer the project Makefile instead of calling `lazbuild` directly. Run `make help` before inventing a new command or target.
- On macOS use `make` (or `gmake`); it finds lazbuild in `/Applications/lazarus` when it is not on PATH.
- Prefer the smallest relevant target: `make`, `make debug`, `make rebuild`, `make run`.
- On Linux `make` builds with gtk3 and links against GTK 3 and its stack: `gtk3-devel` on Fedora, `libgtk-3-dev` on Debian and Ubuntu (what CI installs); without it the link stops at `libgtk-3.so.0`.
- On Windows, where there is no make, `.\make.ps1` has the same targets (build, debug, rebuild, run, lexlib, deps, ide, test, clean, help) and finds lazbuild as Trndi's does (LAZBUILD, PATH, `C:\lazarus`, `C:\fpcupdeluxe\lazarus`). A build from the Lazarus IDE (F9) does not copy the lexers: run `.\make.ps1 lexlib` once, or after the lexers change.
- `make test` builds `tests/gittantests.lpr` with plain `fpc` (no LCL) and runs it: fpcunit tests of the non-visual units in `src/core`, a `tests/test<name>.pp` each (`gittan.git` parsing on its own, the rest against a temporary repository made with the real git). CI runs it on every leg. A new non-visual unit gets a `tests/test<name>.pp` registered in the runner. `tests/testhelpers.pp` holds what the tests share (`RemoveTree`, the deletion of a test's temporary folder) rather than each test its copy. The runner points `GIT_CONFIG_GLOBAL` at a config file of its own (an identity, `core.autocrlf=false`, no signing) and sets `GIT_CONFIG_NOSYSTEM`, and clears `GIT_CONFIG_COUNT` and `GIT_CONFIG_PARAMETERS` (what a parent process or `git -c` passes on), so the developer's and the system's git config (signed commits, a hooks path, Git for Windows' autocrlf) do not reach the tests; a test that needs a setting sets it in its repository or through `GIT_CONFIG_COUNT`.

## macOS linking
- Darwin targets link with Apple's ld. The first ld of Xcode/CLT 27 rejected the Objective-C method lists FPC 3.2.x emits ("malformed method list atom"), and Gittan linked through LLVM's `ld64.lld` for a while; ld-27037 (August 2026) links them again. On "malformed method list atom", update Xcode or the Command Line Tools.
- Debug builds on macOS must use DWARF 2 (`-gw2`); FPC 3.2.x's DWARF 3 writer fails on Objective-C classes.
- `Gittan.lpi` has two build modes. `make`, `make rebuild`, `make run`, `.\make.ps1 build` and CI use Release (`--bm=Release`: `-O2`, no debug or line info, smart linking `-CX -XX`, `-Xs`, its units in `lib/<cpu>-<os>-release`); `make debug` uses Default (DWARF 2, line info, `-O1`). lazbuild's `--opt` cannot take `-g` away, which is why it is a mode. On macOS `-Xs` leaves the symbols in, so the CI's macOS leg runs `strip` on the bundle's binary before signing it. A new compiler option that both builds need goes in both modes.

## CI
- `.github/workflows/build.yml` builds on every push to main and every PR to main or develop: macOS arm64 (cocoa, `.dmg`), Windows x64 (win32, `.zip`) and Linux amd64 (gtk3, `.tar.gz`), each with `lexlib/` beside the executable (in `Contents/Resources` for the bundle). The toolchain is Lazarus 5.0RC1 on every leg (FPC 3.2.4rc2 on macOS, 3.2.2 elsewhere).
- The checkout fetches the submodules, and every leg registers the vendored `.lpk` files with `lazbuild --add-package-link` (the list is `VENDOR_PACKAGES` in the workflow, in dependency order). A new vendored package must be added there too, and in the Makefile and `make.ps1`.
- The macOS leg replaces the bundle's symlink with the binary and signs the bundle ad hoc. The Windows runner has no make, so that leg runs `make.ps1 build` (with `--lazarusdir=C:\Lazarus`) and `make.ps1 test`, the targets a developer runs on Windows.
- Every push to main publishes a release, as in Trndi: the `version` job takes the next build number from the `build-<n>` tags (100 when there is none), and `publish` runs after the three builds, downloads the packages and creates the release `build-<n>` (tagged on the pushed commit by `gh release create`) with the commits since the previous build as its notes: as a draft, then the packages uploaded (`--clobber`), then published, so `releases/latest` never lacks them; a re-run of a publish that failed halfway finds the draft and uploads again, and leaves a release already published alone. A failed leg skips the release. PRs only upload artifacts. The build job passes the number to every leg as `GITTAN_BUILD`, which `gittan.update.pp` compiles in (`{$I %GITTAN_BUILD%}`); a local or PR build has none. The website on the `gh-pages` branch links to `releases/latest`.

## Vendored packages
- `vendor/` holds git submodules: ATSynEdit, its dependencies ATFlatControls and EncConv, and BGRABitmap; EControl and ATSynEdit_Ex for syntax highlighting; CudaText-lexers, the lexer collection; MetaDarkStyle, the dark mode of the LCL's native controls on Windows; and LazInk (TonyStone31/LazInk), which draws HTML and Markdown on the canvas with no browser engine, for the Markdown preview. Clone with `git clone --recursive` or run `git submodule update --init`.
- The Lazarus package links point at these copies, and the IDE is built with ATSynEdit and its dependencies. EControl, ATSynEdit_Ex, MetaDarkStyle and LazInk are used at runtime only (LazInk's package is RunAndDesignTime, but the IDE needs no rebuild for it), so changing them needs no IDE rebuild.
- `make deps` (`.\make.ps1 deps`) registers every vendored package with `lazbuild --add-package-link` and compiles it, in the order of `VENDOR_PACKAGES`; run it after a fresh clone or a submodule move. `make ide` (`.\make.ps1 ide`) rebuilds the Lazarus IDE with `lazbuild --build-ide=` and the IDE's own build profile. The package list is in the Makefile, in `make.ps1` and in the CI workflow; a new vendored package goes in all three.
- Do not edit files under `vendor/`. Update a package by moving its submodule to a new commit, then run `make deps`, and `make ide` if it is one the IDE is built with.

## Main window
- `uwindow.pp` holds `TGittanWindow`, the main form, a `TRepoWindow` (declared in `umain.pp`, what a frame asks of its window): it makes `App` (`gittan.app`, what every repository shares: the settings, the lexers, the icon, the update check) first and frees it last, keeps its own place and size, owns the chrome (the macOS toolbar and the strip under the title bar, the own title bar on Windows and GTK 3) and holds the frames. `umain.pp` holds `TRepoFrame`, a `TFrame` with everything one repository shows, the filter field over its tree and the header's navigator and pills included; the window makes each with no owner (`NewFrame`), places it, calls `Init` (what the form's `FormCreate` did), shows one at a time (`ActivateFrame`, which calls the frame's `Activated`: the menu, the caption, the title bar's shade and band) and passes its events to the frame shown (close and close query to all). Beside the frames the window holds the forge view (`uforge.pp`, `TForgeView`), one for the window, shown over the frame shown from the globe at the right end of the chrome (`ShowForgeView`, `HideForgeView`; spec/github.md) with a menu of its own, the frame counting as in the background meanwhile. The tabs show the frames (`UpdateTabs`: the toolbar's strip on macOS, the own title bar with its menu button on Windows and GTK 3); New Tab, Close Tab and Next/Previous Tab call `TRepoWindow.NewTab`, `CloseFrame` and `StepTab`, and the open tabs are kept in the settings (`Tabs`, `ActiveTab`). A repository opens through `TRepoWindow.OpenRepository`, never the frame's own from inside the frame: it shows the frame that has it open, else uses the shown frame while that one is empty (`IsBlank`), else a new frame; an `AOnOpened` callback gets the frame it opened in as `Sender`. A frame touches the window's chrome only while it is shown (`FWindow.IsActive(Self)`, `OwnBar` nil otherwise); `Handle` for Cocoa, `Menu`, `Caption`, `ActiveControl`, `BoundsRect` and `Visible` go through `FWindow`. `Self` is the frame, and a control parented to `Self` lies over the window's client area.
- `umain.pp` is split: the class and the core (theme, menus, views, repository, tree) are in the unit, the change view building in `umain.diffview.inc` and the menu actions (settings, recent, find, zoom, view options, file stepping, context menus, compare) in `umain.actions.inc`.

## Editing Guidance
- Keep changes focused and minimal. Avoid unrelated refactors or formatting-only edits.
- Unit files must use the `.pp` extension. Formatting follows `JCFSettings.xml` (JEDI Code Formatter).
- When a unit grows large (like a main form), break code out into `.inc` include files.
- PasDoc `{** ... }` comments on public APIs in interfaces; banner-style comments in implementations.
- A control that paints itself takes its lengths (row heights, margins, icon sizes, radii) through `Px` in `gittan.theme`, which scales a 96-DPI value to the screen's: its text comes in the scaled font (`Scaled` is on), so unscaled rows clip it on Windows and GTK above 100 %. Cocoa reports 96, so `Px` changes nothing on macOS. The form scales every control created in FormCreate once more after it (`TCustomForm.AfterConstruction` runs `AutoAdjustLayout` after `DoCreate`), heights and border spacing included, so a control that sets its own height or its children's from `Px` sets them again in a `DoAutoAdjustLayout` override for `lapAutoAdjustForDPI`.
- Cross-platform gotcha: `{$IFDEF UNIX}` does not cover Haiku. Use `{$IF DEFINED(UNIX) OR DEFINED(HAIKU)}` where both apply.
- Do not edit `backup/` directories, `link*.res`, or other generated artifacts.
- Update documentation when behavior or workflow changes: the matching `spec/` file for an area, AGENTS.md for the rules that apply everywhere. A new area gets a spec file and a line in the Specs list.
- `CHANGELOG.md` lists the changes for users, under Unreleased until a build publishes them: a change someone would notice (a feature, a behavior, a fix of a shipped build, a build or platform fix) gets a line there, in plain words; a fix of work not yet in a build does not.

## Validation
- After code changes, run the narrowest relevant build target first.
- To check a language or RTL detail in isolation, run a snippet through `instantfpc` rather than adding a throwaway unit or project to the tree.

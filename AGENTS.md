# AGENTS.md

## Scope
This file applies to the Gittan repository root and its subdirectories.

## Working Rules
- Prefer the project Makefile instead of calling `lazbuild` directly. Run `make help` before inventing a new command or target.
- On macOS use `make` (or `gmake`); it finds lazbuild in `/Applications/lazarus` when it is not on PATH.
- Prefer the smallest relevant target: `make`, `make debug`, `make rebuild`, `make run`.

## macOS linking
- Apple's ld from Xcode/CLT 27 rejects the Objective-C method lists FPC 3.2.x emits, and `-ld_classic` is gone. Darwin targets therefore link through LLVM's `ld64.lld` (`brew install lld`) via the shim in `tools/darwin-lld/ld`, taken from Trndi.
- `Gittan.lpi` adds `-FD$(ProjPath)/tools/darwin-lld` for `TargetOS='darwin'` only, so lazbuild and the Lazarus IDE both use it. Do not remove that conditional.
- Rebuilding the Lazarus IDE (for example after installing a package) also needs the shim:
  ```sh
  /Applications/lazarus/lazbuild --build-ide="-FD$PWD/tools/darwin-lld" --ws=cocoa
  ```
  Tools > Build Lazarus inside the IDE uses Apple's ld unless the build profile carries the same `-FD` option.
- Debug builds on macOS must use DWARF 2 (`-gw2`); FPC 3.2.x's DWARF 3 writer fails on Objective-C classes.

## CI
- `.github/workflows/build.yml` builds on every push to main and every PR: macOS arm64 (cocoa, `.dmg`), Windows x64 (win32, `.zip`) and Linux amd64 (qt6, `.tar.gz`), each with `lexlib/` beside the executable (in `Contents/Resources` for the bundle). The toolchain pins are Trndi's (Lazarus 4.8).
- The checkout fetches the submodules, and every leg registers the vendored `.lpk` files with `lazbuild --add-package-link` (the list is `VENDOR_PACKAGES` in the workflow, in dependency order). A new vendored package must be added there too.
- The macOS leg installs Homebrew's `lld` for the `tools/darwin-lld` shim, replaces the bundle's symlink with the binary and signs the bundle ad hoc. The Windows runner has no make, so that leg copies the lexers and calls lazbuild itself; keep it in step with `make lexlib`.

## Application icon
- `icons/gittan-source.png` is the artwork (a rounded square on a white background with a gray halo). `make icons` runs `tools/makeicons.swift` (macOS only: CoreGraphics and `iconutil`), which measures the outline, cuts the icon out with a transparent background and writes `icons/gittan.png` (1024, the master), `icons/png/gittan-<n>.png` (16 to 512, for Linux desktop files), `icons/Gittan.icns` and `Gittan.ico`. Commit the generated files; other platforms only consume them.
- The halo cannot be told from the icon's light gray right side by color, so the script measures the left, top and right edges and the bottom-left corner profile, where the frame is dark blue, checks it against the dark red bottom-right corner, and mirrors it to the top corners. A new artwork must keep that layout, or the script needs new edge probes.
- `Gittan.ico` beside `Gittan.lpi` is the project icon (`<Icon Value="0"/>` in the .lpi means it is set); Lazarus compiles it into the executable's resources, which the LCL uses for the window and taskbar icon on Windows and Linux. The .icns insets the artwork to Apple's 824/1024 grid so it sits like other dock icons; the .ico and PNGs fill their canvas.
- Lazarus creates `Gittan.app` without an icon, so the Darwin build targets in the Makefile copy `icons/Gittan.icns` into `Contents/Resources` and add `CFBundleIconFile` to `Info.plist` after lazbuild. A bundle built from the Lazarus IDE lacks the icon until the next `make`. Finder caches icons; `touch Gittan.app` or a relaunch of Finder refreshes it.

## Vendored packages
- `vendor/` holds git submodules: ATSynEdit, its dependencies ATFlatControls and EncConv, and BGRABitmap; EControl and ATSynEdit_Ex for syntax highlighting; and CudaText-lexers, the lexer collection. Clone with `git clone --recursive` or run `git submodule update --init`.
- The Lazarus package links point at these copies, and the IDE is built with ATSynEdit and its dependencies. EControl and ATSynEdit_Ex are runtime-only packages, so changing them needs no IDE rebuild.
- Do not edit files under `vendor/`. Update a package by moving its submodule to a new commit; rebuild the IDE as above if it is one the IDE is built with.

## Syntax highlighting
- `gittan.lexers.pp` loads every EControl lexer (`*.lcf`) from one folder and picks a lexer by file name. `umain.pp` shows one read-only editor connected through a `TATAdapterEControl`; the Syntax menu changes its lexer.
- CudaText-lexers keeps one subfolder per lexer, but EControl loads from a flat folder. `make lexlib` copies the lexers into `lexlib/` (generated, gitignored); every build target runs it.
- At runtime the folder is found through `GITTAN_LEXLIB`, then `lexlib` beside the executable, then `Contents/Resources/lexlib` in a macOS bundle.
- After assigning a lexer, call the editor's `DoEventChange(0)`. Without it the adapter never parses and the text stays uncolored.
- `TGittanLexers.Load` normalizes every lexer style: `BgColor` is cleared so lexers only color text (line backgrounds are reserved for the diff colors), and a system font color such as `clWindowText` becomes `clNone`. Cocoa resolves system colors through the desktop theme, so in dark mode they turn white on the editor's light background and the text disappears (seen with the Delphi resources lexer on `.lfm`).
- After replacing the text through `Text` (not `LoadFromFile`), call `WrapInfo.Clear` and `Update(True)`. Setting `Text` skips the wrap rebuild while no fold ranges exist and never flags it, so once the lexer adds folds the old wrap items are reused and lines paint cut off or blank.

## Dark mode
- The empty view draws the application icon from `FAppIcon`, a `TIcon` the form loads from the `MAINICON` resource, not from `Application.Icon`: on Cocoa that one keeps to its first, 16 pixel image whatever `Current` is set to, and drawing any `TIcon` goes through its handle, made from that first image. So the summary sets `Current` on its own copy to the best size for the device pixels and copies that raw image into a `TBitmap` (`LoadFromRawImage`) it draws.
- The native controls (tree, status bar, menus) follow the desktop theme on their own; `Info.plist` does not set `NSRequiresAquaSystemAppearance`. Gittan only adapts what it colors itself.
- `gittan.theme.pp` holds `IsDarkMode` (the window system color darker than its text color, so it works with every widgetset), `ColorLuminance` and `LightenForDark`. Nothing forces an appearance the way Trndi's `nsutils.simpledarkmode` does.
- `ApplyTheme` in `umain.pp` resets `Edit.Colors` with `Init` and, in dark mode, sets a dark palette on top; `EditCalcBookmarkColor` picks dark or light diff colors from `FDark`. The LCL raises no event when the desktop theme changes (`OnActivate` does not fire reliably on Cocoa either), so `ThemeTimer` asks `IsDarkMode` every other second and reapplies the theme on a change; Cocoa reports the new system colors right away.
- The lexer collection uses colors tuned for a white background (clNavy, clMaroon, clBlack and so on). `TGittanLexers.NormalizeStyles` remembers every style's color, and `ApplyTheme(ADark)` restores them for light or runs them through `LightenForDark` for dark: black becomes `clNone` so the editor's text color applies, every other dark color is blended toward white until it reaches a fixed brightness.

## Git
- `gittan.git.pp` wraps the `git` command line tool (found on PATH) through `RunCommandIndir` from fcl-process; it does not link libgit2. `TGittanRepo.Open` resolves any folder to its work tree root with `rev-parse --show-toplevel`.
- File > Open Repository (Cmd+Shift+O) uses the `TSelectDirectoryDialog` on the form (a folder on the command line, `gittan <folder>`, a folder dropped on the window, or File > Open Recent opens one too), then `OpenRepository` in `umain.pp` fills the tree and the summary from `ChangeStats`. There is no toolbar: the summary's hint tells a first-time user what to do. A folder that is not a repository, or a git failure, is shown in the empty view in the hint's place (`ShowError`), not in a dialog.
- `gittan.settings.pp` holds `TGittanSettings`, an ini file in `GetAppConfigDir` (`~/.config/gittan/gittan.ini` on Unix): the window bounds and state, the tree width, the editor font and zoom, the view options (word wrap, hidden unchanged lines, context lines, side by side), an external editor command, and the recent repositories. `ApplySettings` in `umain.actions.inc` applies it before the menu is built, `FormClose` saves it. With no argument on the command line Gittan reopens the most recent repository. The ini is written only on a normal close; a killed process keeps the previous one.
- `umain.pp` is split: the class and the core (theme, menus, views, repository, tree) are in the unit, the change view building in `umain.diffview.inc` and the menu actions (settings, recent, find, zoom, view options, file stepping, context menus, compare) in `umain.actions.inc`.
- `gittan.watch.pp` holds `TGittanWatcher`, a thread that polls the open repository every two seconds (`WatchInterval` in `umain.pp`) and fires `OnChange` in the main thread (through `TThread.Queue`) when `TGittanRepo.Fingerprint` changed: the branch, the status of every changed file, the diff against HEAD, and the size and time of every untracked file. The thread has its own `TGittanRepo`, so git never runs on the main thread for the poll. `Stop` clears the handler before `WaitFor`, because `WaitFor` on the main thread runs the queued calls while it waits. `OpenRepository` restarts the watcher; `RefreshRepository` in `umain.pp` (also View > Refresh, Cmd+R) reloads the tree, summary and status bar through `LoadRepository` and restores the view from `FView`: the expanded folders, the selected file with its caret and top line, or the repository diff. A selected file that is no longer changed falls back to the summary, which says so in a notice line under its header (`TGittanSummary.Notice`, cleared when the user picks a view).
- `gittan.findbar.pp` holds `TGittanFindBar`, the row under the header that Go > Find (Cmd+F) shows: a native `TEdit`, a `TGittanChangeNav` pill reused as previous/next with the match counter, a "Not found" note and a close cross. It only raises `OnSearch`; `FindText` in `umain.actions.inc` searches the editor's lines itself (case-insensitive substring, up to `MaxMatches`), picks the first match after the caret (or the selection start, so retyping extends the match in place), selects it through `DoGotoPos` with the caret after the match, and answers with `SetMatches`. Hidden lines of the change view are skipped. Enter and Shift+Enter step, Escape closes; Find Next/Previous (Cmd+G, Cmd+Shift+G) work with the bar closed.
- `gittan.fileheader.pp` holds `TGittanFileHeader`, a self-painted bar above the editor (`alTop` in `EditorPanel`, the panel from `umain.lfm` that holds the editor and the summary's scroll box): the file's badge from `TreeImages`, its directory dimmed and its name in full color, then on the right the added and deleted counts (or "binary"), the lexer name and the change navigator, which it owns as a child. `ShowChanges` fills it from `FStats` (the stats of the last `LoadRepository`), `ShowRepoDiff` titles it "Repository diff" with the totals, `OpenFile` shows the path alone; `UpdateStatus` sets the lexer name. `ShowEditor` shows it and `ShowSummary` hides it. `ApplyTheme` colors it like the summary, on the gutter's shade.
- `UpdateStatus` keeps the status bar to the repository: "repo on branch [vs base] · N changed files" whenever one is open, since the header names the file and its lexer; the full file path when a plain file is open without a repository, else the lexer name. The full path of the repository or file is the bar's hint. A click on the bar shows the summary; its popup menu copies the branch name or the repository path. `UpdateStatus` also checks the Syntax menu: Automatic (the lexer from the file name; `FManualLexer` is set by a manual pick and cleared when the view changes), and the lexer in use, found through the item's `Hint`, which keeps the name without accelerator ampersands.
- The editor's minimap (`OptMinimapVisible`) is on: it paints the same line backgrounds as the text, so it shows where in the file the changes are. Its tooltip is off, and `OptMinimapCharWidth` keeps it narrow (the default takes a fifth of the editor).
- `UpdateCaption` names the window after the repository, or after the file when none is open; the header names the file, so the title does not change with the selection.
- `ChangeStats` in `gittan.git.pp` joins `ChangedPaths` with `git diff --numstat --no-renames <base>` (or without a base before the first commit) into a `TGittanFileStats` array: path, change kind, added and deleted lines, or `Binary` when numstat prints `-`, and `Staged`/`Unstaged` from the two status columns. A staged file (the index holds any of its change) gets the badge with the check mark from `StagedIcon` in `gittan.icons.pp`, and the summary row and the file header say "staged" or "partly staged" (`SetStage`).
- `TGittanRepo.Base` is the commit the work tree is compared against, empty for HEAD; `RunDiff` puts it into every `git diff` call (before the `--` of a path list) and falls back to the index when HEAD does not exist. With a base set, `ChangedFiles` builds the status lines from `git diff --name-status` plus the untracked files from `git status`, so the tree, the counts, the file diffs and the watcher (which gets the base in its constructor) all follow it. View > Compare With lists `Refs` (local branches, remote branches, tags, most recent commit first, symbolic refs such as origin/HEAD left out; rebuilt by `LoadRepository`) and Other… asks for any ref; `SetBase` in `umain.actions.inc` restarts the watcher and keeps the previous base, with the error as the summary's notice, when git rejects the new one. An untracked file is counted by `CountNewFile` with git's own rule (a NUL in the first 8000 bytes makes it binary). `Branch` is `git symbolic-ref --short HEAD`, which also names an unborn branch, or the short commit id when HEAD is detached.
- The space right of the tree is shared by the editor and the summary; `ShowEditor` and `ShowSummary` in `umain.pp` switch between them. `gittan.summary.pp` holds `TGittanSummary`, a self-painted control (repository name, branch, totals, then one row per file with its badge from `TreeImages`, the counts and a bar comparing the change sizes; "Working tree clean" with a check mark when there are no rows) that sits in a `TScrollBox` created in `FormCreate` for native scrolling. Its `Selected` path marks the row of the file the editor showed last (`ShowChanges` sets it, the other views clear it). `SetRepository` aligns it `alTop` with its height from the content, `SetMessage` (the hint before a repository is open: the application icon, the message and the menu path with its shortcut) aligns it `alClient`; the scroll box's `OnResize` keeps its `MinHeight` at the box height so its background fills the box. A click on a row selects the file in the tree through `SummarySelectFile`, which runs the usual selection handler. `ShowSummary` clears the tree selection so picking the same file again fires it. The View menu has Summary (Cmd+1) and Repository Diff (Cmd+2); `ShowRepoDiff` shows `git diff HEAD` (or `git diff` before the first commit) in the editor under the Diff lexer with its `+`/`-` lines colored.
- The `TTreeView` on the left lists only the changed files, taken from the same `git status --porcelain` output through `ChangedPaths` (untracked files included, a rename shown under its new path), folders first, every folder expanded (`FullExpand` in `FillFileTree`; `RefreshRepository` closes again the folders the user had closed). It has no border and no tree lines (`BorderStyle = bsNone`, no `tvoShowLines`/`tvoShowRoot`), so on the widgetsets that draw them it looks like the native tree on macOS. A file node has `Data` set; folders and submodules have `Data = nil`.
- `ChangedPaths` also condenses each file's "XY" status into a `TGittanChangeKind` (`ChangeKind`), stored in the list's `Objects`. The tree shows it as an icon from `TreeImages`: `gittan.icons.pp` draws the icons at startup with BGRABitmap (a direct dependency of the project, as it already is of ATSynEdit), a folder, one colored badge per kind with git's status letter (M, A, D, R, U for untracked, ! for a conflict), and the folder with a dot in each kind's color (`FolderIcon`), at both 16 and 32 pixels through `AddMultipleResolutions` so the tree picks the sharp one on a Retina screen. There are no image files to ship. A folder node carries the dot of the most severe change inside it (`WorseKind`: conflict, deleted, modified, renamed, added, untracked); `FillFileTree` walks up from each file and reads the folder's current kind back from its `ImageIndex` with `FolderIconKind`.
- Selecting a file calls `ShowChanges`: `FileChanges` runs `git diff --no-renames -U99999999 <base> -- path` so the whole file is one hunk, with deleted lines kept in place. The lines with their markers are kept in `FChangeLines`, and `BuildChangeView` in `umain.diffview.inc` turns them into the editor's rows (`FRows`, `TGittanRow`). The `+`/`-` markers are stripped from the text and become line backgrounds (green added, red deleted) through the editor's second bookmark list (`BookmarkSetForLine_2`), whose entries color a line without a gutter icon; `OnCalcBookmarkColor` maps the kind to the color. An untracked file is read from disk and shown all green. The raw repository diff gets the same colors on its `+`/`-` lines.
- View > Hide Unchanged Lines (Cmd+Shift+U) keeps only the changed lines with View > Context Lines (1, 3, 5 or 10) around them. The hidden lines stay in the text, so the lexer parses the whole file (a comment that starts in a hidden line still ends where it should), marked with `Strings.LinesHidden`, the editor's own folding flag: the wrap info leaves them out, `WrapStructInvalidate` and `Update(True)` rebuild it. Each run of hidden lines gets a gap row before it ("⋯ N unchanged lines ⋯", bookmark kind `bmGap`, no line number); a click on it (`EditMouseUp`, the caret is on the clicked row by then) adds the run to `FExpanded` and rebuilds the view (`ExpandGap`). The gaps opened are kept while the same file is shown again, as on a refresh. The caret must never sit on a hidden row (the editor would unfold the lexer range around it): `VisibleRow` moves it to the next shown row wherever a row index is restored.
- View > Side by Side (Cmd+Shift+S) shows the old side in `FEditOld`, a second `TATSynEdit` with its own adapter (`FAdapterOld`, an adapter parses one text) left of the editor, with a splitter (`FSideRatio` keeps its share). `BuildChangeView` pairs the rows: a context or gap row goes to both sides, a run of deleted lines and the run of added lines after it go to the old and the new side, the shorter padded with filler rows (`bmFiller`, blank, no number). The old side numbers its lines from the old file (a deleted line's number in red), the new side from the new. `ChangeBlocks` ignores gap rows and counts a filler as part of its block, so the navigator still counts changes. `EditorScroll` keeps the two in step on the user's scrolling; `SyncOldSide` does it after every programmatic move (it also sets `LineTopTodo` and runs again from the message loop, since an old side just shown has no wrap info and its resize resets the line top at the next paint). Word wrap is off while both sides show, since wrapped rows would not line up. Every editor helper (`ShowText`, `MarkLine`, `SetRowNumbers`, `ResetLineNumbers`, `UpdateNumberWidth`, `SetLineStatesBand`, `ApplyEditorColors`) takes the editor as a parameter; `SetupEditor` applies the shared options to both, and zoom (View > Zoom In/Out/Actual Size, or the mouse wheel) and View > Font… apply to both.
- Go > Next/Previous Change (F7, Shift+F7) go on to the next or previous changed file in the tree (`StepFile`) past the last or first block, and wrap around in the file only when there is no other file; Go > Next/Previous File (F8, Shift+F8) step files directly.
- Scrolling on with the wheel (or trackpad) at the bottom of a file in the change view pulls in the next file (`EditMouseWheel` in `umain.actions.inc`, set on both editors; `NeighbourFile` finds the node, `StepFile` uses it too). The LCL's `OnMouseWheel` fires before ATSynEdit scrolls, so a wheel step that already sits at the bottom (`ScrollVert.SmoothPos` at `SmoothPosLast`) adds its delta to `FOverscroll`; one that scrolls, or scrolls up, resets it, and `FOverscrollTimer` forgets a pull left half way after `OverscrollForget` ms. At `OverscrollNeeded` (600: five notches of a mouse wheel, about 75 px of a trackpad, since Cocoa's LCL scales a precise delta to 8 per pixel) the next file is shown from its top. A trackpad's momentum runs on after the jump, so the pull is disarmed until the wheel has paused `OverscrollPause` ms (`FOverscrollArmed`). `EditDrawEditor`, the editor's `OnDrawEditor` hook, paints a pill ("Next: name ↓") that rises from the bottom edge of the text and fills from the left with the pull; its colors (`FPull*`) are set in `ApplyTheme` beside the navigator's. There is no pull up to the previous file: after a jump the view sits at the top, where a momentum tail would bounce straight back.
- The tree (right click selects, `tvoRightClickSelect`), the summary rows (`OnContextFile`) and the file header share the popup menu `FFilePopup`: copy the full or the relative path, reveal the file in Finder (or the file manager), and Open in Editor, which runs the `EditorCommand` of the settings file with the path appended, or `OpenDocument` when none is set. `FilePopupPopup` finds the file from the summary's row, the header's file or the tree's selection, and disables the file actions for a path not on disk (a deleted file).
- The change view numbers its lines itself (`SetRowNumbers`): the editor's own numbering would count the deleted lines kept in the text, so every line below a deletion showed a number too high. ATSynEdit has no hook for the number text, but its gutter decor (`GutterDecor`) draws a text per line in the bookmark band. So the number band is hidden, the bookmark band is widened to the widest number (`OptGutterWidthBookmarks`, reapplied by the editor on every update, so the option is set rather than the band), and each row gets its number as decor text; a deleted line (in the unified view), a gap, a filler and a hidden row get none. An added line's number takes the strip's green (the decor's `Tag` keeps the kind, `LineNumberColor` maps it). `ResetLineNumbers` restores the editor's numbering for the file view and the repository diff, `ApplyTheme` recolors the decor, and `OnChangeZoom` resizes the band. The number style is `All` so both views look alike.
- `gittan.changenav.pp` holds `TGittanChangeNav`, a pill at the right end of the file header with a previous and a next arrow and a counter ("2 / 5", or "– / 5" before the caret has reached a change). It paints itself with `TCanvas` primitives in colors `ApplyTheme` sets through `SetColors`, because a native push button keeps its light bezel on a dark background on macOS (the bezel takes the window's white background) while a caption follows the theme's text color and turned white on white. The header anchors it to its right edge and centers it vertically, so it stays in place when it grows with its counter; `TGittanFileHeader.SetChanges` shows or hides it and repaints the header, whose room for the path depends on the pill's width.
- `ChangeBlocks` in `umain.pp` lists the first line of every block of added/deleted lines from the second bookmark list; `GoToChange` jumps to the next or previous block from the caret and scrolls it near the top. The Go menu binds them to F7 and Shift+F7. `UpdateChangeNav` hides the pill while the list is empty and sets the counter to the last block the caret has reached. It runs from the editor's `OnChangeCaretPos`, but through `Application.QueueAsyncCall`: the event fires inside the editor's own updates, and resizing a child there (the pill grows with its counter, and was the editor's child then) made the editor recompute its scroll position from a half-updated state and scroll sideways after a theme change.
- The gutter's line states band (3 px, between the numbers and the fold icons) is the diff's strip: `MarkLine` sets an added line to `TATLineState.Added` and a deleted one to `Changed`, and `ApplyTheme` sets `Colors.StateAdded` green and `Colors.StateChanged` red. ATSynEdit marks every line of a freshly set text as `Added`, so `ShowText` resets the states to `None` before the marks and shows the band through `SetLineStatesBand`; `OpenFile` and `FormCreate` hide it, since a plain file has no changes.
- The gutter's fold band is hidden (`SetupEditor` in `umain.pp`): in a viewer the fold icons are noise, and the change view hides lines through the folding mechanism (below), which a fold or unfold of a lexer range would disturb. Folding stays enabled (`OptFoldEnabled`): the wrap info skips hidden lines only then, and the adapter adds no fold ranges without it.
- The diff line colors in `EditCalcBookmarkColor` are faint tints of the editor background (GitHub's values for light, the same blended onto the dark palette), so the lexer's syntax colors still read on top of them.
- The editor is a viewer: `ModeReadOnly` is set in `FormCreate`. ATSynEdit silently ignores `Text` and `LoadFromFile` while read-only, so `ShowText` and `OpenFile` clear the mode around the load and set it again. Loading does not clear the second bookmark list, so they call `BookmarkDeleteAll_2` first. There is no Save command.

## Editing Guidance
- Keep changes focused and minimal. Avoid unrelated refactors or formatting-only edits.
- Unit files must use the `.pp` extension. Formatting follows `JCFSettings.xml` (JEDI Code Formatter).
- When a unit grows large (like a main form), break code out into `.inc` include files.
- PasDoc `{** ... }` comments on public APIs in interfaces; banner-style comments in implementations.
- Cross-platform gotcha: `{$IFDEF UNIX}` does not cover Haiku. Use `{$IF DEFINED(UNIX) OR DEFINED(HAIKU)}` where both apply.
- Do not edit `backup/` directories, `link*.res`, or other generated artifacts.
- Update documentation when behavior or workflow changes.

## Validation
- After code changes, run the narrowest relevant build target first.
- To check a language or RTL detail in isolation, run a snippet through `instantfpc` rather than adding a throwaway unit or project to the tree.
